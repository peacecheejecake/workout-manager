## 로컬 준비 상태

초기 실험에는 Xcode 26.2 / iOS SDK·Simulator runtime 26.2를 사용했다. 현재 재검증에는
Xcode 27.0 (27A266a) / iOS Simulator SDK·runtime 27.0을 사용했다. 유효한 code-signing identity가 있다는
것만 확인했으며 개인 이름·식별자·profile은 기록하지 않았다. 프로젝트 HealthKit 서명이 가능한지는
미확인이다. 조회 당시 연결 가능한 physical iOS 기기는 0개였다. Apple 계정 로그인이나 provisioning,
개인 건강 자료 조회·전송은 하지 않았다.

## 실행한 제한된 실험

`scripts/fixtures/native-spike`의 standalone Swift 앱을 `scripts/probe-native.mjs`로 빌드한다.
UIKit·HealthKit·WebKit을 링크하고 Simulator용 ad-hoc 서명을 사용한다. 개인 signing identity를
선택하지 않는다. 새 private device set에 임시 iPhone Simulator를 생성해 설치·실행하고 정리한다.
기존 Simulator나 사용자 앱을 변경하지 않는다.

```bash
node scripts/probe-native.mjs           # 설명만 출력
node scripts/probe-native.mjs --execute # Xcode/macOS의 격리된 Simulator probe
```

`HKHealthStore.isHealthDataAvailable()` 반환값만 확인한다. 이 값은 해당 환경의 API 지원 여부이며
읽기 권한·sample 존재·background 수집 성공을 뜻하지 않는다. 권한 요청과 sample query는 하지 않는다.
probe에는 건강 데이터를 다루는 entitlement·사용 목적 승인 흐름이 없다.

WKWebView는 비영속 store와 자체 로컬 scheme의 합성 HTML만 사용한다. frame과 origin, 메시지
형태·version을 검증한 뒤 boolean 지원 상태만 반환하고 JavaScript acknowledgement를 받는다.
잘못된 메시지, 다른 frame·origin, 외부 navigation 거절을 실제 WebKit 실행에서 관측한다.
네트워크 tile/API나 실제 건강 기록·인증 자격을 bridge에 싣지 않는다.

실행 결과는 [native-simulator-result.json](../research/native-simulator-result.json)에 기록한다.
deployment target 15.0으로 컴파일했지만 실제 실행 runtime은 26.2다. iOS 15 실행 검증이 아니다.
최종 Simulator 실행에서 7개 관측을 통과했다. 정상 메시지·제한된 상태 왕복, 잘못된 version·boolean
version 거절, 다른 iframe·main-frame origin 거절, 외부 navigation 취소를 각각 확인했다.
Swift 소스 SHA256을 보고서와 대조했고 실제 컴파일·plist 검사·스크립트 구문/ESLint/포맷 검사를 통과했다.
소유한 Simulator와 임시 파일 정리를 확인했다. 실패한 정리 단계를 성공으로 기록하지 않도록 했다.

## Safe-area 후속 수정

첫 Simulator에서 발견한 제목 겹침을 수정하기 위해 mobile-web Host에 `viewport-fit=cover`와
네 방향 `max(var(--page-padding), env(safe-area-inset-*, 0px))` padding을 적용했다.
기기별 offset을 고정하지 않으며 shared module의 상태·UI 계약은 바꾸지 않는다.
일반 브라우저의 inset이 0이면 기존 responsive padding을 그대로 사용한다.

mobile-web build·typecheck·ESLint·Prettier와 Vite Playwright 13개를 통과했다.
Aside에서 실제 production preview를 열어 제목·활동 목록을 확인하고 메모 입력 후 세로 보기로
전환해 초안 보존을 확인했다. 1440px 화면의 padding은 기존 32px, 제목 top은 약 56px였다.
스크린샷 `artifacts/mobile-safe-area-browser.png`를 직접 검토했다.

수정된 dist를 새 임시 Capacitor 프로젝트로 다시 빌드·설치·실행해 동일한 render/bridge 관측을
통과했고 소유 리소스 정리를 확인했다. iOS Simulator 26.2 portrait screenshot에서 제목이
status bar/Dynamic Island 아래에 표시돼 첫 실행의 겹침이 해소된 것을 직접 확인했다.
첫 보고서는 최신 보고서의 `previousRuns`에 보존했다. 이 결과는 관측한 portrait 초기 화면에 한정하며
landscape·키보드·회전·foreground 전체 수용 조건이나 실기기 검증을 대신하지 않는다.

## 회전·safe-area 계측과 Simulator 재실행

2026-09-17에 기존 임시 Capacitor probe를 세로 → 가로 → 세로 복귀 단계로 확장했다.
실제 window scene 방향과 안정된 geometry를 두 번 관측한 뒤 native safe-area, 제목의 window 좌표,
DOM viewport·가로 넘침을 검사한다. 각 단계의 원시 측정값을 파일로 남기고 runner가 screenshot을
저장한 뒤 ACK를 보내야 다음 회전을 요청한다. 요청 성공만으로 화면 회전을 통과 처리하지 않는다.
[Apple의 scene geometry API](<https://developer.apple.com/documentation/uikit/uiwindowscene/requestgeometryupdate(_:errorhandler:)>)를 사용하며 iOS 16 미만 실행은 실패로 남긴다.

별도 검증기는 단계·실제 화면 비율·필수 측정값의 유한성·양수 크기, inset과 safe rectangle의 일치,
안전 영역 안의 제목, document/body 가로 넘침을 확인한다. `checks: true`만으로 통과하지 않는다.
잘못된 geometry·방향·가로 넘침·필수 값 누락 등을 거절하는 21개 시험, 해당 JS ESLint·Prettier·
구문 검사와 Swift 구문·swift-format 검사를 통과했다. mobile-web production build도 통과했다.

2026-09-17의 첫 `--execute` 시도는 **Xcode 27.0 (27A266a)의 build 단계에서 실패**했다.
`IDESimulatorFoundation`을 로드할 때 시스템 `DVTDownloads`에서 필수 심볼을 찾지 못했다.
이 실행은 runtime 선택·Simulator 생성·설치·회전·screenshot에 도달하지 않았다.
추가 Xcode 설치는 발견하지 못했으며 앱/시스템 프레임워크 설치를 변경하지 않았다.
사용자에게 현재 설치·업데이트 중인지 확인을 요청했다.

2026-09-18 재실행에서 Xcode build는 통과했으나, probe가 iOS 26.2 runtime과 그 runtime에서
지원하지 않는 첫 iPhone 기기 유형을 조합해 Simulator 생성이 실패했다. runtime이 지원하는 iPhone

## Simulator 키보드 표시·닫힘과 표시 중 회전

2026-09-19에 동일한 임시 Capacitor fixture에 **합성 native `UITextField`**를 추가했다. 실제
iOS 소프트웨어 키보드가 `didShow`/`didHide` notification과 함께 나타나고 사라지는지 확인한다.
표시 중에는 scene을 세로 → 가로 → 세로로 회전시키고, 마지막에 입력 포커스를 해제한다.
각 단계에서 native 키보드 끝 프레임·포커스된 컨트롤의 window 좌표와 WebView DOM visualViewport,
제목·safe rectangle·가로 넘침을 측정한다. runner가 stage별 raw JSON과 screenshot을 보존하고
실제 좌표를 별도 validator로 검증한다. 알림이나 `checks: true`만으로 통과 처리하지 않는다.
복사 전후의 전체 Vite dist 파일 해시를 비교해 빌드 중간 산출물 혼합을 거절한다.

첫 재실행은 키보드에 도달하기 전 portrait에서 제목 y≈32px, native safe top 62px으로
겹쳐 실패했다. 당시 dist가 다른 빌드와 시간상 겹쳤을 가능성이 있지만 원인은 확정되지 않았다.
후속 probe는 geometry가 안정돼도 실패한 값이면 제한 시간까지 재관측하고 마지막 raw 값을
보존한다. 안정된 dist로 두 번 더 실행했으며, 마지막 Xcode 27.0 / iOS Simulator 27.0 실행은
세 방향 단계와 `keyboardShown` → `keyboardLandscape` → `keyboardRestored` →
`keyboardDismissed`의 **7단계 모두 통과**했다. 최종 입력 번들 SHA-256은
`b546b79ad86ade4c98e9cabdf337ff31efaf7a61529065bced23676886173f00`이다.

세로에서 키보드 표시 프레임은 y=573px·높이 301px, WebView visualViewport 높이는
874→573px이었다. 제목 y≈78px은 safe top 62px 아래에 있었고 synthetic field는
y=162px로 키보드 위에 남았다. 표시 상태로 가로 회전한 뒤 키보드는 y=222px·높이
180px, visualViewport 높이는 222px, 제목 x=62px과 field x=78px은 좌측 safe inset
62px 안쪽이었다. 세로 복귀 후 키보드·포커스가 유지됐으며, 해제 후 키보드 프레임은
y=874px으로 화면 밖으로 나가고 visualViewport 높이는 874px으로 돌아왔다. 모든 단계에서
제목의 native safe rectangle 포함과 DOM 가로 넘침 검사가 통과했다. 7개 screenshot을
직접 확인해 키보드 표시·회전·복귀·닫힘과 제목·합성 입력 컨트롤의 가시성을 확인했다.
기기·임시 프로젝트 정리는 완료했고 screenshot만 로컬 임시 경로에 남겼다.

최신 [실행 보고서](../research/capacitor-simulator-result.json)는 schemaVersion 3, stage별
raw geometry·screenshot SHA-256·시각 검토와 이전 실패/성공 실행을 보존한다. validator의
키보드 프레임·포커스·방향 위조를 거절하는 전용 시험 포함 39개 Vitest, 관련 ESLint·Prettier,
Swift 구문·swift-format, mobile-web build를 통과했다. 첫 Herdr 리뷰에서 키보드 프레임의
세로 교차만 확인하면 화면 가로 밖의 키보드도 통과할 수 있다는 지적을 받았다. JS 검증기와
native 계측 모두 가로 교차를 확인하도록 고치고 관련 회귀 시험 3개를 추가한 다음 실제
Simulator의 7단계를 다시 실행했다. 최신 7개 screenshot의 SHA-256을 다시 대조하고
직접 확인했다. 합성 native 입력창은 웹 콘텐츠 일부를 가리므로 제품 UI의 키보드 회피
수용은 여전히 미확인이다. Herdr split-pane 독립 재검토는 base
`942ec68a95b65f6a005cdf6df636ee29a0b781ce`와 staged diff SHA-256
`d9083c87e4383e596a96c0c3550b7475d3c90fac1d0a9ff77523d45eb95b95ad`에서
이전 P2 해결과 추가 actionable finding 없음을 확인했다. 이 검토 기록만 추가한
문서 diff는 별도로 확인한다.

이 입력은 **native fixture 전용 컨트롤**이다. WKWebView의 실제 HTML 입력을 사용자가
터치하거나 한국어 IME를 조합·확정·취소한 시험이 아니며, 제품 화면의 키보드 회피·스크롤·
터치 수용이나 실기기 증거도 아니다. [WebKit의 프로그램 포커스 동작](https://bugs.webkit.org/show_bug.cgi?id=195884)은
iOS 버전과 앱의 링크 조건에 따라 달라질 수 있으므로, 이 실행에서는 JS의 무제스처

### 체크리스트 6 · 뒤로 가기 제스처 · 2026-09-26

가로 넘침 없음 → 스와이프 → 경로 `/`, `pageshow persisted: true`(back-forward cache 복원), 메모 상태

### 재개 중 사용자 결정 · 2026-09-26

- 가로 키보드 가림은 native host 키보드 처리로 고친다. 저장되지 않은 변경이 있으면 back 제스처·버튼에서 확인 후 이동한다.
- 앱 표식이 있는 합성 HealthKit 표본의 쓰기·삭제와 background delivery 실행을 허용한다. 기존 건강 자료는 읽거나
  내보내지 않는다. **허용은 실행 증거가 아니며 위 항목은 여전히 not_executed다.**
- 제품 native host 통합은 M3-01에 둔다. 이 probe의 실기기 관측을 제품 host 통합 완료로 계산하지 않는다.

### Phase 검토 후 probe 안전성 수정(실기기 재실행 전)

- 독립 검토에서 `terminate`가 모든 `/App.app/` 경로의 PID를 종료할 수 있다는 지적을 받았다. 종료 대상은
  devicectl 프로세스 목록에서 정확한 probe bundle ID로 확인된 PID만 허용하도록 바꾸고, 조회 실패·신원 필드
  누락·서로 다른 bundle ID 필드는 실패로 기록한다. 목록의 실제 기기 필드 형태는 다시 확인해야 하며, 이 변경을
  실기기 종료 성공으로 계산하지 않는다.
- focus·input·click 계측의 `aria-label`/화면 문자열 원문과 URL 경로 원문은 로그에 남기지 않고 고정 조작·화면
  분류로 바꿨다. Swift 메시지 수신도 허용된 문자열만 기록한다. 합성 개인 문구를 넣은 회귀 시험과 Swift 구문
  검사를 실행했다. 기존 `not_executed` 실기기 항목은 그대로다.

- Node 24에서 기기 종료·계측 집중 시험 6개, Swift 구문 검사, 수정 후 전체 단위
  331파일·4,045개, 격리 PostgreSQL 통합 80파일·797개, generated check·lint·
  typecheck(34 작업)·build(15 작업)·format·diff check가 통과했다. 첫 lint 실행은
  새 시험의 정규식 공백 표기 때문에 실패했고 해당 표기를 고친 뒤 재실행해 통과했다.
  실제 devicectl 프로세스 목록의 bundle 식별 필드는
  기기 응답으로 확인하지 못했으므로 `terminate` 실기기 결과는 `not_executed`다.

### Phase 5차 검토의 devicectl 진단 정보 수정

- 독립 검토에서 `devicectl`의 `NSLocalizedDescription` 원문이 명령 결과 기록에 들어간다는 새 지적을 받았다.
  `install`·`uninstall`·`launch`·`pull`·`apps` 결과는 고정된 성공/실패 상태와 오류 코드만 기록한다.
  설치 bundle도 정확한 probe ID가 일치할 때에만 기록한다. 기기·계정·로컬 경로가 섞인 오류와 임의 outcome을
  넣은 회귀 시험이 통과했다.
- Node 24에서 관련 집중 시험 2파일·7개, 전체 단위 331파일·4,046개, ESLint, Prettier,
  `node --check`, `git diff --check`가 통과했다. 전체 단위의 첫 시도는 sandbox가 localhost fixture
  소켓을 막아 중단했고, 소켓 접근이 가능한 환경에서 재실행해 통과했다.
  수정 후의 실제 기기 명령은 실행하지 않았다. 해당 실기기 항목은 `not_executed`다.

## 현재 feasibility 판정 · 2026-09-27

별도 서명 작성 앱이 만든 표식 있는 합성 심박수에 대해, 종료된 probe의 새 background launch와 observer callback을 실제 iPhone에서 확인했다. 서명·권한·합성 표본 추가/삭제·outbox/anchor/ack·재설치/복구 및 safe-area·IME·Back·foreground 관측은 [실기기 후속 기록](M0-06c-native-host-addendum.md)에 각각 근거가 있다. **M0-06c의 feasibility 범위는 완료**로 판정한다. 이전 절의 날짜별 미실행·실패 기록은 해당 시점의 결과로 보존한다.

미저장 Back 확인창의 버튼별 기계 기록은 확보하지 못했고 사용자 관찰만 있다. 제품 native host 통합, 실제 인증 기반 계정 전환 및 제품 수준의 지속적 HealthKit 동작은 M3-01 이후 범위이며 이 probe의 완료로 통과 처리하지 않는다.
