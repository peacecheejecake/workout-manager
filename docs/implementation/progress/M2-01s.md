상태: **구현·검증 완료, 커밋 전(검토 대기).** 기준 HEAD `eae0ee1`. 계획 7절("계정 erasure는 모든
코스/파일/파생물/재시도까지 제거하며 restore 후 suppression을 재적용한다")을 수용 기준으로 삼았다.

## 0. 결론

**결함이었다 — 다만 질문이 가리킨 자리가 아니다.**

- 질문이 가리킨 자리(말소 tenant의 코스·revision·lineage·preference·protected area·제안·후보·
  썸네일 행·색인 행·트랙 행이 복원 후 재적용에서 지워지는가, 그리고 ledger가 이름하는 객체가
  회수되는가)는 **결함이 아니었다.** `erase_account` 체인(033→034→035→036→037→038→039)이
  테이블 13개를 모두 지우고, 원장이 이름하는 객체를 모두 `account_erased`로 queue하며, 복원
  cluster의 cleanup worker가 즉시 회수한다. drill로 재현했고 행 0·객체 0이 관측됐다(§2).
- 결함은 **reference index에만 남은 객체**다. M2-01c/M2-01m의 색인이 존재하는 이유인 "모든 영수증이
  닫힌 뒤 늦게 publish된 객체"는 7일 뒤 원장 행이 compact/prune되면 **색인만이 이름한다.**
  말소는 두 색인을 **queue 없이 지웠다**(033은 첫 줄에서, 039는 마지막에). 그러면 그 바이트를
  이름하는 것은 원장·색인·queue 어디에도 없고, 스윕은 색인을 읽으므로 **영원히 찾지 못한다.**
  트랙 쪽은 원본 GPX(절대 GPS 좌표)다.
- **복원은 이것을 경합이 아니라 평범한 경우로 만든다.** 색인이 key를 감시하던 시점의 백업은
  색인 행과(객체 archive에서) 객체를 되살린다 — 원본 cluster가 이미 그 객체를 회수했더라도.
  재적용 말소가 색인 행을 지우면 복원된 객체는 영구히 남는다.

## 3. 수정 — migration `042_erasure_queues_watched_object_refs.sql`

`erase_account`를 한 번 더 rename(`erase_account_before_watched_ref_queue`)하고 새 outermost 링크:

1. `77206` → `0` advisory lock(저장소 규약, 재진입)
2. 두 색인에서 이 tenant의 key를 **평범한 SELECT로** 배열에 담는다(행 잠금 없음)
3. 기존 체인을 **그대로** 호출
4. 담아 둔 key를 `account_erased`로 queue. 충돌하는 영수증은 **열림·닫힘과 무관하게** `account_erased`로
   바꾼다 — 033·038이 원장이 이름하는 key에 하는 것과 같은 규칙이고, 30일 말소 재무장도 함께 온다
   (`ON CONFLICT … WHERE completed_at IS NOT NULL OR reason<>'account_erased'`). 이 말소의 앞 단계(038)가
   방금 `account_erased`로 연 영수증만 다시 건드리지 않는다.
5. **`available_at`만은 덮어쓰지 않는다.** 닫힌 영수증은 `now`로 다시 열고, 열린 영수증은
   `greatest(기존, now)` — 절대 앞당기지 않는다(§3-1).

### 3-1. 검토 NB-1 반영 — 열린 다른 사유 영수증

첫 판은 열린 영수증을 사유째 그대로 두었다(`WHERE completed_at IS NOT NULL`). 독립 검토가 실측: 스윕이
먼저 고아를 reclaim해 `upload_abandoned`가 열린 상태에서 말소하면 사유가 그대로 남는다. 객체는 drain이
지우지만(`authorize`는 사유와 무관), `account_erased`의 30일 재무장을 잃고, 같은 말소 안에서 033·038과
규칙이 둘이 된다. 이제 전환한다.

`available_at` 처리는 검토 분석("색인 전용 key의 fence는 원장 prune 때 이미 만료, 당길 fence가 없다")과
**다르게** 했다. 반례가 저장소 시험으로 이미 있다 — `holds a reclaimed key back while a render could still
publish it, even with its row gone`: render가 publication fence를 연 채 **코스가 삭제**되면 원장 행은 cascade로
즉시 사라지고, `course_deleted` 영수증이 fence+1h를 **자기 `available_at`에만** 싣는다. 그 key는 prune을
거치지 않고 곧바로 색인 전용이 된다. 이때 말소하면 042가 전환 주체이고 `authorize`·`finish`는 fence를 볼 수
없으므로, `now`로 덮으면 writer가 아직 publish할 수 있는 동안 삭제가 돈다. 그래서 열린 영수증은
`greatest(기존, now)`로 둔다(033·038은 원장 행이 남아 있어 fence를 다시 계산할 수 있는 key만 다루므로
덮어써도 된다 — 042의 key에는 그 정보가 없다). **독립 검토(r2) 정정**: 상태는 실재하지만 주장한 해(누수)는 일어나지 않는다 —
`now`로 덮어 삭제가 일찍 돌아도, 042가 영수증을 `account_erased`(created_at = 지금)로 전환하므로 `finish`가
30일 동안 매시간 재무장해 늦은 publish를 다음 회차에 지운다(검토자가 늦은 publish 비교 실험으로 `now`·`greatest`
둘 다 결국 객체를 지우는 것을 실측). `greatest`가 사는 것은 쓸데없는 이른 삭제를 건너뛰고 publish 중인
writer 밑에서 임시 객체를 지우지 않는 것뿐이다 — 옳고 보수적이지만 필수는 아니다.

| 시험(course-thumbnails)                                                                   | 단언                                                                                                      |
| ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `turns a receipt the sweep already opened for an orphan into an erasure receipt`          | 스윕이 연 `upload_abandoned` → 말소 후 `account_erased`·열림·due, drain 뒤 객체 null                      |
| `converts a fence-carrying receipt of a deleted course without pulling its fence earlier` | `course_deleted`(fence로 약 1h 뒤) → `account_erased`·열림, `available_at` ≥ 이전 값, 여전히 50분 넘게 뒤 |

비공허성(각각 유일 anchor, 되돌림 확인 `cmp`):

| anchor                                                                              | 결과                                 |
| ----------------------------------------------------------------------------------- | ------------------------------------ |
| `OR public.resource_object_cleanup.reason<>'account_erased'` 줄 삭제(원래 조건으로) | **2 failed** / 76 passed(위 두 시험) |
| `available_at=CASE … greatest(…) … END` → `available_at=EXCLUDED.available_at`      | **1 failed** / 77 passed(fence 시험) |

settled 색인 행도 포함한다. settle은 "마지막으로 봤을 때 없었다"는 뜻이지, 다른 시점에 복사된 객체
archive에 대해서는 아무것도 말하지 않는다.

### 잠금 순서

- 새 간선은 **색인 → queue** 하나뿐이다(queue 행은 체인이 두 색인을 지운 **뒤** 잠긴다). 스윕(settle이
  색인 행 UPDATE, reclaim이 queue INSERT)과 기존 두 말소 단계(033은 색인 삭제 후 queue, 039는 색인을
  마지막에 삭제)가 이미 같은 방향이다.
- **색인 행은 이 링크에서 건드리지 않는다.** M2-01m의 "썸네일 색인은 마지막에"는 그대로다.
- 반복: `lock-order inversion`(course-thumbnails) · `erases without deadlocking`(course-preferences,
  runtime이 `erase_account` 직접 호출) · `does not deadlock`(courses) + 새 재현 2건, **20회 × 5시험 =
  100/100 통과, `40P01` 0건.** 독립 검토도 60/60, `40P01` 0. NB-1 수정 뒤 재실행은 §6.
- NB-1은 잠그는 행을 늘리지 않는다: 같은 INSERT가 같은 충돌 행을 이미 잠그고 있었고(`DO UPDATE … WHERE`는
  조건이 거짓이어도 충돌 행을 잠근다) 이제 그중 일부를 갱신할 뿐이다.

### 격리 DB 업그레이드

`erasure-watched-refs-upgrade.integration.test.ts`: 040까지 migrate한 DB(색인 행·닫힌 영수증 채움)에
runtime role의 040 grant를 준 뒤 한 단계 업그레이드.

- migration 1–40 checksum **불변**
- `erase_account_before_watched_ref_queue`의 본문 = 040의 `erase_account` 본문(byte 동일), grant **0**
- 새 `erase_account`도 grant 0 → `grantOperations` 재실행 후에만 runtime에 부여

**배포 주의(검토 NB-3) — 병합 노트에 옮길 것.** 042를 적용한 뒤 **`grantOperations`를 다시 돌리기 전까지**

**번호**: 처음 파일명은 `042`였고 이 worktree에서는 배열 위치로 version 41이었다. 병합 때 M2-01p의

## 4. 스윕(M2-01m)이 결국 회수하는가

**아니다.** 스윕은 객체 저장소를 나열하지 않고 **색인을 읽는다**(`…_reconcile_window`). 말소가 색인
행을 지운 뒤에는 후보가 0이다(재현 관측 `inspected: 0`). 따라서 042 이전의 시간 상한은 **없음(영구)**
이었다. 042 이후: 말소가 queue한 영수증의 `available_at`은 원장이 이름하는 key는 038의 fence
(`greatest(now, publication_lease_until+1h, lease_until+1h)`), 색인만 이름하는 key는 `now`(열린 영수증이면 기존 값과 `now` 중 늦은 쪽)다. drill에서
7개 모두 `due=true`였고 같은 drain에서 회수됐다. 상한은 cleanup worker 주기 + fence(최대 1시간)다.

## 5. 남긴 것(이 노드에서 없애지 않은 것)

- **render worker 경합은 구멍이 아니다**(검토 분석으로 좁힘). 042는 색인을 체인 전에 읽지만, 새 색인 행은
  항상 `course_thumbnail` 원장 행의 트리거에서 온다. 그 쓰기가 038의 queue 문 이전에 commit되면 038이 원장
  행으로 그 key를 queue하고, 아니면 render 트랜잭션이 말소의 `DELETE FROM course_thumbnail`을 기다린 뒤 0행에
  대해 끝난다. 042가 놓치는 key는 어느 쪽에서도 생기지 않는다.
- **DB 덤프와 다른 시점에 복사된 객체 archive — 별도 노드로 추적됨(root).** dump → archive 복사 사이에
  올라온 객체는 복원 DB에 행이 없어, 그 tenant가 말소되거나 복원 후 suppression이 재생돼도 아무것도 지우지
  않는다(검토 판정 medium-high). DB 기반 경로로는 원리적으로 닫을 수 없다. 이 노드에서는 다루지 않았다.
- M2-01k 매트릭스의 `P7-erasure`는 root 소유라 갱신하지 않았다.
