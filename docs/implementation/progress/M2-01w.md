## 1. 기동 시 discovery → 지연·재시도 discovery

**재현(수정 전)**: 실제 `apps/api/src/start.ts`를 OP 없는 설정으로 띄우면
`API startup failed; verify identity and database configuration.`, `/health` 연결 불가(000).
certified check의 새 항목도 `OP down at API start: the relying party is still created` FAIL.

**설계**: `createOidcProvider`는 설정(issuer/redirect URL, HTTPS, callback 경로)만 즉시 검사하고
discovery는 `discovered()`로 미룬다. 동시 요청은 진행 중인 한 번을 공유하고, 성공은 프로세스 수명 동안
유지하며, 실패는 `discoveryRetryMs`(기본 5000) 동안 네트워크 없이 바로 `ProviderUnavailableError`로
실패한 뒤 다음 요청에서 다시 시도한다. `configured.ts`는 기동 직후 `prepare()`로 한 번 데워 두되 기다리지
않는다.

**fail-closed 근거**: `authorizationUrl`·`exchange`는 모두 발견된 `Configuration`이 있어야 URL을 만들고
토큰을 교환할 수 있다 — 설정 없이 로그인이 **성공하는** 경로는 코드상 없다. `beginLogin`은 그 실패를
`IDENTITY_UNAVAILABLE`로 바꾸고 **시도 행을 만들지 않는다**. `authenticate()`(세션 검증)와 `logout()`은
`IdentityStore`만 쓴다 — OP와 무관(실측: OP를 내린 뒤에도 세션 유지·로그아웃 성공).

**OP 위조 방지**: issuer는 설정값과 URL 정규화 후 일치해야 한다. oauth4webapi/openid-client가 이미
검사하지만 openid-client는 Entra ID·B2C 호스트에서 불일치를 허용하는 예외가 있어, 앱이 예외 없이 다시
검사한다(`new URL(metadata.issuer).href !== issuer.href` → 실패). 불일치 문서는 몇 번 재시도해도
받아들여지지 않는다(단위 시험: 3회 × 2 경로 모두 거절, discovery 6회). endpoint 전부 HTTPS(loopback
시험만 예외) 검사 유지. `end_session_endpoint`도 같은 검사(query만 허용)이나, 2라운드(N2)부터 불합격이면 공급자
로그아웃만 끈다. ID Token `iss`는 계속
`metadata.issuer`와 정확히 일치해야 한다. discovery 응답 자체를 가로채는 공격은 TLS의 몫이다(운영 HTTPS 필수,
기존과 같음).

**부수 발견(범위 밖, 수정 안 함)**: 실제 `start.ts`는 **OP와 무관하게** 기동하지 못한다.
`configured.ts:115`의 `z.record(z.string(), z.unknown()).parse(environment)`가 `process.env`를 거부한다
(zod 4의 record는 plain object만 받는다; `{ ...process.env }`면 통과 — `eae0ee1`에서 들어옴). M2-01u까지는
기동 시 discovery가 먼저 실패해 이 오류를 가렸다. 단위 시험·harness는 plain object를 넘겨 드러나지 않는다.
routing 설정 경계라 이 노드에서 고치지 않고 보고한다. 독립 검토가 재현을 확인했다(zod 4.6.5가
`process.env`를 거부, `{...process.env}`는 통과). **root가 별도 노드로 추적한다 — 이 worktree에서는 고치지 않는다.** 이 노드의 기동 증거는 `createConfiguredApi`에 plain
object 환경을 넘긴 단위 시험과 probe다.

## 2. OP 쪽 로그아웃이 앱에 닿지 않음

**재현(수정 전)**: certified check `RP-initiated logout …` 2개 FAIL(`providerLogoutUrl is not a function`).
M2-01u spec이 이미 "앱 로그아웃 뒤 OP `_session` 남음"을 단언했다.

**판단**:

- **RP-initiated logout — 구현.** 표준이고 IdP 무관(광고하지 않는 IdP는 자동으로 기존 동작). 앱 로그아웃이
  먼저 완결되고(서버 세션 철회 + 표식), **세션·Origin·CSRF 검사를 통과한 logout POST만**
  `200 {"providerLogoutUrl"}`을 준다(그 외 `204`, 401은 URL 없음). 화면은 앱 상태를 지운 뒤 그 URL로 간다.
  `id_token_hint`는 보내지 않는다 — ID Token을 보관하지 않으며, 보관하려면 저장소가 필요하다. 그 결과
  준수 OP는 "로그아웃할까요?"를 묻는다: 공유 브라우저에서 옳은 질문이고, 개인 기기에서 IdP 전체 로그아웃을
  원하지 않는 사용자는 거절할 수 있다(거절해도 표식이 다음 로그인을 다시 묻게 한다). `client_id`로 OP가
  등록된 `post_logout_redirect_uri`(`https://<host>/account`)를 확인한다. `OIDC_PROVIDER_LOGOUT`(기본 true)로 끈다.
- **back-channel logout — 구현하지 않음.** 필요한 것: (a) logout token 검증(서명·`iss`·`aud`·`iat`·`events`
  클레임·`sid`/`sub`·`nonce` 부재), (b) **재생 방지 저장소**(`jti`), (c) **`(issuer, subject)` 또는 `sid`로 세션을
  철회하는 DB 함수**. runtime role은 `identity_private`를 직접 볼 수 없고 허용된 함수 5개(token hash 기준
  철회뿐)만 실행한다. (b)(c)는 새 함수·테이블 = **migration**이다. 지시("migration이 필요하면 먼저 보고")에 따라
  구현하지 않고 보고한다. 운영 IdP의 back-channel 지원도 미정이다.
- **8 h 세션 수명 — 유지.** 줄이면 OP 정지의 도달 상한은 줄지만 0이 되지 않고, 앱에는 조용한 재검증(refresh
  token·`prompt=none`) 경로가 없어 만료마다 사용자가 로그인을 다시 눌러야 한다. 근본 해결은 back-channel
  logout(migration + IdP 지원)이며 그 전까지 상한은 8 h로 문서화한다.

**CSRF 실측(실제 Chromium, `scripts/logout-csrf-browser-check.mts`, 7/7)**: 두 site(`localhost:47831` 앱 /
`127.0.0.1:47832` 공격자) + 기록하는 가짜 OP 로그아웃(`127.0.0.1:47833`). 교차 사이트 `text/plain` 폼
(top-level·popup): 피해자 세션 200 유지·표식 없음(M2-01u 성질 유지), **응답 401, 본문에 URL 없음, 가짜 OP 요청
0건**. same-origin 로그아웃: 앱 세션 401 → `200 {"providerLogoutUrl": …}`, 세션 쿠키 삭제·표식 설정.
공격자가 OP의 `end_session_endpoint`로 **직접** 보내는 것은 이 앱과 무관하며(앱을 거치지 않는다), `id_token_hint`
없는 요청이라 준수 OP는 확인을 묻는다.

## 3. 사람이 읽는 실패 화면

**재현(수정 전)**: 취소 시 `401 {"error":{"code":"LOGIN_REJECTED"},"requestId":…}`(M2-01u spec이 401을 단언,
API 시험도 401 JSON을 단언). certified check `cancel … classified as a cancellation` FAIL(`LOGIN_REJECTED`).

**설계**: `/bff/v1/auth/login`·`/callback`의 실패는 `302 /account?login_error=<code>`. code는 서버의 고정
집합 `cancelled`(이 브라우저 시도에 대한 `error=access_denied`), `failed`(그 밖의 OP 오류·검증 실패·만료·위조
callback), `unavailable`(OP/DB 불가). `error`는 **시도(state+브라우저 결속)를 소비한 뒤에만** 보고 두 코드 중
하나를 고를 뿐이다 — 시도 없는 "취소"는 `failed`. `error_description`·`error_uri`는 읽지도 않는다. 실패 응답은
쿠키를 설정·삭제하지 않는다. `/account` 서버 페이지는 `login_error`를 워크스페이스에 넘기고, 워크스페이스는
`Object.hasOwn`으로 세 코드만 받아 **자기 문구**를 `role="alert"`로 보여 준 뒤 주소에서 코드를 지운다.
`toString`·`__proto__`·배열·객체·HTML은 아무것도 렌더하지 않는다. query 형식 오류(`?returnTo=`)는 계속 400.

**실측**: 위조 교차 사이트 callback(`error_description=<img src=x onerror=…>`)이 로그인 중인 피해자에게
`302 /account?login_error=failed`, Set-Cookie 없음, 쿠키 불변, 세션 200(Chromium). 실제 Next 화면에서
`/account?login_error=<img …>` → alert 0개·`main img` 0개·`window.__xss` 없음, 위조 callback → 고정 문구,
취소 → "로그인을 취소했습니다…", 페이지에 OP 문구("End-User cancelled") 없음(certified spec).

## 4. `auth_time` 확인

**재현(수정 전)**: `prompt`·`max_age`를 버리는 **비준수 OP 모드**를 인증 OP fixture에 추가했다
(`ignoreReauthentication`, 시험 전용). 로그아웃 뒤 Bob으로 로그인하려 해도 OP가 묻지 않고 Alice로 응답하고,
RP가 **받아들였다**: `FAIL non-conformant OP ignores prompt=login/max_age; verifyReauthentication=default (on) —
silent SSO answer accepted`. 재인증 요청에 `max_age` 없음도 FAIL.

**설계**: 재인증(세션 쿠키 또는 로그아웃 표식)일 때 `prompt=login&max_age=0`. callback에서
`authorizationCodeGrant(…, { maxAge: 0 })` — oauth4webapi가 `auth_time`을 필수로 요구하고 30 s 허용 오차로
검사한다. **재인증 요청이었는가**는 callback의 쿠키가 아니라 `beginLogin`이 만든 nonce의 `reauth.` 접두사로
판단한다: nonce는 서버가 생성해 서버측 시도 행에 저장하고 `consumeAttempt`로 돌려받으므로 브라우저가 바꿀 수
없고, DB 제약(16–256자)에 맞아 **migration이 없다**. 설정이 시도 도중(10분 창) 바뀌는 경우만 요청과 검사가
어긋날 수 있다.

**기본값 on — 근거**: `max_age`를 받으면 `auth_time`을 넣는 것은 OIDC Core의 필수 동작이라 준수 OP는 지원한다.
켠 상태에서 비준수 IdP의 실패는 **요란하다**(로그아웃 뒤 로그인이 `failed` 화면 — EXT-OIDC 수용 체크리스트의
"로그아웃 뒤 다른 계정 로그인"에서 즉시 드러난다). 끈 상태의 실패는 **조용하다**(공유 브라우저에서 앞사람
계정으로 로그인 — 실측: `verifyReauthentication=false` → `OBSERVED: accepted silently as the previous user`).
운영자는 IdP가 지원하지 않는다고 확인될 때만 `OIDC_VERIFY_REAUTHENTICATION=false`로 끄고, 그 결과를 알고 끈다.
Google의 `prompt=login`/`max_age` 지원은 **미검증**이다 — EXT-OIDC 확인 항목.

로컬 fixture OP(`scripts/fixtures/oidc-provider.ts`)는 `max_age`가 요청되면 계정 선택 시각을 `auth_time`으로
넣도록 고쳤다(매 요청 선택 화면을 보이므로 선택이 곧 인증이다). fixture 모드는 기본값 그대로다.

## 보존한 성질

M2-01u 표식 쿠키(`__Host-workout_signed_out`), 401 logout 분기의 "표식만 · 허용 origin만"(a·b), `exchange()`의
state·nonce·PKCE·`iss`(RFC 9207)·`sub` 검사는 바뀌지 않았다(M2-01u 시험 전부 그대로 통과, CSRF 브라우저 검사의
M2-01u 3개 포함). `error` 조기 분기는 시도를 소비한 **뒤**에만 오며 결과는 여전히 세션 없음이다.

## EXT-OIDC로 넘기는 확인 항목(root가 task-graph에 반영)

1. **`max_age`/`auth_time` 지원**: `max_age=0` 요청에 새 `auth_time`을 넣는가. 아니면
   `OIDC_VERIFY_REAUTHENTICATION=false`와 그 결과(공급자가 `prompt=login`을 무시하면 조용한 재로그인)를 기록.
   **운영 기본값(on)은 이 확인으로 확정한다.** Google 지원 여부 미검증.
2. **`end_session_endpoint`**: 광고하는가, `post_logout_redirect_uri=https://<host>/account` 등록, `id_token_hint`
   없는 요청에 확인 화면을 보이는가(바로 로그아웃하는 OP면 로그아웃 CSRF가 OP 쪽 문제로 남는다).
3. **back-channel logout 지원 여부**. 지원하고 필요하면 migration을 포함한 후속 노드(세션 철회 함수 + `jti`
   재생 방지). 그 전까지 OP 쪽 계정 정지의 앱 도달 상한은 8 h.
4. 수용 체크리스트에 추가: 취소 → 읽을 수 있는 화면, 앱 로그아웃 → OP 로그아웃 확인 → 다른 계정 로그인,
   OP 장애 중 기존 세션 유지·로그인 `unavailable`.
