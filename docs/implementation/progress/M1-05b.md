# M1-05b · 상담 스레드·사용자 메시지·검토 범위 저장

상태: 구현·검증 완료. S10 / FUT-02의 사용자 대화 저장 기반이다.
부모 M1-05의 EvidenceSnapshot·후보 생성·명시 승인·실제 모델 연동은 별도다.

## 독립 착수와 계약

M1-01 인증/계정, M1-02 불변 계획, M1-06a 계정 운영을 선행 조건으로 사용한다.
S05 계획 종류를 해석하거나 계획을 수정하지 않아 별도 child로 준비할 수 있다.
부모 M1-05의 M1-04 의존성과 외부·지도·native 출시 gate는 유지했다.

상담 스레드는 소유한 불변 `planVersionId`와 session/Block/Phase의 ID·종류를 검증한 후
제목·검토 범위를 고정한다. 명시적으로 선택한 과거 계획 버전도 허용하며 현재 계획으로
바꾸지 않는다. 스레드를 생성할 때 첫 사용자 메시지와 revision 1을 함께 저장한다.
후속 메시지는 `expectedRevision`이 같을 때만 추가하고 revision을 1 증가시킨다.

사용자 메시지에는 `role: user`만 허용한다. 본문은 최대 8,000 UTF-16 code unit이며
유효한 내용의 앞뒤 공백·줄바꿈을 보존한다. 빈/공백 전용·NUL 문자열은 거절한다.
제목·대상 ID·멱등 키는 공백 정규형 1~200자로 제한하고 UUID는 소문자로 정규화한다.
현재 스레드 범위 변경·메시지 수정/삭제는 제공하지 않으며 전체 계정 삭제는 지원한다.

상담 메시지에 제약을 적는 것만으로 계획 제약 원장을 변경하지 않는다. 범위는 고정된 계획의
제약·잠금까지 참조할 수 있는 식별자이며 이번 API가 근거 본문이나 전체 필수 사용자 제약을
로딩한 결과는 아니다. 후속 근거 생성은 그 계획 자료와 별도의 필수 사용자 제약·선호를
빠짐없이 로딩·버전 고정해야 한다. 미입력을 “제약 없음”으로 해석하지 않는다.

## API·동시성·계정 수명주기

- `GET/POST /bff/v1/coaching-threads`: 사용자 스레드 목록·첫 메시지 포함 생성.
- `GET /bff/v1/coaching-threads/:threadId`: 저장된 범위와 현재 revision.
- `GET/POST /bff/v1/coaching-threads/:threadId/messages`: 메시지 조회·추가.
- 목록은 생성 시각 내림차순, ID 오름차순이고 limit 기본 50/최대 100, offset 최대 10,000이다.
  메시지는 `afterRevision` 이후 오름차순, 기본 50/최대 100이며 `hasMore`를 반환한다.
  각 메시지 페이지와 현재 thread head는 하나의 SQL statement snapshot에서 읽는다.
  여러 페이지 사이에 추가된 메시지는 후속 조회에 포함될 수 있다.
- 소유자는 인증에서 파생한다. CSRF/세션 검증, 엄격한 path/query/body·멱등 헤더,
  쓰기 body 64KiB 제한과 기존 sanitized 오류 응답을 적용했다.
- tenant 수명주기 lock과 기존 명령 직렬화를 사용한다. 같은 멱등 키의 같은 명령은
  stale 검사보다 먼저 원래 영수증을 반환하며, 내용이 다르면 충돌한다. 긴 키도 허용하도록
  내부 receipt/outbox 키에 명령별 namespace와 SHA-256을 사용한다.
- head·메시지·영수증·outbox가 함께 커밋/rollback한다. outbox에는 ID와 revision만 넣고
  본문·제목은 넣지 않는다. 계획 head나 실제 활동은 변경하지 않는다.
- Migration 012는 소유 계획 FK, 메시지 revision 유일성, 강제 RLS·불변 메시지와
  계정 삭제 wrapper를 추가한다. runtime은 thread revision/updated_at 열만 수정할 수 있다.
- v5 계정 export에 `coachingThreads`/`coachingMessages`를 추가하고 v2/v3/v4 읽기는 유지한다.
  기존 컬렉션별 1,000행·전체 8MiB 제한을 초과하면 전체 export가 실패하며 누락 성공은 없다.
  삭제는 메시지→스레드→계획 순서다. backup restore도 같은 삭제 ledger를 재적용한다.

이 단계는 서버에 사용자 대화를 저장하는 기능이다. 모델 전송·assistant 답변·도구 실행·근거
스냅샷·코칭 후보·승인 버튼을 생성하지 않는다. AI 전송 동의는 후속 실행 경로에서 별도로
검사해야 하며, 대화 저장 성공을 AI 처리 동의나 승인으로 간주하지 않는다.

## 검증

- 계약/API 단위 검사 37개: 소유자 전달, UUID 정규화, 엄격한 입력·user role·NUL·본문 한도,
  인증·세션·CSRF, 404/409 매핑과 응답 검증·오류 비노출을 확인했다.
- `pnpm check --maxWorkers=2`: 생성물·Prettier·ESLint·전체 consumer typecheck,
  unit/component 1,523개/136 files 통과. 처음에는 sandbox의 localhost listen EPERM으로
  기존 OIDC/Garmin fixture 검사가 실패했다. 로컬 서버 실행 권한으로 전체 재실행해 통과했다.
- `pnpm test:integration`: 실제 PostgreSQL 163개/21 files 통과. 새 대화 시험은 과거 계획
  고정, 200자 멱등 키, 중복/경쟁 추가, owner/scope 검증, RLS/열 권한, 페이지 조회,
  export/erase, outbox 실패 시 rollback, 동시 append 중 단일 SQL 조회 snapshot을 검증한다.
  처음에는 기존 migration 목록 시험에서 새 012번이 빠져 실패했고 목록 갱신 후 모두 통과했다.
- `API_ORIGIN=http://127.0.0.1:4301 pnpm build`: 7개 build task 통과.
- 실제 OIDC/Next proxy/API/DB E2E 3개 통과: 새 상담 저장·재전송·충돌·페이지·타 계정
  접근 차단·v5 export/계정 삭제, 기존 운영 수명주기, 기존 완료 확인·철회/이동 보호.
  새 시험의 첫 실행은 필수 세션 헤더 누락으로 409를 받았다. 시험 요청을 수정한 최종
  실행은 모두 통과했으며 production 인증 검사는 변경하지 않았다.
- `pnpm exec tsx scripts/backup-restore-drill.mts --execute`: 16개 검증 통과.
  대화 범위·revision·본문·v5 export와 기존 영수증이 복원 뒤 보존되고 재시도에 중복이 없었다.
  삭제 ledger 재적용 후 두 대화 테이블이 제거되고 삭제 계정 쓰기는 차단됐다.
  [결과](../research/backup-restore-result.json)에 이전 실행을 보존했다. 임시 DB·백업·ledger는 정리됐다.
- 92개 DAG node의 참조·비순환·완료 선행 조건과 부모 gate 유지를 확인했다.
  UI를 추가하지 않아 새 상담 화면의 Aside 검증으로 주장하지 않는다.

M1-05b만 완료하며 M1-04와 부모 M1-05 통합은 미완료다. 규칙 파일은 변경하지 않았다.
