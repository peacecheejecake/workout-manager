# M2-03 · 갤러리와 media 객체 생명주기

상태: **구현 완료 · 통합 검토 대기**. M2-04b의 private object storage port와 M2-04b/c의 durable
cleanup manifest 위에 tenant 소유 사진·동영상 원장, bounded upload 수명주기, 파생물 포함 삭제,
계정 export와 갤러리 화면(S17 일부)을 연결했다. transcoding, 서버측 thumbnail 생성, EXIF 위치 제거,
앨범 관리 화면, 공유와 coach 사용은 구현하지 않았다.

## 고정한 경계

- media item은 tenant/athlete 소유이며 `visibility='private'` 하나만 존재한다. 소유자는 인증에서만
  유도하고 client가 보낸 athlete id를 신뢰하지 않는다. 공유 범위는 이 작업에서 넓히지 않는다.
- `include_for_coach`는 `CHECK (NOT include_for_coach)`로 고정한다. 갤러리 열람과 업로드 성공은
  AI 전송 동의나 coach 사용으로 승격하지 않는다.
- 허용 content type은 `image/jpeg`, `image/png`, `image/webp`, `video/mp4`, `video/webm`뿐이다.
  선언한 content type과 확장자가 일치해야 하고, 스트리밍 중 magic byte signature를 다시 검사한다.
  사진 15 MiB, 동영상 64 MiB, preview 2 MiB 상한을 HTTP 경계와 SQL CHECK 양쪽에서 강제한다.
- 동영상은 업로드한 원본 그대로 보관한다. transcoding, 재다중화, 자막 생성은 수행하지 않으며
  화면도 “자막 없음”을 명시한다. 검증할 수 없는 변환 주장을 하지 않는다.
- 파생물은 client가 명시적으로 올린 `preview` object뿐이다. 서버가 thumbnail을 만들지 않는다.
- 저장 경로는 기존 object port의 key 규칙을 확장한 tenant/media-item/upload scoped key다. upload마다
  고유한 final key를 쓰므로 한 intent의 보상 정리가 다른 object를 지우지 못한다.
- public DTO, 로그, 계정 export 어디에도 storage ref, signed URL, credential, 내부 오류를 넣지 않는다.
  content 응답은 `cache-control: private, no-store`로 내려준다.

- `packages/contracts/src/gallery.ts`: media kind/type/extension, descriptor, list/read/update/delete,
  upload 예약 계약과 형식별 byte 상한. storage ref field가 없다.
- `packages/server/persistence/migrations/031_gallery_media.sql`: `gallery_media_item`,
  `gallery_media_derivative`, `gallery_media_object`, `gallery_upload_intent`와 FORCE RLS tenant policy,

  `prune_resource_upload_history`, `authorize_resource_object_cleanup`을 `CREATE OR REPLACE`로

  일치하는지 다시 확인한다.
- `packages/modules/gallery/**`: 갤러리 화면. loading / empty / partial(`전체 N개 중 M개`) / error +
  재시도 / upload pending(예약·업로드·확정) 상태, semantic token과 CSS Modules, label과 가시적 focus,
  320px 대응, IntersectionObserver 기반 지연 로딩과 unmount 시 blob URL 해제. 목록은
  `useInfiniteQuery`와 `더 보기`로 50개 단위 페이지를 이어 붙인다. 삭제 성공 시 해당 항목의 detail
  cache 항목을 제거하고 명시적 삭제 상태로 전환해, 404가 되는 refetch 뒤에도 이전 payload가 남아
  삭제된 미디어와 blob URL이 계속 렌더되지 않게 한다.
- `apps/web/app/gallery/**`, `apps/mobile-web/src/gallery-page.tsx`: `/gallery`와
  `/gallery/:mediaItemId` 라우트, URL이 소유하는 `mediaKind`·`album` 필터.
- 계정 export는 v16으로 올려 `galleryMediaItems`, `galleryMediaDerivatives`를 포함한다. v2~v15 artifact

## 독립 검토(base `850519b`) 결과 반영

1. **삭제 후 detail 화면에 stale 미디어 유지(차단)**: 삭제 성공 시 detail query를 invalidate만 하면
   TanStack Query가 404 refetch 뒤에도 직전 `data`를 보존해 삭제된 미디어와 blob URL이 오류 문구와
   함께 계속 렌더됐다. 삭제한 id를 즉시 cache에서 제거하고 query를 비활성화한 뒤 “삭제되어 더 이상
   열람할 수 없습니다” 상태로 전환하도록 고쳤다. preview component가 unmount되며 object URL이
   해제되는 것까지 회귀 테스트로 확인한다.
2. **preview finalize의 stale revision(차단)**: `expectedAccessRevision`을 예약 시점에만 확인하고
   intent에 남기지 않아, 예약 → 메타데이터 수정 → preview finalize 순서에서 오래된 쓰기가 성공했다.
   migration 031에 `expected_access_revision` 컬럼과 operation별 CHECK, 불변 trigger 항목을 추가하고
   finalize transaction 안에서 CAS 재확인 후 item revision을 올리도록 고쳤다. 실제 PostgreSQL 경합
   테스트를 추가했다.
3. **content hash 기반 재업로드 차단 제안(무효로 판단)**: `docs/.pre`의 삭제 억제(suppression)는
   provider 동기화·backfill이 삭제한 항목을 **재생성**하지 못하게 하는 규칙이다(01 S07, 04 55행,
   05 V2-A20). 사용자가 직접 지운 사진을 다시 올리는 것은 정상 제품 동작이며, 같은 hash라는 이유로
   막으면 제품 결함이 된다. 실제로 지켜야 하는 불변식은 **삭제된 item의 재시도·idempotent replay·
   진행 중 intent가 그 item을 되살리지 못하는 것**이고, 이는 `cancel_gallery_uploads`,
   command receipt tombstone, `authorize_resource_object_cleanup` 참조 검사로 보장되며
   `gallery-media.integration.test.ts`의 “keeps deletion suppression across a late finalize and a
   repeated delete”가 실제 PostgreSQL로 확인한다. `docs/.pre` 어디에도 hash 기반 억제 요구가 없어
   추가하지 않았다.
4. **목록 50개 상한(비차단)**: “일부만 표시” 문구만으로는 51번째 이후에 접근할 수 없었다.
   `useInfiniteQuery` 기반 `더 보기`를 구현했고 backlog 항목은 만들지 않았다.
5. **cleanup worker 미검증(비차단)**: 실제 local filesystem store에 raw·preview object를 publish한 뒤
   기존 `processOneResourceObjectCleanup`을 그대로 돌려 retry 1회 → 두 object 실제 삭제 → queue 비움을
   확인하는 실제 DB 테스트를 추가했다. 공용 queue이므로 실행 중 무관한 대기 항목을 잠시 미뤘다가
   복원한다.
6. **pending 상태 테스트(비차단)**: deferred promise로 `업로드 준비 중` → `업로드 중`(진행률 표시) →
   `저장 확정 중` 순서를 검증하고, 실패 후 앨범·설명 초안 보존과 제출 버튼 focus 복귀를 검증하는
   테스트를 추가했다.

## 재검토(2차) 결과 반영

1. **공용 cleanup queue 상태 훼손(차단)**: worker end-to-end 테스트가 무관한 대기 항목을 미룰 때
   `UPDATE ... RETURNING available_at`이 **변경된 값**을 돌려주어, 복원 루프가 `+1시간`을 그대로 다시
   써 넣고 있었다. 이제 UPDATE 전에 원래 `available_at`을 `SELECT`로 먼저 포착하고 그 값으로
   복원하며, 각 행이 원래 시각으로 돌아왔는지 대조까지 한다. 다른 suite가 정당하게 먼 미래로 예약한
   행이 있으므로 절대 시각 임계값이 아니라 포착값과 비교한다.
2. **다른 탭·기기 삭제 시 stale detail(차단)**: `deletedMediaIds`는 이 탭에서 시작한 삭제만 덮었다.
   다른 곳에서 삭제되면 detail refetch가 404가 되지만 TanStack Query는 직전 `data`를 유지하므로
   비공개 미디어와 blob URL이 오류 문구 뒤에 계속 보였다. 이제 `detail.isSuccess`인 경우에만 읽기
   결과를 렌더한다. 회귀 테스트는 detail이 available인 상태에서 refetch가 404가 되도록 만들어,
   `img`가 사라지고 object URL이 revoke되는 것을 확인한다.
3. **focus 복귀 테스트가 자기 자신을 증명(비차단)**: 업로드 실패 시 구현이 제출 버튼으로 focus를
   되돌리도록 `submitButton` ref를 추가했고(업로드 중 disabled 때문에 focus가 사라진다), 테스트는
   더 이상 `focus()`를 직접 호출하지 않고 복귀만 단언한다.
4. **offset pagination 경계 이동(비차단)**: offset은 유지하되 위치가 아니라 identity로 표시를
   결정한다. 페이지를 이어 붙일 때 id 기준으로 중복을 제거하고, 변경 command는 목록 전체를
   invalidate해 적재된 모든 페이지를 함께 refetch한다. 동시 삽입으로 두 번째 페이지가 첫 페이지의
   항목을 되풀이해도 한 번만 렌더되는 회귀 테스트를 추가했다. **남은 한계**: offset 기반이므로 앞쪽
   삭제로 창이 당겨지면 아직 적재하지 않은 항목을 건너뛸 수 있다. 안정적인 cursor 계약은 후속
   과제로 남긴다.
5. **`as never` 우회(비차단)**: 공개 key 생성 함수 `createGalleryFinalObjectKey`로 실제
   `FinalObjectKey`를 만들어 publish하고, 그것이 원장의 storage ref와 같은지 대조한다.

## 재검토(3차) 결과 반영

1. **목록도 오류 상태에서 cache를 렌더(차단)**: detail만 `isSuccess`로 막고 목록은 막지 않아,
   다른 탭에서 삭제된 직후 목록 refetch가 실패하면 grid가 캐시된 thumbnail과 blob URL을 계속
   보여 줬다. 목록·총계·`더 보기`를 모두 `list.isSuccess`로 게이트했다. 회귀 테스트는 detail이
   404가 되는 **동시에 목록 refetch도 실패**하는 경우를 만들어 `img`가 0개가 되고 object URL이
   revoke되며 목록 오류 문구가 뜨는 것을 확인한다.
2. **focus 복귀가 실제가 아님(비차단)**: `onError`에서 곧바로 `focus()`를 부르면 React가 아직
   enabled 상태를 commit하지 않아 실제 브라우저에서는 disabled 요소에 대한 no-op이었다. 이제
   토큰을 올리고 `stage === 'idle'`이 commit된 뒤 실행되는 effect에서 focus를 되돌린다. 증거는
   jsdom 단언이 아니라 실제 Chromium이다: 갤러리 Playwright spec에 실패 업로드 후 제출 버튼이
   enabled이며 focus를 가졌고 앨범·설명 초안이 보존되는 시험을 추가했다. 이 과정에서 Host file
   transfer 실패가 항상 “요청을 완료하지 못했습니다”로만 보이던 문제도 드러나, 서버 오류 코드를
   사람이 읽을 수 있는 문구로 변환하도록 고쳤다.
3. **pagination이 dedup 이전 길이로 전진(비차단)**: 다음 offset과 종료 판정이 원본 page 길이를
   써서, 앞쪽 삽입으로 창이 겹치면 한 번도 표시되지 않은 identity를 건너뛰었다. 이제 보유한
   **distinct identity 수**로 다음 offset을 정하고 `distinct >= total`이거나 새 identity가 늘지
   않으면 종료한다. 창이 겹쳐도 다시 읽어 누락된 identity를 회수하고 무한 반복은 하지 않는다.
   회귀 테스트가 offset `0 → 1 → 2` 진행과 중복 1회 렌더, 정상 종료를 확인한다.

## 재검토(4차) 결과 반영

1. **목록 refetch가 도착하기 전 구간(차단)**: `isSuccess` 게이트는 refetch가 **이미 실패한** 경우만
   막았다. detail 404가 확정됐는데 목록 refetch가 아직 진행 중이면 목록은 직전 성공 상태라 삭제된
   항목의 카드와 blob URL이 응답이 올 때까지 남았다. 이제 detail이 404이거나 `unavailable`로
   확정되면 해당 id를 목록 필터에서 **즉시** 제외한다. 회귀 테스트는 목록 refetch 응답을 deferred로
   **열어 둔 채** detail 404만 먼저 해소시켜, 목록이 답하기 전에 카드와 object URL이 사라지는지
   확인한다.
2. **`FILE_TOO_LARGE` 누락(비차단)**: content PUT이 돌려주는 이 코드가 transfer 허용 목록에 없어
   일반 문구로 보였다. 크기 한도 문구를 추가했고, 전송 경로에서 실패를 주입하는 테스트를 붙였다.
   같은 허용 목록을 JSON API 오류 코드에도 적용해 `UPLOAD_RESUME_REQUIRED` 같은 예약 단계 실패도
   사람이 읽을 수 있게 했다(허용 목록 밖 코드는 여전히 일반 문구로만 노출한다).
3. **`retryFocusToken` 미소비(비차단)**: 토큰이 0보다 큰 상태로 남아, 이후 **성공한** 업로드가
   idle로 돌아올 때 effect가 다시 돌며 사용자가 옮겨 둔 focus를 제출 버튼으로 뺏었다. focus를
   적용할 때 요청을 소비하도록 고쳤고, 실패 → focus 복귀 → 성공 업로드 중 다른 입력으로 이동 →
   focus 유지를 확인하는 테스트를 추가했다.
4. **pagination 문구 정정(비차단)**: distinct identity 전진은 **한 페이지보다 작은 겹침**만
   회수한다. 한 페이지 전체가 이미 본 항목이면 새 identity가 없어 목록이 종료되므로, 예컨대 50개를
   적재한 뒤 앞쪽에 50개가 삽입되면 그 너머의 항목은 회수하지 못한다. 코드 주석과 아래 한계 절을
   이 범위로 좁혔다. 또한 dedup은 first-wins이므로 뒤 페이지가 같은 id의 더 새로운 revision을
   담고 있으면 다음 전체 refetch 전까지는 이전 값이 유지된다.

## 재검토(5차) 결과 반영

1. **오류 문구 allowlist의 prototype 키(비차단)**: `TRANSFER_MESSAGES[code]`에 own-property 검사가
   없어 `constructor`·`toString`·`__proto__` 같은 상속 키가 상속값을 돌려줄 수 있었다. 서버 문자열이
   새는 경로는 아니지만 함수/객체가 render에 도달해 빈 alert이나 React 오류가 될 수 있다. transfer와
   JSON API 조회 모두 `Object.hasOwn()`으로 정확한 멤버십만 인정하도록 고치고, 상속 키가 일반 문구로
   떨어지는 회귀 테스트를 추가했다.
2. **focus 미탈취 테스트의 타이밍 미증명(비차단, 테스트 품질)**: 두 번째 업로드가 즉시 완료되고
   테스트가 직접 `caption.focus()`를 불렀는데, 그 입력은 업로드 중 disabled라 실제 사용자는 갈 수
   없는 위치였다. finalize를 deferred로 잡아 `저장 확정 중` 상태를 유지한 채, 업로드 중에도 enabled인
   필터 navigation link로 focus를 옮기고 완료 후에도 그 focus가 유지되는지 검증하도록 바꿨다.
3. **문서 서술 오류(비차단)**: 4차 항목 1의 설명이 "목록 응답을 열어 두지 않은 채"로 거꾸로 적혀
   있었다. 실제 테스트는 목록 응답을 열어 둔다. 문구를 바로잡았다.
