# M2-05 · RAG·검토 자료·코치

상태: **구현 완료, 검증은 아래 수치만**. M2-04d가 비워 둔 파생 저장소(검색 색인, retrieval
cache, grounding 발췌, 저장된 인용)를 실제로 만들고, 그 저장소들의 삭제 실행기를 기존
`resource_derived_cleanup` manifest에 연결했다. ACL 필터 retrieval, 자료 version에 고정된 인용,
삭제 누출 시험, `resource-access-v1`의 evidence dependency 통합을 함께 넣었다.

## 고정한 경계

- **실제 파생 저장소.** Migration 032가 `resource_passage`(검색 색인), `resource_retrieval_cache`,
  `resource_grounding` + `resource_grounding_excerpt`(모델에 건넨 발췌 사본 = 파생 텍스트),
  `resource_citation`(저장된 인용)을 추가한다. 네 target이 manifest의 `derivedData`·`searchIndex`·
  `cache`·`citations`와 1:1로 대응한다.
- **병렬 queue를 만들지 않았다.** 삭제는 M2-04d의 `resource_derived_cleanup` manifest, 같은 lease,
  같은 bounded retry, 같은 dead-letter, 같은 worker 프로세스를 그대로 쓴다. 새로 추가한 것은
  target별 실행기 하나뿐이다. 실행기는 `public.purge_resource_derived_store(manifest,worker,target)`를
  호출하고, 이 함수는 **해당 manifest에 대해 아직 유효한 lease를 그 worker가 들고 있을 때만** 동작한다.
  tenant와 resource는 호출자가 아니라 manifest row에서 읽는다. lease가 없으면
  `DERIVED_CLEANUP_LEASE_LOST`로 실패하고 아무것도 지우지 않는다.
  실행기가 없는 target이 attempt·dead-letter 예산을 쓰지 않는 M2-04d의 성질은 그대로다:
  `processOneResourceDerivedCleanup`의 빈 map·부분 map 경로를 바꾸지 않았고 회귀 테스트도 남겼다.
  이제 네 target 모두 실행기가 있으므로 열린 manifest는 완료되고
  `resource_coach_use_authorized()` gate는 다시 열린다.
- **ACL 필터 retrieval.** 모든 읽기는 색인·cache·고정된 manifest가 아니라
  `public.resource_coach_use_authorized(id)` **gate 함수 자체**를 조인한다. 술어를 복제하지 않았으므로
  사용 시점 gate와 갈라질 수 없다. 삭제, 동의 철회, 공유 철회, 검토 해제, coach 사용 중지, 열린
  파생 cleanup manifest는 모두 다음 statement부터 retrieval을 막는다. 필터는 **순위 계산 전에**
  적용되어 인가되지 않은 행이 후보에 들어가지 못한다. 모델에게 걸러 내게 하지 않는다.
  추가로 `p.version_id = r.current_version_id`를 요구하므로 한 답변에 두 version이 섞이지 않는다.
  version을 추가하면 이전 version의 passage는 더 이상 매칭되지 않는다. 새 version은 **검토 pin이
  현재 version으로 옮겨진 뒤에만** 색인된다(아래 "검토는 검토한 버전에 고정된다" 참조). 그 전까지는
  검색 중지이며 이전 version을 쓰지 않는다.
- **한 질의는 하나의 인가 집합만 본다.** manifest 수집·인가 집합 조회·검색은 서로 다른
  statement다. manifest 완료는 집합을 넓히므로 `finish_resource_derived_cleanup`이 이제 access
  ledger와 같은 tenant command advisory lock을 잡아 그 사이에 끼어들 수 없다. 그 위에 검색 직후
  집합을 다시 수집해 digest가 같은지 확인하고, 다르면 cache를 쓰지도 결과를 돌려주지도 않고 최대
  3회까지 다시 시도한 뒤 `RETRIEVAL_SET_UNSTABLE`로 실패한다.
- **cache는 인가 근거가 아니다.** cache key는 tenant, corpus version, **인가 집합 전체의 digest**
  (`resource-access-v1`의 `entriesDigest`), 정규화된 filter, 질의문으로 만든다. 따라서 ACL·동의·검토
  변화는 다른 key를 만든다. 그 위에 hit마다 저장된 passage 식별자를 **다시 인가**하고, 하나라도
  통과하지 못하면 항목 전체를 버리고 miss로 처리한다. TTL은 읽기 필터만이 아니다: 질의 시점에
  만료 행을 실제로 삭제하고 tenant당 50개로 제한하며, cleanup worker가 매 주기
  `prune_resource_retrieval_cache(500)`으로 전역 회수한다.
- **인용은 발췌보다 오래 살 수 없다.** `resource_citation`은 인용문을 저장하지 않는다. 자료·version·
  passage 식별자와 offset, 그리고 인용 구간의 SHA-256만 저장한다. 본문은 읽을 때마다 gate를 통과해
  passage에서 해석한다. 그리고 `resource_citation`과 `resource_grounding_excerpt`는
  `resource_passage`에 대한 `ON DELETE CASCADE` 외래 키를 갖는다. 색인 행이 지워지면 파생 사본과 인용
  행이 **구조적으로** 함께 사라진다. 저장된 답변을 다시 열어도 삭제된 발췌가 재노출되지 않는다.
  인가가 아직 살아 있지 않은 인용은 본문 없이 `unavailable`로만 보고한다.
- **인용 식별자는 자료 version에 고정된다.** `passage_id`는
  `sha256('resource-passage-v1', tenant, versionId, ordinal, contentHash)`에서 유도한 결정론적
  UUID다. 같은 version을 두 번 색인해도 같은 식별자가 나오므로 동시 색인이 중복 행을 만들지 않고
  재색인이 인용을 고아로 만들지도 않는다.
- **인용 쓰기는 사용 시점에 다시 검증한다.** worker는 고정된 사본을 그대로 쓰지 않고 gate를 통과한
  발췌만 adapter에 넘긴다. adapter가 돌려준 인용은 (1) 이 grounding이 실제로 고정한 passage인지,
  (2) 지금도 인가되는지, (3) offset이 살아 있는 passage 안인지를 **한 행도 쓰기 전에** 모두 검사한다.
  하나라도 실패하면 분석 결과를 저장하지 않고 `invalid_output`으로 끝낸다.
- **검토는 검토한 버전에 고정된다.** `resource.reviewed_version_id`가 실제로 검토된 version을
  가리키고, gate는 그것이 현재 version일 것을 요구한다. 새 version을 추가하면 본문이 바뀌므로
  검토 표시가 남아 있어도 gate가 닫히고, 색인·retrieval·인용 본문이 모두 막히며 소유자가 현재
  버전을 다시 검토 표시해야 열린다. M2-04d는 version append가 검토/coach 사용을 **승격**하지
  못하게 했지만, 이미 켜진 값을 본문 교체 너머로 **유지**하는 것은 콘텐츠가 색인되어 모델에
  들어가는 지금은 안전하지 않다. trigger가 pointer 이동을 현재 version으로만 허용하므로 다른
  access command가 몰래 재검토 처리할 수 없다. 겹쳐 쓴 이전 version의 색인 행은 다음 질의에서
  회수한다.
- **검토된 콘텐츠만.** 색인 대상은 gate가 인가한 자료, 즉 `reviewed_state='reviewed'`이고
  `include_for_coach`이며 AI 동의가 살아 있고 열린 cleanup이 없는 자료뿐이다. 미검토 자료는 색인되지도
  검색되지도 않는다. passage는 저장된 문단(locator 포함)에서만 만들고 생성 요약은 만들지도 색인하지도
  않는다. 기능 테스트가 생리학적 타당성을 입증하지 않는다는 점은 계약 주석과 UI 문구에 남겼다.
- **검색 방식의 한계를 이름 그대로 적었다.** `to_tsvector('simple')` + `plainto_tsquery('simple')`의
  lexical 후보 선별이며 `ts_rank_cd`는 BM25가 아니고 근거의 질도 아니다. 한국어 형태소 분석, 영어
  stemming, embedding, rerank는 구현하지 않았다. migration 주석과 계약 주석에 명시했다.
- **검색된 텍스트와 모델 출력은 신뢰하지 않는 데이터다.** passage 안의 "이전 규칙을 무시하라" 같은
  문장은 데이터일 뿐이며 도구 권한·정책 변경·승인 권한을 주지 않는다. heading 경로는 파서 출력이므로
  계약이 허용하는 범위로 정규화한 뒤 저장한다. 계약·모듈·UI 문구에 같은 경계를 적었다.
- **LLM은 호출하지 않았다.** 이 저장소에 설정된 coaching 실행 경로는 결정론적 fixture
  (`synthetic-v1`)뿐이고 provider adapter는 `COACHING_PROVIDER_NOT_CONFIGURED`로 거절된다. retrieval과
  색인은 provider 호출이 없는 순수 SQL·CPU 작업이라 caller transaction 안에서 수행해도 "DB transaction
  안에서 LLM 호출 금지" 규칙을 어기지 않는다. 모델 실행 자체는 기존 outbox·lease 경로(`coaching.run_queued`)
  로만 일어난다.
- **evidence dependency 통합.** `packages/contracts/src/evidence-dependencies.ts`가
  `resource-access-v1` manifest를 `resourceAccessDependencyManifestSchema`로 1급 의존성으로 받아들이고,
  `compareResourceAccessDependencies`(동의 head·인가 집합 digest 비교)와, core ledger head와
  resource access를 **둘 다 요구하는** `evidenceDependencyManifestSchema` /
  `compareEvidenceDependencies`를 제공한다. 한쪽이 빠진 manifest는 "변화 없음"이 아니라
  `unsupported`다.
  coaching basis의 `retrieval` 필드는 `{kind:'none'}`에서
  `{kind:'resource-access-v1', query, manifest}` union으로 확장됐다. 고정한 run은 승인 시점에 같은
  transaction에서 manifest를 다시 수집해 **집합 전체**를 비교하며, 달라지면
  `retrieval.authorizedSet`/`retrieval.aiConsent` 변화로 `STALE_BASIS`가 된다. retrieval을 고정하지
  않은 run은 자료 의존성이 없으므로 뒤에 자료를 켜도 stale이 되지 않는다.
- **승인 경로.** `coaching-candidates.ts`의 `currentContext`(fixture 후보 생성·부분 후보·승인이 모두
  통과하는 지점)가 승인 transaction 안에서 resource access manifest를 다시 수집해 비교한다. 따라서
  검토 자료에 근거한 후보는 그 자료 집합이 그대로일 때만 승인된다. 네 도메인 통합 승인과 joint 승인은
  검색된 콘텐츠를 소비하지 않으므로 고정할 resource 의존성이 없다(이 점은 아래 "검증하지 않은 것"에
  명시).

## 구현 기록

- Migration **032** `032_resource_retrieval.sql`: 위 네 테이블, tenant RLS,
  `purge_resource_derived_store`, 그리고 파생 저장소를 먼저 지우는 `erase_account` 래퍼.
  `resource_version.index_status`는 M2-04a의 immutability trigger가 모든 UPDATE를 막으므로 손대지
  않았고, 색인 상태의 근거는 `resource_passage` 행의 존재라는 점을 migration 주석에 적었다.
- `packages/server/resource-ingestion/src/chunk.ts`: 저장된 문단을 byte 상한으로 묶는 순수 결정론적
  chunker. locator offset을 보존하고, heading 경로가 좁아지면 새 passage를 시작하며, 코드 포인트
  경계에서만 자른다.
- `packages/server/persistence/src/resource-retrieval.ts`: 인가 집합 조회, bounded lazy 색인
  (호출당 최대 5개 자료), lexical 검색, cache 읽기/무효화/쓰기, grounding 준비/기록, 인용 검증/기록,
  gate를 다시 통과시키는 grounding 읽기.
- `resource-derived-cleanup.ts`에 `purgeTarget`과 `createResourceDerivedStorePurge`를 추가하고,
  worker 기본 실행기 map을 빈 map에서 이 실제 실행기로 교체했다.
- 계약: `packages/contracts/src/resource-retrieval.ts`(질의·발췌·인용·grounding·retrieval 요청/기저),
  `evidence-dependencies.ts`(위 통합), `coaching-basis.ts`(retrieval union과 비교),
  `coaching-runs.ts`(run 생성 command의 선택적 `retrieval`, 생략 시 자료를 읽지 않음).
- API: `POST /bff/v1/retrieval/queries`, `GET /bff/v1/coaching-runs/:runId/grounding`. tenant는 인증에서만
  얻고 본문의 athlete 식별자는 400으로 거절한다.
- UI: 코칭 실행 패널에 `검토 자료 검색어(선택)` 입력과 `검토 자료 인용` 영역(인용 다시 확인 버튼,
  고정 자료 수, 현재 볼 수 없는 발췌 수, 인용 목록, 철회 안내)을 추가했다.
- root `vitest.config.ts`의 node project include에
  `packages/server/resource-ingestion/tests/**`와 `apps/worker/tests/**`를 추가했다(아래 검증 항목 참조).
- `database.ts`의 non-owner 검사 목록에 `resource_share`, `resource_access_audit`,
  `resource_derived_cleanup`과 새 네 테이블을 추가했다. runtime role이 이들을 소유하면
  `createDatabase()`가 거절한다.
- `resource_citation`에 `(athlete_id, grounding_id, passage_id)` → `resource_grounding_excerpt`
  외래 키를 추가해, 자기 grounding이 고정하지 않은 passage를 인용하는 것을 DB가 막는다.
- 계정 export를 v16 → **v17**로 올리고 `resourcePassages`, `resourceGroundings`,
  `resourceGroundingExcerpts`, `resourceCitations`를 추가했다. passage·발췌 **본문은 내보내지 않는다**
  (export가 이미 담고 있는 자료 version의 사본이고, 인용은 식별자와 offset으로 참조한다).
  retrieval cache는 재생성 가능한 cache이므로 export 대상이 아니며 말소 시 삭제된다.

- `pnpm test:integration`: 실제 PostgreSQL에서 **42 files / 373 tests 통과**(기준선 40 files /
  357 tests). 처음 작성한 cleanup drain helper가 한 번 간헐 실패했다(`empty` 응답을 보고 조기
  종료해 manifest가 남은 상태로 단언). helper를 "열린 manifest가 0이 될 때까지 돌고, 남아 있으면
  명확한 메시지로 실패"하도록 고치고 lease도 초기화하게 바꾼 뒤 연속 실행에서 재현되지 않았다.
  이 간헐성은 테스트 helper의 문제였고 제품 코드 경로는 바뀌지 않았다. 새 파일 `resource-retrieval.integration.test.ts` 12건은 다음을 실DB로 확인한다.
  - 미검토 자료는 색인되지도 검색되지도 않고, 검토+coach 사용 자료만 색인·반환된다.
  - 두 번째 조회는 `revalidated` cache hit이고 같은 발췌·같은 digest를 준다.
  - 다른 tenant는 남의 색인·cache·인용을 보지 못한다.
  - version을 추가하면 새 version만 반환되고 두 version이 섞이지 않는다.
  - 새 version을 추가하면 검토가 이전 version에 고정된 채 남아 gate가 닫히고, 겹쳐 쓴 색인 행이
    회수되며, 현재 version을 다시 검토 표시해야 다시 검색된다.
  - retrieval cache는 tenant당 상한과 TTL 회수가 실제로 동작하고 worker prune이 만료 행을 지운다.

   하므로 순서를 추론할 필요 없이 pin하고, 그 외에는 `reviewed_at > v.created_at`의 **엄격한**
   비교만 인정한다. 동률은 증명 불가이므로 고정하지 않는다.
   031 schema에 더 나은 신호는 없다: `resource_version`에는 access revision이 없고
   `resource_access_audit`에는 version append action 자체가 없어서 revision으로 비교할 방법이
   없다. 단일 version 규칙이 유일한 순수 구조적 신호이며, 그 다음은 M2-04d에 재검토 전환이
   없었다는 사실(이미 reviewed인 자료를 reviewed로 표시하면 no-op)에 기대어 `reviewed_at`이
   "현재 유효한 검토의 시각"임을 이용한 엄격 비교다. upgrade 테스트에 동률 2-version(미고정)과
   동률 1-version(고정) 두 경우를 추가했다.
2. **"새 legacy 미고정 행은 생길 수 없다"는 주석이 실제 제약이 아니었다.** CHECK는 reviewed +
   NULL pin을 허용하고 head transition trigger는 BEFORE UPDATE뿐이며 runtime role은 `resource`에
   INSERT 권한이 있다(현재 서비스 insert는 모두 unreviewed이고 gate는 fail-closed라 노출은 없었다).
   `resource_reviewed_insert` BEFORE INSERT trigger를 추가해 reviewed + 미고정 INSERT를 거절하고,
   주석을 실제 강제 수단(CHECK + insert trigger + update trigger)으로 고쳤다. upgrade 테스트가
   업그레이드 후 그런 INSERT가 거절되는 것을 확인한다.
3. **재검토 시각.** 재검토가 pin만 옮기고 `reviewed_at`은 `coalesce`로 옛 값을 유지해, 보고되는
   검토 시각이 다른 본문에 대한 검토의 시각이었다. pin이 현재 version으로 이동할 때는
   `statement_timestamp()`로 함께 전진시킨다.
4. 이 문서의 앞부분(ACL 필터 항목)이 version append 후 "다음 retrieval이 현재 version을 색인한다"고
   말해 재검토 gate를 건너뛰는 것처럼 읽히던 문장을, 뒤쪽 설명과 같게 "검토 pin이 현재 version으로
   옮겨진 뒤에만 색인된다"로 고쳤다.
