# M2-01aa · API 실제 진입점이 `process.env`로 부팅하지 못함

상태: **완료.** 기준 HEAD `3ee5ca0`. 독립 검토 승인(차단 0). 코드 변경은
`apps/api/src/configured.ts`(수정)와 `apps/api/tests/configured-environment.test.ts`(신규)이고, 이 문서가 더해진다.

## 1. 재현

실제 진입점 `node --import tsx apps/api/src/start.ts`를 돌렸다. 환경은 도달 불가능한 DB
(`postgres://…@127.0.0.1:1/…`), 임시 저장소 root, 로컬 가짜 OIDC discovery 서버(127.0.0.1:48922,
`/.well-known/openid-configuration`만 응답)이고, API 포트는 48921이다. 하네스 포트는 쓰지 않았다.

- 수정 전 `start.ts`는 `API startup failed; verify identity and database configuration.`를 내고 exit 1로
  끝났다. 가짜 OIDC 서버에는 discovery 요청이 들어왔다. 즉 OIDC 단계는 통과했다.
- 이 메시지는 `start.ts`가 원인을 일부러 숨긴 것이다. 그래서 `createConfiguredApi(process.env)`를 같은 방식으로
  부르는 디버그 래퍼로 원인을 확인했다. zod `invalid_type` 오류
  `Invalid input: expected record, received `(`path: []`)였다. 예상한 DB·OIDC 오류가 아니다.

## 2. 원인

`configured.ts`는 routing 설정을 넘길 때 `z.record(z.string(), z.unknown()).parse(environment)`를 호출한다.
이 코드는 eae0ee1(routing settings)에서 들어왔다. zod 4.6.5의 record는 plain object만 받는다.
`process.env`의 prototype은 `Object.prototype`이 아니어서 거부된다. 같은 버전에서 확인한 결과는 다음과 같다.

- record: `process.env`는 실패한다. `{...process.env}`와 `Object.create(null)`은 통과한다.
- `z.object`/`z.looseObject`: `process.env`를 받는다.

지금까지 이 오류가 드러나지 않은 이유는 startup OIDC discovery가 먼저 실패했기 때문이다. 단위 테스트는 모두
object literal을 넘기므로 이 오류를 잡지 못했다.

## 3. 수정

`plainEnvironment(environment)`를 추가했다. non-array object면 own entries를 plain object로
복사(`Object.fromEntries(Object.entries(…))`)하고, 그 밖의 값은 그대로 schema에 넘겨 거부되게 한다.
record parse 한 줄만 이 함수를 거치게 바꿨다. 값 검증은 약해지지 않았다. 앞선 `environmentSchema`
검증과 routing의 부분 설정 거부는 그대로다. OIDC discovery 부근(M2-01w 작업 영역)에서 바뀐 것은
이 한 줄뿐이다.

## 4. 함께 확인한 진입점

- `apps/worker/src/{start,resource-cleanup,url-ingestion,course-thumbnail}.ts`: `process.env`를
  `parse*WorkerConfig`에 넘긴다. 이 함수들은 zod를 쓰지 않고 key 접근만 하므로 **영향이 없다.**
- `configuredGarmin(environment, …)`: `z.object`(`schema.parse(environment)`)를 쓴다. `process.env`를
  받으므로 **영향이 없다.** 수정 뒤 부팅에서도 통과했다.
  `scripts/process-garmin-revocations.mts`도 `process.env`를 `configuredGarmin`에 넘기며 같은 이유로 안전하다(독립 검토가 찾음).
- `environmentSchema.parse(environment)`(`z.object`)도 **영향이 없다.**
- `scripts/identity-e2e.mts`: `createConfiguredWalkingRoutes(process.env)`를 직접 부른다. zod record를
  거치지 않으므로 영향이 없다. 반대로 이것 때문에 E2E가 이 결함을 가렸다.
- `.parse(process.env`의 다른 사용처는 없다(`start.ts`의 `PORT` 값 parse만 있음). web·mobile-web은
  `process.env[...]`를 직접 읽는다.

## 5. 결과

- 회귀 테스트 `configured-environment.test.ts`(OIDC provider만 mock, 실제 `process.env`와 `vi.stubEnv`):
  1. 실제 `process.env`로 `createConfiguredApi`가 resolve되고 `/health`가 200을 돌려준다.
  2. `ROUTING_ENGINE_ALLOWED_HOSTS`만 설정하면 `ROUTING_CONFIGURATION_INCOMPLETE`로 거부된다. 정규화가
     값을 버리지 않는다는 뜻이다.
- 회귀 테스트 결과: 수정 전에는 두 테스트 모두 `expected record`로 실패했고, 수정 뒤에는 2/2 통과했다.
- 수정 뒤 실제 진입점: `start.ts`가 `Server listening at http://127.0.0.1:48921`를 냈고
  `GET /health`가 `{"status":"ok"}`를 돌려줬다. SIGTERM을 보내자 exit 0으로 끝났다. DB pool은 lazy라
  도달 불가능한 DB로도 listen까지 간다. DB가 필요한 요청은 이 검증에 포함하지 않았다.
- 변이 검사(단일 anchor): record parse 인자를 `environment`로 되돌리면 새 테스트가 2/2 `expected record`로
  실패했다. 복원 뒤 `cmp`로 동일함을 확인했고 다시 2/2 통과했다.
