## 1. 참조 walk가 루트를 `lstat`하지 않았다

### 1.1 재현(기준 코드, 실제 파일시스템)

객체 하나를 쓴 뒤 루트를 바꾸고 각 연산을 호출했다(임시 스크립트, 기준 `local-filesystem.ts` 그대로).

| 루트를 바꾼 방식                      | `assertReachable`     | `stat`          | `open`          | `writeTemporary`(새 key)                            | `delete`                  |
| ------------------------------------- | --------------------- | --------------- | --------------- | --------------------------------------------------- | ------------------------- |
| 빈 디렉터리를 가리키는 symlink        | `UNSAFE_STORAGE_PATH` | **`null`**      | **`null`**      | **성공 — link 대상 안에 key 경로 전체와 객체 생성** | **resolve(아무 일 없음)** |
| 루트 삭제(ENOENT)                     | `ENOENT`              | **`null`**      | **`null`**      | `ENOENT`                                            | **resolve**               |
| 일반 파일로 교체                      | `UNSAFE_STORAGE_PATH` | `ENOTDIR`       | `ENOTDIR`       | `ENOTDIR`                                           | `ENOTDIR`                 |
| 객체 사본이 있는 디렉터리로의 symlink | `UNSAFE_STORAGE_PATH` | **사본의 객체** | **사본의 객체** | **성공 — 사본 안에 생성**                           | **사본의 객체를 지움**    |

(검토자 추가 확인: 같은 사본 symlink에서 `publishTemporary`도 **사본 안에 게시**했다.)

검토자 실측(symlink 루트에서 `stat`이 `null`)을 재현했고, 범위보다 넓은 결과도 나왔다: **쓰기가 루트
밖(link 대상)으로 나가고, 게시가 link 대상 안에 되며, 삭제가 link 대상의 객체를 지운다.** 스윕 경로에서는 검토자 분석대로 결과가
누수(DB settle 하한이 reclaim을 막음)지만, 업로드·삭제 경로에서는 가드 밖 쓰기·삭제다.

### 1.2 수정

- `assertRootIntact()`: `lstat(canonicalRoot)`, 디렉터리가 아니면 `UnsafeStoragePathError`. **ENOENT는
  흡수하지 않는다** — `lstatIfPresent`를 쓰지 않는다. 참조 단위의 "부재 → null"과 루트의 "부재 → 저장소
  없음(실패)"은 다른 의미이고, M2-01n의 `assertReachable`이 이미 그은 선을 그대로 따른다.
- **모든 walk 앞에서** 호출: `assertSafeExistingFile`(stat·open·delete·publish의 임시/최종 확인)과
  `prepareParents`(writeTemporary·publish).
- **답하기 직전에 다시 묻는다**: `assertSafeExistingFile`은 "부재"(`absentUnderIntactRoot`)든 "있음"이든
  답을 돌려주기 전에 루트를 한 번 더 확인한다.
- **부작용 뒤에 다시 묻는다(재검토 반영, §1.4)**: 각 연산의 **마지막 경로 호출 뒤** — `writeTemporary`의
  close·`lstat` 뒤, `publishTemporary`의 link·unlink 뒤(`published`와 `already_present` 두 갈래),
  `delete`의 unlink·prune 뒤, `hashFile`·`readFileBody`의 `open` 직후 — 루트를 다시 확인하고, 온전하지
  않으면 `UnsafeStoragePathError`로 실패한다.
- `lstat`은 symlink를 디렉터리로 보고하지 않으므로 `!isDirectory()` 하나로 link·파일·기타를 모두 거절한다.

**M2-01m·M2-01n 가드 무변경**: `prepareParents`의 루프 본문(`missing()`+`lstat()`, ENOENT만 흡수,
symlink·비디렉터리 거절, `chmod`)과 `assertSafeExistingFile`의 성분 루프(한 번의 `lstatIfPresent`,
ENOENT만 흡수), `unitPrivateDirectoryDepth`·`pruneEmptyParents`는 **한 글자도 바뀌지 않았다.** 추가된
것은 루트 확인 호출뿐이다 — 루프 앞, 답하기 직전, 각 연산의 마지막 경로 호출 뒤. 어떤 기존 거절도
통과로 바뀌지 않았고, 새로 생긴 결과는 전부 "실패"다. 다섯 consumer 통합 시험 통과(§8).

### 1.3 남는 위험 — 막지 못하는 것(재검토로 정정)

**1차 보고는 이 위험을 실제보다 작게 적었다.** 정정한다.

이 파일의 모든 연산은 **경로 기반**이다: walk의 `lstat`들, `mkdir`, `chmod`, `open`, `link`, `unlink`.
Node에는 `openat`이 없어 이 호출들을 루트 descriptor에 묶을 수 없다. 그래서 **루트 확인 뒤, 연산의
마지막 경로 호출 전에 루트가 한 방향으로 한 번만 바뀌어도**(되돌릴 필요 없음 — ABA 불필요), 그 뒤의 모든
호출이 link를 따라간다:

- **`writeTemporary`·`publishTemporary`·`delete`는 루트 밖(link 대상)에 쓰고·게시하고·지운다.**
- **`stat`·`open`은 link 대상의 객체를 돌려준다.**

창은 "walk 하나(µs)"가 아니다. **여러 event-loop 턴과 thread-pool 호출**(성분 `lstat` 약 11회, 이어서
`mkdir`·`chmod`·`open`·쓰기·`fsync`…)에 걸친다.

독립 검토자의 측정(1차 수정 r1 대상, 시도마다 새 저장소와 그 사본, k = 0..40 `setImmediate` 틱 뒤 루트를
사본 symlink로 **한 방향으로만** 교체, 연산당 615회):

| 연산               | r1 결과                                     |
| ------------------ | ------------------------------------------- |
| `writeTemporary`   | **471 / 615가 사본에 기록**, 144 거절       |
| `publishTemporary` | **267 / 615가 사본에 게시**                 |
| `delete`           | **193 / 615가 사본의 객체를 삭제**          |
| `stat`             | 579가 사본의 객체를 돌려줌, 36 거절, null 0 |

r1이 보장한 것은 "부재로 답하지 않는다"(null 0)뿐이었다. 이 노드의 최종 상태가 보장하는 것은 §1.4의
**"조용히 성공하지 않는다"**이고, **탈출 자체는 여전히 일어난다.** `openat` 없이는 완전히 닫을 수 없다는
판단에는 검토자도 동의했다.

그 밖에 남는 것:

- **ABA**: 한 연산 **안에서** 루트가 바뀌었다가 **되돌아오면**, 경로 기반 확인은 모두 같은 디렉터리를
  보므로 탈출(쓰기·삭제)도 잘못된 읽기도 **조용히 성공**할 수 있다. 읽기 쪽 측정(루트를 계속 왕복
  교체하는 루프 + 3000회 `stat`): 무부하 **0 / 24,000**, 6 프로세스 동시(부하 평균 ~10) **3 / 72,000**이
  부재로 답함. 쓰기 쪽 ABA는 측정하지 않았다. 알려진 한계로 시험에서 제외했다.
  - 이 측정의 계기: 처음 쓴 `stat` 경합 시험은 위 왕복 루프였고 부하 아래서 2회 실패했다(메시지 미포착,
    격리 재실행 20×3000회 재현 안 됨, 부하 실험에서 원인 확인). 시험을 단방향으로 바꿨다.
- **마운트 해제로 빈 마운트 지점이 남는 경우**: 루트는 여전히 실제 디렉터리이므로 모든 확인을 통과하고
  참조는 부재로 읽힌다. 잡으려면 루트 `dev`/`ino`를 기억해 비교해야 하고, 그러면 재마운트마다 프로세스
  재시작이 필요하다(운영 동작 변경). scope 밖이라 **하지 않았다.**
- `canonicalRoot`의 **조상** 경로는 여전히 따라간다(구성 신뢰 범위, 이전과 같음).

### 1.4 부작용 뒤 재확인 — 탈출을 막지는 못하지만 조용히 성공하지 않게

**무엇을 하나**: 각 연산이 마지막 경로 호출 뒤 루트를 다시 묻는다(§1.2). 한 방향 swap이 연산 도중에
들어와 **연산이 끝날 때까지 지속되면**, 탈출했든 안 했든 연산은 `UnsafeStoragePathError`로 끝난다.
ABA를 뺀 **지속되는 모든 swap**이 소리 나게 된다.

**되돌리기는 하지 않는다 — 근거**: 루트 밖에 만든 임시·최종 객체를 지우거나 사본에서 지운 객체를
복원하려는 호출도 **같은 경로, 같은 link를 따라간다.** 되돌리기가 루트 밖을 한 번 더 건드리고, 그 사이
루트가 또 바뀌면 무엇을 건드리는지조차 모른다. 이미 일어난 부작용은 오류로 보고만 하고 손대지 않는다.
`writeTemporary`의 이 재확인은 기존 `try`(쓰기 실패 시 `unlink`하는 블록) **밖**에 두어 정리 `unlink`가
돌지 않게 했다.

**호출자가 이 오류를 성공으로 처리하지 않는지** — 확인함:

| 호출자                                         | 이 오류를 받으면                                                                                                                                                               |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `storeValidatedUpload`(`upload.ts`)            | 그대로 던짐. write 실패면 `temporaryOwned`가 false라 삭제 시도 없음, publish 실패는 `durablyPrepared` 뒤라 삭제 시도 없음                                                      |
| gallery 업로드(`gallery-media-upload.ts`)      | `upload.ts`와 같은 모양, 던짐                                                                                                                                                  |
| track 업로드(`activity-track-routes.ts`)       | `publish` 실패 → catch, durable 전이면 best-effort 삭제, 이후 `requeueObjects` — 성공 처리 아님                                                                                |
| URL 수집 worker                                | publish 실패 → `cleanupUncommittedArtifact`(임시 삭제 `.catch`) 후 실패 경로. `publishedByThisRun`은 false로 남아 `abandonPublishedObject`를 부르지 않음 — 아래 거짓 양성 참고 |
| course 썸네일 worker                           | publish·write 실패 → 임시 삭제(`.catch`) 후 `repository.fail(…'RENDER_FAILED')` → 재시도                                                                                       |
| cleanup drain(`resource-cleanup-worker.ts`)    | `delete` 실패 → `OBJECT_DELETE_FAILED` → `retry_scheduled`(검토자 확인)                                                                                                        |
| best-effort `delete(…).catch(() => undefined)` | 정리 호출이며 주 연산은 이미 실패 중. 조용히 삼켜지는 것은 **정리 실패**이지 주 연산의 성공이 아님                                                                             |

알려진 비용(시끄러운 쪽 거짓 양성): swap이 **마지막 경로 호출 뒤, 재확인 전**에 들어오면 부작용은 실제
저장소에 정확히 일어났는데도 연산이 실패한다. publish라면 객체는 실제 저장소에 게시되었고 호출자는 실패로
본다. 다섯 호출자 모두 publish **전에** 최종 이름을 durable하게 기록한다(upload·gallery `onPrepared`,
track `durablyPrepared`, URL `prepareRaw`/`prepareParsed`, 썸네일 `prepare`). 그 기록이 실패한 작업의
객체까지 회수하는지는 호출자별 기존 경로(reaper·manifest)에 기대며, 구현자는 끝까지 추적하지 않았다.
**독립 검토(r2)가 다섯 호출자를 코드로 추적해 영구 고아가 없음을 판정했다**(전체 경로의 end-to-end 실행은 아님):

- 리소스 파일 upload(`upload.ts`): 오류가 검증·충돌이 아니면 `fail()`을 부르지 않아 intent가 `prepared`로 남고
  `storage_ref`는 최종 이름이다. 재시도는 같은 key로 `already_present`에 채택되고, 만료되면
  `reap_expired_resource_uploads` → `queue_resource_upload_refs`가 임시·최종 ref를 모두 `upload_abandoned`로 큐한다.
- gallery upload: 같은 모양, 같은 reaper의 두 번째 루프 → `queue_gallery_upload_refs`.
- track upload: `durablyPrepared` 뒤 catch가 `requeueObjects`를 부르고, 만료 reaper가 ref 6개를 큐한다.
  prepare 때 기록된 참조 색인이 M2-01m 스윕이라는 또 하나의 안전망이다.
- URL 수집 worker: `prepare_resource_url_raw`/`…_parsed`는 ref를 한 번만 설정한다. 재시도 가능한
  `FETCH_FAILED` → 같은 내용이면 `already_present` 채택, 다르면 충돌, `attempt≥5`면
  `fail_resource_url_ingestion` → `queue_resource_url_refs`가 ref 넷을 큐한다. 만료도 같은 큐.
  `abandonPublishedObject`를 부르지 않아도 해가 없다.
- 썸네일 worker: `prepare`가 `storage_ref`를 기록하고 트리거가 색인 행을 남긴다. 재시도 가능한 `fail`은
  ref를 유지하고(같은 기하 → 같은 key → `already_present`), 영구 실패는 ref를 큐하며, 색인에만 남은 것은
  스윕이 회수한다.
- cleanup drain(연산은 delete뿐): unlink가 성공했는데 실패로 보고되면 `finish(ok:false)`가 재시도하고,
  객체가 이미 없으니 `delete`가 resolve되어 영수증이 완료된다.

**단서(이 노드가 넓힌 것은 아님)**: "결국 회수"는 루트가 복구된다는 전제다. swap이 지속되는 동안은
모든 cleanup `delete`가 실패하고 `attempts=100`(backoff 상한 5분, 약 8시간) 뒤 `lease`가 그 영수증을
제외해 운영자 개입을 기다린다. 어떤 저장소 장애에도 같다. 이전에는 link 뒤에 publish가 실패하는 경로가 없었으므로(임시 unlink 실패는 삼킴) 새로 생긴
모양이다 — 예컨대 URL worker는 `publishedByThisRun`이 false라 `abandonPublishedObject`를 부르지 않는다.
쓰기에서는 `fsync`가 길어 이 경우가 흔하다(아래 `error ENOENT`: 쓰기는 실제 저장소에 됐고, 마지막
`lstat(path)`가 link 너머에서 ENOENT).

**시험 — `ends every operation through a root swapped mid-operation in an error, never a silent success`**:

- 연산 6종(write, publish, republish = `already_present` 갈래, delete, stat, open). 시도마다 새 저장소와
  그 사본(읽기용으로 사본의 객체 내용을 다르게), 다른 파일시스템 호출 k번(k = 0..150) 뒤 루트를 사본
  symlink로 **동기적으로**(`renameSync`+`symlinkSync` — 두 단계 사이에 연산의 호출이 끼지 않는 깨끗한
  한 방향 swap) 교체, 연산이 끝날 때까지 되돌리지 않음. delete·open은 창이 한두 호출 폭이라 지연마다 3회.
- 판정: 연산이 **resolve했는데** 부작용이 사본에 있거나(쓰기·게시·삭제), 사본의 객체를 읽었거나, 실제
  저장소에 아무 일도 없었으면 `SILENT`. **`SILENT`가 0이어야 한다.** 탈출 후 오류(`(escaped)`)는 허용하고
  센다.
- **거짓 실패 불가**: 루트가 연산 중 되돌아오지 않으므로, resolve했다면 재확인이 실제 루트를 보았다는 뜻이고
  그러면 swap은 모든 경로 호출 뒤였다 — 부작용은 실제 저장소에 있다. ABA는 의도적으로 생성하지 않는다.
- 첫 설계(비동기 `rename`→`symlink`)는 두 단계 사이의 "루트 없음" 순간에 연산이 거의 항상 ENOENT로
  걸려 탈출이 거의 생성되지 않았다(쓰기 탈출 1/151). 동기 교체로 바꾼 뒤 탈출이 실제로 생성된다(아래).

## 2. `assertReachable`의 순서

`lstat`(루트 확인) → `access(R_OK|X_OK)` → `open(O_RDONLY|O_DIRECTORY|O_NOFOLLOW)` → `fstat`으로
바꿨다. `access`는 경로로 동작하고 link를 따라가며(Node에 fd 기반 `faccessat` 없음), 이제 그것이
`open` **앞**에 오므로 마지막 권위 있는 검사가 실제로 연 디렉터리에 걸린다. 기존 `isSymbolicLink() ||`
중복 항은 `assertRootIntact`로 대체되며 사라졌다(생성자·`prepareParents`의 같은 모양은 범위 밖이라
그대로 둠).

순서 자체(access가 open 앞)를 지키는 시험은 **없다** — 창이 `close`와 `access` 사이 한 syscall이라
결정적으로 만들 수 없다. 이는 비공허성 표의 "측정 불가" 항목이다.

## 3. 루트에 요구하는 권한(주석 정정)

이전 주석 "stat이 필요로 하는 search와 read"는 틀렸다 — 루트 아래 `stat`에는 **search(X)만** 필요하다.
실측을 시험으로 고정: `0o100` 루트에서 `stat`은 객체를 돌려주고, `assertReachable`은 `EACCES`로 거절.

**R_OK는 유지**했고 근거를 주석에 적었다: 마지막 검사를 descriptor 기반으로 만드는
`open(O_RDONLY|O_DIRECTORY)`가 read를 요구하고(Node에 `O_SEARCH` 없음), 이 저장소가 `0o700`으로 만든
루트가 read를 잃었다면 시작 후 누가 바꾼 것이다. 즉 보수적 쪽(도달 불가로 보고) 오류이며, 읽을 수 없는
저장소를 비어 있다고 읽는 쪽으로는 틀리지 않는다. 되돌림 결과 `access`의 `R_OK`는 `open`의 read 요구와
**중복 방어**다(§5, B8: 0건).

## 4. grant 헬퍼의 원자성

### 4.1 재현

`grant-helper-atomicity.integration.test.ts`: 전용 role을 만들고, 그 role의 연결이 좁혀진 권한을 쓰는
**0행 문장**(권한 검사만 실행, RLS·제약·데이터 무관)을 쉬지 않고 보내는 동안 헬퍼를 반복 실행한다.

| 헬퍼(기준 코드)                           | 탐침                                                                                             | 결과              |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------ | ----------------- |
| `grantActivityTracks` ×150                | `INSERT INTO activity_track_object_ref(storage_ref,athlete_id,recorded_at) SELECT … WHERE false` | **`42501` 231건** |
| `grantResources`·`grantOperations` 각 ×60 | `SELECT athlete_id, state FROM resource_url_ingestion WHERE false`                               | **`42501` 268건** |

두 번째 줄은 scope에 없던 같은 모양이다: `grantSafeResourceUrlReadColumns`가 URL 수집 6개 표의 표 단위
`SELECT`를 회수한 뒤 열 단위로 다시 준다(M2 이전부터). `grantResources`와 `grantOperations`가 모두 부른다.

### 4.2 수정

`inOneGrantTransaction(pool, work)`: pool에서 client 하나를 받아 `BEGIN` … `COMMIT`(실패 시 `ROLLBACK`
후 원래 오류). GRANT/REVOKE는 PostgreSQL에서 transactional이고 동시 문장은 커밋된 ACL로 권한을 검사하므로,
role은 옛 권한에서 새 권한으로 틈 없이 넘어간다. 적용:

- `grantActivityTracks`의 `REVOKE INSERT` + 열 `GRANT`
- `grantSafeResourceUrlReadColumns` 전체(REVOKE + 열 GRANT 6개)

`grantResourceObjectCleanupWorker`는 **바꾸지 않았다**: 순서가 새 함수 GRANT → 옛 candidates REVOKE라
권한이 비는 순간이 없다(같은 모양이 아님). 중간 실패 시 "둘 다 가진" 상태가 남지만 오류로 크게 끝나고,
헬퍼 재실행이 복구한다(M2-01n §2.8 시험). 원자화하려면 긴 GRANT 문장을 재들여쓰기해야 해 diff만 커진다.

## 6. F6 — publish의 해시·크기 검사를 각각 지키는 시험

기존 표본(`'different'` 9 byte vs `'expected'` 8 byte)은 크기와 해시가 **둘 다** 달라 어느 한 검사만으로
잡혔다(root 보고: 해시 제거 44/44, 크기 두 곳 제거 44/44). 추가한 시험:

- **크기 같고 해시만 다름**: `'tampered'` vs `'expected'`(둘 다 8 byte) → `ObjectStorageConflictError`.
- **해시 같고 크기만 다름**: 올바른 바이트, 선언 크기 +1 / −1 → `ObjectStorageConflictError`.
- 두 시험 모두 거절 뒤: 최종 key `stat` = `null`, 최종 쪽 `objects/` 디렉터리 **자체가 없음**(검사가
  `prepareParents(finalPath)` 앞에 있으므로), **임시 객체는 원래 바이트 그대로 남음**.

**임시 객체가 남는 것은 기존 계약이다**: publish 시점의 임시 객체는 호출자가 이미 `onPrepared`로
durable하게 기록했고, 그 기록이 회수한다(`upload.ts`는 `durablyPrepared` 이후 실패에서 임시를 지우지 않음,
기존 시험 "records exact refs before publish and retains a durably tracked temp on interruption"). publish가 지우면 그 계약과 충돌한다. 그래서
"남지 않음"이 아니라 "**최종은 생기지 않고 임시는 손대지 않음**"을 고정했다.

되돌림(각 8회, 유일 anchor, 최종 코드에서 재실행 — 부하 평균 26~52, 결과는 1차와 동일):

| 되돌림                                             | 결과  | 실패한 시험                  |
| -------------------------------------------------- | ----- | ---------------------------- |
| 해시 비교 제거                                     | 1 × 8 | 크기 같고 해시만 다름 **만** |
| 크기 비교 두 곳(stat 크기 + 해시한 바이트 수) 제거 | 1 × 8 | 해시 같고 크기만 다름 **만** |
| stat 크기 비교만 제거                              | 0 × 8 | — 중복 방어                  |
| 해시한 바이트 수 비교만 제거                       | 0 × 8 | — 중복 방어                  |

두 크기 비교는 서로의 중복이다: 파일이 `stat`과 해시 사이에 바뀌지 않는 한 같은 값을 비교한다. stat
쪽은 큰 파일을 해시하기 전의 조기 거절, 해시 쪽은 `stat`↔읽기 사이 변경에 대한 방어이며, 후자의 창은
임시 객체의 writer가 그 단위 하나뿐이라 결정적 시험을 만들 수 없다. **검사 로직은 바꾸지 않았다**
(옳다고 판단).

## 7. 성능(루트 `lstat` 추가분)

같은 프로세스에서 기준(`17effce`)과 수정 구현을 번갈아 8라운드, 중앙값. 연산당 루트 `lstat`은 walk 전
1회 + 답/부작용 뒤 1회(+ 본문 `open` 뒤 1회)로 늘었다.

| 경로                                    | 기준     | 1차(사전 확인만) | 최종(부작용 뒤 재확인 포함) | 최종 차이 |
| --------------------------------------- | -------- | ---------------- | --------------------------- | --------- |
| `stat`(있음, track 임시 key — 11 성분)  | 189.2 µs | +10.9%           | 204.5 µs                    | +8.1%     |
| `stat`(부재, 부모 존재 — 스윕의 "없음") | 121.2 µs | +20.3%           | 146.5 µs                    | +20.9%    |
| write + publish + delete, 64 KiB        | 7,574 µs | +1.5%            | 7,742 µs                    | +2.2%     |

최종 측정 시 부하 평균 ~9(1차 ~~7~~10). 있음 경로가 1차보다 작게 나온 것은 잡음 범위다(두 측정의 기준값도
178→189 µs로 움직였다). 부재 경로는 `lstat`이 2개(사전 + 재확인) 늘어 비율이 가장 크다. 절대값은 참조당 ~25 µs이고, 스윕은
참조마다 DB 왕복(settle/reclaim, ms 단위)을 하므로 창 크기 1,000이어도 +25 ms 수준이다. 업로드는 네트워크·
검증·DB를 빼고 파일시스템만 잰 값에서 +1.5%다. 문제 되지 않는다고 판단한다.
