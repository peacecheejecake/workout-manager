## 1. 설계 근거

- **예산은 데이터다.** 예산은 [performance-budget.json](../research/performance-budget.json)에 있다. 판정은
  [scripts/performance-budget.ts](../../../scripts/performance-budget.ts)의 `evaluateBudget` 한 곳에서 한다.
  서버 probe와 브라우저 spec이 같은 함수를 쓴다.
- **예산의 성격.** 이 예산은 **2배 이상의 회귀를 잡는 장치**다. 지연 SLO가 아니다. 여유 배수(시간 2배)
  때문에, 경로가 두 배 가까이 느려지기 전까지는 통과한다. 사용자 체감 목표는 따로 정해야 한다.
- **예산은 측정에서 나온다.** 기록 전용(record-only) 기준선 3회를 먼저 돌렸다. 예산은
  `기준선 통계 × 여유 배수`이고, 두 자리 유효숫자로 올림한다(+10 % 이내). 예산이 기준선보다 낮거나 배수로
  설명되지 않으면 `parseBudgetFile`이 파일을 거부한다. 기준선은 `perRunStatistic`, 표본 수, 부하 범위와 함께
  예산 파일에 남긴다.
- **여유 배수와 이유**(파일의 `headroom.reason`):
  - 수백 ms 이상 시간 2배: 부하가 많은 공유 기계. 경로가 두 배로 느려지는 회귀는 잡는다.
  - 수 ms 시간 5배: GC 한 번, 스케줄 지연 한 번과 같은 크기다.
  - 메모리 1.5배.
  - 직렬화 크기 1.1배: 고정 합성 track이라 결정적이다.
  - heap ceiling 사다리 2배: 사다리가 이산적이다(16/24/32/48/64/96…).
- **잡음 대책**:
  - 모든 표본에 그 순간의 `os.loadavg()[0]`을 붙인다.
  - p95 지표는 run당 **20표본 이상**(`minimumSamples`)을 요구한다. 20이 nearest-rank p95가 최댓값이 아닌
    가장 작은 n이라, 이상치 하나가 p95 예산을 혼자 결정하지 못한다. `parseBudgetFile`이 p95 지표의
    `minimumSamples < 20`을 거부한다(변이 M8).
  - **p95 기준선은 run 2개에 기대고 있다.** 기준선 1은 n=7이었다. 20 미만이라 p95 기준선에서 뺐다(기록에는
    남아 있다). max 지표(메모리·크기·heap 사다리)는 run 3개를 모두 쓴다.
  - `worker.concurrentAtBoundMs`는 부하에 특히 민감하다. 기준선 run 간 p95가 1,293 ms와 608 ms로 두 배
    넘게 달랐다. 예산 2,600 ms는 최악 run의 2배다.
  - **허용 부하 규칙(4차에서 추가, 판정 run 3이 실패한 뒤 정했다. §10·§11).**
    - 판정 run에서 **시간** 예산을 넘었고, 그 지표의 표본 중 하나라도 해당 지표 기준선의 최고 부하
      (`baseline.loadAverage1m.max`)보다 높은 부하에서 쟀다면 그 지표는 `inconclusive`다. `failed`도
      `passed`도 아니다.
    - `inconclusive`인 run은 허용 부하에서 다시 돌려야 한다.
    - 지표별 허용 최고 부하: api 시간 22.53, worker parse 23.21, worker 동시 26.93, 엔진 route 30.06,
      in-process parse 35.15, 브라우저 next 50.64, 브라우저 vite 48.29.
    - 부하는 실패만 보류시킨다. 예산 안의 값은 부하와 상관없이 passed다. 메모리·크기 지표는 CPU 경합에 따라
      움직이지 않으므로 부하로 보류하지 않는다.
    - 평가기가 이 규칙을 강제한다(`evaluateBudget`의 `inconclusive`). 단위 시험과 변이 R4M1–R4M4가 있다.
    - 1차·2차 판에는 이런 규칙이 없었다. 그 판들은 "표본에 부하를 붙인다"는 것만 말했다.
  - 예산은 **정상 suite 밖**의 별도 단계에서만 판정한다(`pnpm test`·`pnpm test:identity`에는 없다).
    - 서버: `node --import tsx scripts/probe-performance-budget.mts --execute`
    - 브라우저: `npx playwright test --config playwright.performance.config.ts`(harness lock 아래).
      `package.json`에 script는 추가하지 않았다(공유 manifest). 위 명령이 실제 명령이다.
    - **로그 위치(M2-01al).** probe 로그와 결과를 `test-results/`·`playwright-report/`·`coverage/` 아래에 두지
      않는다. Playwright가 시작할 때 `test-results/`를 비우고, coverage 실행이 `coverage/`를 비운다(M2-01ai·
      M2-01aj 로그가 이렇게 지워졌다). 서버 probe는 콘솔 출력을 `verification-logs/performance-budget/<시작 시각>.log`
      (git·Prettier 제외)에 함께 쓰고, `--out`·`--log`가 그 세 디렉터리 아래면 측정 전에 거부한다. 브라우저
      spec의 `PERF_OUT`도 같다. 셸로 돌린 출력도 `verification-logs/`로 보낸다.
  - **자동 재실행 한 번(M2-01al).** 판정 run의 첫 시도가 **시간** 예산만 `failed`·`inconclusive`이고 check와
    메모리·크기 예산이 모두 통과했으면, probe가 30초 뒤 모든 phase를 새 프로세스에서 한 번 더 잰다. 두 시도가
    결과 파일에 남고, 두 번째 run의 `attempt`가 첫 시도와 그 미통과 지표를 밝힌다. 한 쌍은 재실행이 **혼자서**
    전부 통과할 때만 통과다. 1분 load average가 짧은 경합 급증을 늦게 반영해 허용 부하 규칙이 그런 급증을
    가리지 못하기 때문이다(근거와 시험: [M2-01al.md](M2-01al.md)). 허용 부하 규칙 자체는 바뀌지 않았다.
    - 비용: 예산은 최악 기준선 통계의 2배라서, 예산에 딱 닿는 회귀는 한 시도에서 대략 절반 확률로 통과한다.
      재실행이 있으면 쌍으로는 약 75 %다. 예산을 뚜렷이 넘는 회귀는 두 시도 모두에서 실패한다. 예산의 몇 % 안쪽에
      걸친 회귀만 두 번 기회를 받는다.
    - 출력 경로 검사는 대소문자를 가리지 않고, 심볼릭 링크를 도착지까지 따라가서 판정한다(M2-01al 검토 N3).
  - 부하를 인위로 만들지 않았다. 엔진 "부하"는 제품 요청이다. 두 tenant가 각자 동시성 한도(2)에서 보내고,
    횟수는 tenant rate window(20/분)가 허용하는 만큼(9라운드)이다.
- **데스크톱과 실기기를 분리한다.** 실기기 지표 4개는 `realDevice`에 `not_executed`, `budget: null`로 둔다.
  평가기는 그 id로 들어온 표본을 **예외로 거부**한다. 데스크톱이나 Simulator 값은 대신 쓸 수 없다.
- **예산이 제품 한도 안에 있는지 probe가 확인한다.** 이 단언은 probe의 `boundChecks`에 있다.
  - heap 예산 96 MiB ≤ 제품 ceiling 256 MiB
  - worker parse 예산 980 ms < parser deadline 5 s
  - route 예산 200 ms < routing deadline 8 s
  - normalized 예산 < 출력 한도 8 MiB

### 4.1 변이 실행 사고와 처리

- 원인: M2d 사다리 확인 실행이 세션 watchdog으로 중단됐다. 그래서 `parse-worker.ts`가 변이된 채 남았다.
- 처리: 복구 뒤 HEAD 내용과 `cmp`로 같음을 확인했다.
- 오염된 run 버림: 그 사이에 돈 서버 기준선 3은 변이된 tree에서 측정됐고 exit 143으로 끝났다. 결과 파일에
  기록되지 않았으며 버렸다.
- 재측정: 깨끗한 tree에서 기준선 3을 다시 돌렸다.
- **1차 판에서 적은 `TREE_MUTATED` 가드는 저장소 밖에 있었다.** 세션 scratchpad의 wrapper 셸 스크립트였다.
  그 wrapper는 tracked 파일 중 `packages`·`apps` 아래만 HEAD와 비교했다. untracked 파일과 `scripts/`는
  보지 않았고, 저장소에 들어가지도 않았다. 1차 판의 문장은 그 한계를 말하지 않았다.
- **2차 판에서 실제 가드를 probe와 spec 안으로 옮겼다.** `assertMeasurableSourceTree`
  (`scripts/performance-budget.ts`)는 측정 전에
  `git status --porcelain=v1 -z --untracked-files=all -- <검사 대상>`으로 변경을 모은다. `-z`라서 공백이나
  비ASCII 문자가 있는 경로도 따옴표 없이 읽고, rename은 양쪽 경로를 모두 센다(3차).
  - 검사 대상(4차에서 넓혔다, N-e): `packages/`, `apps/`, `scripts/`, `tests/`, 그리고 루트의
    `playwright*.config.ts`, `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `turbo.json`,
    `tsconfig*.json`.
    - 3차 판까지는 앞의 세 디렉터리만 봤다. 그래서 `tests/performance/*.spec.ts`,
      `tests/identity/map-evidence.ts`, Playwright config, workspace 파일의 변경이 가드와 hash 밖에 있었다.
    - 새로 넣은 것은 모두 **제품 코드가 아니다**. 변경이 있으면 이유가 필요하고 hash에 들어가지만, 이름으로
      허용할 필요는 없다.

  - **제품 코드**의 변경은 `--allow-product=<경로,…>`(`PERF_ALLOW_PRODUCT`)에 **그 파일이 이름으로** 있어야만
    허용한다. 다른 제품 파일에 남은 mutant는 run을 멈춘다.

    migration, 설정, public asset이 모두 들어간다. 시험과 fixture만 뺀다: `test`·`tests`·`__tests__`·`fixtures`
    디렉터리, `*.test.*`·`*.spec.*` 파일.
  - **probe 입력을 만드는 fixture도 시험 경로다(N-f).** 합성 FIT 바이트는
    `packages/track-parsing/tests/fit-fixture.ts`가 만든다(`scripts/fixtures/long-track.ts`가 부름).
    - 시험 경로라서 변경은 이유만 있으면 허용된다.
    - 대신 hash에 들어가고, probe의 표본·정점 check가 결과를 지킨다: 20,000 sample, map_path 20,000 정점,
      worker 결과 sample 수.
  - 2차 판은 제품 코드를 `packages|apps/<name>/src/`로만 잡았다. 그래서 `apps/web/app/**`와
    `packages/server/persistence/migrations/*.sql`의 변경이 통과했다. 2차 검토 R2-B1이 이를 재현했고, 3차에서
    정의를 넓혔다.
  - **가드는 소스만 본다. 빌드 산출물(`.next`, Vite `dist`)은 보지 않는다.** 브라우저 단계 전에는 shell을 다시
    빌드해야 한다(`pnpm build`). 이 노드의 브라우저 판정 run들은 그 직전 `pnpm build`의 산출물로 쟀다.
  - 결과에는 `sourceTree`(HEAD, 변경 경로, 변경 전체의 SHA-256, 이유, 허용 경로)를 기록한다.

## 5. 발견

- **F1(열림, 제품 위험).** worker `resourceLimits`가 OOM을 항상 worker 안에 가두지는 못한다.
  - 재현: M2d 변이(parse-worker가 track 복사본 8개를 보유)를 48 MiB ceiling에서 돌렸다. 한 프로세스에 rung
    하나씩 11번 실행해 1번은 `TRACK_PARSE_MEMORY_EXCEEDED`로 정상 종료했다. 다른 1번과 M2b·M2d probe에서는
    V8이 `FATAL ERROR: Reached heap limit`로 **부모 프로세스를 abort**했다(exit 134/−6).
  - 근본 원인(검토에서 정정): 실패한 할당은 native `node::worker` structured clone 역직렬화
    (`ValueDeserializer`) 안에 있다. 1차 판은 crypto 콜백(`CryptoJob<HashTraits>`)을 원인처럼 적었는데,
    그것은 그 microtask를 깨운 호출자일 뿐이다. Node는 heap 한도 근처에서 worker를 끝낼 유예를 주지만, 끼어들
    수 없는 native 할당이 그 유예를 다 쓰면 V8이 프로세스 전체를 abort한다.
  - 변이하지 않은 제품에서는 사다리 rung(16/24/32)이 이 노드의 판정 run, 기준선 3회, 6×2회에서 모두 정상
    코드로 끝났다.
  - 과장된 주석을 고쳤다(`parse-worker.ts` 헤더, `parse-host.ts`의 resourceLimits 설명). 이제 "normally ends
    the worker"라고 쓰고, 보장되지 않음과 이 발견을 가리킨다.
  - 제품 수정은 이 노드 범위 밖이다. root가 follow-up 노드를 연다(child-process parser 또는 supervisor).
- **F3(관찰, 검토에서).** heap-ceiling 문턱은 결정적이지 않다. 검토자의 재실행에서 32 MiB가 3회 중 1회
  성공했다(이 노드의 run에서는 32가 매번 실패, 48이 성공). `worker.minimumHeapCeilingMiB`는 사다리 한 칸
  단위로 흔들릴 수 있다. 예산 96 MiB는 그 흔들림보다 두 칸 이상 위에 있다.
- **F2(관찰).** MapLibre lazy 경계가 세 겹이다. 한 겹만 되돌리는 변이(M4)는 살아남는다. 이것은 결함이
  아니다. 단언이 지키는 것은 "경로 탭 전에는 MapLibre 코드와 worker가 없다"는 결과다.

## 10. 3차 — 2차 검토 반영(R2-B1, N-a–N-d)

2차 검토는 1차 지적이 모두 FIXED라고 판정했다. N4는 선택 사항으로 수용됐다. 검토자는 `diffSha256`
`a0e749df…`를 독립적으로 다시 계산해 일치를 확인했다. 차단 지적은 한 건이었다.

**R2-B1 · `src/` 밖의 제품 코드가 검사를 우회했다.**

- 원인: 제품 코드를 `(packages|apps)/<name>/src/`로만 판정했다.
- 검토자는 `--allow-dirty`와 허용 경로 두 개로 다음 두 변이를 통과시켰다.
  - `apps/web/app/activities/activities-page.tsx`의 한 줄 변이
  - `migrations/001_foundation.sql`의 한 줄 변이
- 수정: `isProductPath`는 `packages/`·`apps/` 아래 전부를 제품 코드로 본다. 시험과 fixture만 뺀다(§4.1).
- 시험: 임시 git 저장소에서 `src/`, Next `app/` route, SQL migration 세 경우를 확인한다. 각각 이유만 주면
  `SOURCE_TREE_MUTATED`로 거부되고, 다른 파일을 허용해도 거부되며, 그 파일을 정확히 이름으로 줄 때만
  허용된다. 이름으로 허용해도 두 내용은 서로 다른 hash가 된다.
- 실제 tree 재현: 검토자와 같은 두 변이를 판정 run과 똑같은 플래그로 실행했다. 둘 다
  `SOURCE_TREE_MUTATED: product code differs from HEAD: <그 경로>`로 거부됐고, 결과 파일은 만들어지지 않았다.
  `cmp`로 복원을 확인했다.

**N-a · untracked 내용 hash.** untracked 파일의 내용만 바꿔도 hash가 달라지는지 확인하는 시험을 더했다.
검토자의 변이(`'??'` 필터 → 빈 목록)와 같은 R3M2가 이제 실패한다.

**N-b · 경로 해석.** `git status --porcelain=v1 -z`로 바꾸고 `parseStatusZ`로 읽는다.

- rename은 양쪽 경로를 모두 센다.
- 시험은 다음 경로를 정확한 이름으로 확인한다.
  - `scripts/새 파일.mts`(untracked)
