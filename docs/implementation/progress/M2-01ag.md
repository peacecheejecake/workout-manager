## 1. 설계 근거

- **(a) 주소로 연 코스를 목록 안에서 보이게 한다.** `course-workbench.tsx`의 선택된 `li`에 ref를 달고, 선택이
  바뀌거나(주소·클릭·가져오기), 목록에 처음 나타나거나, 목록을 펼치거나, layout이 바뀔 때
  `scrollIntoView({ block: 'nearest' })`를 부른다.
  - **focus는 옮기지 않는다.** scroll 위치만 바뀐다(변이 G2가 이를 지킨다).
  - **list pane이 스스로 scroll container일 때만** 부른다(`scrollsInside`: `overflow-y`가 auto/scroll이고
    내용이 넘칠 때). `scrollIntoView`는 모든 조상을 scroll하므로, 목록이 내용만큼 자라는 desktop에서 부르면
    목록 대신 페이지가 움직인다. mobile에서는 코스를 열면 목록이 `display:none`이라 해당 없음.
  - 카드 정보와 선호(즐겨찾기 우선 정렬)가 **처음** 도착할 때 한 번 더 부른다. 둘 다 위쪽 행의 높이·순서를 바꾸기
    때문이다. `isPending` 전이만 의존하므로 나중의 refetch는 사용자가 스크롤한 pane을 되돌리지 않는다.
  - 순서 전환(이름/최근)으로는 다시 부르지 않는다. 범위는 "선택될 때"다.
- **(b) 접기·순서 전환 줄을 sticky로.** 두 버튼을 `div.listControls`(`data-list-controls`)로 묶고, tablet에서만
  `position: sticky; top: 0; z-index: 1`, 불투명 `var(--canvas)` 배경. desktop/mobile에는 sticky를 두지 않는다
  (그곳의 pane은 scroll하지 않아, sticky가 viewport에 붙게 된다).
- **sticky 줄이 focus된 항목을 가리지 않게**(WCAG 2.4.11): tablet list pane에 `scroll-padding-top`을 둔다.
  값은 workbench가 `ResizeObserver`로 잰 제어 줄 높이(`--course-list-controls-size`, 좁은 container에서 버튼이
  두 줄로 감길 수 있으므로)이고, fallback은 한 줄 높이(44px + 8px). 이 padding은 (a)의 reveal과 키보드 Tab에 따른
  브라우저 focus scroll 둘 다에 적용된다.
  - 실제로 padding이 필요한 경우는 **위쪽으로의** reveal이다. `nearest`는 행의 top을 pane의 top에 맞추므로 padding이
    없으면 sticky 줄 아래에 놓인다. 아래쪽 reveal은 행의 bottom을 맞추므로 영향이 없다. Chromium은 focus로 스크롤할
    때 요소를 **가운데**에 두므로, Chromium의 Tab 이동에서는 padding 없이도 가려지지 않는다(G5 1차 실행에서 확인).
- 변경은 list pane과 그 CSS에 한정했다.

## 7. 독립 검토 r1 반영(m2-01ag-review-r1: APPROVE, 비차단)

### 7.1 고친 것

- **지적 1 · reveal이 창을 스크롤할 수 있다.** `scrollIntoView`는 스크롤 가능한 조상을 모두 스크롤한다. 그래서 pane이
  화면에 다 들어오지 않는 짧은 tablet viewport(가로 휴대폰)나, 페이지를 내려 둔 채 layout이 바뀔 때 창이 움직였다.
  - `revealInPane(pane, row)`로 바꿨다. pane의 `scrollTop`만 직접 정한다.
  - 규칙은 `nearest`와 같다. band는 pane의 client 영역에서 계산된 `scroll-padding-top/bottom`을 뺀 구간이다.
    행이 band 위에 있으면 top을, 아래에 있으면 bottom을 맞춘다. 행이 band보다 크면 top을 맞춘다.
  - 이전의 `scrollsInside` 가드(overflow 검사)는 없앴다. pane이 스스로 스크롤하지 않으면 모든 행이 band 안에 있어
    아무것도 움직이지 않는다. 그래서 가드는 동치 코드였고, 그것을 지우는 G3은 동치 변이가 된다. G3은 폐기하고,
    지적 1을 직접 되돌리는 **G6**(`scrollIntoView` 복원)을 새로 두었다.
- **지적 2 · 초점 고리가 sticky 줄 아래에 잘린다.** `scroll-padding-top`을 `calc(측정한 제어 줄 높이 + 6px)`로 바꾸고
  `scroll-padding-bottom: 6px`을 더했다. 6px은 foundation 초점 고리(2px outline, 3px offset)에 1px 여유를 둔 값이다.
  - E2E: 위쪽 reveal 뒤 가져온 코스의 top ≥ 제어 줄 bottom + 5(±1)를 단언한다.
- **지적 3 · 카드 정보가 늦게 오는 경우의 절충.** reveal은 선택·목록 등장·펼침·layout 변경과, 카드 정보·선호가
  **처음** 도착할 때만 다시 돈다. 그 뒤의 refetch나 썸네일 교체로 위쪽 행 높이가 바뀌면 열린 코스가 band에서 조금
  벗어날 수 있다. 사용자가 이미 스크롤한 pane을 되돌리지 않는 쪽을 택했다(Chromium은 스크롤 앵커링으로 대부분
  보정한다).
- **지적 4 · spec이 남기는 코스.** 위쪽 reveal에 쓴 "0000 위로 …" 코스는 반복마다 API(`DELETE …?expectedRevision=1`,
  200 단언)로 지운다. "힣 …" 코스는 관례대로 남긴다.
- **지적 5·6 · 단위 테스트.** `packages/modules/courses/tests/course-list-reveal.test.tsx`(jsdom, 4개).
  - 상자는 stub한다: pane은 200px band, 행 i의 top은 `60 + 100·i`. `scrollTop`은 한계로 clamp하는 저장소로,
    `scrollIntoView`는 "페이지가 움직였다" spy로 stub한다.
  - ① 주소로 연 코스까지 pane이 스크롤된다: bottom 정렬, focus는 `body`, 페이지 이동 spy는 호출되지 않는다.
  - ② 내용만큼 자라는 pane은 그대로 둔다.
  - ③ 접었다 펴면 다시 보인다.
  - ④ layout이 desktop → tablet으로 바뀌면 다시 보인다.
- **E2E 보강**(`course-list-scroll.spec.ts`): "페이지를 움직이지 않는다"를 **별도 test**로 떼어 냈다. 앞 test의
  단언이 먼저 실패해도 이 검사들이 실행되도록 하기 위해서다. 세 검사는 `expect.soft`라서 회귀가 깨뜨린 경우를
  모두 보고한다.
  - desktop 1280: 열린 코스가 페이지 좌표로 900 아래에 있다(전제). `scrollY === 0`.
  - **844×320**(가로 휴대폰, 브라우저 막대가 보이는 상태): pane이 첫 화면을 넘어간다(전제, 페이지 좌표 bottom > 320).
    pane은 스크롤되고 `scrollY === 0`이다.
    - 처음 쓴 900×400은 pane 전체가 첫 화면에 들어와(열린 코스 bottom 371.8) 전제가 실패했다. 그래서 바꿨다.
  - **layout 변경**: 1280×600 desktop에서 코스를 열고 페이지 끝까지 내린 뒤 1024×600(tablet)으로 줄인다. pane은
    다시 reveal되고, `scrollY > 0`이며, pane bottom ≤ 0(여전히 화면 위)이다.
- 지적 7(선택)은 하지 않았다.
