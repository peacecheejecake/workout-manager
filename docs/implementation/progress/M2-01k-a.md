## 1. 설계 근거

사양 01 §9: "S13 코스 카드에 지도 썸네일, 실제/추정 거리, 고도 데이터 출처, 노면 정보의 확인 상태, 접근성 메모,
마지막 사용을 표시한다." 매트릭스 행의 공백은 모두 같은 모양이었다. 사실은 상세에만 있었고 **목록 카드**에는
없었으며, 카드 단위로 단언한 시험이 없었다.

- **새 읽기 `GET /bff/v1/courses/cards`, 기존 목록은 그대로.** `courseListSchema`와 `courseHeadSchema`는
  `strictObject`다. 목록 응답에 필드를 더하면 옛 형태로 parse하는 소비자가 모르는 필드를 거절하므로 가산적
  변경이 아니다. 그래서 목록 옆에 카드 읽기를 새로 두었다. 계약은 새 subpath `@workout/contracts/course-cards`다.
  `courses.ts`는 `geo-data.ts`에 import되므로(순환 방지) 고도 dataset identity를 쓰는 카드 계약은 별도 파일이다.
  migration은 없다. 이미 서버에 있는 데이터만 쓴다.
- **서버가 이미 가진 것만 쓴다.** 카드 하나는 그 코스의 head 읽기(`CourseRepository.read`) 하나에서 파생된다.
  head 선과 생성 조건(`generation`), M2-01l이 revision마다 두는 저장 썸네일 상태, M2-01j가 시작할 때 읽는
  자체 고도 dataset(`ElevationIndex.profile`)이다. 상세가 말하지 않는 것은 카드도 말하지 못한다. repository
  interface에 method를 더하지 않았다(API 시험의 기존 repository fake들을 건드리지 않으려고). 목록과 읽기 사이에 지워진 코스는
  카드에서 빠진다.
- **실제/추정 구분(`distance.basis`).** `plannedLineMeters`는 저장된 선의 길이이고 그 외의 무엇도 아니다.
  `basis`가 그 선이 무엇인지 말한다. 우리 기록에서 잘라낸 선은 `recorded`로 **실제**라 부르는 유일한 경우다.
  엔진 선(`routed-waypoints`·`target-distance-loop`)은 `engine-estimate`이고 엔진 자신의 추정치를 곁에 둔다.
  파일에서 읽은 선은 `imported-file`이며 **실제도 추정도 아니다**(GPX `trk`의 "기록" 주장은 확인할 수 없다).
  보호 구역 제거본은 원래 선의 성격을 잇지만 엔진 수치는 떨군다(제거 전 선을 설명한 수치이므로 `null`).
  제거본의 제거본은 원래 종류를 기록하지 않으므로 `unknown`이다.
- **고도 출처.** dataset이 없으면 `not_deployed` → 카드 "없음"이다(빈 profile이나 0이 아니다). 있으면
  `sampled`(attribution·dataset id·표본 n곳 중 값 있는 k곳) 또는 `outside_region`이다.
- **노면.** 이 build에는 노면 출처가 없다. 계약은 `confirmation: z.literal('unknown')`이다(후보 평가의
  `courseCandidateKnowledgeSchema`와 같은 규칙). 다른 값을 쓰는 것은 값이 아니라 계약 변경이다. 카드
  "확인되지 않음 · 통행 가능 여부·안전을 뜻하지 않음".
- **썸네일.** 저장 썸네일 상태 + 그 그림을 그리는 균등 표본(`sampleCourseThumbnailVertices`, 최대 400점=renderer
  예산)을 보낸다. `ready`면 카드가 기존 `StoredCourseThumbnail`(owner 인증 fetch, object URL 수명 규칙 그대로)을,
  아니면 같은 투영의 `CourseThumbnail`을 그린다. 전체 선(최대 20,000점)은 목록에 싣지 않는다. 표본은 owner에게만
  가며(인증·tenant 소유), 같은 owner가 상세에서 이미 받는 전체 선의 부분집합이다.
- **마지막 사용·접근성 메모는 다시 싣지 않는다.** 둘 다 owner의 preference·note 읽기가 원본이다. 카드는
  preference 읽기를 쓰되 **읽기 실패를 "사용 기록 없음"으로 말하지 않게** 고쳤다(이전 코드는 실패·로딩 중에도
  "사용 기록 없음"이었다). 로딩 "마지막 사용 확인 중", 실패 "마지막 사용 확인하지 못함".
- **모름은 모름으로.** 카드 읽기가 로딩·실패·누락이면 각 사실이 "확인 중"/"불러오지 못함"/"확인되지 않음"이다.
  숫자나 0을 보이지 않는다. 카드는 `role="alert"`를 내지 않는다(화면의 alert는 화면의 것이다).
- **다른 노드와 겹침 최소화.** M2-01k-i(경유점 목록·draft·`courses.module.css`)와 M2-01ag(목록 pane)를 피해
  카드 표시는 새 파일 `course-list-card.tsx`와 새 CSS `course-list-card.module.css`에 두었다. 공유 파일 변경은
  작고 가산적이다. `course-workbench.tsx`는 카드 query 하나와 목록 `li` 안의 컴포넌트 하나(마지막 사용 문구를
  `span`에서 카드로 옮김), `course-thumbnail.tsx`는 선택 prop `testId`(기본값 그대로) 하나,
  `course-extras-api.ts`는 `cards()` 하나다. `courses.module.css`는 건드리지 않았다.
- **`testId`가 필요한 이유.** 상세의 썸네일은 `data-testid="course-thumbnail"`이고 기존 E2E가
  `workbench.getByTestId('course-thumbnail')`로 찾는다. 카드가 같은 id를 쓰면 strict mode에서 여러 개가 잡힌다.
  카드는 `course-card-thumbnail`을 쓴다.

### 2.1 E2E `tests/identity/course-list-cards.spec.ts` (두 shell)

실제 OIDC session, API, PostgreSQL, 객체 저장소, 썸네일 worker, harness의 routing port(기본 결정적 fixture).

1. **카드별 다섯 항목**(Next·Vite 각각). 종류가 다른 코스 셋을 만든다. 저장된 FIT 기록에서 자른 코스(실제),
   `route-previews`→저장한 엔진 코스(추정), GPX 가져오기(둘 다 아님). `/courses`의 **목록 `li` 하나하나**에서:
   - 썸네일: 보이고, `drawn`이면 `path d`가 API가 준 head 선의 `courseThumbnailPath`와 같다. worker가 세 그림을
     만든 뒤(`thumbnail.status === 'ready'` poll) 다시 열면 세 카드 모두 `data-source="stored"`.
   - 거리: 기록 카드 `계획 거리 <API distanceMeters> · 실제 기록 구간의 거리(지도 단순화 선 기준)`(`data-basis=recorded`), 엔진 카드
     `계획 거리 … · 추정 거리(경로 엔진 <API engineDistanceMeters>)`이고 "실제"가 없다, 파일 카드 `… · 가져온 파일의
선, 실제/추정 확인되지 않음`. 모두 글자 전체 일치.
   - 고도 출처: 같은 코스의 `/elevation` 응답과 카드가 같다. `no_dataset`이면 `data-status=not_deployed`이고
     "없음"으로 시작, `profile`이면 attribution·dataset id·"표본 n곳 중 k곳 값 있음"이고 "없음"으로 시작하지 않음.
   - 노면: `data-confirmation=unknown`, "확인되지 않음"으로 시작.
   - 마지막 사용: 연 적 없는 코스 "사용 기록 없음". 파일 코스를 목록에서 열면(서버가 사용 시각 기록) 다시 연
     목록의 카드가 `마지막 사용 <서버 lastUsedAt을 브라우저 ko-KR로>`, 열지 않은 코스는 계속 "사용 기록 없음".
2. **배포된 고도 dataset은 카드에 이름이 나오고 "없음"이 아니다**(두 shell). 이 기계의 `.geo-build/geo-data/
elevation.json`에서 dataset identity와 영역 안의 점 하나를 읽어, 첫 정점이 그 점에 놓인 코스를 가져온다. 카드는
   `data-status=sampled`, "없음"으로 시작하지 않음, 파일의 dataset id·attribution, "표본 2곳 중 1–2곳 값 있음".
   **dataset이 이 기계에 없으면 skip으로 보고한다(CI).** 통과로 세지 않는다. dataset이 있는데 카드가 "없음"이면
   실패한다. 즉 "배포되지 않음"을 성공으로 받는 시험이 아니다.

- **노면 데이터 출처 없음.** 카드는 "확인되지 않음"을 정직하게 보이지만, 노면 사실을 가진 출처(OSM `surface` 태그

  그 사실을 말할 뿐 누락을 채우지 않는다. dataset 시험은 dataset이 없는 CI에서는 skip이다.
- **비용.** 카드 읽기는 코스마다 head 읽기(전체 선 포함)를 한다. 검토자 측정: 최악(200코스 × 20,000점)에서
  `GET /courses/cards` 한 번에 **약 3.85초 CPU**. 동시 4개로 묶었고 한 읽기가 실패하면 나머지는 멈추며(N3), 화면은
  카드를 60초 동안 새로 읽지 않고 focus에도 다시 읽지 않는다(N2). 그래도 요청 하나의 CPU는 그대로다.
- **후속(root가 task-graph 노드 추가 예정):** persistence 쪽 카드 요약 읽기(한 transaction, 표본·길이·생성 조건만),
  또는 `revisionId`를 key로 하는 카드 LRU(revision은 불변이므로 thumbnail 상태만 따로 읽으면 된다).

**main에서 들어온 `map-lifecycle.spec.ts`(M2-01k-d)와의 상호작용.** 그 시험은 코스 목록이 보인 뒤 mark를 찍고, 코스를
열고 닫은 뒤 mark 이후 만들어져 아직 살아 있는 것(blob URL 등)이 없어야 한다고 본다. 목록 카드의 저장 썸네일은
목록이 화면에 있는 동안 blob URL을 **정당하게** 쥔다(목록은 코스보다 오래 산다). 코스를 열면 상세가 `ready`를 알고
N2 로직이 카드를 다시 읽어 저장 그림을 받아 오므로, 그 blob URL이 mark **뒤**에 생겨 남은 것으로 세어졌다. 제품의
수명 규칙(`StoredCourseThumbnail`: 효과 정리에서 revoke)은 그대로 맞다. 시험을 고쳤다. 그 코스의 썸네일이
`ready`가 될 때까지 기다리고, 목록 카드가 준비되고 `ready`인 카드가 모두 저장 그림을 보일 때(카드 그림 상자에 새
`data-thumbnail-state` 속성) mark를 찍는다. 그러면 mark 뒤에 세는 것은 코스를 연 일이 만든 것뿐이다. 이 파일은
M2-01k-d 소유이므로 root가 병합 때 확인해야 한다.
