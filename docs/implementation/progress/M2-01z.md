# M2-01z · tenant prefix purge 운영 가시성

상태: **완료.** 구현 기준 HEAD `3ee5ca0`, 병합 때 `abea557`(M2-01aa) 위로 rebase했다. 독립 검토 승인(차단 0), 검토 지적(스트레스 시험 주석, runbook 세 문장, 1.4초 수치의 조건)은 병합 때 반영했다. 범위는
`task-graph.json`의 `M2-01z` scope(M2-01x 독립 검토의 비차단 지적 세 가지). 구현은 root 소유인
`task-graph.json`·`m2-01k-requirement-matrix.json`을 건드리지 않았다. 같은 시기 M2-01y가 다른 worktree에서
migration 045를 더할 수 있다 — 이 노드의 upgrade 시험은 migration을 **파일 이름**으로 찾으므로 병합 때 번호가
밀려도 시험은 바뀌지 않는다(`migrate.ts` 목록 순서와 `foundation` 시험의 version 줄만 조정).

## 0. 결론

세 지적 모두 **실제 PostgreSQL에서 재현했고 닫았다.** 과잉 삭제 방지 가드는 한 글자도 약화하지 않았다
(lease 후보 질의는 044와 동일, 삭제 경로 `processOneTenantObjectPurge`는 무변경).

| 지적                                                          | 결정                                                                                                                                                                                     |
| ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| (1) 계정이 남아 lease가 거절한 행이 조용히 남음               | lease가 그 행에 **`INCONSISTENT_LEDGER:IDENTITY_ACCOUNT_PRESENT`를 한 번 기록**. lease·attempt 차감·삭제 없음                                                                            |
| (2) lease를 잃은 실행이 100회에 `last_error_code NULL`로 끝남 | 인계 시 `LEASE_EXPIRED` 기록, 100번째 시도가 lease를 잃으면 다음 lease 호출이 **`DEAD_LETTER:LEASE_EXPIRED`** 로 격리. **CHECK**가 "attempts=100·무lease·무표식" 상태를 표 수준에서 금지 |
| (3) worker 호출당 purge 1회                                   | **호출당 최대 10 run**(각 run은 자기 lease·삭제 예산 200·첫 오류 중단 그대로), 실패·lease 유실·빈 queue에서 batch 중단. 한계를 수치로 runbook에 문서화                                   |

## 1. 재현(수정 전 동작, 044)

- (1) `tenant-object-purge.integration.test.ts > does not lease a tenant that still has an identity account`의
  기존 단언이 곧 재현이다: drain 뒤 행 `{passes:0, attempts:0}`, `last_error_code NULL`, lease 없음 — 운영자가 볼 수
  있는 흔적 0. 새 단언(표식)은 044에서 실패한다(mutation Z1).
- (2) 044의 `finish`는 `lease_until>now`를 요구하므로 lease를 넘긴 run은 아무것도 기록하지 못하고, 다음 lease가
  attempts만 올린다. 새 시험 `dead-letters a purge whose 100th attempt lost its lease…`가 실제 worker 경로
  (`processOneTenantObjectPurge` + listing 도중 DB 시계로 lease 만료)로 99·100번째 시도를 잃게 한다. 045 없이
  (mutation Z5) 행은 `attempts 100, lease_owner 남음, last_error_code 'LEASE_EXPIRED'`(인계 표식만)로 영원히
  남는다 — 인계 표식도 끄면(Z8) 원래 지적대로 `NULL`.
- (3) 044에서 worker는 호출당 `processOneTenantObjectPurge` 1회. 말소 tenant 하나는 30일 × 24 = **720 pass**가
  필요하므로 처리 가능한 30일 창 안의 tenant 수 = scheduler 호출/시간(분당 1회면 60명).

## 2. 설계 판단

### 2-1. 어디로 드러내는가 — 행의 오류 코드, 기존 선례 그대로

- `/bff/v1/operations/status`는 **인증된 tenant 자신의** 상태(outbox·Garmin·audit)만 돌려준다. purge 행은 이미
  말소된 tenant의 것이라 그 endpoint의 주인이 없다. 운영자 전역 상태 endpoint는 이 저장소에 없고, 새로 만들지 않았다.
- 선례는 둘이다: queue(028)의 "`attempts=100`·`completed_at NULL`·`last_error_code=DEAD_LETTER:*`인 운영 개입
  상태"(runbook M2-04b 절)와 040의 "operator finds both kinds of stuck work with one query"(`DEAD_LETTER:` 접두사).
  같은 채널을 썼다: 행의 `last_error_code` + 접두사, runbook에 한 질의.
- 새 접두사 `INCONSISTENT_LEDGER:`는 **재시도로 풀리지 않는** 상태를 `DEAD_LETTER:`(재시도 소진)와 구별하려고
  두었다. 거절은 시도가 아니므로 attempts를 차감하지 않는다(차감하면 100회 뒤 계정이 여전히 있는 행이
  dead-letter로 위장된다).
- **새 함수·새 grant 없음.** 표식은 전부 `lease_tenant_object_purge` 안에서 쓴다(`CREATE OR REPLACE`, 시그니처·
  반환형 동일). 그래서 worker의 기존 EXECUTE가 그대로 남고 **045는 grant helper 재실행 없이 배포된다**(upgrade
  시험이 확인). worker 결과 JSON에 개수를 더하려면 표를 읽을 새 함수와 새 grant가 필요했고, grant 전에 배포되면
  worker run 전체가 `42501`로 멈춘다(M2-01x 배포 주의 2) — 그 위험을 들이지 않았다.

### 2-2. 거절 표식

- 조건은 lease 후보와 같다(열림·attempts<100·due·lease 없음/만료)에 "account 있음"을 더한 것. **한 번만** 쓴다
  (`IS DISTINCT FROM` — 매 run마다 같은 행을 다시 쓰지 않음, 시험이 `xmin` 불변으로 확인).
- 지워지는 때: 계정이 사라져 lease되고 pass가 끝나면 `finish`가 `NULL`로, 또는 말소 재생의 upsert가 re-arm하며
  `NULL`로. 재생 뒤에도 계정이 남아 있으면 다음 lease 호출이 다시 쓴다(스트레스 시험이 그 순서를 단언).

### 2-3. lease 유실

- **인계 표식**: 만료된 lease를 가진 행을 새 run이 lease하면 `last_error_code='LEASE_EXPIRED'`. 직전 시도의
  실제 결말이므로 정확하고, 재시도는 계속된다(정보용).
- **마지막 시도**: `attempts>=100`, lease 있음, `lease_until<=now`인 행을 lease 호출 첫 문장이
  `DEAD_LETTER:LEASE_EXPIRED`로 바꾸고 낡은 lease를 지운다. **아직 살아 있는 100번째 lease는 건드리지 않는다**
  (시험: 그 사이 다른 worker의 lease 호출 뒤에도 `finish`가 성공). 크래시한 worker도 finish를 부르지 않으므로
  finish 쪽이 아니라 lease 쪽에 두었다.
- **CHECK** `tenant_object_purge_dead_letter_labelled`: `attempts<100 OR completed_at IS NOT NULL OR
lease_owner IS NOT NULL OR coalesce(starts_with(last_error_code,'DEAD_LETTER:'),false)`. `coalesce`가 핵심이다 —
  처음 쓴 `last_error_code LIKE 'DEAD_LETTER:%'`는 NULL에서 CHECK가 통과해 **바로 그 NULL 상태를 허용했다**(새
  시험이 잡음, mutation Z10). `LIKE`의 `_` 와일드카드도 피하려고 `starts_with`.
- 남는 과도 상태: 100번째 lease가 만료된 순간부터 다음 worker의 lease 호출까지 행은 "lease 있음·만료"로 보인다.
  worker가 매 실행마다 lease를 부르므로 그 간격은 scheduler 주기다.
- **backfill**: 045 적용 시 이미 "attempts≥100·lease 없음 또는 만료·표식 없음"인 행을 표식(만료 lease면
  `DEAD_LETTER:LEASE_EXPIRED`, 아니면 `DEAD_LETTER:<기존 코드 또는 TENANT_PURGE_FAILED>`)한 뒤 CHECK를 건다.
  아직 살아 있는 100번째 lease는 건드리지 않는다(upgrade 시험, Z12).

### 2-4. 처리량 — batch로 조정하고 한계를 문서화

- `processTenantObjectPurges(repository, storage, runs=10, budget=200)`: `processOneTenantObjectPurge`를 **차례로**
  최대 10회. 계속 조건은 직전 run이 `passed` 또는 `continuing`일 때뿐, `empty`·`retry_scheduled`·`lease_lost`에서
  멈춘다. 그래서 망가진 저장소(루트 swap 등)는 호출당 **실패 run 1회**만 쓴다(044와 같음). 각 run의 예산 200·목록
  100·첫 오류 중단·ENOENT 규칙은 그대로다. `continuing`(예산 소진)은 같은 batch에서 다시 lease될 수 있다.
- 실측(개인 cluster, 로컬 FS, load 12): 빈 tenant 10 run = **16 ms**(run당 ≈1.6 ms), 객체 200개 tenant 10 run
  (삭제 2,000) = **1,389 ms**. 로컬 파일시스템에서 호출 하나가 이후 derived·sweep·housekeeping을 미룬 시간은 약 1.4초였다. 벽시계 상한은 없어서 느린 저장소에서는 run당 2분 lease × 10, 최대 약 20분까지 늘어날 수 있다(독립 검토 지적, runbook에 적음).
- 한계(runbook에 기록): 분당 호출이면 매시간 주기를 지키는 30일 창 안의 말소 tenant ≈ **600명**(하루 ≈20건),
  5분 주기면 ≈120명(044는 각각 60·12). 넘치면 due 행이 `available_at` 순으로 기다릴 뿐 빠지지 않는다 — 주기만
  늘어나고, 30일 종료는 `armed_at` 기준이라 그 경우 pass 수가 줄어든다. 복원 재생은 원장 전체를 한꺼번에 재무장하므로
  그 소진 시간을 이 한도로 계산해야 한다.
- 10을 고른 이유: 위 실측으로 최악 호출 시간이 초 단위에 머물고, 2분 lease보다 훨씬 짧으며, 단일 purge를 더 많이
  돌리는 것보다 scheduler 주기를 줄이는 편이 운영에서 조정하기 쉽다.

## 3. 잠금 순서

- 새 문장 세 개(마지막 시도 dead-letter, 거절 표식, 인계 표식)는 **purge 행만** 잠그고 모두
  `FOR UPDATE SKIP LOCKED`(인계 표식은 기존 후보 CTE의 잠금 안). `identity_private.account`는 잠금 없는 읽기다.
  lease 함수는 purge 행을 잡은 채로 **무엇도 기다리지 않는다** → 말소 순서(77206 → 0 → 행 → purge 행)로 돌아가는
  간선이 없다. batch는 run을 겹치지 않으므로 worker는 한 번에 purge 행 lease 하나만 가진다.
- 스트레스: `tenant-object-purge > adds no lock-order inversion`에 **계정이 남은 불일치 tenant 4명**(말소가 계정을
  못 지우는 순서)을 넣어 거절 표식이 말소·재생 upsert와 겨루게 했고, worker 6개가 batch(`processTenantObjectPurges`)를
  돌린다. `course-thumbnails > adds no new lock-order inversion`의 drain도 batch로 바꿨다. 이 둘과
  `course-preferences`의 교착 시험 2건, `courses > does not deadlock`을 **20회 반복: 100/100 통과,
  `40P01` 0, cluster 로그 `deadlock detected` 0**(load 8→21).
- 비공허성(anchor L2): 거절 표식 뒤에 "purge 행을 잡은 채 due tenant의 advisory `0`을 잡는" 역순을 넣으면 **3회 중 2회
  `40P01`**(cluster 로그 `deadlock detected` 11건). 되돌린 뒤 `shasum -c` 일치.

## 4. mutation(단일 anchor, 적용 → 실행 → 복원 → `cmp` 동일)

각 anchor는 파일 안 정확히 1건(스크립트가 count==1 확인). SQL anchor는 매번 새 DB에서 migrate. 시험 대상:
`tenant-object-purge.integration`, `tenant-object-purge-visibility-upgrade.integration`, worker unit.
모든 복원 뒤 `cmp` 동일, 마지막에 세 파일의 sha256이 mutation 전과 같음.

## 5. migration `045_tenant_object_purge_visibility.sql`과 권한

- backfill UPDATE → CHECK 추가 → 부분 index `tenant_object_purge_final_lease`(100번째 lease를 가진 행만) →
  `CREATE OR REPLACE FUNCTION public.lease_tenant_object_purge(uuid,timestamptz,timestamptz)`(SECURITY DEFINER,
  `search_path=pg_catalog`, `REVOKE … FROM PUBLIC` 재실행). `erase_account`는 rename하지 않았다.
- `migrate.ts`의 `migrationFiles` 끝에 추가. `grantResourceObjectCleanupWorker`는 **무변경**(새 함수 없음) —
  그래서 `course-thumbnail-reconciliation-upgrade`의 worker 표면 열거도 무변경이며 새 목록 그대로 통과한다.
- **격리 DB 업그레이드**(`tenant-object-purge-visibility-upgrade.integration.test.ts`): `migrationFileNames`에서
  `/^\d+_tenant_object_purge_visibility\.sql$/`로 찾는다. 직전까지 migrate한 DB에 044가 허용한 상태 다섯 가지(유실된
  100번째 lease, 무lease·평문 코드 100회, **살아 있는** 100번째 lease, 재시도 중, 계정 있는 불일치 행)를 채우고 worker
  EXECUTE를 손으로 부여(grant helper는 head 스키마를 이름하므로 **전체 `migrate()` 뒤에만** 부른다) → 한 단계:
  이전 checksum 불변, **바뀐 함수 본문은 lease 하나뿐**(`erase_account` 포함 나머지 전부 byte 동일), worker grant
  유지·PUBLIC 없음, definer+`search_path`, backfill 결과 정확. 이어서 worker 역할로 lease 1회 → 살아 있던 lease가
  만료 뒤 dead-letter, 불일치 행 표식, CHECK가 NULL 거절. 마지막에 전체 `migrate()` 뒤 `grantResourceObjectCleanupWorker`
  → 같은 두 함수만, 표 권한 0. `dropIsolatedDatabase`로 정리.
- `foundation.integration.test.ts`: version 45 추가.

### 배포 주의 — 병합 노트에 옮길 것

1. **045는 grant 재실행이 필요 없다**(함수 교체만). 다만 M2-01x의 044 배포 주의(grantOperations +
   grantResourceObjectCleanupWorker 재실행)는 044를 아직 적용하지 않은 환경에 그대로 유효하다.
2. 새 worker build의 결과 JSON 키가 `tenantPurge`(문자열) → **`tenantPurges`(배열)** 로 바뀐다. 이 키를 읽는 로그
   파서·알림이 있으면 함께 바꾼다(저장소 안에는 소비자 없음).
3. 045 적용 직후 CHECK 추가는 표 전체를 한 번 검사한다(행 수 = 누적 말소 tenant 수, 작음).
4. M2-01y가 045를 먼저 쓰면 이 파일을 046으로 옮기고 `migrationFiles`·`foundation` version만 조정한다.

## 6. 남긴 것

- **운영자 알림은 없다.** 표식은 질의로 찾는다(runbook 절). 전역 운영 status endpoint가 생기면 두 접두사 개수를
  거기에 올리는 것이 다음 단계다 — 운영자 인증 경계가 없어 이번에 만들지 않았다.
- **lease 유실 run이 지운 객체 수**는 기록되지 않는다(`finish`가 거절되므로 `objects_purged`에 안 더해짐). 삭제는
  실제로 일어났다(시험이 확인). 통계만 과소 집계된다.
- queue(`resource_object_cleanup`, `resource_derived_cleanup`)도 같은 "lease 유실 → 표식 없이 attempts 소진" 구조다.
  이 노드 범위(tenant purge) 밖이라 건드리지 않았다 — **별도 추적 권고**.
- **`media/tenant-listing` root-swap 시험이 부하(load ~50–75)에서 link를 통한 답 1–2건을 관측**했다(§7). M2-01x
  코드이며 이 노드와 무관하다 — **별도 추적 권고**(M2-01x M1 가드의 잔여 경합인지 시험 분류 문제인지 판정 필요).
- 한 invocation의 batch 상한 10은 상수다. scheduler 주기와 함께 조정하려면 설정 값으로 올려야 한다.
