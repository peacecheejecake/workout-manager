## 2. `oidc.spec.ts:55` — 기제와 보안 판정

계정 화면(`identity-workspace.tsx`)에는 세션에 묶인 읽기가 세 개 있다. 동의(`consents/ai`),
`GarminPanel`의 `integrations/garmin/status`, `OperationsPanel`의 `operations/status`다.
`visibilitychange`가 오면 react-query가 셋을 동시에 다시 읽는다. 쿠키는 이미 Bob의 것이고
`x-workout-session-id`는 Alice의 것이라, 서버(`apps/api/src/app.ts` preValidation)는 셋 모두에
몇 ms 안에 `409 SESSION_CHANGED`를 돌려준다.

브라우저에 **먼저 도착한** 409가 `onSessionChanged`를 부르면 계정 트리가 해체된다. 이때 react-query가
나머지 요청의 signal을 abort한다. Garmin이나 ops의 409가 먼저 오면 동의 요청은 `net::ERR_ABORTED`로
끝난다. 동의 409는 서버가 보냈지만 브라우저에서 읽히지 않는다. 시험은 동의 409만 기다리므로 시험
타임아웃(30초)까지 기다린다.

실패한 실행의 기록(`base-163756`, 서버 기준 시각)은 이렇다.

```
16.923 REQ GET /bff/v1/integrations/garmin/status 409 1ms
16.924 REQ GET /bff/v1/operations/status 409 2ms
16.924 REQ GET /bff/v1/consents/ai 409 3ms
(브라우저) 16.929 requestfailed GET /bff/v1/consents/ai net::ERR_ABORTED
(브라우저) 16.931 response GET /bff/v1/integrations/garmin/status 409
```

**보안 판정: 결함 아님.** 전체 1회와 단독 60회, 합계 61회의 기록에서 Alice 세션으로 나간 동의 읽기는
두 가지로만 끝났다. 서버가 409를 주거나, 응답이 도착하기 전에 abort되었다. 409가 아닌 응답은 한 번도
없었다. 실패 5회는 모두 "409가 브라우저에 안 옴(abort)"이었고 "다른 응답이 옴"은 없었다. 서버 쪽 차단은
세션 id 헤더와 쿠키 principal을 직접 비교한다. 따라서 응답 순서와 무관하다.

제품 동작에 대한 판단: 먼저 온 409 하나로 계정 트리를 해체하고 형제 요청을 끊는 것은 **올바르다.**
끊기는 요청은 모두 버려질 Alice 계정의 것이다. 사용자에게는 "로그인 상태 확인 중" 다음에 Bob 계정이
보일 뿐, 끊긴 요청의 흔적(오류 표시)은 남지 않는다. 고칠 제품 결함은 없다.

**수정(시험만).** `session`과 함께 두 패널 읽기(`garmin/status`, `operations/status`)도 해제 시점까지
붙잡는다. 그러면 전환 뒤 응답할 수 있는 계정 읽기는 동의 하나뿐이고, 시험은 이름대로의 경로를 매번
탄다. 단언도 하나 더했다. 전환 뒤 Alice 세션 헤더로 나간 동의 GET의 응답 상태를 전부 모아 409 외의
값이 없는지 두 번(해제 전, Bob 표시 후) 확인한다. 전환 전에 Alice의 동의가 실제로 캐시에 있도록
`현재 동의:` 표시도 먼저 기다린다. 타임아웃은 바꾸지 않았다.

변이 확인: 서버가 이전 세션 헤더의 동의 GET을 통과시키도록 `app.ts`를 임시로 바꾸면, 수정한 시험이
실패한다(§5).

## 3. 통합 스위트 57P01 (M2-01p 관측)

`pg-pool@3.14.0`의 `Pool.end()`는 idle client마다 `client.end()`를 **호출만 하고** 곧바로 resolve한다
(`_pulseQueue` → `_remove`). backend가 종료 메시지를 읽기 전에 `DROP DATABASE … WITH (FORCE)`가 그
backend를 죽이면 어떻게 되는가. backend는 FATAL 57P01을 보낸다. client는 활성 query가 없으므로 이를
`error` 이벤트로 낸다. 아직 붙어 있는 pool의 idle listener가 이를 `pool.emit('error')`로 다시 낸다.
listener가 없으니 uncaught가 된다. 모든 시험이 통과했는데도 vitest가 exit 1로 끝나는 이유다.

재현(스크래치 PostgreSQL 14): DB 생성 → pool에 client 3개 → `await pool.end()` → 곧바로 FORCE drop.
이 흐름에서 **200회 중 10회 uncaught 57P01**이 났다. drop 전에 `pg_stat_activity`가 그 DB를 더 이상
나열하지 않을 때까지 기다리면 **200회 중 0회**였다.

수정: `packages/server/persistence/tests/drop-isolated-database.ts`(`dropIsolatedDatabase`)를 추가했다.
backend가 다 나갈 때까지(최대 5초) 기다린 뒤 drop하고, FORCE는 끝까지 안 나가는 backend를 위한 최후
수단으로만 남긴다. 같은 패턴을 쓰는 다섯 파일, 여섯 곳에 적용했다.

- `course-thumbnail-reconciliation-upgrade.integration.test.ts`(afterAll, 그리고 backfill 시험의 finally)
- `reconcile-sweep-faults-upgrade.integration.test.ts`
- `resource-retrieval-upgrade.integration.test.ts`
- `course-route-proposal-supersession-upgrade.integration.test.ts`(M2-01p, rebase 뒤 독립 검토가 발견)
- `erasure-watched-refs-upgrade.integration.test.ts`(M2-01s, 같은 경로로 발견)

`resource-url-ingestion-upgrade`는 DB를 drop하지 않는다.

## 4. 실패율

전체 스위트 157건, `workers: 1`. load는 5초 간격 `uptime` 1분 평균이고, 이 기계는 8코어다.

| 묶음                   | 횟수 | 실패한 실행 | 실패 spec (실패 시점 load)                                             | 실행 중 load 중앙값 |
| ---------------------- | ---- | ----------- | ---------------------------------------------------------------------- | ------------------- |
| 수정 전 전체           | 3    | 1           | `oidc.spec.ts:55` (14.8)                                               | 7.2 ~ 13.8          |
| 수정 전 oidc 단독 ×60  | 60   | 4           | 전부 `oidc` 경쟁                                                       | —                   |
| 수정 후 oidc 단독 ×120 | 120  | 0           | —                                                                      | —                   |
| 수정 후 전체           | 4    | 2           | `wellbeing.spec.ts:203` (약 77), `session-targets.spec.ts:203` (약 52) | 22 ~ 45             |

최종 트리 전체 실행(진단 계측 제거 후) 결과는 §5에 적는다.

통계. oidc 경쟁은 단독 반복으로 쟀다. 전체 스위트 한 번에는 이 시험이 한 번만 들어 있어, 전체 반복으로는
검정력이 거의 없기 때문이다. 주 근거는 통계가 아니라 기제다. 요청을 붙잡아 두면 경쟁이 구조적으로 사라진다.
통계는 이를 보조할 뿐이다. 수정 전 4/60의 95% Clopper-Pearson 구간은 약 1.8%–16%이고, 하한 1.8%라면
120회 연속 통과 확률은 약 0.11이다. 4/60 대 0/120을 직접 비교한 단측 Fisher 정확검정의 p는 약 0.012다.
수정 후 실패율의 단측 95% 상한은 3/120 ≈ 2.5%다.

독립 검토(태그 `m2-01v-review-r1`)가 실제 브라우저에서 확인했다. 수정한 `:55`는 3/3 통과했고, Alice 세션 응답
목록은 매번 `[409]`로 비어 있지 않았다. 변이 A(동의 GET 세션 불일치 통과)에서는 2/2 실패했다. 새 "409 외 응답
없음" 단언은 변이 A에서 `await rejected` 타임아웃보다 늦게 평가되므로 보조 검사에 가깝다. 즉시 실패하도록 바꾸는
것은 후속 개선으로 남긴다.

부하 의존 실패는 수정 후 전체 실행 4회 중 2회 났다. 두 경우 모두 load가 52–77(코어당 6.5–9.6)일 때이고
API 쪽은 한가했다. 나머지 두 spec의 시간 초과가 브라우저의 `setViewportSize`·`fill` 대기에서 났다.
정상 부하(load 8 이하) 표본은 수정 전 실행 1회(중앙값 7.2, 통과)뿐이라, **정상 부하에서의 실패율은
이 데이터로 말할 수 없다.** 부하는 여러 에이전트가 동시에 돌아 생긴 것이며 운영을 대표하지 않는다.

`planned-completion-status.spec.ts:184`는 이번 전체 실행 7회(+ 최종)에서 한 번도 나지 않았다.
코드 모양을 보면 "완료 상태 다시 확인"은 계획 쿼리와 완료 쿼리를 함께 reset한다. 그러나 한 응답이 화면을
해체해 다른 응답을 끊는 oidc형 구조는 아니다. 그 5초 대기에는 Playwright `route.fetch()` 왕복이 끼어
있다. 시험 쪽 경쟁인지 부하 의존인지는 **모른다.**
