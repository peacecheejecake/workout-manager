# M2-01au · 남은 queue·state 경로를 superuser가 아닌 migration 소유 역할에서

상태: **완료(부분집합, 2026-09-26), `phase/m2-01`에 커밋.** 사용자 결정(2026-09-26)으로 task별 peer review 대신 M2-01 phase
리뷰(Codex CLI `gpt-6-sol` high)를 받는다. 기준 `5299292`(`merge-at` — migration은 051까지)에서 구현했다. 작업 중 파일 이름은
**053**이었고, M2-01as보다 먼저 들어가서 병합 때 root가 **`052_queue_state_plain_owner.sql`로 바꿨다**(아래 본문의 "053"은 작업 당시
이름이다). 남은 worker 경로는 후속 M2-01av다. 범위는 `task-graph.json`의 `M2-01au` scope, 출처는 [M2-01at](M2-01at.md) §5·§8.
`AGENTS.md`·`CLAUDE.md`·`task-graph.json`·`.geo-build`·요구 매트릭스·HANDOFF는 바꾸지 않았다. 개인 FIT/GPS·토큰·자격
증명은 없다(시험 tenant·객체·계정은 모두 합성).

## 0. 결론

superuser도 BYPASSRLS도 아닌 소유 역할(`NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE`, DB 소유자)이 schema 전체를 만든
DB에서, **말소·삭제 경로와 object·파생 정리 queue 전체, sweep의 행 단위 함수, 두 cursor, 복원 replay의 외래 id 거절이
이제 돈다.** 먼저 실패하는 시험 15개가 수정 전 base에서 실패했고(§3), 수정 뒤 통과한다. `authorize_resource_object_cleanup`의
13개 읽기는 object key가 이름 붙인 tenant로 읽는다 — policy만 더하고 이것을 되돌리는 변이 M5는 **살아 있는 추적 객체를 실제로
지웠고** 시험이 잡았다. 051 lease의 INCONSISTENT 단계는 due 순서의 앞 100행만 묻도록 바꿔 10만 행에서 약 0.66–0.88 s →
1.3 ms가 됐다(§5). `*_definer` policy 10개는 새 함수 `retarget_definer_policies()`로 새 소유자를 따라간다(`REASSIGN OWNED`,
`DROP OWNED`, 실제 `pg_restore --no-owner`에서 확인).

**남은 것(닫힌 실패):** 썸네일 render·URL 수집 worker, 업로드·render·URL reap, 업로드·썸네일 history prune, 검색 cache prune,
두 sweep window. 이들은 tenant 표를 여러 tenant에 걸쳐 tenant 없이 훑어 due 일을 찾는다 — "손에 든 행"이 없어 행의 tenant를
세울 수 없다. 이 소유 역할에서 여전히 아무것도 보지 못하고 아무것도 바꾸지 않는다(시험으로 확인). 그래서 **runbook의
superuser·BYPASSRLS 조건은 그대로 둔다**(지금 도는 것과 남은 것을 적어 갱신).

## 1. 설계 (`053_queue_state_plain_owner.sql`)

1. **owner 전용 policy 넷** — `resource_object_cleanup`, `resource_derived_cleanup`, `activity_track_reconcile_state`,
   `course_thumbnail_reconcile_state`(`TO current_user USING (true) WITH CHECK (true)`, 047·049·050·051 선례). 넷 다 tenant 표가
   아니고, runtime·worker 어떤 역할도 권한이 없다(grant helper 9개를 다 돌린 뒤까지 upgrade 시험이 단언). **tenant 표에는 policy를
   더하지 않는다** — 소유자의 다른 definer 함수 시야는 그대로다(upgrade 시험: policy 차이는 이 넷뿐, FORCE 플래그 동일, 소유자는
   tenant 없이 `activity_canonical`을 여전히 0행으로 본다).
2. **행마다 tenant를 세우는 읽기.** queue를 보이게 하면, 그 queue 행을 받은 뒤 tenant 표를 tenant 없이 읽는 함수는 "참조 없음"을
   답해 fail-open이 된다. 그래서 그 읽기를 모두 **행이 이름 붙인 tenant를 그 읽기 동안만** `app.athlete_id`로 두고 기존 tenant
   policy로 묻고, 호출자의 설정을 곧바로 되돌린다(050 `read_course_share`·051 방식):
   - `resource_object_cleanup`에는 tenant 열이 없다. key가 이름 붙인다(`private/v1/tenants/<uuid>/…`, `object_key_tenant(text)`).
     authorize의 fence 2 + 참조 11 읽기(`resource_object_publication_fence`·`resource_object_referenced`), finish의 게시 창 2 읽기
     (`resource_object_publication_window`), sweep reclaim 둘(`activity_track_object_held`·`course_thumbnail_object_held`)은 helper로
     옮겼다 — **옮긴 읽기는 글자 그대로**다(upgrade 시험이 이전 본문에서 잘라 낸 조각을 helper 본문에서 정확히 한 번 찾는다).
     settle 둘은 대상 자체가 tenant 표(`*_object_ref`)라 그 한 문장을 key의 tenant로 감쌌다.
   - **tenant를 이름 붙이지 않는 key는 authorize가 거절한다**: `INCONSISTENT_LEDGER:OBJECT_KEY_TENANT`로 닫고 지우지 않는다. 그런
     key는 tenant로 읽을 방법이 없어서다. 시스템이 만드는 key는 모두 tenant를 이름 붙이고, storage의 `validateObjectKey`도 그런
     key는 지우지 못한다. superuser 소유에서도 적용되는 유일한 동작 변화다 — 기존 시험 하나(`resource-file-uploads` "database
     time")가 `test/database-time/finish` 같은 임의 key를 authorize까지 보냈으므로 tenant key로 바꿨다(의미는 그대로).
   - `purge_resource_derived_store`는 lease한 manifest의 tenant로 지운다. **이전에는 plain 소유자에서 0행을 지우고 queue는 완료로
     적혔을 것이다**(policy만 더하면 그렇게 된다 — 변이 M18이 그 상태이고, 시험은 그 tenant의 cache 행이 남는 것으로 잡는다).
   - superuser 소유에서는 `set_config`가 아무것도 바꾸지 않는다(RLS를 보지 않음) — 판정은 전과 같다.
   - 한 가지 차이: plain 소유자에서 key의 tenant가 아닌 **다른 tenant의 행**이 그 key를 참조하면 보지 못한다. key는 서버가 인증된
     tenant로 만들므로 정상 경로에는 없다(runbook·§6).
3. **복원 replay**(`replay_absent_activity_deletion` 046, `replay_course_deletion` 049 — invoker, 복원 역할 = 소유자). 전역 읽기는
   그대로 두고(superuser·BYPASSRLS에서는 정확), `restore_foreign_scope_present(tenant,kind,id)`를 OR로 더했다: RLS가 적용되는
   호출자면 identity 계정이 있는 다른 tenant를 하나씩 이름 붙여 PK로 확인한다(계정 없는 tenant는 확인 못 함 — 정상 상태에는
   그런 행이 없다; runbook). RLS를 보지 않는 호출자면 전역 읽기가 이미 답했으므로 곧바로 false. 비용 §5.
   - 다른 invoker 함수 재감사: 이주 파일 전체에서 `athlete_id<>`/다른 tenant 읽기는 이 둘뿐이다. 나머지 invoker(`apply_course_deletion`,
     `arm_object_scope_purge`, `queue_*_refs`, trigger guard들, `record_*`)는 `$1`/`NEW`의 tenant만 읽고, 호출 문맥에서 그 tenant가
     세워져 있다(replay는 tenant 불일치를 먼저 거절). 예외는 C 계열 worker에서 불리는 `queue_course_thumbnail_refs`·
     `queue_resource_url_refs`·`close_resource_url_attempts`·`protect_resource_url_ref` — 호출자가 아무것도 보지 못하니 불리지 않는다.
4. **051 lease 비용**: INCONSISTENT 표시 단계가 모든 due 행에 plpgsql helper를 부르던 것을, **due 순서 앞의 라벨 없는 100행만**
   묻도록 바꿨다(두 단계 모두 `MATERIALIZED` CTE — 처음 판에서는 planner가 nested loop로 helper를 30,201번 불렀고 호출 수 시험이
   잡았다). 살아 있는 소유자의 행이 더 뒤에 있으면 앞에 올 때 라벨이 붙는다 — 그 전에도 candidate 단계가 lease하지 않는다.
   "값싼 SQL 선별"은 plain 소유자에서는 불가능하다(tenant 없이는 SQL로 볼 수 있는 것이 없다) — 그래서 선별 대신 창을 좁혔다.
5. **소유 이전**: `retarget_definer_policies()`(invoker, 누구에게도 grant 없음). 먼저 열 표 모두 호출자가 소유하는지 확인하고
   (아니면 `DEFINER_POLICY_OWNER_MISMATCH`), 표 이름 순으로 policy를 `ALTER POLICY … TO current_user`, 없으면(DROP OWNED로
   사라짐) migration이 만든 그대로 `CREATE POLICY`. 10을 돌려준다. 자동으로 따라가게 하는 `TO PUBLIC USING (current_user = 표
소유자)`형 policy도 검토했지만 tenant 정책과 OR로 묶여 runtime 질의마다 평가되고(course_share 등은 runtime이 읽는 tenant
   표다) index 사용에 영향을 줄 수 있어 택하지 않았다.
6. **잠금 순서**: 053은 tenant 표를 잠그지 않고 backfill이 없다. 첫 문장에서 네 표를 한 번에 잠근다(sweep state 둘 → 파생 queue →
   object queue: 자료 삭제가 잡는 순서). helper는 잠금을 잡지 않고, lease는 여전히 queue 행만 `SKIP LOCKED`로 잡는다 — 말소의
   77206 → 0 → 행 → queue 행에 되돌아오는 간선이 없다. 051의 tenant 표 AccessExclusive 문제는 051 자체(승인됨, 수정하지 않음)라
   runbook의 "멈추거나 `lock_timeout`" 지시를 유지했다. **잠금 문 자체는 변이로 구별되지 않는다**(DO 블록의 policy 생성이 같은
   순서로 잠그므로 관찰 차이가 없다) — 명시와 순서 고정을 위한 것이다.
7. 교체한 함수 10개는 서명이 같아 grant가 남는다(helper 재실행 불필요). search path는 `pg_catalog, pg_temp`로 고정(049–051처럼).

## 6. 남은 것(다음 노드 제안)

M2-01at §5의 B 36개 중: **동작** — 사용자 경로(추적 활동 삭제 trigger, protect 3, supersede, compact 3, enqueue 3, requeue 추적,
말소 체인 단계 6, pending bytes, 파생 pending·coach 확인)는 tenant 문맥이라 policy로, queue만 쓰는 worker 함수(lease·finish·release·
prune 정리/파생, cursor 4)는 policy로, authorize·finish·reclaim 2·settle 2·파생 purge는 행 tenant 읽기로. **닫힌 채 남음** —
`prepare_course_thumbnail`, `requeue_course_thumbnail_refs`, `prune_course_thumbnail_history`, `prune_resource_upload_history`
(job id·tenant 표 스캔), `enqueue_abandoned_resource_url_object`(요청 행을 못 봐 이미 queue된 ref만 재무장 — authorize가 key
tenant로 막는다).

C 30개 중 남은 것: 썸네일 render lease·finalize·fail·release·mark_unavailable·publication fence·reap, URL 수집 lease·prepare 2·
mark 2·finalize·bookmark·fail·hop·reap, sweep window 2(+candidates 2)·fault record/clear 4, `reap_expired_resource_uploads`,
`prune_resource_retrieval_cache`. (`reap_course_shares`는 050 policy로 이미 돈다. `assert_*_quota`·`supersede_course_thumbnails`는
tenant 문맥에서 불린다.)

이들은 **due 일을 찾을 tenant 출처**가 필요하다. 후속 설계 선택지(root 결정):

1. **owner 전용 작업 색인 표**(tenant 열 + 종류 + due 시각) — 해당 tenant 표의 trigger(definer)가 채우고, lease는 색인에서 한 행을
   집은 뒤 그 행의 tenant로 본 표를 읽는다. O(1) lease, 쓰기 경로에 trigger 비용.
2. **identity 계정 목록을 tenant 출처로**(replay 탐침과 같은 방식) — 변경이 작지만 poll마다 O(계정 수), 계정 없는 tenant는 못 봄;
   superuser 소유에서는 전역 경로를 지름길로 둬야 한다.
3. by-id worker 함수(render prepare/finalize…, URL prepare/mark…)는 **worker가 lease가 돌려준 tenant를 트랜잭션에 세우고 부르게**
   하면 SQL 변경 없이 된다(lease token이 권한이므로 tenant를 아는 것이 넓힘이 아니다). 1·2와 함께 필요.

비밀 값으로 gate한 owner policy를 tenant 표에 두는 방법은 이 노드 지시("tenant 표에서 definer 시야를 넓히지 않는다")에 어긋나
택하지 않았다.

기타:

- runbook의 superuser·BYPASSRLS 조건은 유지(위가 끝나기 전에는 내리지 않는다).
- plain 소유자에서 superuser가 tenant를 세우지 않고 `activity_canonical`에 직접 INSERT하면 `bump_integrated_dependency_head`
  trigger가 `integrated_dependency_head`에서 `42501`로 거절한다(upgrade 시험 준비 중 관찰; 앱 경로는 항상 tenant를 세운다).
- 실제 운영 배포의 소유 역할 구성은 확인하지 않았다(`not_executed`).
- peer review: 규칙대로 받지 않았다(root 몫).
