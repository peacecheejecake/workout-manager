## 1. 결정과 근거

### 1.1 PostgreSQL lease limiter (M2-01k-e §1.4의 결정을 구현)

`routing_admission` 표(migration 047) 한 행이 **허가 하나**다. `started_at`은 tenant의 rate 창에서 세고, 행은
`released_at IS NULL AND lease_until > now`인 동안 tenant 동시성과 엔진 동시성의 한 자리를 잡는다.

- **획득·반환은 각자 짧은 트랜잭션.** `acquire_routing_permit`이 판단과 insert를 한 번에 하고 commit한다. 엔진이 돈다.
  `release_routing_permit`이 행을 released로 표시하고 commit한다. 엔진 호출 동안 열린 트랜잭션은 없다(AGENTS 규칙).
  서비스는 여전히 `engineReleased`에서 반환한다(M2-01k-e §1.2의 4). 호출자가 끊어도, 다른 인스턴스에서도 그 허가가 센다.
- **만료 = deadline + 유예.** API가 주는 lease는 `8 000 + 2 000(hard stop) + 2 000(반환 왕복 여유) = 12 000 ms`다.
  살아 있는 인스턴스는 늘 그 전에 반환한다(엔진 연결은 deadline + 2초에 끊기므로). 죽은 인스턴스의 허가는 lease가
  끝나는 순간부터 세지 않는다. 누가 죽음을 알아차릴 필요가 없다.
- **rate도 같은 표**에서 센다: `started_at > now − 창` 행 수. 거절 시 `retry-after`는 창 안의 가장 오래된 시작 + 창 − now.
- **시각은 DB 시계**(`clock_timestamp()`). 인스턴스 시계가 어긋나도 만료와 창 판단이 같다.
- **직렬화.** 획득은 `pg_advisory_xact_lock(77206, 47)`(두 정수 key 공간이라 `hashtextextended`의 bigint key와 겹치지
  않는다)을 잡은 뒤 tenant 수·엔진 수를 세고 insert한다. 두 인스턴스가 "한 자리 남음"을 동시에 보고 둘 다 가져갈 수 없다.
  잠금 순서는 저장소 규칙 그대로다: tenant 트랜잭션의 계정 잠금(77206, shared) → 이 잠금 → 행. 반환은 잠그지 않는다
  (자리를 줄 뿐 늘리지 않는다). 청소(창을 벗어나고 허가를 잡지 않은 행, 최대 500)는 `FOR UPDATE SKIP LOCKED`라 삭제
  중인 erasure의 행 잠금을 기다리지 않는다.
- **닫힌 쪽으로 실패.** DB에 묻지 못하면 `limiter_unavailable`로 거절한다(`overloaded`, `retry-after: 1`). 프로세스
  안에서 세는 fallback은 없다. 반환 실패는 lease 만료가 대신한다.
- **RLS.** 표는 FORCE RLS이고 tenant 정책이 있다. runtime 역할은 표 권한이 **전혀 없고** 두 함수의 EXECUTE만 있다
  (`grantCourses`). 엔진 상한은 모든 tenant의 행을 세야 하므로 함수는 SECURITY DEFINER이고, migration을 실행한 역할에
  `routing_admission_definer` 정책(`TO <migration 역할> USING (true)`)을 따로 준다. 이것이 없으면 superuser도
  BYPASSRLS도 아닌 소유자에서는 FORCE 때문에 호출 tenant의 행만 보여 **엔진 상한이 조용히 tenant 상한이 된다.**
  소유자만 쓰도록 trigger(`routing_admission_writer_is_owner`)도 둔다(course_thumbnail과 같은 방식).
- **삭제.** `erase_account`를 한 번 더 감싸 tenant의 허가 행을 지운다(77206 → 0 → 행, 그 뒤 이전 chain). 행에는
  건강 데이터가 없지만(tenant id와 시각 셋) tenant의 사용 기록이므로 계정과 함께 지운다. backup drill이 복원 뒤 재생에서
  지워짐을 확인한다(§3.4).

**process-local `TenantAdmissionControl`은 남겼다.** 둘 다 새 `RoutingAdmission` interface를 구현한다. production
composition은 PostgreSQL limiter만 쓴다. `createConfiguredWalkingRoutes`의 `admission` 옵션을 **필수**로 바꿔,
어떤 composition도 말없이 프로세스 안 계산으로 떨어지지 않게 했다. 단위 시험과 DB 없는 probe seam은 in-process
limiter를 명시적으로 넘긴다.

### 1.2 전역 엔진 동시성 상한

`ROUTING_ENGINE_CONCURRENCY`(정수 1–1024, 기본 8): 모든 tenant·모든 인스턴스를 합친 허가 수. 같은 획득 함수가
tenant 한도(자기 탓)를 먼저, 엔진 상한을 나중에 본다. 거절은 `engine_capacity`, 응답은 기존과 같은 429
`overloaded` + `retry-after: 1`이다(contract 변화 없음).

- 기본 8은 probe를 돌린 데스크톱의 논리 코어 수(`hw.ncpu` 8)다. GraphHopper flexible 탐색은 계산 하나에 스레드 하나를
  쓰는 CPU 작업이라 코어 수가 출발점이다. **측정된 최적값이 아니다.** runbook은 엔진 기계의 코어 수로 두라고 적는다.
- routing 네 변수 없이 이것만 두면 `ROUTING_CONFIGURATION_INCOMPLETE`(host allowlist와 같은 규칙), 형식이 틀리면
  `ROUTING_CONFIGURATION_INVALID`로 기동을 거절한다.
- **관측.** 기동 로그 `routing_admission_configured`(`limiter: postgresql`, `engineConcurrency`). 엔진 상한 도달과
  limiter 불통은 `routing_admission_refused`(`reason`, `engineInFlight`, `engineConcurrency`, tenant id 없음) warn.
  tenant가 자기 한도에 걸린 것은 평범한 429라 로그하지 않는다. 운영자는 소유자 역할로
  `SELECT count(*) FROM routing_admission WHERE released_at IS NULL AND lease_until > clock_timestamp()`로 현재 부하를 본다.

### 1.3 다중 leg `timeout` warning (M2-01k-e §1.3의 남은 일)

`routeWarningCodeSchema`에 `timeout_may_be_no_route`를 **더했다**(additive). schemaVersion 1은 그대로이고 기존 값은
모두 그대로 parse된다. 이 저장소에는 생성된 JSON schema 산출물이 없다(`check:generated`는 responsive 상수만 본다). 조사:
contract 소비자는 warning을 문자열로 그대로 보여 주거나(course 편집기) 저장된 revision에 싣는데, `timeout`은 저장되지
않으므로 **저장된 revision·export에 이 값이 들어가는 경로는 없다.**

어댑터는 엔진 답을 시간 규칙으로 `timeout`이라 분류하고 **leg가 둘 이상**일 때만 이 warning을 단다. leg 하나면 규칙이
전송 시간 오차 안에서 정확하고, 우리 deadline이 먼저 끝난 `timeout`(엔진이 답하지 않음)은 모호하지 않으므로 달지 않는다.
결과는 여전히 `timeout`이다(오류가 `timeout` 쪽으로만 나는 설계는 유지).

## 7. 남은 것 / 한계

- **교체의 원자성은 프로세스 단위.** 공유 limiter는 한도만 공유한다. 여러 인스턴스의 graph 전환을 한 번에 하는
  장치(공유 활성 배포 참조 등)는 없다. 필요하면 별도 노드다.
- **엔진 상한은 허가 수다.** GraphHopper Jetty 스레드 풀이나 엔진 CPU를 직접 재지 않는다. 기본 8은 측정된 최적값이
  아니다. 엔진 기계의 코어 수로 맞춘 부하 측정은 하지 않았다.
- **획득은 전역 advisory lock 하나로 직렬화된다.** 획득마다 count 두 번과 insert 한 번이며 부하 측정은 하지 않았다.
  초당 수백 건 규모가 되면 tenant별 잠금과 엔진 수 분리(예: 엔진 상한용 슬롯 표)를 검토한다.
- **DB 장애는 routing을 닫는다**(`limiter_unavailable`). 의도한 닫힌 실패다. `lock_timeout` 3초·`statement_timeout`
  5초를 넘는 경합은 검토 N3 뒤 `limiter_contended`로 따로 거절·로그한다(둘 다 429 `overloaded`).
- **한도는 호출자가 준다(검토 N2).** `acquire_routing_permit`은 tenant 동시성·rate·창·엔진 상한·lease를 **인자로**
  받고 범위와 `창 ≥ lease`만 검사한다. 인스턴스마다 값이 다르면 각자 자기 값으로 공유된 수를 판단한다(runbook 남은
  조건 2). 한도를 DB에 두고(설정 표, 소유자만 쓰기) 함수가 거기서 읽게 하는 것은 향후 hardening이며 이 노드는 하지 않았다.
- **청소의 `released OR 만료` guard는 `창 ≥ lease`에서 중복이다(검토 N5).** 창을 벗어난 행은 lease도 이미 끝났으므로
  guard를 지운 변이 MX는 기본값에서 살아남는다(설계상). 대신 `창 ≥ lease`를 limiter 생성과 SQL 함수 양쪽에서 강제하고,
  그 검사를 푼 변이 MY(SQL)·MZ(limiter)가 실패한다. guard는 방어 겹으로 남긴다.
- **lease 12초**는 deadline + hard stop + 여유다. DB 왕복이 2초를 넘게 느려지면 살아 있는 계산의 허가가 반환 전에
  만료될 수 있다(그 순간 한도가 하나 느슨해진다). 반대 방향(허가가 필요 이상 오래 남음)은 없다.
- **반환은 답보다 늦다.** 허가는 엔진이 멈춘 뒤 별도 트랜잭션으로 반환된다(수 ms). 답을 받자마자 같은 tenant가 연달아
  두 건을 더 보내면 그 사이에 `concurrency` 429를 받을 수 있다(probe 초기화 기록의 `permitsHeld`가 그 순간이다).
  in-process limiter에서는 이 틈이 microtask 하나였다.
- **종료 시 대기.** API 종료는 진행 중 허가의 반환을 최대 12초 기다린 뒤 pool을 닫는다(`drain`). 그보다 오래 걸리면 lease가 끝낸다.
- **probe 수정.** 두 probe는 섹션마다 새 API 인스턴스를 만들며 in-process 한도가 초기화되는 것에 기대고 있었다. 공유
  limiter에서는 창이 인스턴스를 넘어 남으므로(이 노드가 만든 성질) 첫 재실행에서 운영 probe 2개, swap probe 5개
  check가 tenant rate 거절로 실패했다(§5.1). probe가 섹션 시작마다 **이력만**(잡은 허가는 남김) 지우도록 고쳤다.
- **UI 없음.** `timeout_may_be_no_route`는 contract와 계산 기록에 실린다. 편집기는 `timeout` 결과를 저장하지 않고
  재시도를 안내하므로 화면 문구는 바꾸지 않았다(Aside·Chrome·Playwright 모두 이 노드에서 쓰지 않음).
- 검토: node-rules에 따라 이 agent는 검토자를 띄우지 않았다. 커밋 전 독립 검토는 root 몫이다.
