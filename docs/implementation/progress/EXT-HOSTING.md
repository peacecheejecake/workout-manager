## 단일 서버의 Workout Manager 준비

- phase 브랜치의 추적 소스를 새 서버 `/srv/workout-manager/source`로 전송했다. 첫 생산용 Docker 이미지 빌드와 새 `deploy/lightsail` 구성의 앱·GraphHopper 이미지 빌드를 새 서버에서 실제로 완료했다. 이는 빌드 증거이고 제품 앱 기동·공개 검증 증거는 아니다. 기존 사이트의 Compose·Caddy·PostgreSQL 볼륨은 수정하지 않았다.
- 새 ODbL 전국 graph 308 MiB와 배경 지도 dist 97 MiB, 고정된 GraphHopper JAR·serving 설정·원본 extract를 `/srv/workout-manager/data`에 전송했다. `rsync --checksum --dry-run`에서 graph·basemap 파일 변경이 없었고, JAR·설정·extract SHA-256은 로컬 원본과 각각 일치했다. 비공개 Docker 테스트 컨테이너에서 GraphHopper `/healthcheck`가 200, 공개 장소를 이용한 서울 합성 두 지점의 보행 경로 계산이 200·1 path·593 m였다. 테스트 컨테이너 중지 뒤 graph의 파일 내용 재대조에는 디렉터리 mtime 외 변경이 없었다. 공개 라우팅 API와 coverage 판정은 아직 미검증이다.
- 기존 사이트와 별개인 Workout 전용 PostgreSQL 컨테이너를 기동해 healthy를 확인했다. Git 밖의 `/srv/workout-manager/secrets`에 root 전용 0600 파일과 서로 다른 무작위 DB 비밀번호를 만들었다. 실제 `db_setup` 컨테이너가 `DATABASE_SETUP_COMPLETE`로 마이그레이션 65개를 적용했다. 후속 SQL 조회에서 RLS가 켜진 public 테이블 139개, 앱·소유자·작업자 다섯 역할의 `SUPERUSER`·`BYPASSRLS`·`CREATEDB`·`CREATEROLE` 모두 false를 확인했다. 제한된 `workout_runtime` 계정으로 직접 로그인해 `consent` SELECT 권한은 true, public 스키마 CREATE 권한은 false였다. 이 검증은 전용 빈 DB의 역할·스키마 준비에 한정하며 사용자 데이터/백업 복구 시험은 아니다.
- 사용자가 로컬 Zitadel issuer·client ID·client secret의 정확한 AWS 목적지 전송을 승인한 뒤 서울 Secrets Manager `workout-manager/prod/oidc` 생성을 확인했다. 값을 담은 임시 로컬 파일은 삭제했다. Secrets Manager에서 새 서버 root 전용 `app.env`로 전달하는 첫 요청은 자동 승인 검토가 **거절**했다. AWS 저장소 전송 승인만으로는 서버 목적지를 승인한 것이 아니라는 이유였다. 사용자가 계정·secret·서버·파일을 지정한 전송을 별도로 명시 승인한 뒤 재시도해 `oidc_delivery_written`을 확인했다. 파일은 `0600`·root 소유, OIDC 세 항목이 있으며 값은 출력하지 않았다.
- 비공개 앱 컨테이너에서 설정된 issuer의 OIDC discovery를 요청해 HTTP 200과 응답 issuer의 정확한 일치를 확인했다. 주소·client ID·secret·응답 본문은 출력하지 않았다. 이 검사는 공급자 메타데이터 접근 증거이며 앱 등록, HTTPS redirect, 사용자 로그인 또는 로그아웃 수용 증거는 아니다.
- URL 수집 작업자만 전용 `workout_egress` bridge와 기존 내부 DB 네트워크 양쪽에 연결했다. 서버의 이전 Compose 파일 해시가 변경 전 브랜치 파일과 같음을 확인하고 백업한 뒤, 새 파일을 적용해 실제 환경의 Compose 검증을 통과했다. 실제 one-shot 컨테이너에서 `wm-postgres` DNS가 해석되고 OSM 사이트로의 HTTPS HEAD가 200인 것을 확인했다. 임시 컨테이너는 제거됐고 앱은 healthy, 기존 공개 사이트는 200·TLS 검증 0이었다. 시험 시 `RESOURCE_URL_ALLOWED_HOSTS`는 설정되지 않아 **실제 URL 수집 작업은 실행하지 않았다**. 네트워크 연결은 허용 호스트 지정·fetch/parse·재시도·삭제 억제·스케줄링의 수용 증거가 아니다.
- 앱과 GraphHopper를 새 서버에서 비공개로 기동했다. 첫 앱 health는 PostgreSQL 인증 오류 `28P01`이었다. `app.env`와 `setup.env`의 사용자명·비밀번호·호스트·DB는 같았고, 전용 DB의 SCRAM 해시는 해당 비밀번호와 일치했다. 앱은 기존 사이트의 Caddy 네트워크와 Workout 내부 네트워크 양쪽에 붙고 양쪽에 `postgres`라는 이름이 있어 기존 사이트 DB를 선택한 것이 원인이었다. ## 복원 세대값 저장 준비 (migration 076)

## 복원 이전 create 요청 차단 (로컬 구현)

- `IntakeEntry`와 `RecoveryActionLog` 생성 요청에 현재 복원 세대 UUID를 필수로 묶었다. 인증된 `GET /bff/v1/restore-generation`은 캐시하지 않는 응답으로 세대를 읽고, 서버는 생성 명령의 거래 안에서 receipt 재생과 INSERT **전에** 세대를 비교한다. 이전 세대는 `409 STALE_RESTORE_GENERATION`이며, 기존 성공 요청의 재생도 복원 세대가 바뀌면 거절한다. 브라우저는 생성 의도 때 세대를 읽고 결과가 불확실한 재시도에는 같은 세대·멱등 키를 유지한다. 명시적 stale 응답 뒤에는 입력을 보존하고 새 확인/저장 의도에서만 새 세대·키를 얻는다. 수정·삭제 명령은 이 생성 전용 필드를 받지 않는다.
- 계약/API/화면 관련 Vitest **6파일·40시험 통과**, 브라우저 세션 전송 계층 **1파일·100시험 통과**, 전체 타입 검사 **34개 패키지 통과**, 전체 빌드 **15개 작업 통과**. 변경 TS ESLint·Prettier와 `git diff --check` 통과. 격리 PostgreSQL 14 전체 통합 시험 **104파일·890시험 통과**, 임시 서버 종료. Playwright의 격리 OIDC·API·DB·실제 Chromium에서 영양·회복 **2시험 통과**. 첫 브라우저 실행은 다른 시험 서버 포트에 연결돼 로그인 단계에서 실패했고, 별도 포트 빌드 후에는 시험 API의 조회 경로 누락과 브라우저 Host 허용 경로 누락을 발견해 수정했다. 이 두 실패를 통과로 바꾸지 않고 최종 재실행 결과를 별도로 기록한다. Aside 업데이트는 `fetch failed`, Chrome 직접 제어는 시간 초과여서 브라우저 검증 도구는 Playwright였다.
- 공유 메모리 슬롯이 고아 세그먼트 31개로 소진되어 최초 DB 시험은 `initdb` 전에 실패했다. 사용자 명시 승인 뒤 연결 수 0인 세그먼트 31개만 정리하고 활성 PostgreSQL의 세그먼트 1개는 유지했다. 그 후 위 전체 통합 시험이 통과했다.
- 이 변경은 **백업 이전/이후 생성 요청의 재시도 식별**만 다룬다. 삭제 사건, 외부 독립 반출, 복원 replay, 운영 PostgreSQL 17.6 적용, 공개 서비스 검증은 여전히 **not_executed**다. 실제 복원 작업은 앱 쓰기를 차단하고 소유자 전용 `rotate_restore_generation()`을 복원 접근 재개 전에 호출해야 한다. 그 운영 절차와 복원 드릴도 아직 검증하지 않았다.

## 실제 기록 사용자 삭제 사건 (로컬 구현)
