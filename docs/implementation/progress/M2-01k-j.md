## 1. 설계 근거

### 1.1 왕복 초안은 평범한 세 경유점 초안이다

- **adapter를 바꾸지 않았다.** M2-01ah(admission, `timeout_may_be_no_route`)와 검토 중인 M2-01af(POST `/route`)가
  adapter를 고치고 있다. 왕복 초안은 경유점 목록 `[A(start), B(via), A(finish)]`이고, 기존 경로 제안 요청
  (`route-proposals` → `computeWalkingRoute`)이 그대로 계산한다. M2-01g의 순서 검사(첫 snap에서 시작, 요청 순서로
  경유점 방문, 마지막 snap에서 끝)가 그대로 적용된다. 엔진의 `round_trip`은 쓰지 않았다(M2-01i와 같은 이유).
- **draft store 동작 `makeOutAndBack()`**(`course-draft.ts`): 시작 A와 현재 끝 지점 B로 A→B→A를 만든다. 되돌리기
  한 번으로 되돌아가는 **변경 한 번**이다(revision 증가, 이전 계산 무효). 규칙:
  - B는 현재 끝 지점이다. B의 id·이름·잠금은 유지된다(같은 지점이 반환점이 됨).
  - 새 끝 지점은 A의 위치·이름이지만 `sourceSampleId: null`, `locked: false`다. 기록 표본 하나를 두 경유점이
    주장하지 않는다(M2-01i 후보의 귀환점과 같은 규칙).
  - 이미 A→B→A면 아무것도 바꾸지 않는다(revision 불변).
  - 사이의 경유점은 쓰지 않는다. **잠긴 via가 있으면 거절**(`OUT_AND_BACK_LOCKED_VIA`) — 잠금을 조용히 버리지 않는다.
    B가 A와 같은 위치면 `OUT_AND_BACK_SAME_POINT`, 지점이 둘 미만이면 `OUT_AND_BACK_NEEDS_TWO_POINTS`.
  - 거절은 반환값이고 목록의 `refusal`을 쓰지 않는다. 그래서 `course-waypoint-list.tsx`(공유 파일)를 건드리지 않았다.
- **편집기 버튼 "왕복 초안 계산 (A→B→A)"**(목표 거리 후보 절, 후보 생성 버튼 옆): `makeOutAndBack()` 뒤 기존
  `compute()`를 부른다. 그 시점 목표 거리 칸의 값(유효 범위일 때)을 **그 draft revision에 묶어** 기억한다. 다른
  draft의 경로에는 목표가 붙지 않는다. 검토·저장은 기존 경로 검토("검토한 경로 저장", `reroute`)와 같다. 저장된
  revision은 `routed-waypoints` generation이며 graph·엔진 버전이 담긴 computation 전체를 가진다.

### 1.2 겹침 계산(`packages/modules/courses/src/out-and-back.ts`, 순수 함수)

- 계산된 선을 **snap된 반환점 B**에서 나눈다(`turnaroundIndex`: 시작 이후 첫 정점 중 B에서 1m 안 — route guard와
  같은 anchor. 없으면 가장 가까운 안쪽 정점). 가는 길 = `[0..i]`, 오는 길 = `[i..]`. snap 위치는 제안 응답의
  `snappedWaypoints`에서 받아 `ComputedDraftRoute.snappedWaypoints`(선택 필드)에 둔다.
- `outAndBackOverlap(out, back)`: 오는 길을 4m 이하 조각으로 자르고, 조각 중점이 가는 길에서 **12m 안**이면 겹침이다.
  연속한 겹침 조각은 한 구간이고, **20m 미만 구간은 버린다**(A·B에서 두 선이 만나는 접점일 뿐 두 번 걷는 길이 아님).
  결과: 가는 길·오는 길 길이, 겹침 m, 오는 길 대비 비율, 구간 목록(오는 길 기준 시작·끝 m, 선 좌표).
- **정점 분할과 무관**하다(정점 간격이 곡선 반지름보다 충분히 작은 경우; 반지름 10 m 곡선을 10 m 간격 등 서로 다른 정점으로 인코딩한 두 다리는 방향 조건에 걸려 놓칠 수 있다. 실제 엔진은 두 다리에 같은 edge geometry를 역순으로 주므로 해당하지 않는다, 2차 검토): 같은 길을 다른 정점으로 인코딩해도 같은 답(시험 "however either is encoded"). M2-01i의
  서버 `repeatedSection`이 vertex 쌍 비교에서 격자 걷기로 바꾼 이유와 같다.
- **방향 조건(검토 1차 #2):** 조각은 근처 가는 길 선분과 **나란할 때만**(|cos| ≥ 0.9, 약 25° 이내, 같은 방향이든
  반대 방향이든) 겹침이다. 이것이 없으면 다른 길로 돌아오며 가는 길을 90°로 **가로지르는** 곳(허용 오차 안에
  2·12/sin θ = 24m)이나 B에서 30°로 다른 길로 떠나는 곳이 "24m · 1곳"으로 보고됐다.
- 공간 색인: 가는 길을 반 칸 간격으로 걸으며 선분을 자기 칸과 주변 8칸에 등록하고, **조회도 자기 칸과 주변 8칸**을
  본다(검토 1차 #3: 전에는 주석만 9칸이라 하고 코드는 자기 칸만 봤다). 색인 크기는 선 **길이**에 비례한다(대각선 긴
  선분의 bbox 면적에 비례하지 않음).
- 정의는 `outAndBackOverlapDefinition`(v1)으로 화면에 표시한다. 겹침은 **선 모양의 측정**일 뿐 통행 가능성의
  증거가 아니라고 화면이 말한다.
- 서버 계약은 바꾸지 않았다. 겹침은 저장 전 검토 표시이며 revision에 저장하지 않는다(§8).

### 1.3 지도: `overlap` 역할과 렌더 증거

- geo-kit `MapPathRole`에 `'overlap'`을 더했다. MapLibre 선 layer가 이 역할을 **폭 8·주황(#c2410c)·불투명도 0.75**로
  그린다(다른 선은 폭 4). 편집기는 제안선(`candidate`) 위에 `course-overlap` 경로(구간 사이는 `breaks`로 끊음)를 준다.
  draft가 바뀌면 경로가 사라진다(제안이 현재 draft의 것일 때만).
- **렌더 증거**: `MapRenderIdleInfo.renderedLineRoles`(선택 필드) — idle/render 시 `queryRenderedFeatures`로 선 layer에
  실제로 그려진 feature의 `role`을 모은다. `MapView`가 `data-rendered-line-roles`로 노출한다. 그래서 E2E가 "겹침
  구간이 **렌더러에** 그려졌다"를 단언한다(좌표 목록이나 React props가 아니라).

### 1.4 목표 표시(P6)와 "확인되지 않음"

- 목표 거리 후보마다 각각 **별도 줄·testid**로: 목표 오차(`candidate-error-N`), 연결성(`candidate-connectivity-N`),
  반복·왕복 구간(`candidate-repeat-N`, 기존), **알려진 접근 제한**(`candidate-access-N`, 신규 — 전에는 계단·노면·야간과
  한 줄), 계단·노면·야간 통행(`candidate-knowledge-N`), 경사 출처(`candidate-gradient-N`).
- 왕복 검토(`out-and-back-review`)도 같은 항목: 겹침(`route-overlap`, 구간 목록), 목표 오차(`route-target-error`),
  연결성(`route-connectivity`), 접근 제한(`route-access`), 계단·노면·야간(`route-conditions`), 경사 출처(`route-gradient`).
- **자료를 만들지 않았고, 모르는 이유를 사실대로 적는다(검토 1차 #1).** "자료 없음"은 거짓이었다: 서빙 graph는
  `road_access`·`foot_access`·`surface`를 인코딩한다(`.geo-build/routing-graph/foot/properties.txt`의
  `graph.encoded_values`, `scripts/geo/graphhopper-foot*.yml`의 `graph.encoded_values`). adapter가 `details=road_class`만
  요청할 뿐이다. 그래서 항목마다 이유가 다르다:

  | 항목      | 화면 문구                                                        | 사실                                                                                                                           |
  | --------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
  | 접근 제한 | 확인되지 않음 (엔진에 요청하지 않음)                             | graph에 `road_access`·`foot_access` 있음, 요청 안 함                                                                           |
  | 노면      | 확인되지 않음 (엔진에 요청하지 않음)                             | graph에 `surface` 있음, 요청 안 함                                                                                             |
  | 계단      | 확인되지 않음 (엔진 도로 등급을 검증에만 쓰고 보관하지 않음)     | `road_class`(steps 포함)는 요청하지만 답 검증에만 쓰고 버림                                                                    |
  | 야간 통행 | 확인되지 않음 (자료 없음)                                        | 조명·운영 시간은 graph에도 자체 자료에도 없음                                                                                  |
  | 경사 출처 | 확인되지 않음 (엔진 경사 자료 없음 · 고도 표본은 고도 확인 참조) | graph에 elevation 없음, 요청도 `elevation=false`. 희소 고도 표본은 M2-01j 자료로 고도 확인(M2-01k-b 프로파일 포함)이 보여 준다 |

  계약은 `knowledge.*`를 literal `'unknown'`, `gradientSource`를 `'none'`으로 고정한다. `knowledgeText(key, value)`·
  `gradientSourceText`·`connectivityText`는 그 literal에 대한 `switch`라서, 계약이 알려진 값을 더하면 **컴파일 오류**가
  난다(조용한 "충족" 불가).

- **왕복 검토도 계약 필드로 그린다(검토 1차 #5).** 전에는 `knowledgeText('unknown')` 같은 literal을 넘겼다. 이제
  `routedProposalFacts: Pick<CourseCandidateEvaluation, 'connectivity' | 'knowledge' | 'gradientSource'>`(계약 타입)을
  받아 필드마다 그린다. 후보의 "계단·노면·야간" 줄도 전에는 `stairs`만 읽었다. 이제 세 필드를 각각 이유와 함께 쓴다.
- **후보의 목표 오차는 서버가 저장한 `distanceErrorMeters`·`distanceErrorRatio`를 그대로 쓴다(검토 1차 #6).** 왕복
  검토에는 서버 evaluation이 없으므로 엔진 거리 − 목표로 계산한다.
- 가는 길·오는 길 길이는 **선 길이**라고 적는다("가는 길 선 길이 (A→B)", 검토 1차 #7). 엔진 거리와 다른 값이다.
- 왕복을 만들며 사이 경유점을 뺐으면 검토에 "사이의 경유점 N개를 뺐습니다. 되돌리기로 되살릴 수 있습니다"(검토 1차 #11).
- 연결성 문구: "엔진이 지났다고 밝힌 도로 구간으로 이어짐 · 지금 통행할 수 있다는 보장은 아님".

## 3. E2E 설계(`tests/identity/course-out-and-back.spec.ts`)

실제 OIDC 세션·API·PostgreSQL, `IDENTITY_E2E_ROUTING=graphhopper`면 helper(`graphhopperJavaArguments`)로 띄운 자체
GraphHopper(`.geo-build`, graph `c57f12f5975347e8`, 10.0). 한 테스트:

1. API로 A(126.978, 37.566)→B(126.982, 37.569) 코스를 가져온다(revision 1). `/courses`에서 열고 지도가 선을 그렸음을 확인.
2. 목표 1000m 입력, "왕복 초안 계산". **엔진 요청 본문의 경유점이 `[start A, via B, finish A]`**(편도 A→B가 아님).
   응답 200 `route_computed`.
3. 검토: `route-graph` = 기대 graph. `route-overlap` — graphhopper 모드는 `"<m> (<p>%) · <n>곳"`이고 p ≥ 50, 구간 목록
   "1구간"; fixture 모드는 "겹치는 구간 없음"(fixture 엔진은 각 leg를 제 쪽으로 휘게 그려 되돌아오는 길이 겹치지
   않는다 — 정직한 답). `route-target-error` = 응답의 엔진 거리와 목표로 계산한 정확 문구. 연결성·접근 제한·경사
   출처 정확 문구.
4. 지도: 새 경로에 대한 "drawn" 판정 뒤 `data-rendered-line-roles`에 `overlap`(graphhopper) / 없음(fixture).
5. 제안은 저장이 아님(revision 1) → 검토 체크 → 저장 → revision 2. API로 읽은 revision: `routed-waypoints`,
   `graphBuildId`·`engineVersion`·`identitySource: engine`·`waypointCount: 3`이 기대값, 저장 경유점 `[A, B, A]`, 저장된
   엔진 거리 = 제안 거리.
6. 같은 코스에서 목표 1200m 후보 생성 → 0번 후보의 목표 오차(응답 거리로 계산한 정확 문구), 연결성, 반복 구간,
   접근 제한, 경사 출처.

실측(graphhopper, 3회 모두 같은 값): 엔진 1,457.869 m, 겹침 "729m (100%) · 1곳", 저장 revision 2 graph
`c57f12f5975347e8` engine `10.0`. 엔진 로그에서 좌표 형태 줄 0건.

## 8. 남은 것

- **후속 노드 제안: "routing 경로 속성 details(접근 제한·노면·계단)".** adapter가 `details`에 `road_access`·
  `foot_access`·`surface`를 더 요청하고(`road_class`의 steps는 이미 옴), 계약의 `knowledge.accessRestrictions`·
  `surface`·`stairs`에 `'unknown'` 외의 값(구간 목록과 출처 graph)을 더하고, 저장 revision·export 호환(schema 버전)과
  후보 evaluation v2를 정한다. 화면은 이 노드의 `knowledgeText` switch가 컴파일 오류로 알려 준다. 그 노드가
  P6-target-display를 passed로 닫는다. 야간 통행과 엔진 경사는 graph에 없어 자료 원천부터 정해야 한다.
- 겹침은 저장 전 검토에서만 계산한다. 저장된 revision의 generation에는 겹침 측정이 없다(계약 변경 없이 한 선택).
  저장 뒤 코스 화면에서 겹침을 다시 보여 주려면 저장된 경유점·선으로 같은 함수를 다시 부르면 된다.
- `/courses/new`(새 코스 화면)에는 왕복 버튼이 없다(`course-new.tsx`는 M2-01k-b와 겹칠 수 있어 건드리지 않음).
  store 동작과 검토 블록은 재사용 가능하다.
- 왕복 초안의 반환점은 **끝 지점**이다. 사이 경유점은 쓰지 않는다(잠겨 있으면 거절). 선택한 경유점을 반환점으로 쓰는
  선택지는 없다.
- fixture 엔진은 되돌아오는 길을 겹치게 그리지 않는다. 그래서 fixture 모드 E2E는 "겹치는 구간 없음"을 단언하고,
  겹침 표시의 핵심 증거는 graphhopper 모드 실행이다.
- 겹침 허용 오차 12m는 같은 길의 양쪽 보도(OSM에서 따로 그려진 경우)를 겹침으로 셀 수도, 못 셀 수도 있다. 정의 v1로
  화면에 명시했다.
- 독립 검토는 1차 REQUEST CHANGES, 2차 APPROVE였고 root가 M2-01k-b 위로 병합했다.
