## 2. 항목 2 · timeout 난 시험 본문의 격리

- 원인(M2-01ac): vitest는 timeout 난 시험 본문을 멈추지 않는다. 모든 component 시험은 `document` 하나를
  공유한다. 그래서 cleanup 뒤에도 남은 `user.click(screen…)`이 다음 시험의 요소를 누른다.
- 수정: `packages/tooling/test-isolation.ts`(component setup에서 설치).
  - `aroundEach`로 시험마다 `AsyncLocalStorage` 문맥을 연다. 시험 본문과 그 본문이 남긴 모든 async 작업은 이
    문맥을 물려받는다. vitest 4.1의 `aroundEach`는 `runTest()` 안에서 본문을 부르므로 문맥이 전파된다. 시험
    timeout은 hook timeout에 포함되지 않는다.
  - 시험이 끝나면(통과·실패·timeout) 문맥을 `finished`로 표시한다.
  - `EventTarget.prototype.dispatchEvent`를 감싼다. 끝난 시험의 문맥에서 **문서에 붙은 노드·document·window**로
    event를 보내면 `LeakedTestWorkError`를 던지고 기록한다. user-event와 `fireEvent`는 모두 이 경로를 쓴다.
    문서에서 떨어진 노드(끝난 시험 자신의 unmount된 트리)는 공유되지 않으므로 그대로 허용한다.
  - 파일 끝의 `afterAll`에서 기록이 있으면 어느 시험이 남긴 작업인지 적어 **파일을 실패시킨다**.
- 검증
  - 결정적 자기 시험 `packages/tooling/tests/test-isolation.test.tsx`(3개): 첫 시험이 대기 중인 click을 남기고
    끝난다. 다음 시험이 버튼을 그린 뒤 그 작업을 풀어 준다. 결과는 click 거부(`LeakedTestWorkError`), 다음 시험의
    버튼 click 수 0, 자기 click은 정상이다. 떨어진 노드로의 event는 허용된다. guard를 끄면 이 시험은
    `promise resolved "undefined" instead of rejecting`으로 실패한다(확인함).
  - M2-01ac 방식의 재현: `activity-workbench.test.tsx`의 "unmounts controlled panel content…"를 300 ms timeout으로
    줄였다(임시 편집, 되돌림). load 5–6.
    - guard 전: 8회 중 **6회** "bounds 20k records…"가 `expected …(500) to have a length of 499 but got 500`으로
      실패했다(M2-01ac 증상 그대로). 2회는 연쇄 없이 timeout 1건.

### 4.4 가림(redaction) · 검토 B1 수정

검토에서 한 probe가 CSRF token과 session id를 평문으로 남겼다. 이 probe는 `page.evaluate`에 session header를 넘겼다.
규칙이 Playwright의 직렬화 형태 `{"k":"x-csrf-token","v":"…"}`와 `returnByValue` 결과의 unescaped
`"csrfToken":"…"`를 다루지 못했다. 규칙을 형태별로 다시 짰다(`tests/identity/diagnostics/protocol-lines.ts`의
`redactionRules`). 민감 키는 cookie, set-cookie, authorization, x-csrf-token, x-workout-session-id, csrfToken,
sessionId, accessToken, refreshToken, idToken, password, code_verifier, nonce다.

| 규칙                  | 다루는 형태                                                                                                                                                    |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `key-value`           | JSON `"k":"v"`, escape된 `\"k\":\"v\"`(여러 겹 포함), script 원문 `'k': 'v'`·`k: 'v'`. CDP header 객체, 응답 본문, `returnByValue` 결과, `Runtime.evaluate` 식 |
| `serialized-property` | Playwright 직렬화 인자·결과 `{"k":"…","v":"…"}`, `{"k":"…","v":{"s":"…"}}`(escape 형태 포함)                                                                   |
| `name-value`          | cookie jar·header 배열 `{"name":"…","value":"…"}`                                                                                                              |
| `header-text`         | header 원문(`set-cookie: …`, `x-csrf-token: …`)과 `pw:api` header 로그                                                                                         |
| `cookie-pair`         | 이 앱의 cookie가 단독으로 나올 때(`document.cookie`): `workout_session=…`                                                                                      |
| `oidc-parameter`      | `?code=`, `&state=`, `nonce=`, `#session_state=`, `code_verifier=`                                                                                             |

- 단위 시험(`packages/tooling/tests/identity-diagnostics.test.ts`): 위 형태 18개가 모두 가려진다. 비밀이 아닌 값
  (`athleteId`, `{"k":"athleteId",…}`)은 남는다. 변이 시험은 규칙을 하나씩 뺀다. 그러면 그 규칙에 딸린 형태가 다시
  새어 나온다. 이렇게 6개 규칙 모두 실제로 쓰임(non-vacuous)을 확인한다.
- 종단 검증(lock 아래). 임시 spec을 썼고 실행 뒤 spec, 출력, 비밀 목록을 모두 지웠다.
  - 흐름: 로그인 → session header를 `page.evaluate`로 넘김 → `fetch('/bff/v1/session').json()`(csrfToken·sessionId
    포함)과 `document.cookie`를 돌려받음 → 일부러 실패.
  - 실제 값 6개(sessionId, csrfToken, `workout_session` cookie, OIDC code·state·nonce)를 진단 출력 전체에서 찾았다
    (`protocol-<pid>.log`, 실패 시험의 `protocol.log`·`summary.txt`·`pressure.log`). 결과는 **모두 0건**이고 가림 표시는 1,166개다.
  - 실제 캡처에 `"k":"x-csrf-token","v":"[redacted]"` 같은 직렬화 형태가 나타났다. 새 규칙이 실제로 작동했다.
- **이미 있던 노출(이번에 고치지 않음)**: Playwright `retain-on-failure`의 trace.zip에는 같은 값이 가려지지 않은 채
  들어 있다. 같은 probe의 trace에서 sessionId 10건, csrfToken 7건, session cookie 10건, OIDC state 8건·nonce 7건·code 2건이
  나왔다. 진단과 무관한 기존 설정의 동작이다. `test-results/`는 버전 관리에서 제외되어 있다. README에 적었다.
- 이전 검토 대상 run이 옛 규칙으로 남긴 진단 출력은 삭제했다.

## 5. 항목 4 · hand-off 파일 sweep

- `scripts/fixtures/identity-handoff-sweep.ts`, 하네스(`scripts/identity-e2e.mts`)가 cluster를 만들기 전에 부른다.
- 지우는 조건(모두 만족):
  - 이름이 정확히 `workout-(coaching-worker|certified-oidc)-e2e-<1–5자리 port>-<[a-z0-9-]{1,64} run id>.json`
    (run id 검증 규칙과 같다. 옛 port-only 이름, 다른 접두·접미는 대상이 아니다).
  - `lstat` 결과 일반 파일(symlink·디렉터리 제외)이고 소유자가 현재 uid.
  - writer가 없다.
    - 파일에 `harnessPid`가 있으면 그 프로세스가 없고(`kill(pid, 0)`이 ESRCH, EPERM은 살아 있음으로 본다),
      파일이 60 s보다 오래됐을 때.
    - pid가 없으면(이번 변경 전 하네스가 쓴 파일) 24 h보다 오래됐을 때.
- 임계값 근거
  - 실행 중인 하네스는 자기 pid가 살아 있으므로 나이와 무관하게 **절대 지워지지 않는다**. 다른 checkout의 동시 하네스도
    마찬가지다.
  - pid가 없는 옛 형식 파일은 살아 있는지 알 수 없다. 그래서 가장 느린 관측 전체 run(10.4 m)의 100배가 넘는
    24 h를 기다린다. `--repeat-each` 같은 긴 실행도 이 안에 든다.
  - 60 s는 막 쓰인 파일을 읽지 않기 위한 여유다. 파일 이름에 run UUID가 있어 죽은 writer의 이름을 새 하네스가 다시 쓰지 않는다.
  - 남는 위험: 죽은 하네스의 pid가 다른 프로세스에 재사용되면 그 파일은 OS가 임시 디렉터리를 정리할 때까지 남는다.
    안전한 쪽(남김)으로 틀린다.
- sweep은 예외를 던지지 않는다(검토 비차단 지적).
  - 디렉터리를 읽지 못하거나 `lstat`·읽기·삭제가 실패하면 그 항목을 건너뛴다. 예를 들어 그 사이 같은 이름이
    디렉터리가 된 경우다. 하네스는 `Identity E2E: left hand-off entry <name> in place (<code>).`를 남기고 그대로 시작한다.
  - 삭제는 `unlink`만 쓰므로 디렉터리를 지우지 않는다. ENOENT(다른 하네스가 먼저 지움)는 조용히 넘어간다.
- 하네스는 두 hand-off 파일에 `harnessPid`를 함께 쓴다. 소비자(`coaching-*` spec, oidc-certified spec)는 필요한 필드만
  검사하므로 영향이 없다.
- 검증: 단위 시험 9개(`packages/tooling/tests/identity-handoff-sweep.test.ts`). 죽은 writer 두 종류 삭제, 살아 있는 writer는
  3일 된 것도 유지, 60 s 미만 유지, pid 없는 파일 24 h 경계, 비슷한 이름 7종 무시, symlink·디렉터리 무시,
  다른 uid 무시, 실제 종료한 자식 pid 판정, 쓸 수 없는 디렉터리(EACCES)·없는 디렉터리(ENOENT)에서 예외 없이 보고. 실제 하네스: tmpdir에 죽은 pid(99991)·살아 있는 pid(1)·pid 없는 파일을 각각
  3시간 전 시각으로 두고 실행 → `Identity E2E: removed 1 stale hand-off file(s).`, 죽은 pid 파일만 사라짐.
- 범위 밖으로 남는 것: SIGKILL된 하네스의 임시 PostgreSQL cluster(`workout-identity-e2e-*`, `pg_ctl`로 띄운 데몬)도 남는다.
  이번 sweep은 hand-off 파일만 다룬다.
