## 1. 설계 근거

### 1.1 한 개의 재배치 동작

- 이전 draft store에는 인접 교환 두 개(`moveEarlier`, `moveLater`)가 있었다. drag는 한 번에 여러 칸을 옮기므로
  교환을 여러 번 부르면 되돌리기 한 번이 drag 한 번을 되돌리지 못한다. 그래서 **두 동작을 지우고
  `moveWaypoint(id, toIndex)` 하나로 바꿨다.**
  - 버튼: "n번 앞으로" = `moveWaypoint(id, n-2)`, "n번 뒤로" = `moveWaypoint(id, n)`(0-based 목표).
  - drag(pointer·keyboard): 놓은 위치로 `moveWaypoint(id, to)`.
  - 두 경로 모두 `WaypointEntries`의 `commit(id, to)`를 거쳐 이 동작을 부른다. drag는 목록 행을 직접 옮기지 않는다.
    화면의 순서는 언제나 draft의 순서다.
- **잠금 규칙(단일 위치):** `from`과 `to` 사이(양끝 포함)의 경유점은 모두 한 칸씩 움직인다. 그중 하나라도 잠겨 있으면
  `WAYPOINT_LOCKED`로 거절한다. 인접 교환에서는 이전 규칙("둘 중 하나라도 잠기면 거절")과 정확히 같다. 잠긴 경유점
  자신도, 잠긴 이웃을 넘는 이동도 거절한다.
- 제자리 놓기(`to === from`)는 변경이 아니다. revision·history가 늘지 않는다. 목록 밖 위치와 없는 id는
  `WAYPOINT_NOT_FOUND`다(이전 경계 동작과 같다. 경계 버튼은 disabled다).
- 변경은 기존 `change()`를 거치므로 revision 단조 증가, undo stack, redo 가지 삭제, 계산 결과 무효화가 그대로
  적용된다. **drag 한 번 = 되돌리기 한 번.**

### 1.2 목록 UI (`WaypointEntries`만 바꿈, 접기는 그대로)

M2-01k-c1이 나눈 구조대로 `WaypointEntries`에만 더했다. `CollapsibleWaypointList`·`WaypointListEditor`의 조립과
접기는 바꾸지 않았다. 접힌 동안 행은 `hidden`이므로 drag 대상이 없다.

- 행마다 **"n번 끌어 옮기기" 손잡이 버튼**을 더했다. 보이는 글자가 접근 가능한 이름이다(WCAG 2.5.3). 설명 문단
  (`aria-describedby`)이 pointer·keyboard 사용법과 "앞으로·뒤로 버튼도 같은 순서를 바꿉니다"를 말한다.
- **pointer**(mouse·pen·touch): `pointerdown`에서 `setPointerCapture`, `pointermove`에서 다른 행들의 세로 중점과
  비교해 놓을 위치를 계산, `pointerup`에서 놓는다. `pointercancel`·capture 상실은 취소다. 손잡이에
  `touch-action: none`을 두어 touch drag가 목록 스크롤로 새지 않게 했다.
- **keyboard(pick-up/move/drop):** 손잡이에서 Space·Enter(또는 보조기기의 활성화)로 든다 → 위·아래 방향키,
  Home·End로 위치를 고른다 → Space·Enter로 놓는다. Escape나 focus 이탈은 취소다. 든 동안 `aria-pressed="true"`.
  놓은 뒤 focus는 옮겨진 경유점의 손잡이를 따라간다 — **draft가 실제로 옮겼을 때만**(검토 B1, §9).
  - 활성화는 `click`에서 받되 `event.detail !== 0`(pointer의 click)은 무시한다. 그래서 스크린 리더의 가상 커서
    활성화도 동작하고, pointer drag의 끝 click이 keyboard 들기로 오인되지 않는다.
- **드는 동안 행은 움직이지 않는다.** 들고 있는 행에 `data-carried`, 놓일 자리에 `data-drop="before|after"` 선을
  그린다. 행을 미리 재배치하지 않는 이유: (1) keyboard로 든 손잡이가 DOM 이동으로 focus를 잃고, (2) draft가 거절할
  이동을 화면이 먼저 보여 주면 되돌릴 것이 생긴다.
- **알림(live region):** `role="status"`·`aria-live="polite"` 문단 하나(`data-testid="waypoint-move-announcement"`).
  들기, 예정 위치("3번 경유점을 1번 위치에 놓으려 합니다. 전체 4개."), 결과, 취소를 말한다. **결과 문구는 제스처가
  아니라 draft를 다시 읽어 만든다**: 옮겨졌으면 "3번 경유점을 1번 위치로 옮겼습니다. 이제 시작입니다. 전체 4개.",
  거절됐으면 "잠긴 경유점이 있어 옮기지 않았습니다. 3번 경유점은 그대로 3번입니다." 버튼 이동도 같은 `commit`을
  거치므로 같은 결과 문구를 낸다. 거절 사유는 기존 `role="alert"`("잠긴 경유점입니다…")도 그대로 말한다.
- **IME:** keyboard 처리는 손잡이의 `keydown`에만 있고 `isComposing` 또는 `keyCode === 229`면 아무것도 하지 않는다
  (preventDefault 없음). 이름 입력 칸 등 다른 control의 키는 가로채지 않는다(전역 listener 없음).
- **버튼 대안 유지:** "앞으로/뒤로" 버튼은 그대로 있고, E2E의 세 방법 중 하나가 버튼만으로 재배치·저장을 끝낸다.
- 지도 marker drag는 하지 않았다(선택 사항).
- 새 의존성 없음(lockfile 불변). planning의 dnd-kit을 들이지 않고 Pointer Events로 직접 구현했다.

## 3. E2E 설계 (`course-waypoint-drag.spec.ts`, 실제 OIDC·API·PostgreSQL·routing 포트)

1. **drag와 버튼의 동일성.** shell마다 같은 GPX로 코스를 세 개 만들고(시작·끝), 각각 같은 두 경유점을 좌표로 더해
   `[S, V1, V2, F]`로 시작한다. 셋을 각각 **pointer drag**(실제 mouse down/move/up), **keyboard drag**(Space·방향키·
   Space), **버튼만**으로 `[V2, F, S, V1]`로 바꾼다. drag는 3→1, 4→2 두 번(각 알림 문구 단언, draft revision +2),
   버튼은 네 번(+4). 각 코스에서 "경로 계산" 요청 본문의 waypoint 순서·role을 잡고, 검토·저장 뒤 API
   `GET /bff/v1/courses/:id`의 revision waypoints를 읽는다. 세 방법 모두 요청과 저장이 기대 순서·role
   (`start V2, via F, via S, finish V1`)과 같고, 서로도 같다.
2. **잠금 거절과 undo.** 2번을 잠근 뒤 pointer drag 3→1, keyboard drag 3→1, 잠긴 2번 자체의 pointer drag 2→4가 모두
   거절된다: alert 문구, 알림 문구, 행 내용 불변, draft revision 불변. 버튼 "3번 앞으로"도 같은 규칙으로 불변.
   잠금을 넘지 않는 pointer drag 4→3은 성공한다. 되돌리기 한 번이 그 drag를 통째로 되돌리고 다시 실행이 재적용한다.
   이어서 계산 요청의 `draftRevision`이 화면의 것이고 waypoints(순서·role·잠금)가 redo 결과와 같다.

## 9. 독립 검토 1차(tag `m2-01k-i-review-r1`, tree `267a24c9`) 반영

판정 REQUEST CHANGES, 차단 1건(B1)과 비차단 N1–N5.

- **B1(차단) — 거절·제자리 keyboard 놓기 뒤 focus 탈취.** `drop`이 `refocus`를 무조건 걸었는데, 거절·제자리 놓기는
  `state.waypoints`를 바꾸지 않아 effect가 소비하지 않았다. 다음 무관한 변경(이름 입력 한 글자, 잠금, 지도 고르기)에서
  focus가 손잡이로 튀었다. 수정: `commit`이 draft가 실제로 옮겼는지(boolean)를 돌려주고, 옮기지 않았으면
  `drop`이 `refocus`를 즉시 비운다. 시험: 검토자의 P1(2번 잠금 → 3번 keyboard 위로 두 칸, 거절 → "1번 경유점 이름"에
  "ab" 입력 → focus·값 유지)과 P2(Space·Space 제자리 → 이름 칸 입력 유지, 이어서 실제 이동은 focus가 따라감). 변이
  **B1-refocus-armed**(guard 제거)가 두 시험을 실패시킨다(§9 표).
- **N1 — 다른 pointer가 drag를 조종.** `Carry.pointerId`를 두고 move·up·cancel·capture 상실을 그 pointer에만 반응하게
  했다(`ownPointer`). 시험: pointer 1로 든 뒤 pointer 2의 move·up·cancel이 무시되고(표시 없음, 순서 불변, 여전히 들림)
  pointer 1이 놓는다. 변이 **N1-any-pointer**.
- **N2 — 알림이 틀린 사유를 말함.** 제자리(`to === from`)를 먼저 가르고, 옮기지 않은 나머지는 이번 호출의 거절 코드로
