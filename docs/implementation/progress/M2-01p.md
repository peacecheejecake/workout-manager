## 2. 설계 판단

### 2.1 무엇을 셀 것인가 → (c) 같은 코스에서 **대체된 답을 지운다**

- (b) "셈에서만 뺀다"는 버렸다. 서버에는 "편집기의 현재 draft"라는 개념이 없고 옛 제안은 자기
  `draftRevision`을 보내면 **여전히 저장 가능**하다(035 consume). 세지 않으면서 저장 가능하게 두면
  클라이언트가 draft 번호만 올려 저장 가능한 경로를 무한히 쥘 수 있다. 상한이 막으려던 것(개인 좌표
  누적, 한 소유자가 표를 채우는 것 — 035 주석)이 사라진다.
- (a) "새 draft가 오면 옛 draft를 무효화"를 **정밀화**했다. 무효화는 `expires_at`을 바꿀 수 없으므로
  (write-once 트리거) **삭제**다. 저장되지 않은 것은 저장할 수 없고, 좌표도 남지 않고, 자리도 없다.
- 두 가지를 더 봐야 했다.
  1. **draft 번호는 순서로 비교할 수 없다.** `revision`은 편집 세션마다 1부터 시작한다
     (`course-draft.ts` `revision: 1`). "더 오래된 draft"를 지우는 규칙이면 새로고침 뒤 새 세션의
     draft 1…4는 옛 세션의 draft 7 행을 지우지 못하고 30분 막힌다. 그래서 **같음/다름**으로 비교한다.
  2. **같은 draft의 재계산도 대체다.** 편집기는 waypoint를 건드리지 않은 재계산을 허용하고
     (`course-editor.tsx` 리뷰 주석), 경로는 `route` 하나, 탐색은 `candidates` 하나로 **덮어쓴다.**
     draft만 보는 규칙이면 같은 draft에서 탐색을 두 번 하면(4+4>5) 여전히 429다.

규칙(코스 하나, draft N의 답을 저장할 때):

- **같은 종류**의 이전 답은 draft와 무관하게 대체된다(경로→경로, 탐색→탐색).
- **다른 종류**는 같은 draft N일 때만 남는다(화면이 경로와 탐색을 나란히 보여 주는 유일한 경우).

결과적으로 한 코스는 **경로 1 + 탐색 1(후보 ≤4) = 최대 5**를 넘지 않는다. 코스당 상한 5는 이제
대체 규칙의 **불변식**이다. 코스당 검사는 방어로 남겼지만 제품 경로로는 도달하지 않는다 — §4의
비공허성에서 이 검사 하나만 떼어 낸 변이는 없다(떼어 내도 실패할 시험이 없다, 중복 방어).
테넌트 상한 20은 여러 코스를 30분 안에 편집하는 소유자가 **여전히 만날 수 있고**, 시험으로 고정했다.

**대가(명시):** 한 코스에 편집기 두 개를 열면 서로의 저장하지 않은 답을 대체한다. 밀려난 쪽은 저장
시점에 "만료되었거나 이미 저장되었습니다. 다시 계산하세요"를 본다(사실이다). 두 편집기는 저장 시
revision CAS에서 어차피 충돌한다.

같은 대가의 두 변형(검토 지적, 비차단):

- 밀려난 쪽이 **후보**를 저장하면 set이 이미 지워져 `ROUTE_CANDIDATE_SET_MISMATCH` — "고른 후보가 이
  탐색의 것이 아닙니다. 후보를 다시 생성하세요."가 나온다. 저장되는 것은 없고 행동 지시도 맞지만,
  경로 쪽 문구("만료되었거나 이미 저장되었습니다")와 설명이 다르다. 문구는 맞추지 않았다.
- 편집기가 unmount로 abort한 요청을 엔진이 이미 끝냈다면 서버가 그것을 저장하고, 새로고침·두 번째
  탭의 새 세션 route를 대체할 수 있다. 결과는 위와 같다(저장 시 재계산 안내).

### 2.2 후보 형제

같은 원리다. 쓸 수 없는 행은 자리를 잡지 않는다. 두 곳에서 닫힌다.

- 재경로 저장 경로도 **set reaper를 먼저** 부른다(소비·만료된 탐색과 그 형제 제거). 같은 draft의
  재경로는 대체 규칙이 탐색을 남기므로 이 reaper만이 형제를 치운다 — 시험
  "stops counting the siblings of a picked candidate before the next reroute".
- 다른 draft의 답은 대체 규칙이 탐색째 지운다.

### 2.3 계산 전 확인 + 저장 시 재확인

`assertRouteProposalRoom`을 추가했다. API는 코스 확인 직후, **엔진을 부르기 전에** 묻는다
(경로 1칸, 탐색은 최대 후보 수 4칸). 이 확인은 잠금 없는 읽기이고, 저장은 테넌트 잠금 안에서 reap →
대체 → **같은 함수로 재확인**한다. 확인과 저장 사이 경합은 저장이 닫는다(API 시험 "still refuses at
the store when the room went between the check and the write").

탐색 사전 확인은 최대치(4)를 요구하므로, 실제로는 후보가 적게 나와 들어갔을 탐색을 미리 거절할 수
있다. 테넌트 상한 근처에서만 생기고, 대가는 엔진 시간 0과 같은 대기다. 의도한 보수성이다.

`course_route_proposal_room`(SQL)이 "reap·대체 후에도 자리를 잡을 행"을 세고, 저장 경로는 대체 후
같은 함수를 부른다. 삭제 규칙(`supersede_…`)과 셈 규칙이 migration 한 파일에 나란히 있다.

### 2.4 사용자 문구

대체 뒤 코스당 상한은 도달하지 않으므로 사용자가 만나는 것은 테넌트 상한이다. compute·탐색
catch에 코드별 문구를 두었다:

> 저장하지 않은 경로 제안이 한도(모든 코스 합쳐 20개)에 찼습니다. 제안이 만료되는 대로 자리가 나며,
> 늦어도 30분 뒤에는 다시 계산할 수 있습니다. 저장된 것은 없습니다.

"늦어도 30분"은 참이다: 열린 제안은 모두 30분 TTL이다. "가장 오래된 것이 만료되면"은 탐색(4칸)에는
거짓일 수 있어 쓰지 않았다. `saveErrors.ROUTE_PROPOSAL_QUOTA_EXCEEDED`는 **삭제했다** — 저장은
제안을 만들지 않고, 429는 `provesNothingWasStored`가 배제해 이 표에 도달하지도 않는다(이중 사망).

### 2.5 잠금 순서

모든 저장 경로: `77206`(공유, `database.tenant`) → `0`(`tenantLock`) → **탐색 행 → 제안 행**.
`reapAndSupersede`는 set reaper → 대체(탐색 먼저, 그 cascade로 후보, 그다음 plain 제안) → proposal
reaper 순이다. 036이 정한 "탐색 먼저" 규칙을 따르며 역방향 간선을 만들지 않는다. 부수 효과: HEAD의
재경로 경로는 proposal reaper만 불러 **만료된 후보 행을 탐색보다 먼저** 지울 수 있었다. 이제 set
reaper가 먼저 돈다. (HEAD에서 이것이 교착을 낸 것을 관측하지는 않았다 — 아래 변이로 그 순서의 교착만
관측했다.)

### 4.1 잠금 순서 반복

"takes a search before its candidates when a reroute reaps it"(탐색 행을 잡은 reaper 자리와 재경로의
경합), "stays deadlock-free while stores, saves, reaping and deletion race on one tenant"(6+3 worker × 12
단계 저장·저장/소비, 코스 삭제·활동 삭제·계정 erasure 동시), 기존 deadlock 3개를 묶어 **20회 반복:
20/20 통과.** 첫 20회는 13/20이었는데, 원인은 교착이 아니라 내가 넣은 활성도 하한(`saves > 5`)이었다
— 동시 저장 대부분이 대체·CAS에 지는 것이 정상이라 `> 0`으로 낮췄다. 그 7건 모두 실패 목록(교착
포함)은 비어 있었다.

### 4.2 검토 후 보강

- **업그레이드 시험**은 supersession migration을 번호·위치가 아닌 **파일 이름**으로 찾는다
  (`migrationFileNames`, `migrate.ts`에서 `Object.freeze`한 **복사본**으로 내보냄 — 처음 판은 타입만 `readonly`이고 `migrate`가 적용하는 배열 객체 자체를 내보내, 독립 검토가 `push`로 적용 목록이 41 → 42로 바뀌는 것을 실측했다). 그 직전까지 적용 → 그것 하나만 적용해
  checksum·함수 본문·무부여를 단언 → 끝까지 migrate한 뒤 `grantCourses`(뒤 migration의 함수를 이름으로
  부를 수 있으므로). 검증: 임시 `099_placeholder.sql`과 목록 항목을 넣고 실행 **2/2 통과**, 복원 확인.
  옛 단언(`files.sort().at(-1)`)이 placeholder로 실패하는 것은 따로 돌리지 않았다(자명하나 미관측).
- **supersede 함수 안 순서** 시험 "supersedes a search before the plain route it also replaces":
  잠금 없는 연결이 set 행 → route 행 순으로 잡는 동안 다음 draft의 route를 저장한다. 검토자 R1 변이
  (함수 안에서 routes를 sets보다 먼저)로 **3회 모두 1/54 실패, `40P01 deadlock detected`**.
- **liveness 분리:** 경합 시험이 경로 저장·후보 저장을 따로 세고 각각 `> 0`.
- 위 두 시험 + 순서·교착 시험 묶음을 **새 DB에서 20회: 20/20 통과**, 거짓 실패 0.
- `course_route_proposal_room`을 `STABLE` → `VOLATILE`(`clock_timestamp()`를 읽으므로).
