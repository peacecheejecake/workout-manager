상태: **완료.** 독립 검토 승인(tree `26b3dd97`, 차단 0). 구현 기준 HEAD `2669850`, 병합 때 `4d5b9e9` 위로 rebase했다. 제품 코드는 바꾸지 않았다.
바뀐 것은 시험 9개 파일, identity 하네스 설정 3개 파일(+신규 1개), 이 문서다.

## 1. 방법

- 부하 생성기는 쓰지 않았다. 기계의 기존 부하(load 6–33)에서 반복 실행했다. identity/Playwright 실행은
  모두 harness lock 아래에서 했다.
- 과거 실패의 원문은 scratchpad에 남은 다른 노드의 실행 로그 616개(그중 vitest 요약이 있는 것 235개)에서
  찾았다. 부하가 26–45일 때의 실패를 여기서 다시 만들 수는 없었다. 그래서 원인은 다음 세 가지로 좁혔다.
  - CPU profile(`node:inspector`)과 질의별 시간 측정(RTL `screen`/`within`/user-event 래퍼, 임시 파일, 삭제함)
  - 테스트별 wall/CPU 비교(`process.cpuUsage`, 임시 setup, 삭제함)
  - 한 지점만 바꾸는 probe(지연 주입, 외부 삭제, timeout 축소)로 과거 증상을 재현한 뒤 수정본과 비교
- 브라우저 쪽 재현 시도: Chromium `Emulation.setCPUThrottlingRate` 6×/20×(렌더러만 느리게 함, 다른 에이전트에는
  영향 없음), `requestAnimationFrame` 간격과 long task 기록, trace.

## 3. 공통 결론(unit)

실패한 unit 시험은 과거 로그 순서와 CPU 사용량 순서가 거의 같다. wall/CPU 비율은 약 1이다. 기다리는 조건이
틀린 것이 아니다. jsdom 접근성 계산의 비용(문서 전체 트리 순회: 요소마다 `labels`, 버튼마다 이름 계산,
`getComputedStyle`)에 부하 배수를 곱한 값이 5 s를 넘은 것이다. 이 비용의 대부분은 시험이 문서 전체를
질의하는 방식에서 나왔다. 그래서 timeout을 늘리지 않고 질의 범위를 좁혔다. 예외는 두 가지다. route-tab은
1 s `findBy` 창에 컴파일 시간이 섞여 있었고, workbench의 500/499와 img 부재는 앞 시험이 남긴 연쇄였다.

## 4. 미해결: Playwright의 5 s 정지(planner-operations, activity-tags, dashboard-layout 원 증상)

- 확보한 원문 4건은 모두 **렌더러 쪽 단계**에서 진행 로그 없이 5 s를 채웠다.
  - aa-id4: `handle.scrollIntoViewIfNeeded` "waiting for element to be stable"
  - aa-id2: click "scrolling into view if needed"(CDP `DOM.scrollIntoViewIfNeeded`가 반환하지 않음)
  - M2-01s-id1(activity-tags): 같은 scroll 단계
  - z-id1(dashboard-layout): "visible, enabled and stable"
- 앞의 3건은 모두 `page.setViewportSize` 뒤다. aa-id4(전체 5.2 m)와 z-id1(5.8 m)은 전체 속도가 정상인 run이었다.
  그래서 기계 전체가 균일하게 느려졌다는 설명만으로는 부족하다.
- 여기서의 재현 시도는 모두 통과했다.
  - `planner-operations:129` ×12(load 18–20), trace ×4, 파일 전체 ×3(15개)
  - 렌더러 CPU 6× ×8(load 19–24), 20× ×6(load 11–18)
  - 전체 identity ×3(load 9–26)
  - 수정 뒤 반복 ×5
- 측정 결과, rAF 간격 최대 33 ms, long task(>50 ms) 0건이었다. 제품의 drop animation(dnd-kit 0.5 `runDropAnimation`)은
  250 ms로 끝나고, 시험은 그것이 끝나기(`data-dragging` 0개)를 이미 기다린다.
- 결론: 시험의 경쟁 조건도, 제품의 결함도 입증하지 못했다. 근거 없이 대기를 추가하거나 timeout을 늘리지 않았다.
- **별도 노드 제안**(M2-01ac 후속): 재발 시 원인을 가를 수 있게 identity 실행에 진단을 붙인다. 실패 시
  `DEBUG=pw:protocol`에서 멈춘 CDP 호출과 브라우저 프로세스 CPU/메모리 압박을 남긴다. 그 증거로
  (a) `setViewportSize` 직후 렌더러 쪽 대기의 Chromium headless 동작, (b) OS 스케줄링·메모리 압박 중 무엇인지
  가른다.

## 5. 남은 위험

- vitest는 timeout 난 시험 본문을 멈추지 않는다. 그래서 한 시험이 timeout 나면 뒤 시험의 DOM을 건드려
  **엉뚱한 단언 실패**로 보일 수 있다(2절의 499/500). 이번 수정은 방아쇠만 없앴다. 구조적 차단(예: 시험별
  container 조회)은 별도 작업이다.
- `course-editor.test.tsx`의 여러 시험은 wall 1.1–1.5 s 중 CPU가 0.15–0.3 s뿐이다. 약 1 s를 idle로 기다린다.
  이 노드 범위 밖이며 원인은 확인하지 않았다.
