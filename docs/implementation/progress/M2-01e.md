# M2-01e · 저장 활동 지도·차트

상태: **구현·검증 완료.** 서버에 저장된 track(M2-01c)을 S09 활동 상세의 **경로 탭**에서 다시
조회해, 자체 호스팅 배경 지도(M2-01d) 위에 실제로 그리고, 기존 chart/lap/관측 선택 저장소와
같은 선택을 주고받는 것까지 **실제 브라우저에서** 확인했다. 기준 HEAD `eb3a22d`.
계획 문서는 [map-implementation-plan.md](../map-implementation-plan.md) 3·4·5·8절이며 5절
(컴포넌트·서비스 경계와 UX)을 수용 기준으로 삼았다. `task-graph.json` 상태는 root가 소유하므로
바꾸지 않았다.

이 노드는 **저장된 track의 첫 실제 브라우저 증거**다. M2-01c는 UI를 만들지 않았고 M2-01b의
증거는 저장 전 preview였다. 그래서 아래 "실제 브라우저" 절이 이 문서의 중심이다.

먼저 이 노드가 물려받은 공백 하나를 분명히 적는다.

**`detailLink`는 파서가 채우지 않는다.** M2-01a의 `trackSampleSchema`에는 표본 →
`activity-details` 관측 순번을 가리키는 `detailLink`가 있지만, `packages/track-parsing`의 FIT·GPX
정규화는 **모든 표본에 `detailLink: null`을 넣는다**(`normalize.ts`의 `toSample`). 그래서 차트
관측과 표본을 잇는 **저장된 링크가 없다.** 이 화면은 그 사실을 숨기지 않는다. 대응은 두 쪽이
같은 원본 stream에서 가져온 **기록 시각**으로 하고, 화면에 그렇게 적는다("현재 파서는 표본에
관측 순번 링크를 남기지 않으므로 기록 시각이 같은 표본으로 대응하며, 같은 시각이 없으면 대응
없음으로 표시합니다"). 그리고 그 대응은 **그 시각의 표본도 관측도 각각 하나일 때만** 성립한다.
같은 시각이 없으면 가까운 표본을 고르지 않고 대응 없음이며, **어느 쪽이든** 같은 시각이 여럿이면
"첫 번째"를 고르지 않고 **대응하지 않는다**(두 방향이 같은 판정을 쓴다). 랩은 다르다: FIT 표본은 `lapIndex`를 싣고 있어 **저장된 대응**을
쓰고, 그것이 없는 기록(GPX)에서만 랩 구간 시간으로 떨어지며 화면이 어느 쪽을 썼는지 말한다.
파서를 고쳐 `detailLink`를 채우는 것은 **대응 digest를 바꾸므로 새 track revision**이며
M2-01c의 저장 내부에 속한다. 이 노드는 그 경계를 넘지 않았고, root에 보고한다.

## 고정한 경계

- **두 번째 Activity도, 두 번째 selection store도 만들지 않았다.** 지도는 M1-04au의
  `detail-selection.ts` 저장소를 **그대로** 읽고 쓴다. 그 저장소는 지금까지 `ActivityWorkbench`
  안에서만 만들어졌으므로, 소유자가 하나를 만들어 내려주는 `DetailSelectionProvider`를 두고
  워크벤치는 **provider가 있으면 그것을, 없으면 자기 것을** 쓴다(독립 사용 유지).
  선택은 활동/원본 identity마다 새로 시작하며, provider는 **key로 subtree를 다시 마운트하지 않고**
  render 중에 저장소를 교체한다. key를 쓴 첫 판은 `detail` 조회가 도착하는 순간 상세 영역 DOM을
  통째로 갈아치워 기존 시험 9건을 깨뜨렸다(재현함).
- **선택은 표시 인덱스가 아니라 표본 식별자로 다닌다.** 서버가 저장한 `map_path` 객체의
  `vertexSampleIds`가 정점 ↔ 표본의 유일한 출처다. 화면은 그것을 평탄화하면서 정점마다 표본
  식별자를 붙이고, 역방향 조회표를 같은 순회에서 만든다. 어떤 경로로도 "n번째 점 = n번째 표본"을
  가정하지 않는다.
- **선택한 표본도 공유 저장소에 있다.** `detail-selection.ts`에 `sample: {trackRevision, sampleId}`를
  더했다. 그래서 (1) 경로 탭을 떠나 지도 화면이 unmount돼도 같은 지점이 선택된 채로 돌아오고,
  (2) 대응하는 관측이 없는 표본도 화면 전체가 합의하는 하나의 선택이며, (3) 다른 track revision의
  선택이 이 revision에 적용되지 않는다. 첫 판은 이 선택을 지도 화면의 지역 state에 두어 탭을
  왕복하면 잃었고, 서로 다른 두 공유 선택이 모두 "대응 없음"일 때 옛 지역 선택이 계속 이겼다.
- **같은 시각에 둘이 있으면 어느 방향으로도 선택을 옮기지 않는다.** 기록 시각 대응은 **양쪽 모두
  유일할 때만** 성립하며, 그 규칙을 두 방향이 **같은 판정으로** 적용한다
  (`definiteRecordForSample`, `definiteSampleForRecord`). 한쪽이라도 여럿이면 `ambiguous`이고,
  화면은 고른 표본을 그대로 둔 채 차트 선택을 바꾸지 않으며 어느 쪽이 여럿인지 적는다.
  두 번 고쳤다. (1) 첫 판은 양쪽에서 "첫 항목"을 골랐고 독립 검토가 실제 함수로
  `0:1 → 관측 0 → 0:0`을 재현했다. (2) 두 번째 판은 표본 쪽만 검사해 **방향이 비대칭**이었다:
  관측 2개 · 표본 1개인 시각에서 차트→표본은 유일로 보고 마커를 찍는데 표본→차트는 모호로 보고
  거절해, 그 관측을 고른 뒤 자기 표본을 누르면 관측 선택이 사라졌다(독립 검토가 현재 함수로
  재현). 지금은 두 방향이 같은 답을 낸다. 결정적인 것과 옳은 것은 다르다.
- **서버 캐시는 TanStack Query, 선택은 Zustand.** 두 질의를 둔다: revision 메타데이터
  (`users/<id>/sessions/<id>/…/stored-track/<activityId>`)와 기하 객체
  (`…/stored-track-artifacts/<activityId>/<trackId>/<trackRevision>/<normalized sha>/<map_path sha>`).
  **새 revision은 새 key**이므로 이전 항목을 덮어쓰지 않는다. 응답은 어느 것도 Zustand에 복사하지
  않는다.
- **캐시 key를 믿지 않는다.** 두 파생 객체는 계약으로 검증한 뒤 **자기 provenance가 메타데이터의
  activity/source revision/track revision과 정확히 같은지** 다시 확인한다. 아니면
  `STORED_TRACK_ARTIFACT_MISMATCH`로 그리지 않는다. key만 맞으면 이웃 revision의 표본 식별자가
  이 revision의 것으로 쓰였을 자리다.
- **지도는 client-only lazy leaf 하나이고 두 shell이 같은 것을 쓴다.** M2-01b가 만든 leaf를
  `map-leaf.tsx`로 이름만 바꿔(`TrackPreviewMap` → `MapLeaf`) preview와 저장 track이 **같은 leaf**를
  각자 명시적으로 조합한다. boolean mode prop을 늘리지 않았다. 경로 패널 자체도 module scope
  `lazy()` + 전용 boundary라 지도 kit이 활동 화면의 초기 번들에 들어가지 않는다.
- **S09의 큰 그래프와 지도는 desktop에서 한 화면에 있다.** 경로 탭은 map pane·chart pane·
  요약/표본 pane 세 개로 구성되고, desktop split-pane에서 지도와 그래프가 나란히, mobile에서는
  개별 탭이다. 그래프는 구간 탭과 **같은 `DetailChart`**이며 같은 선택 저장소에 쓴다 — 차트 구현도
  선택 저장소도 두 벌이 되지 않는다. 랩·구간 선택은 마커 하나가 아니라 **그 구간이 덮는 표본들을
  지도에서 강조**하며(별도 `candidate` path), 끊긴 구간은 강조에서도 이어 붙이지 않는다.
- **mount 수명 동안 렌더러 하나.** 선택은 선택 마커만, resize는 resize만 바꾼다. `fitBounds`는
  최초 ready와 "전체 보기" 요청에서만 일어난다(활동/ revision 전환은 패널을 새로 마운트한다).
  반응형 전환도 렌더러를 다시 만들지 않는다 — 세 layout이 **하나의 DOM**이고 pane은 `display`만
  바뀐다.
- **지도가 실패해도 요약과 차트는 그대로다.** 구분하는 상태: 조회 중 / 저장된 경로 없음 /
  조회 실패 / 좌표 조회 실패 / stale(옛 원본 수정본) / GPS 없음 / 부분 기록(끊김·미표시 구간) /
  **배경 지도 불가** / **WebGL(렌더러) 불가** / 좌표 없음 / 표시 계약 위반. 뒤의 두 실패를
  가르기 위해 geo-kit에 분류된 실패를 내보내는 경로를 **추가**했다(아래 "geo-kit 추가").
- **표시 단순화가 집계를 바꾸지 않는다.** 요약은 `summarizeTrack(track)` — 표본만 읽는다.
  그려진 정점이 몇 개든 경과 시간·기기 거리·GPS 재계산 거리·페이스·평균 심박은 그대로다.
  기기 보고 거리와 GPS 재계산 거리는 끝까지 **다른 값**으로 표시한다.
- **원시 GPS·정확한 waypoint·객체 key를 로그에 넣지 않는다.** 이 노드의 코드에 로깅이 없고,
  객체 key는 애초에 클라이언트로 오지 않는다(`activityTrackRevisionSchema`에 자리가 없다).
  blob/object URL도 만들지 않는다(JSON을 transport로 받는다).
- **계정 전환·로그아웃.** 활동 화면은 athlete+session으로 remount되고 QueryClient가 unmount에서
  `clear()`된다. 늦게 도착한 이전 계정의 응답은 그 client와 함께 사라진다.

### shell 배선

- `apps/web/app/map/basemap/[...path]/route.ts` — 자체 호스팅 배경 자산의 정적 서빙.
  `BASEMAP_DIST_DIR`가 없으면 **전부 404**(opt-in). 세그먼트 검사 + 확장자 allowlist + 해석 후
  배포 디렉터리 포함 재확인, `nosniff`, 타일만 `content-encoding: gzip`.
  **캐시 정책은 두 갈래다**: 배포 디렉터리 안의 자산만 `public, max-age=604800, immutable`이고,
  배포 포인터 `current.json`은 **가변**이므로 `no-store`다. 포인터를 immutable로 캐시하면 교체·
  rollback 후에도 클라이언트가 옛 배포를 가리키고, 그 배포가 회수되면 지도가 아예 멈춘다.
  private track 객체 경로(인증 API, `no-store`)와는 경로·인증·캐시가 모두 분리다.
- `apps/web/app/basemap-config.ts` + `app/activities/page.tsx` — 서버에서 배포 pointer와
  `ATTRIBUTION.txt`를 읽어 **직렬화 가능한 descriptor**로 내려준다. 클라이언트는 환경변수도
  디스크 경로도 모른다. 페이지는 `force-dynamic`이다(빌드 시점 pointer를 굳히지 않는다).
- `apps/mobile-web/src/activities-page.tsx` + `main.tsx` — 같은 `ActivityBrowser`를 이 shell에서
  조합한다. `src/basemap.ts`가 같은 origin의 공개 pointer/attribution을 읽어 descriptor를 만든다.
  포인터는 `cache: 'no-store'`로, 배포 디렉터리의 attribution은 기본 캐시로 읽는다.
- `apps/mobile-web/vite.config.ts` — 개발·preview에서만 `BASEMAP_ORIGIN`으로 `/map/basemap` proxy.
  기존 `/bff` proxy와 같은 방식이고 Node 내장 모듈을 들여오지 않는다(browser 패키지 경계 규칙).

### 검증 배선

`scripts/identity-e2e.mts`에 `activityTracks`(repository + object storage + bounded parser)를
추가했다. 이 harness에는 track 서비스가 배선되어 있지 않아 저장 API 자체가 없었다.
`playwright.identity.config.ts`는 `.geo-build/dist/current.json`이 있을 때만 web 서버에
`BASEMAP_DIST_DIR`를, mobile-web preview에 `BASEMAP_ORIGIN`을 준다.

## 검증하지 않은 것 / 한계

- **`detailLink`는 여전히 `null`이다.** 관측 ↔ 표본 대응은 기록 시각이며 **저장된 링크가 아니다.**
  같은 시각의 표본이나 관측이 둘 이상이면 **어느 방향에서도** 대응을 성립시키지 않는다(선택이
  다른 지점으로 옮겨가지 않게). 그 대신 그 시각의 관측·표본은 서로를 가리키지 못한 채로 남는다 — 대응을
  복구한 것이 아니라 틀린 대응을 만들지 않은 것뿐이다. 시각이 서로 어긋나게 기록된 원본(예:
  상세는 초 단위, track은 밀리초)에서는 대응이 **전부 없음**이 될 수 있다. 근본 해결은 파서가
  `detailLink`를 채우는 것이고 그것은 새 track revision이다(root 보고 사항).
- **S09의 "차트 선택 → lap table 동일 구간 강조"는 이 노드에 없다.** 경로 탭에는 lap table이
  없고, 랩 표는 구간 탭에 그대로 있다. 구현한 것은 **큰 그래프 + 지도의 desktop split-pane과
  그 둘의 선택 연동, 그리고 랩·구간 선택의 지도 구간 강조**까지다. 차트에서 시간 **범위**를
  드래그로 긋는 입력도 없다(범위는 구간 탭의 UTC 입력으로 지정하며, 그 범위가 지도에서
  강조된다). 나머지는 M2-01f 이후로 이월한다.
- **차트 위 커서를 따라 마커가 움직이지는 않는다.** 점을 선택해야 마커가 움직인다. 계획 5절이
  "cursor 이동에서는 선택 마커만 갱신"을 요구하지만 hover 추적 자체를 만들지 않았다.
- **지도 pan/제스처와 페이지 스크롤 탈출을 실제 입력으로 시험하지 않았다.** 어댑터는
  `cooperativeGestures: true`를 쓰지만(M2-01d), 이 노드에서 실제 터치·휠 입력으로 확인하지 않았다.
  회전(orientationchange)도 listener만 등록했고 실기기에서 관측하지 않았다.
- **대표 장기 track의 시간·메모리·GPU 측정이 없다.** E2E track은 표본 6개다. 표본 목록은 50개씩
  페이지를 나누고 kit의 대체 목록은 200개로 묶여 있지만, 20,000점 track의 실제 렌더 시간과
  메모리는 이 노드에서 측정하지 않았다(계획 8절의 "대표 track 측정"은 M2-01d의 harness 측정이
  전부다).
- **stale 판정은 `sourceRevision` 비교 하나다.** 같은 원본 수정본에서 track만 다시 저장된 경우
  (track revision 증가)는 새 캐시 key로 새로 읽지만 "예전 것을 보고 있었다"고 알리지는 않는다.
- **배경 지도 서빙은 이 저장소에서 개발·검증용으로만 배선했다.** Next route handler는 `BASEMAP_DIST_DIR`
