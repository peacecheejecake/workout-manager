# M2-01b · 로컬 파일 viewer

상태: **구현·검증 완료.** 파일 1개 선택 → 전용 worker에서 메모리 parse → RunMap 표시 →
시작/끝·전체 보기·기본 요약까지 **실제 FIT·GPX bytes로** 동작을 확인했다. 정상/gap/no-GPS/
오류/취소와 loading·파일 교체를 각각 구분하며 **자동 upload는 없다**(이 화면에는 transport가
아예 없다). 기준 HEAD `f037694`. 계획 문서는
[map-implementation-plan.md](../map-implementation-plan.md) 3·4·5·7·8절이다.
`task-graph.json` 상태는 root가 소유하므로 바꾸지 않았다.

남은 미충족 항목은 **계획 7절의 "메모리 상한"**이다. 아래 "메모리 상한" 절에 무엇을 만들었고
무엇을 만들지 못했는지, 그리고 왜 브라우저에서는 만들 수 없는지 수치와 함께 적었다.

## parser 패키지 이전 (root 승인 후 수행)

M2-01a의 parser는 `packages/server/track-ingestion`에 있었고 브라우저에서 쓸 수 없었다.
(1) `parse.ts`가 `node:crypto`를 import해 번들이 깨지고, (2) eslint 경계 규칙이 browser
패키지의 `packages/server/**` import를 막는다. root 승인으로 다음을 수행했다.

- `git mv packages/server/track-ingestion packages/track-parsing`, 패키지 이름
  `@workout/server-track-ingestion` → **`@workout/track-parsing`**. 이 패키지를 import하던
  곳은 이동 시점에 **하나도 없었다.**
- `node:crypto` 제거. **직접 구현하지 않고** 플랫폼의 Web Crypto를 쓴다:
  `hashTrackFileSha256(bytes)`가 `crypto.subtle.digest('SHA-256', …)`로 계산한다.
  `crypto.subtle`은 비동기이므로 진입점을 둘로 나눴다.
  - `parseTrackFileWithDigest(bytes, fileSha256, options)` — **동기 코어.** 기존 호출 형태가
    전부 동기였고(호출 41곳, 대부분 `code(() => parseTrackFile(...))` 형태의 throw 검사),
    파싱은 작업 예산으로 묶여 있어 중간에 await을 끼우고 싶지 않았다. 그래서 주입 방식(b)을
    코어로 택했다.
  - `parseTrackFile(bytes, options)` — **async 편의 진입점.** 크기 검사를 먼저 하고, 해시를
    구한 뒤 코어를 부른다. worker와 브라우저는 이것 하나만 부르면 된다.
  - M2-01a의 테스트는 `tests/sync-parse.ts` 한 줄짜리 shim(테스트에서만 `node:crypto` 사용)을
    통해 **41개 호출을 그대로 둔 채** 동기 코어를 쓴다. 두 경로가 같은 결과를 낸다는 것은
    `digest.test.ts`가 단언한다.
- 패키지 tsconfig를 `bundler.json`으로 바꾸고 내부 상대 import의 `.js` 확장자를 제거했다
  (Next 번들러가 `./limits.js`를 해석하지 못한다. geo-kit에서 실제로 겪은 실패와 같다).
- 참조 갱신: root `vitest.config.ts`의 include 경로(M2-01g가 같은 파일의 routing 줄을
  수정 중이므로 **내 줄만** 바꿨다), `pnpm-lock.yaml`(`pnpm install`로 재생성),
  `docs/implementation/progress/M2-01a.md`의 패키지 신원과 `parse.ts` 설명(내용은 보존하고
  이전 사실만 덧붙였다). `packages/contracts`는 옛 이름을 참조하지 않아 변경 없음.
- 오류 코드가 25개 → 26개가 됐다(`TRACK_DIGEST_UNAVAILABLE`: 런타임에 Web Crypto가 없을 때).

## 고정한 경계

- **preview는 저장이 아니다.** `LocalTrackPreview`는 `transport`를 **받지 않는다.** fetch·
  storage·업로드 경로가 이 파일에 없다. 실브라우저 E2E는 파싱 중 `/bff/v1/activit*` 요청이
  **0건**임을 단언한다. 화면에는 `local-file` provenance와 파일 해시만 있고 **Activity ID를
  만들지 않는다**(계약의 `localFileProvenanceSchema`가 strictObject라 애초에 불가능하다).
- **parse는 전용 worker에서만 한다.** 요청마다 worker 하나를 만들고 **성공·실패·마감시간·취소·
  파일 교체 모든 경로에서 `terminate()`** 한다. 실브라우저에서 parse 1회당 (MapLibre worker가
  아닌) worker가 **정확히 1개 생성되고 1개 종료**되는 것을 확인했다.
  worker를 만들 수 없는 런타임에서는 **조용히 메인 스레드로 내려가지 않고**
  `PREVIEW_PARSER_UNAVAILABLE`로 실패한다. 메인 스레드 parse에는 호출자 마감시간도 없고 동기
  파싱 중에는 취소 버튼도 눌리지 않아, §7의 완화 수단(격리 + 강제 종료)이 그대로 사라지기
  때문이다. `createInlineTrackParser`는 그것을 **명시적으로** 원하는 호출자(테스트, 비브라우저
  호스트)에게만 남아 있다.
- **해시와 파싱은 같은 bytes를 본다.** `parseTrackFile`이 크기 검사 뒤 입력을 한 번 복사하고,
  그 복사본을 해시하고 그 복사본을 파싱한다. 해시는 비동기라서 복사가 없으면 호출자가 그 사이에
  버퍼를 고쳐 `fileSha256`이 다른 내용을 가리킬 수 있다 — 로컬 preview provenance 전체가 이
  동일성에 기대고 있다.
- **해시는 파일 범위만 본다.** 공개 helper `hashTrackFileSha256`도 안에서 `new Uint8Array(bytes)`로
  정확한 범위를 복사한 뒤 그 buffer를 넘긴다. `bytes.buffer`나 `Buffer.prototype.slice()`의
  결과(복사가 아니라 **뷰**다)를 넘기면 Node의 8 KiB pooled `Buffer`에서 파일이 아니라 pool
  전체를 해시하게 된다. `Buffer`는 `Uint8Array`의 하위 타입이라 이 helper에 그대로 들어온다.
- **worker 응답을 신뢰하지 않는다.** 응답은 `parsedTrackFileSchema.safeParse`를 통과해야
  화면에 들어오고, 실패하면 `PREVIEW_REPLY_INVALID`다. worker로 보내는 요청도 worker 쪽에서
  zod로 검증한다. 다른 `requestId`의 응답은 무시한다.
- **오류는 코드만 건넌다.** `^[A-Z][A-Z0-9_]{2,63}$` 형태의 코드만 경계를 넘고 메시지·스택·
  파일 내용은 넘지 않는다. 화면은 코드→한국어 문구 표를 갖고 모르는 코드는 일반 문구+코드로 쓴다.
- **확장자·MIME을 신뢰하지 않는다.** 화면은 `file.name`/`file.type`을 판단에 쓰지 않는다.
  E2E는 **`notes.txt`라는 이름의 FIT 파일**이 `fit-track-v1`로 파싱되는 것과,
  `track.gpx`라는 이름의 ZIP이 `TRACK_ARCHIVE_REJECTED`로 거절되는 것을 확인한다.
- **상한은 읽기 전에 본다.** 선언 크기가 `trackLimits.fileBytes`(32 MiB)를 넘거나 0이면 한
  byte도 읽지 않고 거절한다.
- **파일명은 렌더 전에 소독한다.** C0/C1·bidi override/isolate·`<`/`>`를 제거하고 256자로 자른다.
- **결손을 직선으로 잇지 않는다.** segment 경계마다 break가 생겨 선이 끊긴다. 좌표 없는
  sample은 정점이 되지 않지만 삭제되지도 않고 측정값을 유지하며, 화면이 그 개수를 알린다.
- **표시 정점 → 원본 sample.** `vertexKeys`가 `sampleId`이고, 선택하면 화면이 그 sampleId의
  시각·심박을 보여 준다(E2E에서 `0:0`/`0:4` 확인). 표시 인덱스를 원본 인덱스로 쓰지 않는다.
- **거리를 섞지 않는다.** 기기 보고 거리와 GPS 재계산 거리를 따로 표시하고, 평균 페이스는
  **기기 거리로만** 계산한다. 기기 거리가 없으면 `미확인`이다(실브라우저에서 GPX는 기기 거리
  없음 → 페이스 미확인, FIT은 session 거리 250 m 표시).
- **여러 기록이면 선택 전에는 아무것도 그리지 않는다.** 기록이 2개 이상인 파일은
  `trackIndex: null`로 시작한다. 요약도 지도도 렌더러도 만들지 않고 선택 UI만 보여 준다.
  첫 기록을 임의로 고르면 그것이 그 파일의 유일한 기록인 것처럼 보이기 때문이다.
- **지도 leaf에는 error boundary가 있다.** 어댑터 실패는 `onStatusChange`로 돌아오지만
  **lazy chunk 로딩 실패는 어댑터에 닿지도 못하고** 위로 전파돼 요약까지 같이 날린다. 경계를
  leaf에 두어 지도만 사라지고 요약·표본 목록은 남는다.
- **모든 표본은 지도 없이도 선택할 수 있다.** geo-kit의 좌표 목록은 200개에서 멈추므로(긴
  트랙에서 문서에 수만 개 컨트롤을 만들지 않기 위한 kit의 상한), 모듈이 50개씩 페이지로 넘기는
  `표본 목록`을 따로 제공한다. 선택된 정점이 있으면 그 정점이 있는 페이지를 보여 준다.
- **fitBounds는 세 순간에만.** 최초 ready, 기록 전환, `전체 보기`. 선택 변경은 fit하지 않는다.
  지도 instance는 mount당 하나이고 데이터 갱신으로 다시 만들지 않는다.
- **boolean mode props 대신 조합.** shell이 parser·basemap·renderer factory를 주입한다.
  지도는 `lazy()`로 부르는 client-only leaf다.
- **계정·세션 수명.** `key={athleteId:sessionId}`라서 계정 전환이 remount이며 상태·결과·진행 중
  요청이 함께 사라진다. unmount에서 `AbortController.abort()`로 진행 중 parse를 끊는다.
- **브라우저 저장소에 쓰지 않는다.** 이 화면은 localStorage/sessionStorage/service worker에
  아무것도 쓰지 않는다. 실브라우저에서 `track`을 포함하는 localStorage 키 0개, service worker
  등록 0개를 관측했다(기존 `workout:private:account-scope` 키는 platform이 만든 것이다).
- **blob URL을 만들지 않는다.** `arrayBuffer()`(없으면 `FileReader`)로 bytes만 읽는다.

## 메모리 상한(계획 7절 이월 항목)

M2-01a는 "실제 메모리 상한과 초과 시험"을 b/c로 이월했다. 결과는 다음과 같다.

**한 것**

- parse를 **요청당 전용 worker**에서 돌리고 성공·실패·마감시간·취소·파일 교체 모든 경로에서
  `terminate()`한다. 실브라우저에서 worker 1개 생성/1개 종료를 확인했다. worker가 사라지면
  그 힙도 사라지므로 **수명 상한**은 실재한다.
- 호출자 쪽 **wall-clock 마감시간(기본 30초)**. 파서 예산은 charge 지점에서만 동작하므로
  그 밖에서 멈추는 경우를 덮지 못한다. 마감시간은 terminate로 끝낸다.
- 파일 크기를 bytes를 읽기 **전에** 계약 상한(32 MiB)과 비교한다.
- **예산이 메모리 상한이 아님을 시험으로 고정했다.** 같은 bytes(약 5.1 MB, 60,000점 GPX)·같은
  코드에서 `--max-old-space-size=1024`는 `TRACK_OUTPUT_TOO_LARGE`를 돌려주고 종료 코드 0,
  `--max-old-space-size=32`는 **V8 OOM으로 종료 코드 134**가 된다
  (`heap-ceiling.test.ts`). 즉 상한은 런타임이 거는 것이고 파서 회계는 그것을 대신하지 못한다.
- 부수적으로 확인한 것: 계약 기본 한도 안에서는 **정규화 출력 한도(8 MiB)가 먼저 걸린다.**
  120,000점(약 10.2 MB) GPX도 힙 1 GB에서 `TRACK_OUTPUT_TOO_LARGE`로 끝난다.

**하지 못한 것(명시)**

- **브라우저 worker에는 heap ceiling을 걸 수 없다.** 표준 API가 없고,
  `measureUserAgentSpecificMemory()`는 cross-origin isolation이 필요한 Chromium 전용이라
  제품 기준으로 삼지 않았다. 따라서 브라우저 쪽 보장은 **"상한"이 아니라 "격리 + 종료"**다.
- **worker OOM 시의 사용자 경험은 시험하지 않았다.** 브라우저가 worker를 죽이면 현재 구현은
  `error` 이벤트를 `PREVIEW_WORKER_FAILED`로 보고하도록 되어 있으나, 실제 OOM으로 죽는
  worker를 만들어 그 경로를 관측하지는 않았다.
- **"메모리가 N MB를 넘지 않는다"는 주장은 하지 않는다.** 관측된 수치는 Aside 실브라우저에서
  5점짜리 트랙 기준 `usedJSHeapSize` 14 MB 하나뿐이며 대표 장기 트랙 측정이 아니다.
- 따라서 계획 7절의 "메모리 상한 + 경계/초과 시험"은 **서버(worker/프로세스) 쪽에서 M2-01c가
  마무리해야 한다.** 그쪽에는 `resourceLimits`/cgroup 같은 진짜 상한 수단이 있다.

## Peer review 대응 (base `f037694`)

독립 peer review가 blocking 5건·non-blocking 3건을 **모두 재현된 결함**으로 보고했고 전부
반영했다. 번호는 검토 보고의 번호다.

1. **해시와 파싱이 다른 bytes를 볼 수 있었다.** async 진입점이 원본 버퍼를 해시한 뒤 그 원본을
   파싱해서, 호출 직후 경도를 127→128로 바꾸면 좌표는 128인데 `fileSha256`은 이전 파일의
   것이었다(검토자 재현, 나도 재현). 크기 검사 뒤 입력을 한 번 복사해 **그 복사본을 해시하고
   그 복사본을 파싱**하도록 고쳤다. 새 테스트가 그 변조 시나리오를 그대로 재현하며, 복사를
   빼면 다시 실패하는 것도 확인했다.
2. **worker 실패 시 조용한 메인 스레드 강등.** 취소도 마감시간도 없는 경로로 내려가면서
   §7 완화 수단을 스스로 버리고 있었다. 이제 shell 경로는 **worker 전용**이고 실패는
   `PREVIEW_PARSER_UNAVAILABLE`이다. `createInlineTrackParser`는 명시적 호출자(테스트)용으로만
   남고, jsdom 테스트는 이제 그것을 **직접** 주입한다. worker 없는 런타임에서 화면이 실패를
   보여 주는 테스트 2건을 추가했다.
3. **다중 기록 파일이 선택 전에 첫 기록을 그렸다.** `trackIndex`를 `number | null`로 바꿔
   기록이 2개 이상이면 `null`로 시작한다. 선택 전에는 요약·지도·렌더러가 전혀 만들어지지
   않는다(테스트가 `created === 0`·`fits === 0`까지 단언). 이름과 실제가 어긋났던 기존
   테스트는 두 개로 쪼갰고, 증거표 행도 그에 맞게 고쳤다.
4. **지도 leaf에 error boundary가 없었다.** lazy chunk 거절이 어댑터의 unavailable 처리에
   닿지 못하고 위로 전파됐다. `track-preview-map.tsx`로 leaf를 분리하고 boundary를 넣었다.
   회귀 테스트는 실패하는 렌더러를 주입해 요약과 버튼이 남는지 보며, boundary를 빼면
   `CHUNK_LOAD_FAILED`로 실패하는 것을 확인했다.
5. **202점을 넘는 트랙의 표본에 키보드로 닿을 수 없었다.** kit 목록(200개 상한) 말고 모듈이
   50개씩 페이지로 넘기는 `표본 목록`을 추가했다. 260점 트랙에서 kit 목록이 200개에서 멈추는
   것과, `마지막 묶음` → Space로 `0:259`까지 선택되는 것을 테스트로 고정했다.
6. **(non-blocking) 렌더 증거가 준비 상태였다.** `지도 표시 중` 대신 렌더러가 보고한 경로
   feature 수를 화면에 쓰고 E2E가 그 값이 0이 아님을 단언한다. 이 과정에서 5점 한 구간 트랙이
   **3**으로 보고되는 것을 관측했다(타일 경계로 쪼개진 feature 수). 문구를 그에 맞게 고치고
   "구간 수"라고 주장하지 않는다.
7. **(non-blocking) 업로드 부재 단언이 한 경로만 봤다.** 이제 파싱 동안 **GET이 아닌 요청이
   어떤 URL로도 0건**임을 단언한다.
8. **(non-blocking) 로그아웃·`pagehide`/BFCache 미검증**을 "검증하지 않은 것"에 명시했다.

### 2차 검토 대응

1차의 5건은 fixed로 확인됐고, **새 blocking 1건**과 non-blocking 3건을 반영했다.

1. **같은 provenance 결함이 공개 helper에 남아 있었다.** `hashTrackFileSha256`이
   `bytes.slice().buffer`를 넘기고 있었는데 `Buffer.prototype.slice()`는 **복사가 아니라 뷰**라,
   Node가 pool에서 떼어 주는 `Buffer`(검토자 재현: 8192 B pool의 offset 2856에 있는 124 B 입력)를
   받으면 파일이 아니라 pool 전체를 해시했다. 그 결과를 동기 `parseTrackFileWithDigest()`에
   넣으면 방금 고친 "해시와 내용이 다른" 결함이 그대로 재현된다. helper 안에서
   `new Uint8Array(bytes)`로 정확한 범위를 복사하도록 고치고 pooled `Buffer` 회귀 시험 2건을
   추가했다. 고치기 전 코드로 되돌리면 그 시험이 실제로 실패한다.
2. **(non-blocking) 지도 실패 보고가 영구히 남았다.** sticky boolean을 없애고, 실패 문구를
   **error boundary 자신의 상태**로 렌더한다(경계가 다시 mount되면 문구도 사라진다). 어댑터
   실패 보고는 `rendered`와 같은 방식으로 **geometry revision에 묶었다**. 첫 파일에서 렌더러가
   던지고, 좌표 없는 파일을 거쳐, 세 번째 파일에서 렌더러가 정상 동작하면 문구가 사라지는
   테스트를 추가했다(sticky 플래그를 되살리면 실패한다).
3. **(non-blocking) 문서가 삭제된 구현을 설명하고 있었다.** "main-thread 강등 경로" 항목을
   현재 구현(테스트가 `createInlineTrackParser`를 명시적으로 주입)으로 고쳤다.
4. **(non-blocking) 계정 전환 주장 과장.** `abort()`·`destroy()` 호출을 단언하지 않는다는 점을
   "검증하지 않은 것"에 명시했다. 테스트가 단언하는 것은 화면이 비워진다는 것까지다.

검토자의 feature 수 판단(비영(非零) 단언은 타일 분할 때문에 타당하지만 기하 정확성을 증명하지는
않는다)에 동의하며 문구를 그대로 유지했다.
