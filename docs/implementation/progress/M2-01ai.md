## 1. 설계 근거

### 1.1 F1 — parse를 child process로

- **문제.** M2-01k-f는 parser를 `worker_threads` Worker(`resourceLimits`)에서 돌렸다. 한도 근처에서 native
  structured-clone 할당(`ValueDeserializer`)이 Node의 near-heap-limit 유예를 다 쓰면 V8이 **프로세스 전체**를
  abort한다(exit 134). worker와 API가 한 프로세스라서 API가 같이 죽는다.
- **선택: 한 parse에 child process 하나(`child_process.fork`).** supervisor를 따로 두지 않았다. V8 abort는 그
  isolate가 속한 프로세스를 끝낸다. parse가 자기 프로세스에 있으면 abort가 끝내는 것은 그 child뿐이다. 다른
  경계(별도 supervisor 프로세스, 상주 pool)는 한 겹을 더 두지만 같은 성질을 더 많은 수명 관리로 얻는다.
- **ceiling.** child는 `--max-old-space-size=<ceiling>`을 **마지막 CLI 옵션**으로 받는다. 환경은 host에 값이
  있을 때의 `TMPDIR` 하나뿐이라(검토 NB-7) `NODE_OPTIONS`도 없다. 부모의 heap 옵션은 이제 parse에 닿지 않는다
  (worker에서는 process-global이었다).
  - **host 자신의 heap 옵션(검토 NB-2).** 처음 판은 상속받은 `process.execArgv`에 heap 옵션이 있으면 생성자에서
    `TrackParseRuntimeConflictError`를 던졌다. 그래서 `node --max-old-space-size=2048 --import tsx …`로 띄운
    API는 부팅하지 못했다. 이제 상속분에서는 heap 옵션을 **걸러 내고**, 호출자가 `execArgv`에 **명시적으로**
    넣은 heap 옵션만 거부한다. 시험: `--max-old-space-size=1024` host가 기본 옵션으로 parse하고, 32 MiB
    ceiling에서는 여전히 `TRACK_PARSE_MEMORY_EXCEEDED`다.
    그래도 적용 한도는 **검증한다**: child가 첫 메시지로 V8이 준 `heap_size_limit`을 보고하고, host는 그 값이
    `ceiling + 192 MiB`(측정값, worker와 child가 16–1024 MiB 전 구간에서 같다) 이하일 때만 bytes를 보낸다.
    넘으면 `TRACK_PARSE_CEILING_NOT_APPLIED`.
- **메모리 초과 판정.** child가 V8 heap 한도로 죽으면 stderr에 `… JavaScript heap out of memory`를 쓰고
  abort한다. host는 child stderr를 **보관하지 않고** 이 marker만 찾는다(청크 경계용으로 marker 길이만큼의 꼬리만
  들고 간다). 판정은 `close` 이벤트에서 한다. `close`는 stderr가 끝난 뒤에 오므로 abort 직전의 보고를 이미 읽은
  상태다. marker가 있으면 `TRACK_PARSE_MEMORY_EXCEEDED`, 없이 reply 전에 끝나면 `TRACK_PARSE_WORKER_FAILED`.
  stderr 내용은 로그나 응답으로 나가지 않는다.
  - **이 판정이 잡지 못하는 메모리 초과(검토 NB-3).**
    - OS OOM-killer가 child를 `SIGKILL`로 끝내면 stderr 표지가 없다. 그 경우는 `TRACK_PARSE_WORKER_FAILED`
      (API에서는 503)로 보고된다. 메모리 초과라고 부르지 않는다.
    - heap 밖 메모리는 `--max-old-space-size`가 막지 않는다. 입력 복사본(최대 32 MiB), IPC 직렬화 버퍼,
      Buffer가 여기에 든다. 이것을 묶는 것은 배포의 컨테이너/cgroup 메모리 한도다.
    - 후속 선택지: 예상하지 못한 `SIGKILL`·`SIGABRT` 종료를 별도 코드로 나누는 것. 이 노드에서는 하지 않았다.
- **계약 유지.** 공개 API(`createBoundedTrackParser`, `parse`, `parseFile`, `active`), 옵션, 오류 코드
  (`trackParseHostFailureCodes` 전부, 이름 포함 `TRACK_PARSE_WORKER_FAILED`), deadline(부모 wall-clock),
  동시성(초과는 대기 없이 `TRACK_PARSER_BUSY`), reply의 contract 검증, 코드만 경계를 넘는 규칙이 그대로다.
  추가한 것은 `processIds()`(운영·시험용)와 `close()`(shutdown) 둘이다.
- **bytes 전달.** IPC를 `serialization: 'advanced'`(V8 serializer)로 연다. bytes는 **view 범위만** 이진 복사
  한 번으로 넘어간다(base64·JSON 없음, backing buffer 전체가 아님). worker 때는 부모가 범위를 복사한 뒤
  transfer했다. 이제는 복사본을 만들지 않고 호출자의 view를 직렬화한다. reply는 worker 때와 같은 structured
  clone이다.
- **동시성 = 프로세스 수.** fork는 admission(`active < concurrency`) 뒤에만 한다. slot은 child의 `exit`를
  **기다린 뒤에** 푼다. 그래서 `active()`는 살아 있는 parse 프로세스 수보다 작아지지 않는다. API는 parser 두
  개(course import, activity track)를 만들고 각자 한도 2다. 프로세스는 최대 4개다(§6 열린 항목).
- **정리(cleanup)의 세 겹.**
  1. 모든 경로(성공, parser 실패, 메모리 초과, deadline, 취소, shutdown)에서 `finally`가 `SIGKILL`을 보내고
     `exit`를 기다린다.
  2. host가 JS로 종료하면(`process.exit`, uncaught exception) 모듈 단위 `exit` hook이 살아 있는 child를
     `SIGKILL`한다. 리스너는 프로세스당 하나다.
  3. host가 exit hook 없이 죽으면(SIGKILL, V8 abort) child의 IPC 채널이 닫힌다. child는 `disconnect`에서
     바로 나가고, 보낼 수 없는 reply도 나감으로 끝난다. **한계:** parse가 동기 CPU 구간에 있으면 `disconnect`는
     다음 yield까지 처리되지 않는다. 그 구간의 상한은 parser 자체 예산(5 s)이다.
  - API shutdown: `configured.ts`의 `close` hook이 두 parser의 `close()`를 부른다. 진행 중 parse는
    `TRACK_PARSE_CANCELLED`로 끝나고 child는 kill된다. 이후 호출도 `TRACK_PARSE_CANCELLED`다.
- **입출력 동일성.** parse 본체를 `parse-request.ts`의 `answerParseRequest`로 옮겼다(기존 `parse-worker.ts`의
  로직 그대로, `ArrayBuffer` 대신 `Uint8Array` 범위를 받는다). child(`parse-child.ts`)는 IPC 배선만 한다.
  같은 함수를 시험에서 in-process 기준으로 부를 수 있다.

### 1.2 N-g — 부하 높은 표본은 설명할 수 있는 초과만 보류한다

- **결정(검토 NB-1 반영판).** 시간 예산을 넘었을 때, 그 지표의 허용 부하(`baseline.loadAverage1m.max`)보다
  높은 부하에서 잰 표본을 "부하 표본"이라 한다. 다음 둘 중 하나면 `failed`다.
  - **전체 n의 최선 경우:** 부하 표본을 모두 가능한 최선값 0 ms로 바꿔도 통계가 예산을 넘는다. 표본 수는
    그대로 n이다.
  - **허용 표본만:** 허용 표본이 `minimumSamples` 이상이고, 그것만의 통계가 예산을 넘는다.
  - 둘 다 아니면 `inconclusive`다. 부하 표본이 초과를 설명할 수 있다는 뜻이고, 허용 부하에서 다시 돌려야 한다.
  - 메모리·크기는 전과 같이 부하와 무관하게 `failed`. 전체 통계가 예산 안이면 부하와 무관하게 `passed`.
    부하는 여전히 통과를 만들지 못한다.
- **첫 판의 구멍(NB-1).** 첫 판은 "허용 표본만"의 규칙뿐이었다. probe와 spec의 기본은 20표본이고 p95의
  `minimumSamples`도 20이다. 그래서 부하 표본이 **하나만** 섞여도 허용 표본이 19개가 되어 판정을 못 했다.
  예산의 3배라도 `inconclusive`였다. 최선 경우 규칙은 n을 줄이지 않으므로 이 경우를 `failed`로 잡는다.
  시험("20표본 중 하나가 부하 표본, 모두 3배 → failed")과 변이 NB1-M1이 있다.
- **이유.** M2-01k-f 규칙은 "표본 하나라도 허용 부하 초과 + 예산 초과 → inconclusive"였다. 그러면 부하가
  높은 순간의 표본 하나가 실제 회귀를 가렸다.
- 체크인된 run 3은 새 규칙에서도 같은 5개 지표가 `inconclusive`다. 해당 지표의 표본이 모두 부하 표본이라
  최선 경우가 0이고, 허용 표본도 0개다.

### 3.1 생존(F1) — 실제 host 프로세스, M2b/M2d 조건

10개(16, 24, 32, 40, 44, 48, 52, 56, 64, 96 MiB) × 복사본 2종(8 = M2d, 10 = M2b) × 2 run = 40 parse를 하고,
마지막에 기본 ceiling으로 한 번 더 parse한다. 입력은 대표 장기 track(20,000 sample FIT)이다.

| host | exit | rung parse | `TRACK_PARSE_MEMORY_EXCEEDED` | `ok` | 그 밖 | 마지막 parse |
| ---- | ---- | ---------- | ----------------------------- | ---- | ----- | ------------ |
| 1    | 0    | 40         | 36                            | 4    | 0     | ok           |
| 2    | 0    | 40         | 34                            | 6    | 0     | ok           |
| 3    | 0    | 40         | 35                            | 5    | 0     | ok           |
| 4    | 0    | 40         | 35                            | 5    | 0     | ok           |
| 5    | 0    | 40         | 34                            | 6    | 0     | ok           |

- 합계 200 parse, 174회 child가 V8 heap 한도로 abort(host는 `TRACK_PARSE_MEMORY_EXCEEDED`), 26회 `ok`,
  다른 결과 0회. **5개 host 모두 exit 0.**
- rung별: 복사본 10개는 16–64 MiB에서 10/10 초과, 96 MiB에서 9/10 ok. 복사본 8개는 16–48 MiB에서 10/10 초과,
  52 MiB 1/10 ok, 56 MiB 2/10, 64 MiB 4/10, 96 MiB 10/10 ok. 44–48 MiB가 M2-01k-f에서 host가 죽던 구간이다.
- 대조: 같은 driver를 worker thread 구현(base `2a24749`)으로 돌리면 복사본 10개 · 44 MiB에서 host가
  `FATAL ERROR: Reached heap limit`로 exit 134(MA1). 이 노드의 초기 확인(scratch driver, 같은 preload)에서도 base
  구현은 5번 실행(복사본 8개 2번, 10개 3번) 모두 44 또는 48 MiB rung에서 host가 exit 134로 끝났다.
- 로그: 요약 줄은 `.turbo/m201ai-logs/RECOVERED-FROM-SESSION.txt`(§5의 로그 유실 참고).

### 3.2 출력 동일성

base `2a24749`의 worker host와 이 노드의 child host에 같은 입력 9개를 넣어 결과를 비교했다(일회성 비교
스크립트, 출력은 `.turbo/m201ai-logs/RECOVERED-FROM-SESSION.txt`). 입력: GPX 5점·2,000점·분할 50점, trk+rte+wpt GPX의
`parseFile`과 `parse`, 장기 track FIT의 `parse`와 `parseFile`, 없는 selection, track이 아닌 파일.

- 9개 모두 JSON 문자열이 바이트 단위로 같고, `isDeepStrictEqual`이 참이고, `v8.serialize` 바이트까지 같다
  (`ALL_IDENTICAL`). 장기 track `parse` 결과 JSON은 6,336,300 B, SHA-256 앞자리 `843a7d43beb2b53c`.
- 저장소 시험(`parse-process.test.ts`)은 child host 결과를 같은 함수의 in-process 결과와 비교한다(JSON 바이트 +
  `isDeepStrictEqual`). `v8.serialize` 비교는 시험에 넣지 않았다. in-process 값과 structured clone을 거친 값은
  정수 값을 V8이 small integer로 들고 있는지 double로 들고 있는지가 달라 바이트가 달라진다(값은 같다). worker와
  child는 둘 다 structured clone이라 위의 비교에서는 그것까지 같았다.

  하나로 합치면 기능 간에 `TRACK_PARSER_BUSY`가 번지므로 이 노드에서는 바꾸지 않았다.
- **후속(검토 NB-5): parse 프로세스 메모리 예산.** `api.processPeakRssMiB`는 이제 parse 메모리를 포함하지
  않는다. parse가 child process로 옮겨 갔기 때문이다. 예산 1,100 MiB는 그대로이고 재기준선도 하지 않았다.
  parse 프로세스 RSS는 `details.parseProcessRss`로 기록만 한다(판정 run에서 172·170 MiB). 후속 노드에서:
  1. `parseProcessRss`를 지표로 올려 기록 전용 기준선 run 3회를 돌린다.
  2. 그 기준선에서 child RSS 예산을 정한다.
- 메모리 초과의 다른 경로(§1.1 NB-3): OS OOM-killer의 `SIGKILL`은 `TRACK_PARSE_WORKER_FAILED`로 보고된다.
  heap 밖 메모리는 컨테이너 한도가 묶는다. 예상하지 못한 `SIGKILL`·`SIGABRT` 종료를 별도 코드로 나눌지는 후속
  결정이다.
- worker 지표의 id(`worker.*`)는 이력과 기준선 연결을 위해 그대로 두고 설명만 바꿨다. 기준선은 worker 시절 값이다.
