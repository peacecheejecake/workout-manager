## 1. 결정과 근거

### 1.1 graph 교체: blue/green + API 신원의 단일 전환 (유지보수 창이 아님)

**결정.** 서빙 중인 엔진은 제자리에서 재시작하지 않는다. 새 graph는 **두 번째 엔진**(다른 loopback port)으로
띄우고, API는 "활성 배포" 참조 하나 — **검증된 pin과 엔진 endpoint를 한 쌍으로** — 를 동기 대입 한 번으로
바꾼다(`RoutingDeploymentSwitch`, `apps/api/src/routing-deployment.ts`). rollback은 메모리에 검증된 채
남겨 둔 이전 배포로 같은 대입을 되돌리는 것이다.

**유지보수 창을 고르지 않은 이유.**

- 창을 두면 그동안 모든 계산이 실패한다. M2-01k round 1의 두 단계 절차(엔진 재시작 → API 재배포)가 바로 그
  창이었고, 그 사이 요청은 전부 `graph_mismatch`였다(§3 of M2-01k). 이 노드의 probe는 전환·rollback 중에도
  **실패 0건**을 관측했다(§3.1).
- blue/green은 `/info`↔`/route` 사이의 교체 창(M2-01g가 남긴 잔여 창)을 **절차로** 닫는다. 한 엔진은 서빙 중에
  graph를 바꾸지 않으므로 한 endpoint 뒤의 graph가 두 요청 사이에 바뀔 수 없다. 운영자가 규칙을 어기면 매
  계산의 `/info` 대조가 여전히 잡는다.
- 자원 비용은 교체하는 동안 엔진 두 벌이다. 실측 RSS는 기동 직후 blue 275 MiB, green(중심부 clip) 242 MiB였다.

**지켜지는 것(프로세스 하나 안에서).**

1. 한 계산은 활성 배포를 **한 번** 읽고, 그 배포의 엔진에게만 신원과 경로를 모두 묻는다. "섞인 상태가 없다"는
   **계산 하나 단위**의 성질이다. 여러 계산으로 이루어진 목표 거리 후보 탐색이 전환을 가로지르면, 앞 시도는 A,
   뒤 시도는 C로 계산되어 **한 탐색 결과에 두 graph의 후보가 섞일 수 있다.** 그래도 안전하다. 후보마다 자기
   계산 기록(`computation.graph`)을 지니고, 저장(`pick-candidate`)은 고른 후보의 graph를 `acknowledgedGraph.next`와
   대조해 다르면 거절하며, 저장된 revision에는 실제로 계산한 graph가 남는다. 조용히 다른 graph로 저장되는 경로는 없다.
2. 전환 전에 후보를 디스크에서 검증하고(graph·jar·profile 해시, 기동과 같은 `loadRoutingDeployment`), 그 엔진의
   `/info`가 pin과 정확히 같아야 한다(`verifyEngineIdentity`). 실패하면 아무것도 바뀌지 않는다.
3. 활성 엔진과 같은 origin으로의 전환은 `ROUTING_SWITCH_SAME_ENGINE`으로 거절한다(제자리 교체는 원자적이지 않다).
4. 진행 중 계산은 시작한 엔진에서 끝나고 그 신원을 기록한다. 그래서 blue는 drain될 때까지 끄지 않는다.
5. rollback 대상 엔진이 **아직 같은 graph를 서빙 중**이어야 한다. 아니면 거절하고 현재 배포를 유지한다.
6. tenant admission은 배포 사이에 공유된다(전환이 한도를 초기화하지 않는다).
7. 엔진 host allowlist는 기동 설정이다. 전환 파일은 그것을 담을 수 없다(넓힐 수 없다).
8. 전환은 직렬화된다(동시 두 전환이 교차하지 않는다).

**지켜지지 않는 것.** 원자성은 API **프로세스 하나 안에서**다. 인스턴스가 여럿이면 차례로 옮겨 가고, 그동안
일부는 blue·일부는 green으로 각각 일관되게 답한다(revision에 graph가 기록되고, 다른 graph의 제안 저장은 여전히
양측 확인이 필요하다).

**운영자 트리거.** `start.ts`가 `ROUTING_SWITCH_FILE`(절대 경로)을 SIGHUP에 적용한다. 파일은
`{"action":"switch", <ROUTING_* 네 키>}` 또는 `{"action":"rollback"}`이고(strict schema, 16 KiB 상한), 로그에는
build id와 **코드만** 남는다(`switchRefusalCode`: 오류 메시지의 경로·해시를 싣지 않는다). routing 없이 이 변수만
있으면 기동을 거절한다. 절차는 [operations-runbook](../operations-runbook.md#graph-교체rollback--bluegreen-m2-01k-e).

### 1.2 취소가 엔진 탐색에 하는 일 — 정직한 범위

**GraphHopper 10.0에는 요청 취소가 없다.** `/route` 탐색은 경로를 찾거나, `max_visited_nodes`를 다 쓰거나,
`timeout_ms`를 지날 때까지 돈다. HTTP 연결을 끊어도 멈춘다는 근거가 없고, 끊으면 언제 끝났는지 알 수 없게 될 뿐이다.
그래서 "취소가 엔진 탐색을 멈춘다"를 다음으로 구현했다(`graphhopper-adapter.ts`, `service.ts`).

1. **탐색 전 취소는 탐색을 시작하지 않는다.** 신원 확인(`/info`)은 취소로 끊고 `/route`를 보내지 않는다.
2. **모든 `/route`에 `timeout_ms`를 싣는다**: `(남은 deadline − 예비분) / leg 수`. 예비분은 deadline의 1/4, 최대
   500 ms. GraphHopper는 timeout을 **leg마다** 건다(바이트코드 `AbstractRoutingAlgorithm.setupFinishTime`이
   알고리즘 실행마다 호출되고, 실측에서 `timeout_ms=40`인 4-leg 요청이 173 ms에 답했다). 엔진 쪽 상한은
   `Router.getTimeoutMillis`가 `min(요청값, routing.timeout_ms 30000)`으로 적용한다(jar 바이트코드로 확인).
   그래서 탐색은 취소 여부와 관계없이 **호출자 deadline 안에서 멈춘다.**
3. **탐색 중 취소는 호출자에게 즉시 답하되, 엔진 연결은 엔진이 답할 때까지 연다.** 그래야 엔진이 실제로
   멈춘 시점(`engineReleased`)을 안다. 엔진이 답하지 않으면 deadline + 2초에 연결을 끊는다(무한 대기 없음).
4. **tenant 허가는 엔진을 따라간다.** 서비스는 호출자 답이 아니라 `engineReleased`에서 허가를 반환한다. 이전에는
   취소 즉시 반환해서, 한 tenant가 취소·재요청을 반복하면 엔진이 여전히 돌리는 탐색 수가 동시 한도를 넘을 수 있었다.

실측(§3.4): 취소 없이 4-leg 탐색 256 ms. 60 ms에 취소하면 호출자는 63 ms에 답을 받고, 8초 예산에서는 엔진이
244 ms에 멈췄다(탐색 도중 멈추지 **않는다** — 끝까지 돌았다). 200 ms 예산에서는 엔진이 157 ms에 멈췄다(예산이
탐색을 끊었다). 실제 소켓으로 두 클라이언트가 80 ms에 끊은 직후 같은 tenant의 세 번째 요청은 86 ms에
**429 `retry-after: 1`**, 엔진이 끝난 뒤 309 ms에 200이었다.

### 1.3 `timeout`과 `no_route`의 구별

GraphHopper는 `timeout_ms` 소진을 끊긴 쌍과 **같은** `ConnectionNotFoundException`으로 답한다(M2-01g
`EXP-TIMEOUT-AS-NOROUTE`). 이제 그 예산을 어댑터가 정하므로 시간으로 가른다. 엔진 답이 leg 예산보다 **먼저** 오면
timeout일 수 없으므로 `no_route`, 예산 이후면 `timeout`이다.

**이 규칙의 한계(검토 N1).** 비교 대상은 엔진의 **전체** 응답 시간과 **leg 하나의** 예산이다. 엔진 답은 어느
leg가 실패했는지, leg마다 얼마나 걸렸는지 알려 주지 않기 때문이다. 정확한 것은 한 방향뿐이다. "leg 하나의 예산보다
빨리 답했으면 어떤 leg도 timeout되지 않았다." leg가 여럿이면, 각 leg는 예산 안이었는데 합이 leg 예산을 넘은 진짜
NoRoute가 `timeout`으로 보고된다. leg가 하나면 전송 시간 오차를 빼고 정확하다. 오류는 언제나 `timeout` 쪽이다.
`timeout`은 네트워크에 대해 아무것도 주장하지 않고 재시도를 권한다. 반대로 `no_route`가 가려진 timeout일 수는 없다.
그래서 `no_route_may_be_engine_budget` warning은 더 만들지 않는다(과거 revision 호환을 위해 enum에는 남김).
다중 leg `timeout`에 "NoRoute일 수 있음" warning을 다는 것은 contract enum 추가가 필요해 하지 않았다(§7).

**발견·수정 1건:** graph C(clip)에서 bbox 밖 지점은 `PointOutOfBoundsException`으로 답하는데 어댑터가 이를
`engine_contract_violation`으로 분류했다(probe 첫 실행에서 관측). `outside_coverage`로 고쳤다. graph A는 페리
노선 때문에 bbox가 117.8–127.3°E로 넓어 이 경로가 드러나지 않았다.

### 1.4 여러 인스턴스 limiter — 결정

현재 limiter(`TenantAdmissionControl`)는 **프로세스 안에서만** 센다. 결정:

| 선택지                                  | 판단                                                                                                                                                                                                                                                                   |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **PostgreSQL lease(채택, 구현은 보류)** | 이미 운영하는 유일한 공유 상태. lease 행에 만료(deadline + 유예)를 두어 인스턴스가 죽어도 허가가 돌아온다. 획득·반환은 짧은 트랜잭션 두 번이며 엔진 호출 동안 트랜잭션을 잡지 않는다(AGENTS: DB 트랜잭션 안에서 provider 호출 금지). rate는 같은 표의 시각 창으로 센다 |
| LB의 tenant 고정(sticky)                | 코드로 강제할 수 없고, 인스턴스가 바뀌는 동안 한도가 일시적으로 배가 된다                                                                                                                                                                                              |
| 한도를 인스턴스 수로 나눔               | N을 알아야 하고 불균형 부하에서 과소 허용                                                                                                                                                                                                                              |
| Redis 등 새 인프라                      | 새 운영 대상과 자격 증명. 이득이 없음                                                                                                                                                                                                                                  |

**그 전까지의 운영 전제:** routing을 켠 API는 **한 인스턴스**로 운영한다(runbook에 적음). 두 번째 인스턴스를 띄우는
작업이 PostgreSQL lease 구현의 진입 조건이다. 이 노드는 구현하지 않았다(범위: "결정한다").

### 1.6 엔진 request log — 정확한 waypoint가 로그에 남는 문제(M2-01k-c2 발견, root 조정)

serving profile은 Dropwizard 기본 request log를 켜 둔다. 그래서 `GET /route?...&point=lat,lon` 한 줄마다
사용자 waypoint가 stdout에 그대로 찍힌다. profile 파일을 고치면 manifest가 고정한 `profileConfigSha256`와 모든
graph 신원이 바뀐다. 그런데 graph A를 다시 빌드하려면 `.geo-build`에 써야 하고, 이 노드에는 그것이 금지되어 있다.
그래서 **profile은 바꾸지 않았다.** graph C도 기존 serving profile(바이트 동일)로 import했으므로 profile 해시는
그대로다.

main `19ec979`(M2-01k-c2)로 rebase한 뒤 `startEngine`은 c2의 `graphhopperJavaArguments`로 인자를 만든다. 이 노드는
blue/green `ports`를 그 helper로 넘길 뿐이고, 날(raw) `java` 인자는 남기지 않았다. request log override
(`-Ddw.server.request_log.type=external`)는 helper가 모든 기동(blue·green·import)에 싣는다. c2의 guard 시험
(`graphhopper-launch.test.mjs`)이 통과한다. 그 전에는 같은 override를 `startEngine`에 직접 넣어 실측했다가 root
지시로 뺐었다. `-Ddw.server.request_log.appenders=[]`는 실제 jar에서 기동하지 못했다(`[]`가 목록으로 변환되지 않아
configuration binding에서 엔진이 종료된다. 이 노드에서도 재현했다). 이 노드는 그 값으로 probe를 돌리지 않았다.

실측(graph C 엔진을 `startEngine`으로, KRC-01 `/route` 한 번): override가 있으면 캡처한 엔진 출력에 `GET /route`도
waypoint도 없었다. override가 없으면(M15) 둘 다 있었다. 마지막 swap probe 실행(06:52Z)은 override가 있는 상태였고,
판정 결과에는 영향이 없다. rebase 뒤의 최종 probe 실행도 helper의 override가 있는 상태다(§9).

profile 파일 자체의 수정(`server.request_log.appenders: []`)과 그에 따른 graph 재빌드는 별도 후속 노드다. 그 재빌드는
graph build id를 바꾼다. 저장된 코스를 새 graph로 다시 계산해 저장하려면 이 노드의 blue/green 절차와 양측 graph
확인(`{previous, next}`)을 거쳐야 한다. 조용한 재계산은 없다.

## 7. 남은 것 / 한계

- **여러 인스턴스 limiter**: PostgreSQL lease로 결정, 미구현. 그 전까지 routing API는 단일 인스턴스(runbook).
- **전역 엔진 동시성 상한**(tenant 합계) 없음. tenant당 2 × tenant 수가 엔진 부하 상한이다. 과부하 차단을 엔진
  단위로 두려면 별도 작업이 필요하다(GraphHopper Jetty 스레드 풀과 함께).
- **원자성은 프로세스 단위.** 다중 인스턴스 roll-out 중 혼재는 revision 기록·양측 확인으로 안전하게 드러날 뿐이다.
- **graph C는 clip**이다. 새 스냅샷으로의 교체(데이터 날짜가 바뀌는 경우)는 allowlist URL이 새 파일을 낼 때까지
  실행할 수 없다. 이 경우에도 절차·검증은 같은 코드를 탄다(manifest의 `roadDataAt`이 다를 뿐).
- **탐색 도중 취소로 엔진을 멈추게 하지는 못한다**(GraphHopper 10.0에 수단이 없음). 상한은 deadline이다.
- 운영 deadline 8 s와 응답 20,000점은 이 지역에서 도달 불가라 seam으로만 집행을 관측했다.
- 운영 profile의 `routing.timeout_ms: 30000` 주석(serving yml)은 "요청별 timeout_ms가 주 상한"으로 바뀐 현실과
  어긋나지만, 파일 해시가 manifest에 고정되어 있어 바꾸지 않았다(바꾸면 graph 재빌드가 필요하다).
- 다중 leg `timeout`이 실제로는 NoRoute일 수 있음을 알리는 warning 코드가 없다(§1.3, contract enum 추가 필요).
- 전환 파일의 "다른 uid 소유" 거절은 코드 경로만 있고 단위 시험하지 않았다(§9).
- UI는 바꾸지 않았다(브라우저 검증 해당 없음. Aside·Chrome·Playwright 모두 이 노드에서 쓰지 않음).

## 9. 검토 반영과 rebase(tree `870863c5` 검토 APPROVE 뒤)

- **rebase:** 임시 WIP 커밋을 만들고 `git rebase main`(`19ec979`, M2-01k-c2·k·h·ad 포함)을 했다. 충돌은
  `scripts/build-routing-graph.mts`와 runbook 두 곳이었다. 해결한 뒤 `git reset --mixed main`으로 WIP 커밋을 풀었다.
  main 쪽 변경은 그대로 두었다. `startEngine`은 c2의 `graphhopperJavaArguments`를 쓰고, 이 노드의 raw `java` 인자
  목록은 없앴다. `ports`는 helper로 넘긴다.
- **N2:** `applyRoutingSwitchFile`은 열린 descriptor의 `stat`로 소유 uid가 프로세스 uid와 같은지, 일반 파일인지,
  group·other 쓰기가 없는지 확인한다(`ROUTING_SWITCH_FILE_NOT_OWNED`, `ROUTING_SWITCH_FILE_WRITABLE_BY_OTHERS`).
  시험은 0664·0646·0666을 거절하고, 0600에서는 전환된다. 변이 M16이 그 시험을 실패시킨다. 다른 uid 소유는 시험
  환경에서 만들 수 없어 단위 시험하지 않았다(코드 경로만 있다).
- **N1:** §1.3과 adapter 주석에 "전체 시간과 leg 예산을 비교한다"는 한계를 적었다. 다중 leg warning은 contract
  enum을 늘려야 해서 하지 않았다. `P6-outcomes-distinct` 제안에 한계를 기록했다.
- **N3:** §1.1의 "섞인 상태 없음"을 계산 단위로 한정했다. 전환을 가로지른 후보 탐색이 왜 안전한지도 적었다.
- **N4:** §2 행을 고쳤다. JSON이 어느 tree에서 나왔는지 §5.1의 6에 적었고, 병합된 tree에서 probe를 다시 돌렸다.
- **N5·N6:** runbook의 `IDENTITY_E2E_ROUTING` 문장을 엔진 절로 되돌렸다. green 기동(1단계)은 blue와 같은 helper,
  같은 override로 한다고 적었다. 전환 파일의 소유·권한 조건도 runbook 2단계에 적었다.
- **round 2 검토(APPROVE) 반영:**
  - **R2-1:** 전환 파일을 `O_RDONLY | O_NONBLOCK`로 연다. 전에는 경로에 FIFO를 두면 writer가 나타날 때까지 `open`이 막혀 `fstat` 검사에 닿지 못했다.
    지금은 막히지 않고 `isFile` 검사가 거절한다. 시험은 `mkfifo`로 FIFO를 만들고 1 s 안에 거절되는지 본다(Windows에서는 건너뛴다). M18(`O_NONBLOCK` 제거)은 `BLOCKED`로 실패한다.
  - **R2-2:** 일반 파일이 아닌 것(FIFO·디렉터리·장치)은 `ROUTING_SWITCH_FILE_NOT_REGULAR`다. 시험은 디렉터리와 FIFO를 쓴다. M19가 실패한다. runbook 2단계의 코드 목록도 고쳤다.
  - **선택 항목(`startEngine` 인자 조립을 떼어 내 M17을 단위 시험에서 잡기)은 하지 않았다.** c2의 guard 시험은 `spawn('java', graphhopperJavaArguments(...))`을 호출 자리에서 그대로 요구한다. wrapper 함수로 옮기면 `java with arguments not from the helper`로 걸린다. M17은 여전히 probe가 잡는다.
  - main `e9ce0ee`로 다시 rebase했다(§9.2).
- **판정 주석:** `K-graph-rollback`과 `P6-tenant-limits`를 "passed(전제: 단일 인스턴스)"로 적었다.
