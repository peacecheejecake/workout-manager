# M3-02h · 서명된 iPhone HealthKit 전체 경로 검증

상태: **not_executed**. 2026-09-28 서명된 iPhone 빌드·설치·기본 실행까지 사전 확인했다. 합성 표본 수집, 삭제, background wake, offline ACK 재시도, 재설치, 계정 전환, 공통 화면 검증을 완료한 것으로 판정하지 않는다.

## 2026-09-28 사전 확인

- `devicectl`에서 iPhone 15 Pro Max(`iPhone16,2`) 물리 기기 1대가 `connected`였다. 제품 bundle `org.workoutmanager.app`은 설치돼 있지 않았다.
- Node 24.12.0에서 phase 작업 트리의 잠금 파일 고정 설치를 완료하고 `pnpm build` 15/15를 통과했다. `cap copy ios` 뒤 `mobile-web/dist/index.html`과 iOS `public/index.html`의 SHA-256이 일치했다.
- 초기 모바일 빌드는 오래된 작업 트리 의존성 링크 때문에 실패했다. 오프라인 설치는 캐시에 `fastify` tarball이 없어 실패했고, 잠금 파일 고정 설치를 다시 실행해 완료했다. 모바일 빌드 재시도는 오래된 contracts `dist` export 때문에 실패했으며, 전체 `pnpm build`가 의존 패키지를 먼저 빌드한 뒤 15/15로 통과했다. 앞선 실패를 통과로 소급하지 않는다.
- 개발 계정 연결 전에는 Apple Development 인증서 1개가 있었지만, 제품 iPhone Debug 서명 빌드가 앱 ID의 개발 프로비저닝 프로필 부재로 실패했다. 당시 `-allowProvisioningUpdates` 재시도에서 Xcode가 `No Accounts`를 보고했다. 이후의 서명·설치·실행 결과는 아래에 별도로 기록했다.
- 제품 `Info.plist`의 `WMNativeAPIOrigin`과 `WMNativeIdPOrigin`은 비어 있다. `NativeAuthConfiguration`은 정확한 HTTPS origin을 요구하므로, 현재 localhost OIDC 스택만으로 제품 앱 로그인·서버 동의·업로드를 실행할 수 없다.
- `HealthKitWorkoutCollector`의 observer/anchored 운동 조회는 표식으로 제한되지 않는다(`predicate: nil`). 기존 개인 운동이 있는 기기에서 읽기 권한을 주면 사용자가 허용한 표식 있는 합성 표본 범위를 넘을 수 있다. 기기의 격리 여부를 확인하기 전에는 제품 앱 HealthKit 읽기 권한을 요청하지 않았다.

실행 로그는 Git 제외 임시 경로에만 두었다. 기기 원본 운동 자료·토큰·개인 위치 데이터는 읽거나 저장하지 않았다. 안전한 표본 범위와 HTTPS 시험 서버가 준비되면 이 노드의 실기기 수용 경로를 별도로 실행한다.

독립 phase 검토는 `main` `fa3eb54` → `phase/m3-02` `410b574` 전체 문서 diff에 **APPROVE**를 주었다. JSON·링크·diff 정합성을 확인했고, 기기 상태나 임시 실행 로그를 직접 재검증하지는 않았다. 이 검토 결과를 기록하는 커밋은 다시 검토받는다.

## 개발 계정 로그인 뒤 서명 재확인

- 사용자가 Xcode 개발 계정 로그인을 알렸다. 명령행의 첫 재시도는 여전히 `No Accounts`였다. Xcode의 Apple Accounts 화면에는 계정과 개발팀이 보였고, 프로젝트의 Signing & Capabilities에서는 팀 선택이 `None`이었다. 개발팀을 선택하자 Xcode가 관리 프로필을 준비했고, iPhone 대상 GUI 빌드가 `Build Succeeded`였다.
- 서명된 앱은 `org.workoutmanager.app`, team `XVT9A9T7RP`로 확인됐다. 개발 프로필에는 HealthKit과 background delivery entitlement가 포함됐다. `codesign --verify --deep --strict`는 권한을 갖춘 실행에서 통과했다. Xcode가 자동으로 재정렬한 `Info.plist`와 개발팀을 적은 프로젝트 파일은 작업 트리에서 원복한 뒤, 원래 프로젝트에 `DEVELOPMENT_TEAM`을 실행 옵션으로 지정한 명령행 iPhone 빌드도 **BUILD SUCCEEDED**였다. 소스 변경은 없다.
- 사용자는 이 iPhone에 기존 운동 기록이 있다고 밝혔다. 현재 제품 collector의 `predicate: nil`은 그 기록을 조회할 수 있으므로, 제품 앱의 HealthKit 운동 읽기는 실행하지 않았다.
- 설치 명령은 자동 승인 검토에서 기기 상태 변경에 대한 구체적 승인 부족을 이유로 처음 **거절**됐다. 우회 설치는 하지 않았다. 사용자가 `org.workoutmanager.app`의 이 iPhone 설치를 명시적으로 승인한 뒤 `devicectl` 설치가 통과했고, 기기 앱 목록에서 bundle·버전 1.0/1을 확인했다. 기본 실행의 첫 시도는 기기가 잠겨 있다는 OS 거절로 실패했다. 사용자가 잠금을 해제한 뒤 같은 bundle의 기본 실행은 성공했다. 제품 로그인·운동 수집·화면 수용 검증은 **not_executed**다. HealthKit 권한 요청은 하지 않았다.

## 기존 운동이 있는 기기의 안전한 후속 검증 범위

읽기 전용 코드 감사에서 observer와 anchored 조회 모두 `predicate: nil`임을 재확인했다. 자동 시작과 foreground 재개도 이 경로에 도달할 수 있다. 따라서 현재 제품 빌드에 운동 읽기 권한을 부여하거나 표본 수집을 시작하지 않는다.

후속 Debug 검증에는 실행마다 다른 표식과 제품 앱이 쓴 합성 운동의 source를 **AND**로 결합한 동일한 조회 조건을 observer와 anchored query에 적용해야 한다. 조회 범위가 준비되지 않으면 권한 요청과 자동 수집을 닫고, anchor·알려진 UUID·outbox를 계정과 표식별로 격리해야 한다. 삭제는 앞서 이 범위에서 저장한 UUID에 한해 처리하고, 실제 기기에서 삭제 이벤트가 반환되는지 확인한다. 범위 밖 합성 표본도 함께 심어 유출되지 않는지 검증한다. 이 조건을 구현·검증하기 전에는 개인 운동을 실기기 수용 자료로 사용하지 않는다.

표식 범위의 제품 경로가 통과하더라도 외부 앱 변경에 따른 background wake와 일반 제품 수집 전체를 자동으로 입증하지는 않는다. HTTPS 시험 서버와 정확한 native API/IdP origin, 실기기에서 각 수용 동작의 별도 증거가 필요하다.
