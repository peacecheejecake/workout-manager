## 설계 근거

1. **별칭은 주소 변환일 뿐 아무것도 조회하지 않는다.** `activityDetailAliasTarget(pathId, search)`는 순수 함수다.
   경로의 id를 `selected`로, `tab`을 `detailTab`으로 **글자 그대로** 옮긴다. 서버에 묻지 않으므로 별칭 단계에서
   활동의 존재·소유를 알 방법이 없다. 따라서 **존재 여부를 흘릴 수 없다.** 판단은 도착한 화면이 기존 규칙대로 한다.
   - uuid가 아닌 id → 화면의 기존 잘못된 주소 상태("조회 주소를 확인하세요…", `parsed.invalid`)로 간다.
     상세 요청은 나가지 않는다.
   - 모르는 tab → 기존 지원하지 않는 보기 상태("알 수 없는 활동 상세 보기입니다." + "개요로 이동")로 간다.
   - 남의 활동 → 기존 `NOT_FOUND` 상태("기록이 삭제되었거나 접근할 수 없습니다.")로 간다. 서버는 context와 details를
     둘 다 404로 답한다. 없는 uuid와 응답 상태·화면 문구가 같다.
2. **tab 값은 걸러내지 않고 넘긴다.** 별칭이 tab을 검증하면 두 번째 탭 목록이 생긴다. 그러면 별칭과 화면의 판단이
   어긋날 수 있다. 목록은 `browser-search.ts` 하나로 둔다.
3. **다른 query는 유지한다**(보기·필터). 쿼리에 이미 있는 `selected`·`detailTab`은 버린다. 주소가 가리키는 대상은
   경로와 `tab`이기 때문이다. `tab`이 없으면 `detailTab`도 없다. 그러면 화면 기본값인 개요가 열린다.
4. **두 shell이 같은 함수를 쓴다**(escape 없는 id 한정 — 아래 검토 주석 참고). 함수는 `@workout/modules-activities/detail-address` 공개 subpath로 내보낸다.
   이 모듈에는 React·Next 의존이 없다.
   - Next: `apps/web/app/activities/[id]/page.tsx`가 server `redirect()`로 보낸다(307, 기록 대체).
     `track-preview`·`import`·`new`는 정적 경로라서 `[id]`보다 우선한다.
   - Vite: `main.tsx`가 렌더 전에 `history.replaceState`로 주소를 바꾼다. 그 뒤 기존 `/activities` 분기가 화면을
     그린다. 뒤로 가기 기록에는 별칭이 남지 않는다. Next의 형제 페이지 이름(`track-preview`·`import`·`new`)은
     별칭에서 뺐다. 경로 조각은 `decodeURIComponent`로 푼다. 잘못된 escape는 그대로 넘기도록 했으나, 이 분기는 두 shell
     어디서도 실행되지 않았다(검토 주석 참고).

## E2E가 단언하는 것 (`tests/identity/activity-detail-address.spec.ts`, Next·Vite 각각)

- **여섯 탭**(`:125-148`): `/activities/<id>?tab=<tab>`으로 들어간다. 그러면
  - URL이 정확히 `/activities?selected=<id>&detailTab=<tab>`가 된다.
  - 해당 탭만 `aria-selected=true`이고 나머지 다섯은 `false`다.
  - 상세 제목이 보인다.
  - 그 탭에만 있는 영역이 보인다. 개요는 활동 로컬 태그, 구간은 원본 관측 워크벤치, 경로는 저장된 경로, 영향은
    계획 연결과 관측 영향, 출처는 상세 출처다.
  - 미디어는 탭 선택만 단언한다. 패널은 M2-01k-l이 만든다.
  - `tab`이 없으면 개요가 열린다(`:150-156`).
- **모르는 tab**(`:167-180`): `tab=map`이면 알 수 없는 보기 문구가 보이고, 선택된 탭은 0개다. "개요로 이동"을
  누르면 개요로 간다.
- **잘못된 id**(`:182-199`): `not-an-activity`이면 잘못된 주소 alert가 보이고, 상세 영역은 없다. 그 id로 나간
  `/bff/` 요청은 0건이다.
- **Bob**(`:201-231`): 별도 context에서 Bob으로 로그인한다. Alice 활동의 별칭 주소를 연다. 그러면
  - context·details 응답이 `[404, 404]`다.
  - `NOT_FOUND` alert가 보이고, Alice 제목은 0건이다.
  - 새 무작위 uuid를 열었을 때와 **응답 상태와 상세 영역 전체 텍스트(id만 치환)가 같다.**

## 독립 검토 주석(병합 때 root 반영)

- escape된 id는 두 shell이 다르게 푼다. Next 16.3.5는 `params.id`를 percent-encoding된 채로 넘겨 `%`가 한 번 더
  인코딩된다(`%252F` → Next `selected=%25252F`, Vite `selected=%252F`). 평범한 uuid는 같고, escape된 변형은 두 shell
  모두 잘못된 주소 상태로 간다.
- 짝 없는 `%`: Next `/activities/%`는 500을 낸다(이 변경 때문인지, Next가 모든 경로에 그렇게 답하는지는 확인하지
  않았다). Vite preview는 그 URL에 앱을 내지 않아 `decodeURIComponent` catch 분기에 닿지 않는다.
- `tab=map`은 사양 열 이름 "지도"지만 탭 이름은 `route`이므로 의도적으로 지원하지 않는 보기로 시험한다.
- 대문자 uuid는 그대로 통과한다(화면의 기존 동작, 시험 없음).
