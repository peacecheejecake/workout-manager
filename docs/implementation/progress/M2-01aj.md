# M2-01aj · track parse child 메모리 예산과 종료 순서

상태: **완료(2026-09-25).** 독립 검토 APPROVE 뒤 main `e00a992` 위로 병합했다. 처음 기준 HEAD는 main `d22f760`이었다. 검토의 비차단 항목은 M2-01al로 분리했다. 출처는
[M2-01ai.md](M2-01ai.md) §7(검토 NB-5)과 M2-01ai 2차 검토다. 예산 도출 방법은 [M2-01k-f.md](M2-01k-f.md) §1을 따른다.

## 1. 설계 근거

### 1.1 (a) parse 프로세스 peak RSS 예산

- **무엇을 재는가.** M2-01ai 뒤로 parse는 parse마다 fork되는 child process(`parse-child.ts`, 기본 old-generation
  ceiling 256 MiB)에서 돈다. 그 메모리는 API 프로세스의 RSS에 들어가지 않는다. 새 지표
  `worker.parseProcessPeakRssMiB`는 **parse 하나를 맡은 child 하나의 peak RSS**다(MiB, 통계 `max`).
- **어떻게 재는가.** probe의 worker phase가 parser의 `processIds()`로 그 parser의 child만 골라 `ps -o rss=`를
  20 ms마다 읽는다. parse 하나의 최고값이 표본 하나다. `processIds()`를 쓰므로 tsx의 esbuild service처럼 probe의
  다른 child는 섞이지 않는다(M2-01ai의 `ps -A` + `parse-child` 문자열 필터를 대체).
- **시간 표본과 분리했다.** 처음 판은 `worker.parseMs` 표본을 재는 parse에서 RSS도 읽었다. 부하 27에서
  `worker.parseMs`가 908–1,078 ms로 나왔다(예산 980). 같은 코드에서 읽기를 뺀 parse는 부하 87에서도 449–505 ms였다.
  20 ms마다 `ps`를 띄우는 것이 시간 표본을 오염시켰다. 그래서 RSS는 **별도 parse 20회**에서 읽는다. 기존 시간
  기준선은 그대로 유효하다. 비용은 run당 parse 20회(약 10 s)다.
- **한계.** 20 ms보다 짧은 peak는 놓칠 수 있다. 표본은 참 peak의 하한이다. 기준선도 같은 방식으로 읽었으므로
  예산과 판정은 같은 척도다. child의 `maxRSS`를 reply로 보고하게 하면 정확하지만, 측정을 위해 제품의 child reply
  계약을 바꾸는 일이라 하지 않았다.
- **동시 합계는 기록만 한다.** 한 parser가 동시성 한도(2)에서 두 parse를 돌릴 때 두 child RSS 합의 최고값을
  `details.parseProcessRss.atBoundPeakSumMiB`로 남긴다(346–360 MiB). API는 parser 두 개를 두므로 최대 child 4개다.
  예산 300 MiB × 4 = 1,200 MiB가 API 한 개의 parse 쪽 상한 추정이다. 컨테이너 한도를 정할 때 API 예산
  800 MiB와 더해 본다. 이 합계는 예산이 아니다.
- **예산.** 기준선 run 3회(record-only, 각 20표본, 부하 5.29–7.04)의 run별 최대 197·193·188 MiB. 최악 197 × 여유
  1.5(메모리 배수, M2-01k-f와 같은 이유) = 295.5 → **300 MiB**. `minimumSamples` 5(다른 max 메모리 지표와 같다).
  메모리 지표라서 허용 부하 규칙이 실패를 보류하지 않는다.

### 1.2 (a) `api.processPeakRssMiB` 재도출 — 결정: **다시 도출한다**

- 옛 기준선 716 MiB(예산 1,100)는 parse가 API 프로세스의 worker thread였을 때 쟀다. M2-01ai 뒤 판정 run은 520·530
  MiB였다. 옛 예산을 두면 API 프로세스가 **2.1배** 커져야 실패한다. 예산의 뜻("1.5배 회귀를 잡는다")이 깨진다.
- 새 기준선은 같은 run 3회에서 나왔다. run별 530·495·493 MiB, 부하 5.83–8.43, 60표본. 530 × 1.5 = 795 →
  **800 MiB**. 두 지표가 같은 run을 기준선으로 쓰는지를 단위 시험이 확인한다.
- 이 값에는 probe 자체와 합성 FIT 생성기가 들어 있다(전과 같다). 설명 문자열에 결정과 옛 값을 남겼다.

### 1.3 (b) 종료 순서

- `apps/api/src/configured.ts` close hook이 `routingAdmission.drain(lease)`을 **기다린 뒤** parser를 닫았다. drain은
  engine 검색이 끝나 permit이 풀리기를 lease(deadline + hard-stop 유예 + 2 s, 약 12 s 이상)까지 기다린다. 그 동안
  진행 중 parse가 끝까지 돌았다.
- 이제 `closeParsers()`와 drain을 **함께** 기다린 뒤 store·database를 닫는다. parser close는 즉시 모든 parse를
  `TRACK_PARSE_CANCELLED`로 끝내고 child를 SIGKILL하며, child 종료를 기다린다.
- **공유 상태 없음 확인.**
  - parser(`parse-host.ts`)의 상태: `running` Map, `active` 카운터, `closed` 플래그, 모듈 수준 `liveChildren`. 모두
    child process만 가리킨다. import는 contracts와 `artifacts.ts`뿐이다. database도 routing도 모른다.
  - drain(`packages/server/persistence/src/routing-admission.ts`)은 `outstanding` permit release promise와 타이머만
    기다린다. release는 database pool을 쓴다. pool은 두 작업이 모두 끝난 뒤에야 닫힌다(순서 유지).
  - parse가 취소된 요청 handler가 이어서 DB를 쓰더라도 pool은 아직 열려 있다. 바뀐 것은 parser close 시점뿐이다.

## 6. 매트릭스 판정 제안(root가 재판정)

- **K-performance: passed 유지 제안.** 판정 run 23:11:29Z(부하 3.55–3.77)가 예산 18/18, check 10/10을 통과했다.
  새 예산 `worker.parseProcessPeakRssMiB`(300 MiB)는 기록 전용 기준선 3회에서 도출했고, 재지 않으면 missing(P1),
  child가 커지면 failed(P2), 판정이 무시하면 단위 시험 실패(E1)다. `api.processPeakRssMiB`는 child-process parser
  기준으로 1,100 → 800 MiB로 좁혔다. M2-01ai가 남긴 한계("parse 메모리가 예산 밖")가 닫힌다. M2-01k-f 한계(실기기
  없음, SwiftShader, 2배 회귀 장치, warm cache)는 그대로다. 브라우저 예산은 다시 재지 않았다(이 노드 경로 밖).
- **P7-parser-bounds: passed 유지 제안.** parse 메모리의 heap ceiling(기존)에 더해 프로세스 RSS가 예산으로
  판정된다. 종료 때 parser가 drain을 기다리지 않고 바로 닫혀 진행 중 parse와 child가 즉시 끝난다(B1 killed). 남는
  한계(M2-01ai)는 그대로다.

## 7. 열린 항목

- RSS는 20 ms 표본이라 더 짧은 peak를 놓칠 수 있다. 정확한 값이 필요하면 child가 `resourceUsage().maxRSS`를
  보고하게 하는 제품 변경이 필요하다(계약 변경이라 이 노드에서는 하지 않음).
- 동시 child 4개(parser 두 개)의 합계는 예산이 아니다. 두 parser를 한 parser로 합칠지는 M2-01ai §7의 열린 항목이다.
- `node` 필드는 결과 파일에서 계속 `M2-01k-f`로 찍힌다(probe의 소유 노드 표시). 바꾸지 않았다.
