# M2-01g · 자체 보행 routing

상태: **어댑터·내부 API·상한·실패 구분은 구현하고 실제 엔진으로 측정. 한국 보행 coverage는
`not_reviewed`로 남는다.** 기준 HEAD `f037694`.
계획 [지도 구현 계획](../map-implementation-plan.md) 5·6·7·8절과
[ADR 7절](../research/self-hosted-map-adr.md)의 "M2-01g에서 구현·검증" 목록을 수용 기준으로 삼았다.

M2-01d가 고른 GraphHopper open-source 10.0을 그대로 쓴다. 이 작업에서 그 선정을 다시
검토하지 않았고, 뒤집을 만한 증거도 나오지 않았다. 대신 그 결정이 전제한 것 —
**직선을 성공으로 보고하지 않는다** — 을 코드로 고정했다.

독립 검토에서 blocking 3건(취소 오판정, 직선 방어 우회, graph 해시가 실행 중인 graph에
묶이지 않음)과 기술 정확성 2건을 지적받아 모두 반영했다. 아래 내용은 그 수정 이후 상태다.

## 고정한 경계

- **엔진은 내부에서만 부른다.** 요청 계약(`walkingRouteRequestSchema`)은 `strictObject`라
  URL·host·engine·profile override를 담을 자리가 없다. 엔드포인트는 운영 설정에서만 오고
  `createRoutingEngineEndpoint`가 scheme·자격증명·query·path·host allowlist를 검사한다.
  기본 allowlist는 loopback뿐이고, 경로도 `/route`·`/info`·`/health` 세 개로 닫혀 있다.
  **다만 "엔진이 외부에서 접근 불가"는 방화벽·네트워크의 성질이며 이 코드가 증명하지
  못한다.** 여기서 보장하는 것은 우리 서버가 allowlist 밖 host로 나가지 않는다는 것뿐이다.
- **transport는 redirect를 따라가지 않는다.** `redirect: 'error'` + `credentials: 'omit'`,
  응답 바이트 상한(4 MB)을 넘으면 본문을 버리고 실패시킨다. allowlist 검사는 첫 URL만
  보므로 redirect를 허용하면 그 검사가 무의미해진다.
- **graph 신원은 검증해야만 만들어진다 — 런타임에서도.** 두 번 틀렸다. 처음엔 `PinnedGraph`
  인터페이스와 `pinnedGraphFromManifest`를 공개해 아무 해시나 적힌 manifest를 넘길 수 있었고,
  그 다음엔 "공개 API 아님"이라는 **주석만 붙은 public static** `fromVerifiedParts`를 남겨
  뒀다. 주석은 접근을 막지 못한다. 지금은 생성자가 **export하지 않는 module-private symbol**을
  요구하므로 `as any` 우회까지 런타임에서 거절되고, 공개 static factory는 하나도 없다.
  `loadRoutingDeployment`만이 배포본을 만든다. **생성만 막아서는 부족했다**: 같은 public
  필드를 가진 plain object가 타입을 만족해 어댑터가 그대로 받아들였고, 검증된 적 없는
  해시로 `route_computed`를 돌려줬다. 이제 생성자가 module-private `WeakSet`에 인스턴스를
  등록하고 **어댑터 진입점이 `assertVerifiedDeployment`로 소비 시점에 확인한다.** private
  field로 nominal 타입이기도 해서 구조가 같은 객체는 컴파일 단계에서도 거절된다.
  **그리고 가드가 믿는 값이 밖에서 닿으면 안 된다**: 한때 lint 규칙을 달래려고 붙인 getter가
  nominal field에 담아 둔 construction key를 노출했고, 그 key로 만든 위조 객체를 생성자가
  스스로 WeakSet에 등록해 `isVerified`가 참이 됐다. 지금 nominal field는 key와 무관한 값이고
  getter는 없다. 유효한 인스턴스·프로토타입·클래스에서 읽을 수 있는 모든 값을 긁어 생성자에
  넣어 보는 시험이 이 성질을 고정한다. **가드가 부르는 함수도 마찬가지다**: `assertVerifiedDeployment`가
  공개 static `RoutingDeployment.isVerified`를 부르던 동안에는 `RoutingDeployment.isVerified = () => true`
  한 줄로 위조 객체가 통과했다. 이제 assertion은 **module-private 술어**가 WeakSet을 직접 보게 하고,
  클래스와 prototype을 freeze해 공개 멤버 교체 자체를 막는다(두 겹을 각각 따로 되돌려 서로 다른
  시험이 실패하는 것을 확인했다). 그 함수는
  **graph 파일 해시 · 엔진 jar 해시 · profile 설정 해시 세 가지를 모두 디스크에서 읽어**
  manifest와 대조한다(`GRAPH_CONTENT_CHANGED` / `ENGINE_ARTIFACT_MISMATCH` /
  `PROFILE_CONFIG_MISMATCH`). 엔드포인트도 이 단위 안에 들어가 transport를 함께 들고
  있으므로, 어댑터는 검증된 배포 하나만 바라본다. **검증 이후의 변조도 막는다**: manifest는
  frozen copy로 보관하고 인스턴스 자체도 freeze하므로, 넘겨준 원본을 나중에 고치거나 필드를
  바꿔치기해도 기록되는 해시는 검증 시점의 것이다. 신원은 주장하는 것이 아니라 증명하는 것이다.
- **신원 확인에 캐시가 없다.** 60초 캐시가 있던 동안에는 "캐시가 graph 교체를 넘어
  살아남지 못한다"는 서술이 **거짓**이었다 — 교체를 알아볼 유일한 지점이 바로 그 캐시가
  건너뛰던 `/info` 호출이었기 때문이다. 이제 **매 계산마다** `/info`를 읽어 엔진이 보고한
  `version`·`data_date`·`import_date`를 manifest와 대조한다. 비용은 계산당 loopback 왕복
  한 번(한 자릿수 ms, 계산 예산 8초)이다. **남는 틈은 명시한다**: `/info`와 `/route`는
  두 번의 요청이므로 그 사이에 일어난 교체는 직전에 읽은 신원으로 귀속된다. 이를 닫으려면
  경로 응답 자체가 graph 신원을 담아야 하는데 이 엔진은 그 기능을 제공하지 않는다.
- **결과는 계산이지 저장된 코스가 아니다.** 어댑터는 DB 핸들이 없고 아무것도 쓰지 않는다.
  따라서 "엔진을 DB 트랜잭션 안에서 부르지 않는다"는 규칙을 구조적으로 만족한다. 실패해도
  호출자의 미계산 초안은 그대로다. `RouteComputationRecord`(엔진·profile·graph 신원,
  조건, 요청 id와 **요청 revision**, 계산 시각, 계산 시간, 거리, warnings)를 돌려주고,
  **이것을 `RouteRevision`으로 저장하는 일은 코스 원장(M2-01f/h)의 몫이다.**
- **"직선은 성공이 아니다"의 정확한 의미.** fallback 직선은 모양이 아니라 **뒤에 edge가
  없는 답**이다. 그래서 판정은 모양이 아니라 엔진이 지났다고 밝힌 edge에 건다.
  1. `details=road_class` 구간들이 형상 전체를 0부터 마지막 정점까지 연속으로 덮어야 한다
     (`edgeDetailsCoverGeometry`). GraphHopper는 이 값을 graph edge에서만 만들 수 있다.
  2. 형상이 첫 snap 지점에서 시작해 마지막 snap 지점에서 끝나고, 중간 경유지도 **요청
     순서대로** 형상 위에 있어야 한다(`geometryVisitsWaypointsInOrder`).
  3. 보고 거리가 자기 형상의 길이와 맞아야 하고(허용 오차 `max(10 m, 2 %)`), 양수여야 한다.

  **일부러 검사하지 않는 것: 직선처럼 보이는지.** 이전 판은 "200 m 넘는 구간에서 현으로부터
  1 m 이내면 거절"이었는데, 실제 서울 graph로 재면 **양쪽으로 틀렸다.** 이 graph가 정상적으로
  돌려주는 답 중에 `cycleway` 한 줄로 이어진 **552.1 m(정점 3개, 최대 편차 0.742 m)** 와
  **169.9 m `residential` 도로(정점 2개)** 가 있는데 둘 다 거절당했고, 반대로 임계값 아래의
  짧은 위조 직선이나 2.6 m 정도 휜 위조는 통과했다. 직선인지 여부는 실제 network 직선과
  위조 직선을 가르지 못한다. edge 근거가 가른다.

  **한계를 분명히**: 위 검사는 전부 엔진 자신의 기록을 읽는다. 지어낸 선에 맞춰 edge 구간까지
  일관되게 지어내는 엔진은 통과한다. 이 패키지는 독립적인 지도 대조를 하지 않으며, 부정직한
  엔진을 잡아낸다고 주장하지 않는다. 잡아내는 것은 edge 없이 답하거나, 다른 곳을 답하거나,
  스스로 모순되는 엔진뿐이다. 이 경계는 시험
  `documents the limit: an engine that fabricates matching edge details is accepted`로 고정했다.

- **snap을 직접 잰다.** 엔진의 `snapped_waypoints`와 요청 좌표의 대권 거리를 waypoint마다
  계산해 120 m를 넘으면 `snap_too_far`, 절반을 넘으면 `snap_distance_notable` warning이다.
- **실패를 섞지 않는다.** `no_route` / `outside_coverage` / `snap_too_far` / `timeout` /
  `cancelled` / `overloaded` / `compute_budget_exceeded` / `engine_unavailable` /
  `engine_contract_violation` / `graph_mismatch`가 각각 별개 outcome이고, 어느 것도
  대체 형상을 돌려주지 않는다. deadline 초과(우리 시계)와 호출자 abort를 다르게 분류하며,
  `AbortSignal.any`/`timeout`에 기대지 않고 `AbortController` + `setTimeout`으로 직접 만든다.
- **취소는 연결이 끊겼을 때만이다.** 처음 판은 요청 스트림의 `close`에 걸어 뒀는데, 그
  이벤트는 **요청 본문을 다 읽는 순간** 발생한다. 실제 loopback 서버로 재현했다:
  `onRequest` 시점 기준 `request.raw` `close`가 **1 ms**, `reply.raw` `close`가 **57 ms**
  (계산 50 ms)였다. 즉 정상 POST에서도 먼저 발생하므로 취소 신호로 쓸 수 없다. 지금은
  **응답 스트림의 `close`** 를 보고, 그것도 응답이 아직 쓰이지 않은 경우(`writableEnded`가
  false)에만 abort한다. 정상 요청과 실제 연결 절단을 **실제 HTTP 소켓으로** 각각 시험한다.
- **취소에 서버 자원 상한을 같이 뒀다.** 호출자가 끊기면 HTTP 요청을 abort하고 tenant
  permit을 `finally`에서 반납한다. 그것만으로는 엔진이 계속 계산할 수 있으므로 **모든
  요청이 `max_visited_nodes`를 함께 보낸다**(강제됨을 실측으로 확인).
- **tenant별 상한.** rate window(60초 20건) + 동시성(2건) + 추적 tenant 수 상한(10,000).
  거절은 엔진을 부르기 전에 일어나고 `retry-after`를 함께 돌려준다. **단일 프로세스 한정.**
- **요청 자체도 묶는다.** waypoint 2–12개, leg 직선 30 km, 전체 직선 100 km, 중복 인접
  waypoint 거절, 응답 점 20,000, 경로 거리 250 km, deadline 8초, body 8 KB.

## 구현 기록

### 새 계약 `packages/contracts/src/routing.ts`

`routingLimits`, `routingPositionSchema`, `routingGraphIdentitySchema`(`identitySource`로
관측/고정값을 구분하고 `graphContentSha256`을 포함), `routeConditionsSchema`,
`routeComputationRecordSchema`, `walkingRouteRequestSchema`, `walkingRouteResultSchema`.

계획 좌표와 관측 sample은 다른 데이터다. `packages/contracts/src/tracks.ts`는 건드리지 않았다.

### `apps/api`

`src/routing-routes.ts`가 `POST /bff/v1/routing/walking-routes` 하나를 등록한다. 소유자는
세션에서 나오고, CSRF·인증은 기존 plugin 경계가 담당하며, 연결이 끊기면 응답 스트림의
`close`로 취소가 전달된다. outcome별 상태 코드는 200 / 429(+`retry-after`) / 504 / 502 /
499이고 본문은 항상 계약으로 검증된 결과다. `product-routes.ts`에 `walkingRoutes?` 포트를
additive로 추가했다(미설정이면 라우트가 등록되지 않는다).

### 스크립트

- `scripts/geo/graphhopper-foot-serving.yml`: 운영용 profile. M2-01d의
  `graphhopper-foot.yml`은 **건드리지 않았다** — 그 파일의 SHA-256이 기존 측정 기록에
  들어 있어 수정하면 그 증거가 무효가 된다.
- `scripts/build-routing-graph.mts --execute`: allowlist로 jar 해시를 대조하고, 전용
  디렉터리(`.geo-build/routing-graph/foot`)에 graph를 import한 뒤 **엔진이 종료된 다음**
  파일을 해싱해 manifest를 쓴다. M2-01d의 graph 디렉터리는 그대로 둔다.
  `--reuse`는 **기존 manifest가 지금의 extract·profile·jar 해시와 모두 일치할 때만** 허용하고,
  하나라도 다르면 무엇이 달라졌는지 밝히며 거절한다. 이전 판은 옛 graph를 그대로 두고 현재
  입력의 provenance로 manifest를 새로 써서, **바뀐 extract를 옛 graph에 찍어 붙일 수 있었다.**
- `scripts/probe-routing-coverage.mts --execute`: manifest를 검증해 얻은 신원으로
  **제품 어댑터·서비스를 그대로 호출해** coverage 6건 + 대조군 9건 + 엔진 동작 실험 3건을
  측정하고 [routing-coverage-korea.json](../research/routing-coverage-korea.json)을 쓴다.
  실행 전후 graph 해시가 같은지도 스스로 확인한다. 인자 없이 실행하면 안내만 출력하고,
  `CI`면 예외를 던진다.
- `scripts/probe-routing-engines.mjs`: **변경하지 않았다.**

## 검증하지 않은 것 / 한계

- **coverage 승인은 하지 않았다.** M0-06b의 상태를 바꾸지 않는다.
- **persistence가 없다.** `RouteRevision` 테이블, migration, outbox, 코스 원장 연결은 이
  작업에 없다. "오래된 graph로 계산한 코스를 새 graph로 덮어쓰지 않는다"는 **저장 쪽 규칙이라
  아직 시험되지 않았다.** 여기서 고정한 것은 신원이 결정적이고 다른 graph면 계산을
  거절한다는 것까지다.
- **edge 상세 검사는 증명이 아니다.** 지어낸 선에 맞춰 edge 구간까지 일관되게 지어내는
  엔진은 통과한다(시험으로 고정한 경계). 우리가 가진 것은 엔진 자신의 기록이지 독립적인
  지도 대조가 아니다.
- **형상만 보고 위조 직선을 가려낼 방법은 이 작업에 없다.** 평탄도·길이 임계값을 실제
  graph로 재 보니 정상 경로를 거절하면서 짧은 위조는 통과시켰기에 제거했다. 남은 방어는
  전부 edge 근거·순서·자기일관성이다.
- **`/info`와 `/route` 사이의 교체 창은 닫히지 않는다.** 두 번의 요청 사이에 일어난 graph
  교체는 직전에 읽은 신원으로 귀속된다. 경로 응답이 신원을 담아야 닫히는데 엔진이 그 기능을
  제공하지 않는다.
- **manifest는 외부 권위를 대신하지 않는다.** 구성 요소를 서로 묶을 뿐이고, graph와
  manifest를 함께 다시 만든 경우는 구별하지 못한다.
- **tenant 상한은 단일 프로세스 한정.** 여러 인스턴스에는 공유 limiter가 필요하다.
- **엔진의 외부 비접근성을 증명하지 않았다.** 배포·방화벽·네트워크 격리를 하지 않았다.
- **취소가 엔진의 계산을 멈추지는 않는다.** HTTP 요청은 abort되지만 GraphHopper가 이미
  시작한 탐색을 중단하는지는 확인하지 않았다. 그래서 `max_visited_nodes`를 함께 둔다.
- **`routing.timeout_ms: 30000`이 실제로 발동하는 것은 보지 못했다.** 1 ms로 낮춰 발동
  형태만 관측했다.
- **round_trip(목표 거리)은 다루지 않았다**(M2-01i).
- **`road_class` 상세를 검증에만 쓰고 결과에 담지 않는다.** 노면·계단·횡단 판단에 필요한
  데이터가 결과에 없다. 그 파생 작업은 계획 5절대로 worker의 몫이며 만들지 않았다.
- **부하·과부하 실측을 하지 않았다.** `CTL-OVERLOAD`는 상한 발동 확인이지 부하 시험이
  아니다. 지연 7–77 ms는 이 기기·이 graph·단일 호출자 값이다.
- **elevation·장소 검색은 범위 밖**(M2-01j). **UI가 없다**(M2-01e/h).
- **브라우저 확인을 하지 않았다.** 화면 변경이 없다.
- **`.geo-build/`의 graph·manifest·jar는 Git에 넣지 않았다.** 커밋 대상은 측정 JSON과 문서뿐이다.
- **task-graph.json 상태는 바꾸지 않았다**(root 소유). 루트 공유 파일 중 `vitest.config.ts`에
  새 패키지 테스트 경로 한 줄, `pnpm-lock.yaml`에 importer가 추가됐다. M2-01b의
  `packages/server/track-ingestion` → `packages/track-parsing` 이동이 같은 두 파일을
  건드리므로 root가 직렬 통합해야 한다.
