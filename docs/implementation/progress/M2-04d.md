# M2-04d · 자료 접근·공유·coach 사용 경계

상태: **완료 (M2-04 전체와 FUT-06은 미완료)**. M2-04a~c의 resource 원장, object lifecycle,
URL ingestion 위에 ACL revision, 명시 공유/철회, `reviewed`와 `includeForCoach`의 분리된 전환,
그리고 cache·index·citation dependency manifest를 연결했다. 실제 검색 색인·retrieval·인용 저장소는
아직 존재하지 않으므로 manifest 실행기는 M2-05에서 채운다.

## 고정한 경계

- 접근·동의·정책 변화는 모두 `resource.access_revision`을 단조 증가시킨다. version append와
  access 전환은 서로 다른 head transition이고, DB trigger가 둘을 구분해 검증한다. version append는
  `reviewed_state`와 `include_for_coach`를 절대 바꾸지 못한다.
- `reviewed`와 `includeForCoach`는 양방향으로 별개의 명시 command다. fetch·parse·upload 성공이나
  공유 요청은 둘 중 어느 것도 자동으로 켜지 않는다. 한 UPDATE에서 검토 표시와 coach 사용 활성화를
  동시에 하는 전환, 그리고 coach 사용이 켜진 상태에서 검토를 해제하는 전환을 trigger가 각각
  `INVALID_RESOURCE_TRANSITION`과 `REVIEW_WITHDRAWAL_BLOCKED`로 거부한다. 검토 해제는 coach 사용
  중지를 암묵적으로 끼워 넣지 않는다. `includeForCoach=true`는 `reviewed_state='reviewed'`와 AI 동의를
  요구하고, CHECK 제약과 trigger가 이를 SQL에서 강제한다.
- 공유는 `granteeKind='coach'`와 grantee principal을 지정하는 명시 command다. tenant 소유권은 인증에서
  얻고 client가 보낸 athlete ID는 쓰지 않는다. 같은 principal에 대한 반복 공유는 새 revision을
  만들지 않는 멱등 no-op이고, 활성 grant는 partial unique index로 principal당 하나다.
- 철회는 이후의 모든 읽기를 막는다. grantee의 열람은 SECURITY DEFINER 우회가 아니라 `resource`,
  `resource_version`, `resource_url_provenance`의 RLS policy 자체를 확장해 허용한다. policy는 활성
  share row와 `deleted_at IS NULL`을 요구하므로 철회·삭제는 다음 statement부터 바로 차단된다.
  grantee는 자신에게 부여된 활성 share만 보고 철회 이력은 보지 못한다.
- 삭제, 공유 철회, 동의 철회, `reviewed`/`includeForCoach` 하향은 모두 durable cleanup manifest를
  남긴다. object byte는 M2-04b/c의 `resource_object_cleanup`을 그대로 쓰고, object로 표현할 수 없는
  파생 텍스트·검색 색인·retrieval cache·저장된 인용은 `resource_derived_cleanup`이 같은 lease,
  bounded retry, dead-letter 규율과 **같은 worker 프로세스**로 처리한다. 별도 병렬 경로를 만들지 않는다.
- 미완료 manifest가 있는 동안 `public.resource_coach_use_authorized()`는 false를 반환한다. 고정된
  manifest revision만으로는 사용 권한이 되지 않으며, retrieval·인용·재시도는 사용 시점에 이 gate를
  다시 통과해야 한다. 삭제된 발췌는 manifest가 열려 있는 한 재노출되지 않는다.
- coach 사용 dependency manifest는 해당 tenant에 대해 항상 완전하다. 수집은 tenant command advisory
  lock을 먼저 잡고 consent head, 인가 집합, 수집 시각을 **단일 statement**에서 읽으므로 READ COMMITTED
  에서도 서로 다른 snapshot이 섞이지 않는다. 인가 집합의 술어는 사용 시점 gate와 동일하다. 집합 전체와
  consent head에 대한 SHA-256 digest(`entriesDigest`)를 함께 고정하고, 재검증은 같은 lock·같은
  statement로 현재 집합을 다시 읽어 **집합 전체**를 비교한다. 고정 이후 coach 사용이 켜진 자료는
  `added`로 보고하며 이 경우 `stale=true`다. 재검증은 형태 검증에 더해 제출된 manifest의 consent
  head와 entry로 digest를 다시 계산해 `entriesDigest`와 대조하고, 불일치하면
  `COACH_USE_MANIFEST_INVALID`로 거절한다. digest scope와 계약에 tenant 식별자를 포함하므로 다른
  tenant의 manifest는 — 빈 집합처럼 내용이 같아도 — 이 tenant에서 통과하지 못한다. 같은 자료를 두 번
  고정한 manifest도 계약에서 거절한다.
  이 digest는 key 없는 SHA-256 자기 일관성 검사이므로 **출처를 증명하지 않는다.** capture 이후의 변조,
  다른 tenant의 manifest, 우발적 손상은 잡지만 SHA-256을 계산할 수 있는 호출자는 일관된 manifest를
  위조할 수 있다. manifest는 외부 입력이 아니라 서버 내부 산출물이며 이를 받는 route는 없다. 외부
  입력으로 열려면 HMAC이나 서버 저장 manifest 식별자가 필요하다.
  계약 상한(100)을 넘는 수집은 잘린 snapshot을 반환하지 않고 `COACH_USE_MANIFEST_TOO_LARGE`로
  실패한다. 없음(빈 집합)도 digest로 고정한다.
  완전성의 근거는 lock이 아니라 단일 statement의 MVCC snapshot이다. tenant command advisory lock은
  응용의 access·consent command에 대해서만 직렬화하고, derived cleanup lifecycle 함수나 직접 SQL
  update는 그 lock을 잡지 않는다. 그런 변경은 mixed snapshot이 아니라 digest 불일치로 드러난다.
- 접근 상태는 활성 공유를 전부 반환하고, 철회 이력은 잘림 표시가 있는 별도 bounded page로 준다.
  이력이 아무리 길어도 살아 있는 공유가 목록에서 사라져 철회 불가능해지지 않는다. 철회 이력은
  page 크기+1을 읽어 초과분으로 잘림을 판정하므로 정확히 50건인 이력을 잘렸다고 보고하지 않는다.
- grantee의 공유 목록은 filtered set·page·count를 **단일 CTE statement**에서 읽는다. count 전체 scan에는
  share key와 정렬 key만 buffer하고, 넓은 resource 행은 page에만 join하므로 공유가 많은 principal에서
  temp file spill과 statement timeout 위험을 키우지 않는다. 여러 소유자가
  동시에 공유·철회해도 grantee의 tenant lock으로는 직렬화할 수 없으므로, count와 page를 나누면
  `total < items.length` 같은 계약 위반이 생긴다. `offset`은 10,000으로 제한되며 그 범위를 넘는 공유는
  이 endpoint로 walk할 수 없다(계약 주석에 명시). `total`은 실제 count이므로 한계를 넘은 principal도
  더 많은 공유가 있다는 사실은 알 수 있고, 소유자가 철회에 사용하는 자료별 접근 상태는 활성 공유를
  전부 반환하는 완전한 뷰로 남는다.
- grantee의 파일 원본 열람은 서버 streaming 경로로만 가능하다. 요청 시작 시점에 활성 share·삭제
  여부·현재 version을 한 statement에서 다시 확인하고, storage ref나 signed URL은 client에 전달하지
  않는다. 소유자와 다른 key namespace는 거절한다. **권한 확인은 요청 시작 시점 기준이다. 이미 시작된
  전송은 중간에 끊지 않는다.** 공유 파일은 10 MiB로 제한되고 인가 직후 object를 열므로 노출 창은
  bounded response body 하나다. 계약·API·UI 문구는 이 경계를 그대로 말한다. 자료실의 삭제 안내도
  “이후의 모든 열람 요청이 즉시 차단되고, 이미 시작된 파일 전송은 중단되지 않는다”로 표기한다.
- 변화가 없는 command(이미 활성인 공유 재요청, 이미 철회된 공유, 같은 값 재설정)는 멱등 receipt만
  남기고 `resource.access_unchanged`를 발행한다. 변경 event와 no-op을 구분해 소비자를 오도하지 않는다.
- AI 동의 철회는 정책 변화다. `consent` trigger가 tenant의 모든 자료에서 `include_for_coach`를 끄고
  revision을 올리며 audit fact와 cleanup manifest를 남긴다.
- audit fact는 `resource_access_audit`에 append-only로 쌓고 운영 로그와 분리한다. 본문, storage ref,
  credential은 넣지 않는다. public DTO와 계정 export에도 storage ref·내부 오류는 노출하지 않는다.

## 구현·검증 기록

Migration 030은 `resource`의 review/coach CHECK를 확장하고 `reviewed_at`·`coach_use_enabled_at`을
추가하며, `resource_share`, `resource_access_audit`, `resource_derived_cleanup`과 tenant RLS,
transition trigger, lease/finish/prune 함수, 사용 시점 gate 함수, 동의 철회 trigger,
`revoke_resource_shares`, export 대상 확장, 계정 말소 경로를 추가한다. `erase_account`는 row를 지우기
전에 모든 활성 share를 철회하고 자료별 `account_erased` manifest를 남긴다.

`packages/server/persistence/src/resource-access.ts`는 공유·철회·검토·coach 사용 command,
접근 상태 read, grantee 목록/열람, coaching evidence가 고정하는 `resource-access-v1` manifest 수집과
사용 시점 재검증을 제공한다. 모든 command는 tenant advisory lock, expected revision CAS,
멱등 receipt, outbox event를 한 transaction에 기록한다. 삭제는 coach 사용 해제, share 철회,
파생 manifest, object cleanup, receipt tombstone을 같은 transaction에서 수행한다.

API는 `/resources/:id/access`, `/resources/:id/shares`, `/resources/:id/shares/:shareId`,
`/resources/:id/reviewed`, `/resources/:id/coach-use`, `/resources/shared-with-me[...]`를 제공한다.
검토와 coach 사용은 서로 다른 endpoint이며 strictObject 검증이 한 요청에 두 전환을 섞지 못하게 한다.
멱등키는 헤더에서만 받고, 소유자·grantee는 인증 principal에서만 얻는다. 오류는
404/409/422로 정규화하고 내부 메시지를 노출하지 않는다.

자료실 UI는 reader 아래에 접근 revision, 검토 상태, coach 사용 상태, 미완료 cleanup, 활성 공유 목록과
명시 전환 버튼·공유 폼을 제공한다. 목록·reader의 상태 문구는 실제 `reviewedState`/`includeForCoach`를
반영한다. 계정 export는 `resourceShares`와 `resourceAccessAudit`을 추가한 새 버전을 사용한다(이 세션에서
M2-03 갤러리 작업과 병행되어 최종 번호는 통합 시점 기준 v16이다).

## 검증하지 않은 것

- 검색 색인·retrieval cache·저장된 인용 저장소 자체가 아직 없다. worker의 기본 실행기 map
  `noConfiguredDerivedStorePurge`는 **비어 있다**. 실행기가 하나도 없으면 queue를 lease조차 하지 않고,
  일부만 있으면 lease를 `release_resource_derived_cleanup`으로 되돌려 attempt를 되돌린다. 따라서
  manifest는 완료되지도, dead-letter로 소진되지도 않으며 `resource_coach_use_authorized()` gate도 닫힌
  채로 남는다. M2-05가 실제 삭제 실행기를 등록하면 그동안 쌓인 backlog가 그대로 처리된다.
  (최초 구현은 네 target을 no-op으로 등록해 manifest를 완료 처리했고, 그 경우 gate가 다시 열리며
  M2-05가 실제 저장소를 추가해도 이미 완료된 manifest가 재생되지 않는다. peer review finding 1로
  지적되어 빈 map + 실패 폐쇄로 수정했다.)
- 이 작업의 접근 manifest(`resource-access-v1`)는 resource 범위에서 수집·재검증하지만, 아직
  `coreEvidenceDependencyManifest`(`packages/contracts/src/evidence-dependencies.ts`)에 합쳐 넣지
  않았다. 해당 계약 파일은 이 작업의 write scope 밖이며 M2-05 통합 대상이다.
- grantee 열람은 같은 배포 안의 다른 principal을 대상으로 한 통합 테스트로만 확인했다. 실제 코치 계정
  onboarding, 초대, 알림과 외부 공유 UI는 구현하지 않았다.
- backup/restore drill과 Playwright 전체 E2E suite는 이 작업에서 다시 실행하지 않았다. 병행 중인
  M2-03 갤러리 작업과 계정 export 번호가 겹치므로 통합 시점에 root가 함께 재실행해야 한다.
- grantee 파일 streaming은 로컬 filesystem adapter와 실제 PostgreSQL RLS로만 확인했다. 원격 object
  provider와 대용량 streaming 성능은 별도 배포 검증 대상이다.

## Peer review 대응

base `850519b`에 대한 독립 peer review가 blocking 5건과 non-blocking 3건을 보고했고 모두 반영했다.

1. worker 기본 derived purge map을 비웠다. 실행기가 없는 target은 완료로 기록하지 않고
   `DERIVED_TARGET_UNSUPPORTED`로 재시도한다. worker 테스트도 완료가 아니라 실패 폐쇄를 검증하도록
   바꾸고, 실제 실행기가 모두 있을 때만 완료되는 회귀를 추가했다.
2. 검토 해제가 coach 사용 해제를 함께 수행하던 동작을 제거하고 `REVIEW_WITHDRAWAL_BLOCKED`를
   service와 DB trigger 양쪽에서 강제했다. 실제 PostgreSQL에서 service 경로와 직접 UPDATE 경로를
   모두 거부하는지, coach 사용 중지 후에는 해제가 되는지 검증했다.

### 재검토에서 추가된 3건

1. 실행기가 없는 target이 attempt·dead-letter 예산을 소모하던 문제를 고쳤다. 실행기가 전무하면
   queue를 lease하지 않고, 일부만 있으면 새 `release_resource_derived_cleanup`으로 lease를 되돌려
   `attempts`를 원복한다. dead-letter 임계(100)의 1.5배인 150회씩 두 경로를 돌려도 `attempts=0`,
   미완료 상태가 유지되고, 실행기를 등록하면 곧바로 완료되는 것을 실DB로 확인했다. release는 아직
   유효한 lease에만 적용되므로 거절되면 `lease_lost`를 반환한다.
2. manifest 완전성을 literal 주장이 아니라 실제로 강제했다. 수집과 재검증 모두 tenant advisory lock을
   잡고 consent head·인가 집합·시각을 한 statement에서 읽으며, 집합 digest를 고정해 사용 시점에 집합
   전체를 비교한다. 고정 이후 인가된 자료는 `added`로 보고한다. 동일 tenant 반복 수집의 digest 동일성,
   동의 철회 시 digest 변화, 새 자료의 `added` 보고를 실DB로 확인했다.
3. 공유 파일 전송의 인가 경계를 요청 시작 시점으로 명시했다. 전송 중 중단은 구현하지 않기로 한 결정에
   따라 계약 주석, API 주석, 자료실 삭제 안내 문구, 이 문서를 모두 “이후의 모든 열람 요청을 차단하며
   이미 시작된 전송은 중단하지 않는다”로 맞췄다. 파일 상한 10 MiB와 인가 직후 object open으로 창을

4. 철회 이력 잘림 판정을 page+1 읽기로 바꿔 정확히 50건인 이력을 잘렸다고 보고하지 않는다.
