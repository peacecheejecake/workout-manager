## 2. `walkingRoutes` 운영 배선 — 실제 엔진으로 했다

**이 기계에서 엔진이 뜬다.** Java 17(`/opt/homebrew/opt/openjdk@17`)과 `.geo-build/`의 GraphHopper jar,
서울 graph(`foot`, manifest `c57f12f5975347e8`)가 있다. `loadRoutingDeployment`가 디스크에서 세 해시를
모두 통과시켰다(graph `c5fbcdec…`, jar `e5a1268f…`, profile `e72537c1…`).
엔진은 loopback 8991에서 약 1.1초 만에 뜨고, 기동 직후 RSS는 243–274 MiB였다.

**배선.** 새 모듈 `apps/api/src/routing-deployment.ts`의 `createConfiguredWalkingRoutes`를 추가했다.
입구는 `loadRoutingDeployment` 하나이고 신원을 손으로 만드는 경로가 없다. 가드를 우회하지 않았다.
`configured.ts`와 identity harness가 이 함수 하나를 함께 쓴다.

| 상태                                         | 결과                                                         |
| -------------------------------------------- | ------------------------------------------------------------ |
| `ROUTING_*` 네 변수 모두 없음                | `null`: 라우트 미등록(이전과 같음)                           |
| 일부만 있음 / 허용 host만 있음               | 기동 거절 `ROUTING_CONFIGURATION_INCOMPLETE`                 |

[operations-runbook](../operations-runbook.md#자체-보행-routing-엔진-배선-m2-01k)과
`routing-deployment.ts` 주석에 적었다.

검증된 신원으로의 계산, `/info`의 import가 다를 때의 `graph_mismatch`를 고정한다.

**운영 증거**는 `scripts/probe-routing-operational.mts --execute`다. 이 probe는

## 3. graph 교체·rollback

graph B는 `scripts/build-routing-graph.mts`의 manifest writer를 그대로 써서 만들었다. 그 스크립트의
import 단계를 `importRoutingGraph`로 꺼냈다. 이 함수는 호출자가 준 디렉터리를 **`rm -rf`한 뒤** import하며,
주석에 그렇게 적었다.

리팩터된 경로를 실제로 실행한 것은 **graph B 빌드 한 번**뿐이다(probe 첫 실행, import 후 manifest를
`loadRoutingDeployment`가 검증함). `main()`의 비-reuse 분기(graph A 재빌드)는 다시 돌리지 않았다.
`--reuse` 실행은 리팩터가 건드리지 않은 분기라 "동작이 같다"의 근거가 되지 않는다.

기록된 probe 실행([routing-operational-acceptance.json](../research/routing-operational-acceptance.json))은
**B를 다시 빌드하지 않고 재사용**했다(`builtThisRun: false`).
같은 extract·jar·profile을 **다시 import**한 별도 빌드이므로 `graphImportedAt`이 다르다
(A `2026-09-21T14:09:12Z`, B `2026-09-23T04:11:56Z`). build id는 A `c57f12f5975347e8`, B
`f2448701c8f6e2da`다. **더 새로운 지도 데이터가 아니다.** 시스템이 다른 graph로 취급해야 하는 다른
빌드일 뿐이다. 디렉터리는 `.geo-build/routing-graph/swap-b/`이며 Git에 넣지 않는다.

관측(한 코스 위 revision `번호:graph`):

1. A 위에서 저장: `1:null 2:A 3:A`.
2. 엔진만 B로 바꾸고 API는 A에 고정: 계산이 **502 `graph_mismatch`**, 아무것도 쓰지 않음.
3. API를 B로 재배포: revision 세 개의 번호·graph·**content digest가 그대로**다(비교한 것은 digest다).
   조용한 재계산이 없다.
4. B 제안을 `{previous: A, next: A}`로 저장하면 **409 `COURSE_GRAPH_ACKNOWLEDGEMENT_STALE`**.
   `{A, B}`로 저장하면 `4:B`가 추가되고 앞 세 개는 불변이다.
5. rollback으로 엔진을 A로 되돌리고 API는 B에 둠: **502 `graph_mismatch`**. API도 A로 되돌리면
   계산된 graph id가 **정확히 A와 같다.** `{B, A}` 확인으로 저장하면 `5:A`가 추가되고 이력은 그대로다.

**가드가 공허하지 않음:** 어댑터의 `import_date` 비교를 끄고 돌리면 2단계와 5단계 검사가 **실패**한다
(API가 틀린 신원으로 `route_computed`를 답함). 원복 뒤 `git diff`가 비어 있음을 확인했다.

**판정 partial.** 계획 149행은 "**원자적** graph 교체"를 요구한다. 교체 절차는 엔진 재시작과 API 재배포, 두 단계다. 그 사이 창에서는 `graph_mismatch`가
나고(안전한 쪽), 무중단 교체나 blue/green은 없다. `/info`와 `/route` 사이의 교체 창(M2-01g)은
여전히 닫히지 않는다. 다른 extract로 만든 graph로 교체하는 경우는 extract가 하나뿐이라 시험하지 않았다.

## 4. 통합 수용 spec — `tests/identity/course-acceptance.spec.ts`

한 계정(Alice), 기록 하나, 코스 두 개가 끝까지 상태를 이어받는 **테스트 1개**다. 실제 DB와 로컬
파일시스템 객체 저장소에서 돈다. OIDC는 **fixture provider**다. 구현은 별도 agent가 했고, 나는 이를 읽고
실제 엔진 모드로 돌렸으며 §5의 가드를 추가했다.

1. 실제 FIT를 업로드하고 finalize한다.
2. UI에서 구간을 잘라 코스 A를 만든다.
3. 코스를 연다. 같은 origin의 map worker 요청을 확인하고, **지도가 idle 뒤 코스 선 feature를 실제로
   그렸는지**(`data-rendered-path-features` > 0) 확인한다. 경유점을 추가해 제안을 받고, 저장 전
   revision 불변을 확인한 뒤 검토 저장한다(`acknowledgedGraph {null, g}`).
4. 1,200 m 후보를 만들고 골라 저장한다(`{g, g}`).
5. UI에서 GPX를 가져와 코스 B를 만든다.
6. B에 보호 구역 trim을 적용한다.
7. 썸네일이 둘 다 ready가 되고, 인증 다운로드의 SVG path가 geometry와 일치한다. Bob은 404를 받는다.
8. GPX를 내보낸다. UI 파일과 API 응답이 바이트까지 같다.
9. 계정 export v21에 코스·revision·썸네일·보호 구역이 있고 원장에 좌표가 없다.
10. 원본 활동을 삭제한다. 영향 목록은 A만이고 digest가 일치한다.
11. A는 unavailable이 되고 썸네일은 404, GPX는 410이다. B는 revision·썸네일·GPX 바이트가 모두 불변이다.
12. 같은 source로 재가져오기를 하면 `suppressed`이고, 코스 재생성·복사는 거절된다.
13. B를 삭제한다.

엔진 모드는 `IDENTITY_E2E_ROUTING`으로 고른다. 저장된 revision의 graph·엔진 버전·`identitySource`를
**모드별 기대값과 단언**하므로 fixture 녹색이 실제 엔진 증거로 오인될 수 없다.

| 실행                                           | 결과                                          |
| ---------------------------------------------- | --------------------------------------------- |
| fixture 모드 단독(구현 agent, 초판)            | 4/4                                           |
| **실제 엔진 모드**, 렌더 단언을 넣은 최종 spec | **3/3**(12.7 s, 13.7 s, 12.4 s)               |
| fixture 모드, 최종 spec                        | 1/1                                           |
| F2를 되돌리고(worker 대기는 끔) web 재빌드     | **실패**: spec:327 `Expected > 0, Received 0` |
| 전체 identity 스위트, 최종 트리                | §10                                           |

**렌더 증거.** `data-rendered-path-features`는 map adapter가 idle마다 경로 layer에만
`queryRenderedFeatures`를 실행한 결과다(`maplibre-adapter.ts:274-285`). 코스 모듈은 이 값을 이미
받을 수 있었지만 쓰지 않았다. 지금은 `course-map-leaf.tsx`가 `onRenderIdle`을 넘기고,
`course-workbench.tsx`가 그 값을 지도 pane의 data 속성으로 둔다. 화면 문구는 바뀌지 않는다.
basemap tile만으로는 이 값이 0보다 커지지 않는다(코스 source의 layer만 센다). 단서: 세는 layer에 point
layer가 포함되므로 **선 없이 점만 그려져도 0보다 크다.** 그리고 이 단언은 Next shell에서만 돈다. worker 요청 대기는 대리 지표이므로 렌더 단언과
함께 남겨 두었고, 비공허성 확인 때는 worker 대기를 끈 채 렌더 단언만으로 실패하는 것을 봤다.

"복원"은 이 제품에 **코스 복원 기능이 없다.** 구현된 동작은 삭제 억제와 재생성·복사 거절뿐이며 E2E는
그것만 단언한다. 계정 erasure는 뒤 spec의 계정을 지우므로 이 흐름에서 하지 않았다(§6).

## 5. 발견

**F1 — 반복 편집이 제안 quota에 막힌다 (failed, 고치지 않음).** 코스당 저장하지 않은 제안 상한은 5,
TTL은 30분이다(`packages/server/persistence/src/courses.ts:880-895`). 이 상한은 만료·저장되지 않은
**모든** 제안을 센다. 편집기는 최신 draft의 제안만 저장할 수 있으므로, 쓸 수 없게 된 옛 제안이
30분 동안 자리를 차지한다. 실제 엔진으로 재현한 결과(`iterative-recompute-refused-by-proposal-quota`):

```text
1:200:route_computed 2:200 3:200 4:200 5:200 6:429:ROUTE_PROPOSAL_QUOTA_EXCEEDED
```

- 거절은 **엔진이 계산을 끝낸 뒤**에 온다. 엔진 자원을 쓰고 버린다.
- 고른 후보의 형제 3개도 계속 자리를 잡는다. 그래서 후보 하나를 저장한 뒤에는 30분 동안 재계산이 두 번뿐이다.
- 저장하지 않은 재계산 두 번 뒤에는 후보 탐색(4칸 필요)이 429다. 성능 probe의 첫 판에서 실제로 관측했다.
- **1차 판의 문구 주장을 정정한다.** "저장하지 않은 경로 제안이 너무 많습니다. 잠시 후 다시 시도하세요."
  (`course-editor.tsx:137-138`)는 **저장 오류 표(`saveErrors`)에만** 있다. 재계산 경로(`course-editor.tsx:309-323`의
