## 1. 결정과 근거

### 1.1 extract: Geofabrik 월간 `south-korea-260901.osm.pbf`, SHA-256 pin

- `south-korea-latest.osm.pbf`는 날짜 붙은 최신 파일로 가는 302다. allowlist 취득은 redirect를 따라가지 않으므로
  (`--max-redirs 0`) **날짜 붙은 파일 자체**를 allowlist(`osm-extract-south-korea`)에 고정했다. 날짜 붙은 이름의 바이트는
  바뀌지 않으므로 SHA-256을 pin했다.
- **월간 파일을 고른 이유(검토 1차 item 6).** 2026-09-25 Geofabrik 목록: 일간 파일은 약 1주(260918–260924), 월간 파일은
  약 석 달(260701–260901), 연초 `YY0101`은 2015년부터. 처음 고정한 일간 `260924`는 일주일 뒤 다시 받을 수 없다. 연초
  `260101`은 오래 남지만 9개월 묵은 데이터다. 월간 `260901`이 그 사이다. 보관 기간이 지나면 다시 받기는 404로 닫힌 쪽으로
  실패하므로 **PBF를 graph와 함께 보관한다**(runbook). 새 snapshot은 pin 변경과 새 graph import다.
- 다운로드(allowlist fetcher, 33.1 s): 286,403,403 bytes, SHA-256
  `848daadc56b2c2a808b30b2778f834c2802097ab382805c9fd42f248f4d6284b`, `Last-Modified: Wed, 02 Sep 2026 05:13:33 GMT`,
  ETag `"11122b4b-65a7918cd6a87"`. **Geofabrik이 게시한 `south-korea-260901.osm.pbf.md5`
  (`3f6596139dedbbe2f6b2b9a4ff486c63`)와 같은 바이트의 MD5가 일치했다** — pin이 게시자의 파일을 가리킨다는 독립 대조.
- PBF 헤더: `osmosis_replication_timestamp=2026-09-01T20:20:50Z`, bbox `124.3188,32.36076 – 132.3386,38.64966`.
- 라이선스: ODbL 1.0, `© OpenStreetMap contributors`. Geofabrik은 user·changeset 메타데이터를 뺀 OSM 원본을 재배포한다
  (지역 페이지 문구). 새 출처를 지어내지 않았다.

### 1.2 extract 선택은 allowlist id — `ROUTING_EXTRACT_SOURCE`

`build-routing-graph.mts`의 extract 경로·지역 이름이 상수(Seoul)였다. `routingExtractFrom(id, root)`를 더했다.

- 없음/`osm-extract-seoul`: `.geo-build/source/region.osm.pbf`, `Seoul (BBBike city extract)`, import heap 2048 MiB.
  **기본 동작은 전과 같다.**
- `osm-extract-south-korea`: `<ROUTING_GRAPH_ROOT>/extract/south-korea.osm.pbf`, `South Korea (Geofabrik extract
2026-09-01)`, import heap 4096 MiB. 공유 `.geo-build`에 쓰지 않으므로 기본 root에서는
  `ROUTING_EXTRACT_NEEDS_A_RELOCATED_ROOT`로 거절한다.
- 그 밖의 값(경로·URL 포함)은 `ROUTING_EXTRACT_SOURCE_UNKNOWN`.
- build는 import 전에 `verifyAllowedSourceFile(sourceId, path)`로 **extract pin**을 대조한다(전에는 jar만 대조했다).
- manifest의 `extractRegion`은 선택된 extract의 지역이다.
- build·엔진 로그·rollout·swap·운영·coverage·성능 probe가 같은 두 변수(`ROUTING_GRAPH_ROOT`,
  `ROUTING_EXTRACT_SOURCE`)를 따른다.

### 1.3 `ROUTING_GRAPH_ROOT`는 가리키는 곳으로 판단한다 (검토 1차 item 3·4에서 고침)

검토 전 판은 `.geo-build`의 lexical 철자와 `realpath(.geo-build)` 두 철자만 비교했고, "두 철자 모두 거절한다"고 적었다.
**그 주장은 불완전했다**: 대소문자(`.GEO-BUILD`, APFS는 대소문자를 구분하지 않는다)와 `.geo-build`를 가리키는 다른
symlink(`elsewhere/geo-link`)로 우회됐다. 지금은:

- 후보 root의 **가장 가까운 존재하는 조상을 realpath**로 풀고 나머지를 붙인 뒤, `.geo-build`의 realpath·lexical 철자와
  **대소문자 없이** 비교한다(M2-01al `realOutputPath`와 같은 방식).
- `routingGraphRootFrom(value, geoBuild)`가 `.geo-build` 경로를 인자로 받는다. 시험은 임시 디렉터리에 `main/.geo-build`와
  그것을 가리키는 `workspace/.geo-build` link를 만들어 쓴다. 그래서 `.geo-build`가 symlink가 아닌 checkout(CI 포함)에서도
  실경로·별칭 link·대소문자 세 경우가 모두 실제로 시험된다.
- 대소문자를 구분하는 볼륨에서도 lower-case로 비교하므로 `.GEO-BUILD`라는 별개 디렉터리도 거절된다(닫힌 쪽).

### 1.5 "배포 전환"이 이 기계에서 뜻하는 것

이 기계에는 상주하는 API·엔진이 없다(시작 시 8991–8999·3100·4200·4300·4400 listen 0). 그래서 전환은 runbook의
blue/green 절차를 **실제 production composition(`createConfiguredApi`)** 안에서 실행한 것이다:
`probe-routing-profile-rollout.mts`가 blue = 옛 deployment, green = 새 root를 helper로 띄우고, API의
`RoutingDeploymentSwitch.switchTo`/`rollback`(SIGHUP 처리기가 부르는 같은 함수)으로 옮긴다. 이 노드는 여기에
"전진 재전환 → blue 종료 → green 단독 서빙"(runbook 4·5단계)을 더했다. 운영 호스트·SIGHUP 파일 경로 자체의
실행은 이 노드의 증거가 아니다.

`relocatedDeploymentNote()`는 전에 옮긴 root를 무조건 "scratch, 영속하지 않음"이라고 적었다. 이 노드의 root는 영속
위치다. 이제 확인 가능한 사실만 적는다: root가 임시 디렉터리 안인지(`rootLocation`), 선택된 extract, 기본 layout이
가진 graph id. 임시 디렉터리 안이면 예전 문구를 그대로 쓴다.

### 1.6 옛 graph에서 계산된 코스 revision — **그대로 받아들인다**

기존 graph 신원 설계(M2-01h, M2-01k-e)를 따른다. 새 규칙을 만들지 않았다.

- revision은 자기를 계산한 graph 신원(`computation.graph`)을 지닌다. graph 교체는 저장된 코스를 재계산하지 않는다.
- **재라우팅 표시(flag)를 하지 않는다.** 그런 상태는 설계에 없고, 도입하면 "자동 재계산 없음 · 재계산은 언제나
  사용자가 누르는 버튼"(M2-01h)과 어긋나는 새 상태를 만든다. 편집 화면은 제안의 graph가 head의 graph와 다를 때
  이미 경고한다(M2-01h `says the graph changed before a course computed on an older one is replaced`).
- 새 graph의 제안 저장은 양측 확인 `{previous: c57f12f5975347e8, next: 188b65effcc6ef5c}`만 받는다. `{old→old}`는 409
  `COURSE_GRAPH_ACKNOWLEDGEMENT_STALE`.
- 실측(rollout probe): 전환 뒤 저장 revision의 digest 불변, 재라우팅하지 않은 코스를 blue 종료 뒤 읽으면 200
  `available`, head revision·digest·graph(`c57f…`) 그대로(`course-on-the-old-graph-accepted-unchanged`).

### 1.7 엔진 메모리 예산은 기준선 graph에 묶인다 (검토 1차 item 2)

전국 graph는 Seoul graph의 약 7배이고 엔진 RSS는 약 2.3배다. 넓힌 예산(idle 1100, 부하 2000 MiB)을 Seoul graph run에
적용하면 Seoul RSS가 두 배가 되어도 통과한다. 그래서:

- `performance-budget.json`의 engine-phase MiB 지표는 `baseline.routingGraphContentSha256`(기준선 run의 graph)을 **반드시**
  지닌다(`parseBudgetFile`: 없거나 형식이 틀리면 `BUDGET_BASELINE_GRAPH_INVALID`, 다른 지표에 있어도 거절).
- probe는 결과에 측정한 graph(`details.routingGraph.graphContentSha256`)를 남긴다. `evaluateBudget`는 그 지표의 표본이
  다른 graph나 graph를 기록하지 않은 run에서 왔으면 **판정을 거절**한다(`ENGINE_GRAPH_NOT_BASELINED`, 실패가 아니라 거절).
- `verifyBaselinesAgainstRuns`(N-h)도 기준선 run 각각의 graph가 그 값인지 확인한다(`BASELINE_RUN_GRAPH_MISMATCH`).
- 예산 파일 `method.graphBinding`과 두 지표의 `description`에 넓힌 사실과 옛 값(470·800)을 적었다.
- `engine.routeUnderLoadMs`(시간)는 묶지 않았고 M2-01k-f(Seoul) 기준선을 그대로 둔다.
