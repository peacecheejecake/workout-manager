## 1. `pruneEmptyParents` × `prepareParents` 디렉터리 경합

### 1.1 재현

`delete`는 객체를 지운 뒤 비게 된 상위 디렉터리를 root 직전까지 올라가며 지웠다. 형제 쓰기의
`prepareParents`는 상위 디렉터리를 하나씩 `lstat`→(`mkdir`)→`lstat`→`chmod` 하며 내려간다. 공유
디렉터리가 **비어 있는 순간**은 정확히 형제가 아직 아무것도 만들지 않은 순간이므로, 그 순간 삭제의
가지치기가 그 디렉터리를 치우면 형제 쓰기는 어느 단계에서든 터진다.

실측(macOS 27 / APFS, 이 기계):

| 재현                                                              | 결과                                                                                                 |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 한 프로세스, 형제 썸네일 임시 객체 write/delete 400쌍(800 연산)   | 0 ~ 19건 실패 (타이밍 의존)                                                                          |
| **4 프로세스**, 각자 write→delete 100회, 같은 코스(≈800 연산) × 3 | **67 / 40 / 41건 실패** — `ENOENT@mkdir·lstat·chmod·open`, `EINVAL@mkdir`                            |
| 실패 경로                                                         | `private/`, `private/v1`, `tenants`, `tenants/T`, `courses/C`, `thumbnails`, `temporary` **모든 층** |

검토자의 수치(800 중 269)보다 낮지만 같은 모양이다. 저장소 시험으로 남긴 것은 실제 운영 모양(여러
worker 프로세스가 한 저장소를 공유)인 **다중 프로세스** 재현이다 —
`local-filesystem.test.ts > lets siblings write and delete side by side in several processes without one failure`
(4 프로세스 × 25 라운드 × 키 모양 5종 × write·publish·delete = 1,500 연산).

### 1.2 macOS `mkdir`의 `EINVAL`이 무엇인지 — 측정

추측으로 흡수하지 않기 위해 C로 따로 측정했다(`mkdir(P)`·`mkdir(P/X)` 100만 회 vs 다른 스레드의
`rmdir(P/X)`·`rmdir(P)` 반복).

| 조건                                                  | `mkdir(P/X)` 결과                                                 |
| ----------------------------------------------------- | ----------------------------------------------------------------- |
| 동시 `rmdir(P)` 있음                                  | ok 101,376 · ENOENT 103,140 · EEXIST 671,639 · **EINVAL 123,845** |
| 동시 `rmdir(P)` 없음(대조군)                          | ok 208,816 · EEXIST 791,184 · **EINVAL 0**                        |
| 순차: 이미 지워진 디렉터리 fd 기준 `mkdirat`/`openat` | **ENOENT** (EINVAL 아님)                                          |

즉 이 기계에서 `mkdir`의 `EINVAL`은 **부모 디렉터리가 호출 도중에 제거되는 경우**에만 나온다. 다만
`EINVAL`은 다른 이유(파일시스템이 받지 않는 이름 등)로도 쓰이는 errno이므로, "`EINVAL`=부모가
사라짐"으로 흡수하는 것은 이 한 기계의 관측을 일반 규칙으로 올리는 것이 된다. 이것이 아래 선택의
근거 하나다.

### 1.3 두 접근 비교와 선택

| 접근                                                             | 무엇을 결정해야 하나                                                                                                                                                                                                               | 판정                                          |
| ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| A. `prepareParents`가 `ENOENT`/`EINVAL`을 흡수하고 걷기를 재시도 | `EINVAL`의 의미(위: 기계 의존), 재시도 상한, 흡수 후 재검증. 게다가 `prepareParents`가 끝난 **뒤** `open(O_CREAT)`·`link` 사이 창도 남아 거기서도 ENOENT를 흡수해야 하고, `link`의 ENOENT는 "임시 원본이 사라짐"과 구별되지 않는다 | 기각 — symlink 가드 안에서 오류 해석이 늘어남 |
| B-1. 검토자 제안: tenant/course 층만 지우지 않음                 | 없음                                                                                                                                                                                                                               | **불충분 — 측정으로 기각**                    |
| **B-2. 형제가 공유하는 층은 전부 지우지 않음(쓰기 단위 바닥)**   | 키 모양별로 "이 객체의 쓰기 단위만 쓰는 디렉터리" 깊이                                                                                                                                                                             | **채택**                                      |

B-1을 되돌림으로 측정했다: 가지치기를 `private/v1/tenants/T/<컬렉션>/<소유자>` 아래까지만 허용하도록
바꾸자 다중 프로세스 시험이 **8/8 실패**(회당 8~31건, `ENOENT@mkdir·lstat·chmod`, `EINVAL@mkdir`는 4회에서 관측).
형제 썸네일 임시 객체는 `courses/C/thumbnails/temporary/` **한 디렉터리에 나란히** 놓이므로,
course 층을 지켜도 그 아래 `thumbnails/`·`temporary/`가 여전히 경합 지점이다.

B-2는 경합을 **견디는 것이 아니라 없앤다**: 다른 쓰기 단위가 쓰고 있을 수 있는 디렉터리는 아무도
지우지 않으므로 `prepareParents`가 잃을 것이 없다. `prepareParents`는 **한 글자도 바뀌지 않았고**
(M2-01m의 `missing()`+`lstat()` 합치기, ENOENT만 흡수, EACCES·ELOOP·symlink 거절 그대로),
`mkdir` 오류를 새로 흡수하지도 않는다.

쓰기 단위 = 한 시점에 한 writer만 소유하는 것(업로드, URL 수집, 코스 revision의 렌더). 그 단위의
id로 이름 붙은 디렉터리만, 그 단위의 writer 또는 그 writer가 끝나거나 포기된 뒤의 같은 단위
cleanup만 만들고 지운다.

| 키 모양               | 지워지는 단위 디렉터리                      | 남는 공유 바닥              |
| --------------------- | ------------------------------------------- | --------------------------- |
| resource/gallery 임시 | 없음                                        | `…/temporary`               |
| resource/gallery 최종 | `uploads/<upload>`, `…/sha256`              | `…/objects/uploads`         |
| URL 임시              | `url-ingestions/<ingestion>`, `…/temporary` | `…/url-ingestions`          |
| URL 최종              | `<ingestion>`, `<kind>`, `sha256`           | `…/url-ingestions`          |
| track 임시            | `temporary/<upload>`                        | `…/tracks/T/temporary`      |
| track 최종            | `uploads/<upload>`, `…/sha256`              | `…/tracks/T/<kind>/uploads` |
| 썸네일 임시           | 없음                                        | `…/thumbnails/temporary`    |
| 썸네일 최종           | `revisions/<revision>`, `…/sha256`          | `…/thumbnails/revisions`    |

썸네일 최종의 `revisions/<revision>`을 단위로 본 근거: revision 하나에는 `course_thumbnail` 행이
하나뿐이고(039 주석 — enqueue 트리거가 revision INSERT에서만 만든다), 렌더는 결정적이라 같은
revision의 재시도는 같은 키를 쓴다. 이 가정이 깨지면(renderer_version이 올라 한 revision에 다른
sha가 공존) 그 revision 디렉터리 안에서만 좁은 경합이 남고, 그 경우도 렌더 재시도 5회 안에서
흡수된다 — 기존보다 나빠지는 곳은 없다.

비용: 빈 디렉터리가 **객체 수가 아니라 소유 엔티티 수**(tenant·resource·gallery item·track·course)에
비례해 남는다. 원래 주석대로 이것은 위생이지 상한이 아니며 아무것도 여기에 의존하지 않는다.
`switch`는 `satisfies never`로 끝나 새 키 모양을 추가하면 컴파일이 깊이를 요구한다.

## 2. reconciliation 스윕의 참조 단위 오류 격리와 dead-letter

### 2.1 재현(기준 코드 `e2b3bf5` 그대로)

기준 커밋의 `resource-object-cleanup.ts`를 그대로 꺼내(`e2b3bf5` 판본) 039까지 올린 격리
PostgreSQL 14와 실제 파일시스템에 붙여 돌렸다(임시 시험, 실행 후 삭제). 같은 tenant 아래 두 참조 —
앞의 것은 오염, 뒤의 것은 아무것도 참조하지 않는 실제 고아 — 를 8일 전 기록으로 색인에 넣고 cursor를
그 앞에 세운 뒤 창 크기 2로 5회 스윕:

| 오염                         | 5회 결과                                 | cursor   | 뒤의 고아 receipt |
| ---------------------------- | ---------------------------------------- | -------- | ----------------- |
| 썸네일 경로에 심은 symlink   | **5/5 `UNSAFE_STORAGE_PATH`로 run 종료** | 5/5 불변 | **0**             |
| track 경로의 권한 0 디렉터리 | **5/5 `EACCES`로 run 종료**              | 5/5 불변 | **0**             |

즉 검토 지적 그대로: 창이 끝나지 않아 cursor가 전진하지 않고, 뒤의 참조는 다시 검사되지 않으며,
worker에서는 스윕 뒤 prune 다섯 개가 매 tick 건너뛰어진다. 같은 상황을 새 코드에 대해 고정한 것이
`reconcile-sweep-faults.integration.test.ts`의 앞 두 시험이다.

### 2.2 설계

- **격리 범위는 `stat` 한 호출뿐.** `try`는 참조 하나의 `storage.stat`만 감싼다. window 읽기,
  settle, reclaim, cursor 등 **DB 실패는 참조 단위가 아니고 기록할 곳도 없으므로** 이전처럼 run을
  끝낸다.
- **올라간 `stat`은 답으로 읽지 않는다.** "없음"(→ settle 가능)도 "있음"(→ reclaim 가능)도 아니다.
  그 참조에 대해서는 settle·reclaim을 **호출하지 않는다.** 그래서 fault가 삭제로 이어질 경로가
  구조적으로 없다(7절 과잉 삭제 금지). 살아 있는 그림·트랙일 수도 있는 객체를 이 경로는 판단하지
  않는다.
- **오류는 버리지 않고 기록한다.** 그 참조의 색인 행에 `sweep_attempts`, `sweep_error_code`(오류의
  code만 — `EACCES`, `UNSAFE_STORAGE_PATH`, 없으면 `OBJECT_STAT_FAILED`; 경로가 들어갈 수 있는
  message는 저장하지 않음), `sweep_first_failed_at`, `sweep_failed_at`, `sweep_retry_at`을 남긴다.
  run 결과에도 `faulted`·`deferred` 수가 나온다. **기록할 감시 행이 없으면(말소·동시 settle) 원래
  오류를 다시 던져 run을 끝낸다.**
- **backoff**: 1분에서 시작해 연속 실패마다 2배, 상한 1일. 10번째 연속 실패부터 코드에 cleanup
  큐(028)와 같은 `DEAD_LETTER:` 접두사가 붙어 운영자가 한 질의로 두 종류의 막힌 일을 찾는다.
- **dead-letter는 감시 중단이 아니다.** `settled_at`은 건드리지 않고, window에 계속 나오며(backoff
  중에는 `deferred`로), 하루 한 번 재시도된다. 큐 항목과 달리 회전에서 빼지 않은 이유: 재시도 비용은
  읽기 전용 `stat` 하나이고 아무것도 지우지 않으며, 빼면 일시적 권한 오류 뒤의 고아가 영원히
  회수되지 않는다.
- **회복**: `stat`이 다시 답하면 다른 참조와 똑같이 settle/reclaim을 거친 **뒤에만** fault를 지운다.
- **backoff 중인 참조도 window에서 걸러내지 않고 `deferred`로 돌려준다.** 걸러내면 한 run이 창을
  채우려고 deferred 행을 얼마든지 읽을 수 있어 "run당 N행" 상한이 깨진다. deferred 행의 비용은 행
  읽기 하나(`stat`·문장 없음).

#### "catch 없음"과 모순되지 않는 이유

M2-01m이 시험으로 고정한 판단은 "스윕 오류를 '스윕했는데 없었다'로 바꾸면 오류를 알려진 결과로
취급하는 것"이었다. 이 노드는 그 판단을 유지한다 — worker에는 여전히 `catch`가 없고,
`lets a sweep failure end the run rather than reporting a sweep that did not happen` 시험은 그대로
통과한다(window 실패 → run 종료, cursor 불변, housekeeping 생략). 달라진 것은 **참조 하나에 대한
`stat` 오류가 갈 곳이 생겼다는 것**뿐이다. 그 오류는 "없음"이나 "처리함"으로 바뀌지 않고, 코드·횟수
·시각과 함께 DB에 **기록되며**, 기록이 안 되면 원래대로 run을 끝낸다. 삼키는 것이 아니라
옮겨 적는 것이고, 옮겨 적을 수 없을 때의 동작은 이전과 같다.

### 2.3 migration 040

`040_reconcile_sweep_faults.sql`. 033~039는 건드리지 않았다.

- 두 색인 표(`activity_track_object_ref`, `course_thumbnail_object_ref`)에 fault 열 5개 + 일관성
  CHECK. 별도 표가 아닌 이유: 색인 행이 이미 참조당 하나, 이미 RLS FORCE, 이미 말소 대상, 이미
  스윕이 읽는 행 — 별도 표는 말소 지점·외래키 잠금·window 조인을 하나씩 더한다.
- 새 함수 6개(모두 `SECURITY DEFINER SET search_path=pg_catalog`, PUBLIC 회수):
  `{activity_track,course_thumbnail}_reconcile_window(text,integer)`,
  `record_{…}_sweep_fault(text,text)`, `clear_{…}_sweep_fault(text)`.
- 기존 `*_reconcile_candidates`는 결과 열을 바꿀 수 없어 `CREATE OR REPLACE` 대신 새 함수로 두고,
  **삭제·수정하지 않은 채 소유자 외 모든 EXECUTE를 회수**했다(이전 빌드 worker는 조용히 격리 없이
  스윕하는 대신 권한 오류로 크게 실패한다).
- worker role grant: 새 6개 추가, candidates 2개 제외. 표 권한 0 유지.
- 코드 인자는 DB에서도 `^[A-Z][A-Z0-9_]{0,63}$`로 검증(message·경로가 들어갈 수 없음).

**잠금 순서**: 새 writer는 record/clear 두 종류이고, 둘 다 **한 문장·한 행·advisory lock 없음**이다.
기다림은 그 행에 대해 최대 한 번이고 기다리는 동안 쥔 것이 없으므로 어떤 writer와도 순환을 만들 수
없다 — `erase_account`의 `77206` → `0` → 행 순서와도 간선이 생기지 않는다(역방향 간선 없음).
실제 DB에서 말소처럼 행을 지우는 열린 트랜잭션 뒤에서 record가 **기다렸다가 NULL**을 받는 것을
시험으로 고정했다.

### 2.4 시험

- 단위(worker, 8개 추가): 기록 후 창의 나머지·cursor·housekeeping 진행 / track errno 코드 / 코드
  없는 오류의 일반 코드 / 기록 불가(NULL) 시 원래 오류로 run 종료 / DB가 기록을 거부하면 run 종료 /

  권한 0 디렉터리 뒤 track 참조, 입력 검증·동시 기록, 말소 대기, window 읽기 상한, 권한 표면.
- 업그레이드(`reconcile-sweep-faults-upgrade.integration.test.ts`): 격리 DB를 039까지 → 039 시대
  권한 부여 → 040 → checksum 1~39 불변, candidates 본문 불변·권한 회수, 기존 행 fault 없음, 재부여
  시 정확히 6개 추가·2개 제외, RLS FORCE·표 권한 0.
- 기존 `course-thumbnail-reconciliation-upgrade` 시험은 "head = 039"를 가정해 040에서 깨지므로

### 2.6 저장소 전체 장애는 run 실패로 남긴다(검토 지적 1, 이 노드가 들인 회귀)

1차 구현은 참조 단위 격리만 했으므로, 저장소 자체가 죽어 **모든 참조가 EACCES·EIO를 내도** run은
성공하고 `faulted=N`만 남았다. M2-01m이었다면 매 run이 실패해 알람이 울렸을 상황이다 — 참조 단위
오류는 기록되지만 "저장소가 답하지 않는다"는 전역 사실이 성공으로 보고되는, "오류를 알려진 결과로
취급"의 전역 버전이다.

수정: 한 창에서 **실제로 물어본(deferred가 아닌) `stat`이 하나 이상이고 그 전부가 던지면**, fault를
모두 기록한 **뒤** 첫 오류로 run을 끝낸다. cursor는 전진하지 않는다. 워커 진입점
(`apps/worker/src/resource-cleanup.ts`)은 이미 오류를 `exitCode = 1`로 바꾸므로 알람 경로가 되살아난다.

"전부"를 고른 근거:

- 답이 **하나라도** 오면 저장소는 도달 가능하다는 증거다. 그 창은 부분 실패이고, 참조 단위 기록이
  맞는 신호다.
- 비율은 이 코드가 정당화할 수 없는 임계값을 요구하고, 실제 일을 한 run을 실패시킨다.
- fault를 **먼저 기록하므로** 다음 run에서 그 참조들은 deferred가 되어 아무것도 묻지 않고 창을
  통과한다. 이 노드가 고친 "영구 정지"는 이 경로로 돌아오지 않는다(통합 시험이 두 번째 run의 통과까지
  고정).
- 알려진 거짓 양성: 한 창에서 물어본 참조가 오염된 하나뿐이면 그 run도 실패한다. backoff 단계마다(1분,
  2분, …, 최대 하루) 한 번씩이며, 조용한 쪽이 아니라 시끄러운 쪽으로 틀린다.

deferred 참조는 어느 쪽으로도 계산하지 않는다 — 전부 deferred인 창은 물어본 것이 없으므로 장애가
아니고, deferred + 던진 하나인 창은 물어본 전부가 던졌으므로 장애다(단위 시험으로 두 방향 고정).
M2-01m의 "catch 없음" 시험은 그대로 통과한다.

#### 있었다가 닫힌 거짓 음성: 지속 장애 중 간헐적 알람(델타 검토 NB-1)

위 "전부 실패" 검사만으로는 **장애가 지속되는 동안 알람이 간헐적**이었다. 첫 실패 run이 fault를
기록하므로 그 참조들이 deferred인 동안의 run은 아무것도 묻지 않고 `deferred: N, faulted: 0`으로
**exit 0**이 되었다. 색인이 작고(한 창) lease된 cleanup이 없으면 죽은 저장소가 backoff 단계마다 한
번씩만(1분, 2분, … 상한 하루 한 번) 실패했다. 1차 반영 시험은 오히려 이것을 고정하고 있었다(죽은
저장소의 2회차가 `resolves {deferred: 2}`).

수정: **매 run, 창을 읽기 전에 저장소 전체 도달 가능성을 묻는다.** 저장소 도달 가능성은 참조 단위가
아니라 run 단위 사실이므로 참조의 backoff와 분리해 매번 묻는다.

- port: `StoreReachability.assertReachable()`(`object-storage.ts`). 스윕은 루트 경로를 모르고 이
  메서드만 부른다(`SweptStorage`).
- 로컬 구현: 루트를 다른 경로와 같은 가드로 확인한다 — `lstat`으로 symlink 루트 거절,
  `open(O_RDONLY|O_DIRECTORY|O_NOFOLLOW)`로 사이에 바뀐 루트 거절, `access(R_OK|X_OK)`로 아래
  `stat`에 필요한 읽기·탐색 권한 확인. **아무 오류도 흡수하지 않는다.** 루트의 ENOENT는 "비어
  있음"이 아니라 마운트 누락·설정 오류이므로 실패다 — 참조 단위의 "부재 → null"(`lstatIfPresent`)과
  의미가 다르므로 같은 헬퍼를 쓰지 않는다.
- 루트 확인이 실패하면 **fault를 기록하지 않는다.** 어느 참조의 잘못도 아니고, 기록하면 복구 후에도
  참조들이 backoff만큼 불필요하게 지연된다. 창을 읽기 전에 끝나므로 cursor도 그대로다.

두 검사가 각각 잡는 것:

| 검사                     | 잡는 장애                                                                   | fault 기록 |
| ------------------------ | --------------------------------------------------------------------------- | ---------- |
| 매 run 루트 확인         | 루트 권한 사고, EIO, 마운트 누락·루트 부재, 루트가 symlink로 바뀜           | 안 함      |
| 창 안 "물어본 전부 실패" | 루트는 살아 있는데 그 아래가 전부 막힘(하위 트리 권한 사고, 부분 장치 고장) | 함         |

시험: 루트 권한 0에서 **1·2·3회차 모두 EACCES로 실패**하고 fault 0건, 복구 직후 run이 두 참조를 바로
큐에 넣음 / 루트 삭제에서 1·2·3회차 모두 ENOENT로 실패하고 settle 0건 / 루트는 살아 있고 참조 디렉터리가
막히면 "전부 실패" 검사로 실패하고 fault 기록. 루트 확인을 되돌리면 앞의 두 시험이 실패한다(§2.5).

알려진 성질(정지 아님): 같은 창의 오염 참조들이 due 시각이 서로 다르면, "전부 실패" run이 cursor를
전진시키지 않는 동안 창 경계가 움직여 cursor가 여러 run 동안 한 창에 머물 수 있다. 머무는 run 수는
그 창 안의 due 그룹 수로 유계이고, 각 그룹은 기록 후 deferred가 되므로 영구 정지 경로는 없다.

### 2.7 runtime의 색인 쓰기를 기록 열로 좁힘(검토 지적 3)

`grantActivityTracks`가 runtime에 `activity_track_object_ref` **표 단위** INSERT를 주고 있었다.
검토자 실측: runtime이 자기 tenant의 새 행에 100년 deferral을 넣어 그 참조를 스윕에서 사실상 영원히
숨길 수 있다. base에서도 `settled_at` 위조로 숨길 수 있었으므로 실질 능력이 늘지는 않았지만, 이 노드가
더한 fault 열이 노출 면적을 넓혔다.

- 헬퍼: `GRANT SELECT, INSERT(storage_ref, athlete_id, recorded_at) ON activity_track_object_ref`.
  M2-01c의 기록 경로(`INSERT … (storage_ref,athlete_id,recorded_at) … ON CONFLICT DO NOTHING`)는 이
  세 열만 쓰므로 그대로 동작한다(runtime으로 실제 실행해 시험에 고정, activity-tracks 통합 시험도 통과).
- 040: 헬퍼만 좁히면 **이미 부여된 표 단위 권한은 남는다.** 그래서 040이 이 표에 표 단위 INSERT를
  가진 모든 비소유자 역할에서 그것을 회수하고(표 단위 회수는 열 단위 권한까지 함께 회수한다), 같은
  역할에 세 열 INSERT를 다시 준다. 업그레이드 시험이 039 시대 표 단위 권한을 준 역할로 이를 확인한다.
- 실제 DB 시험: runtime이 `settled_at`·`sweep_retry_at`·`sweep_attempts`·`sweep_error_code`를 넣으려
  하면 `42501 permission denied`, UPDATE도 `42501`. 썸네일 색인은 표 권한이 0이다(runtime INSERT도
  `42501`로 확인). 이 조치로 기존 `settled_at` 위조 경로도 함께 닫혔다.
- 040의 회수 루프는 PUBLIC(`grantee<>0`)과 소유자를 제외하고, REVOKE는 이 migration을 실행하는
  사용자가 부여한 권한만 지운다. 현재 부여 경로(마이그레이션 사용자가 실행하는 grant 헬퍼)에는 해당하지
  않는다(델타 검토 판정).

### 2.8 grant 헬퍼 재실행이 스스로 복구한다(델타 검토 NB-2)

1차 반영의 새 헬퍼는 GRANT만 했으므로, 040 이후 옛 헬퍼가 한 번이라도 돌면 표 단위 INSERT(9열 전부)와
옛 candidates EXECUTE가 누가 손대기 전까지 남았다(검토자 실측).

- `grantActivityTracks`: 열 GRANT **전에** `REVOKE INSERT ON activity_track_object_ref FROM runtime`.
  표 단위 회수가 열 권한까지 지우므로 순서는 REVOKE → 열 GRANT다.
- `grantResourceObjectCleanupWorker`: 새 함수 GRANT 뒤에 두 `*_reconcile_candidates`의 EXECUTE를
  그 역할에서 회수한다.
- 실제 DB 시험: 옛 헬퍼가 주던 권한(표 단위 SELECT·INSERT, candidates EXECUTE)을 준 역할에 새 헬퍼
  두 개를 돌린 뒤 — 표 단위 INSERT 없음, `settled_at` INSERT 없음, `recorded_at` INSERT 있음,
  candidates EXECUTE 없음, window EXECUTE 있음. 각 REVOKE를 빼면 이 시험이 실패한다(§2.5).
