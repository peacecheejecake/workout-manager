## 1. 결정과 근거

### 1.1 serving profile이 스스로 안전하다 — 세 겹

전에는 엔진 로그 보호가 profile **밖**의 두 가지에 기댔다: 저장소 helper가 붙이는 기동 인자
`-Ddw.server.request_log.type=external`, 그리고 모든 appender의 `threshold: WARN`. 이제
`scripts/geo/graphhopper-foot-serving.yml` 자체가 막는다.

1. **`server.request_log.appenders: []`.** Dropwizard 3.0.8(jar 안 `dropwizard-core` pom)의
   `LogbackAccessRequestLogFactory.isEnabled()`는 바이트코드로 `!appenders.isEmpty()`다. 실제 jar에서 요청 줄 0을
   관측했다(§3, R1·R4). c2에서 거절된 것은 **JVM 인자** `-Ddw.server.request_log.appenders=[]`였다(Dropwizard가
   `[]`를 문자열로 읽음). profile 파일의 YAML 목록은 받아들여진다. 노드 설명의 "c2에서 `appenders: []`가
   거절됐다"는 이 두 형태를 섞은 것이다.
2. **`logging.level: WARN` + 세 package `OFF`(§8 F1에서 class 단위 고정을 package 단위로 바꿈, §9에서 `navigation` 추가).** 노드 범위는 `RouteResource` 고정이었다. 그런데
   `--console-threshold INFO`로 돌린 첫 probe(R4, 첫 판)가 **FAIL**했다: `RouteResource`를 막아도 범위 밖 점을 보낸
   요청에서 `com.graphhopper.http.MultiExceptionMapper`의 INFO 줄(`bad request: … Point … is out of bounds`)이
   심은 좌표 2건을 찍었다. jar 바이트코드를 보면 요청 내용을 INFO로 쓰는 곳이 셋이다: `RouteResource`(doGet·doPost
   모두 `Logger.info`), `MultiExceptionMapper.toResponse`(`Logger.info`), `IllegalArgumentExceptionMapper`
   (`Logger.info(msg, throwable)`). `GHJerseyViolationExceptionMapper`는 debug다. 그래서:
   - root `level: WARN`: INFO 이벤트가 아예 생기지 않는다. 콘솔 threshold가 이미 WARN이어서 **보이던 것 중 잃는 것은
     없다.**
   - (검토 1차 전의 판) 세 logger를 이름으로 `OFF`에 고정했다. **"root를 INFO로 낮춰도 돌아오지 않는다"는 주장은
     틀렸다**(검토 F1: `SPTResource`가 심은 waypoint를 찍었다). 지금은 `com.graphhopper.resources`와
     `com.graphhopper.http`, 그리고 검토 2차 뒤 `com.graphhopper.navigation`까지 package 전체를 `OFF`로 고정한다
     (§8 F1, §9). 앞의 두 package에는 WARN/ERROR 호출이 없다. `navigation`은 ERROR 하나와 WARN 하나를 잃는다(§9). `OFF`는 YAML 1.1에서 boolean으로 읽힐 수 있는 철자이지만, 실제 jar에서
     `RouteResource: OFF`가 그 줄을 막았다(MP2와 대조: INFO로 바꾸면 샌다).
3. **모든 appender `threshold: WARN`**(그대로). 세 번째 겹.

부수: profile을 어차피 바꾸므로 M2-01k-e §7이 남긴 `routing.timeout_ms` 주석의 어긋남(요청별 `timeout_ms`가 주
상한이 된 현실)을 고쳤다.

### 1.2 adapter는 `POST /route`(JSON body)로 보낸다 — 채택

**채택 이유.** 요청 줄(method·path·query)은 access log가 쓰는 바로 그것이다. body로 옮기면 request log를 켠 채
저장소 밖에서 띄운 엔진이라도 adapter 요청의 요청 줄에는 waypoint가 없다(R6: 옛 profile, override 없음, adapter
요청만 → 요청 줄 6개, query 0, 심은 좌표 0).

**계약은 같다.**

- body는 GET query와 **같은 값**이다: `profile`, `points`, `ch.disable: true`, `points_encoded: false`,
  `instructions: false`, `calc_points: true`, `elevation: false`, `details: ["road_class"]`, `max_visited_nodes`,
  `timeout_ms`. GraphHopper `GHRequest`는 `points`·`details`를 필드로 읽고 나머지는 `@JsonAnySetter putHint`로
  hint가 된다(바이트코드로 확인). 점 순서만 GeoJSON `[lon, lat]`이다.
- 실제 jar 비교(실험, `coverage/m2-01af/exp-all.log`): 같은 두 점의 GET과 POST가 거리 1046.282 m, 정점 36개,
  `road_class` detail, geometry·detail·거리·시간이 **바이트 단위로 같았다**(`sameGeometry: true`, profile 7종 모두).
  POST의 `max_visited_nodes: 10`은 `MaximumNodesExceededException` 400으로 답했다(hint가 적용됨).
- 결과 분류는 바뀌지 않았다: swap probe의 `no_route`·`outside_coverage`·`snap_too_far`·`timeout`(엔진 `timeout_ms`
  소진, 161 ms)·취소·한도, 운영 probe 26 check가 POST adapter로 모두 PASS다(§3.3).

**구조로 막았다.**

- `RoutingEngineEndpoint.resolve(path)`는 query를 받지 않는다. 엔진 URL에 query를 만들 방법이 없다.
- transport는 `get` 대신 `send(request)`이고, 요청 타입이 method와 path를 짝지운다:
  `GET /info|/health` 또는 `POST /route` + `json`. 실행 시에도 다시 검사해 다른 짝(예: `GET /route`)은 보내기 전에
  `ENGINE_REQUEST_SHAPE_REFUSED`로 거절한다.
- `graphhopperRouteBody`(adapter의 body 조립)를 export해 엔진 로그 probe가 **adapter와 똑같은 요청**을 보낸다.

### 1.3 기동 helper — override는 profile이 판단한다

- helper는 profile을 읽고, request log를 스스로 끄는 profile에는 override를 붙이지 않는다(c2의 규칙 유지).
  M2-01d 측정 profile과 **M2-01af 이전 graph의 profile 사본**(지금 배포된 graph A의 `config-serving.yml`,
  manifest가 해시를 고정)에는 계속 붙인다.
- **새 profile에 override를 강제하면 jar가 기동을 거절한다**: `Unrecognized field at: server.request_log.appenders`
  (`ExternalRequestLogFactory`에 `appenders`가 없다). R2에서 관측. 그래서 "override와 함께"는 새 profile에서 실행
  가능한 구성이 아니고, 이것이 helper가 profile을 읽는 이유다.
- probe 전용 옵션 `requestLogOverride: 'profile' | 'add' | 'omit'`(기본 `profile`). guard 시험이 엔진 로그 probe 밖의
  사용을 막는다. 모르는 값은 throw.
- **runbook의 손 기동을 helper의 명령줄로 바꿨다**(`node scripts/geo/graphhopper-launch.mjs --jar … --config …
--extract … --graph … [--application-port … --admin-port …] [--print]`). 손으로 조립한 `java` 명령은 profile마다
  override 유무가 달라져 틀리기 쉽다(새 profile + override = 기동 실패, 옛 profile − override = 누출). guard는 이제
  문서의 raw `java` 기동을 모두 거절하고, runbook에 helper 명령줄 코드 블록이 있어야 한다.

### 1.4 재빌드와 blue/green — `.geo-build` 밖에서

profile SHA-256은 manifest `profileConfigSha256`과 graph id에 묶인다. 배포된 graph를 제자리에서 덮지 않기 위해
`build-routing-graph.mts`의 경로 상수를 `ROUTING_GRAPH_ROOT`(절대 경로, `.geo-build` 안이면 거절)로 옮길 수 있게
했다. build·운영 probe(graph B도 따라감)·swap probe가 같은 상수를 읽으므로 변수 하나로 셋이 새 deployment 위에서
돈다. 기본값(변수 없음)은 전과 같다.

새 probe `scripts/probe-routing-profile-rollout.mts`가 **실제 전환**을 보인다: blue = 배포된 graph A(옛 profile,
helper가 override 추가), green = 전체 재import A′(새 profile, override 없음). 결과
[routing-profile-rollout.json](../research/routing-profile-rollout.json).

### 2.1 guard 문법(fail closed) 확장

`packages/tooling/tests/graphhopper-launch.test.mjs`. YAML parser 없이 줄 문법으로 읽는 c2의 방식을 유지했다.

- `logging:` 안에 `loggers:`를 받는다. 받는 모양은 **문자열 형태 하나**: `    <java.logger.name>: <LEVEL>`(logger는 한
  번씩). 객체 형태(`level`·`additive`·자체 `appenders`)는 계속 거부한다(c2 X1: `additive: false` INFO 콘솔). 줄은 마지막에
  연 section(`loggers`/`appenders`)에만 속한다(appender 사이의 logger 줄, logger 사이의 appender 줄은 거부).
  빈 `loggers:`, 중복 `loggers:`, 따옴표 logger, 따옴표 level, 모르는 level, flow 형태를 거부한다.
- `server:`를 읽는다(`requestLogSetting`). 직계 key는 `  <snake_case>:`(콜론 뒤 값 없음)만, 각 한 번. 그래서
  따옴표 `"request_log":`, inline `{…}`, merge key `<<:`, 두 번째 `request_log`가 거부된다. `request_log:` 안에는 정확히
  `    appenders: []` 한 줄만. 결과는 `disabled` 또는 `default`(없음).
- 새 시험:
  - "serving profile이 스스로 request log를 끄고 고정한다": `requestLogSetting` = `disabled`, root level WARN+, 세
    logger 모두 WARN+.
  - 모든 profile의 모든 logger level WARN+(appender threshold 규칙과 같은 시험).
  - helper의 `profileDisablesRequestLog`와 guard의 엄격한 reader가 **모든 profile에서 같은 답**.
  - 서빙 profile에는 override 없음(`-Ddw.server.request_log*`·`-Ddw.logging*` 인자 0), request log를 켜는 profile
    (측정 profile, M2-01af 이전 사본)에는 `-jar` 앞 override.
  - `requestLogOverride`는 엔진 로그 probe 밖에서 쓰이지 않고, 모르는 값은 throw.
  - 거부 사례 19개(request log 10, logger 9)와 수용 사례.

남았다: `com.graphhopper.navigation.NavigateResource`(`GraphHopperApplication`이 등록)도 요청 점을 INFO로 찍는다.
검토자는 새 profile, root INFO, 콘솔 INFO로 `/navigate/directions/v5/gh/foot/…`에서 심은 waypoint를 관측했다.
`/route`·`/spt`·`/isochrone`·`/match`는 0건이었다.

- **profile**: `com.graphhopper.navigation: OFF`를 더했다. 고정은 세 package다. package 전체를 고른 것은 class 목록이
  두 번 빠뜨렸기 때문이다(1차 `SPTResource`, 2차 `NavigateResource`).
- **교환**: 바이트코드상 `navigation` package에는 `NavigateResource`의 `Logger.error` 하나(실패한 navigate 응답)와
  `NavigateResponseConverter`의 `Logger.warn` 하나가 있다. package를 `OFF`로 두면 둘 다 사라진다. adapter는
  `/navigate`를 부르지 않으므로 이 교환을 택했다. profile 주석에 적었다.
- **guard**: `REQUEST_CONTENT_PACKAGES`에 `com.graphhopper.navigation`을 더했다. 서빙 profile 시험이 세 package 모두
  WARN 이상인지 단언한다.
- **probe**: `/navigate/directions/v5/gh/foot/<lon,lat;lon,lat>?steps=true&geometries=polyline6&overview=full&voice_instructions=true&banner_instructions=true&roundabout_exits=true&voice_units=metric`를
  심은 점으로 보낸다. `/spt`·`/isochrone`과 함께 200이어야 판정이 성립한다.
- **조사 범위 정정**: §7.4와 profile 주석을 고쳤다. 이 노드의 바이트코드 조사는 `resources`·`http`·`navigation`
  package만 덮었다. 검토자가 911 class에서 찾은 나머지 INFO 줄(`GraphHopper`, LM/CH/subnetwork 준비, OSM reader,
  GTFS, `GHUtility`, `LocationIndexTree`, `MaxSpeedCalculator`, `UrbanDensityCalculator`,
  `TileBasedElevationProvider`, `GHLongLongBTree`)은 이름으로 보면 import·기동 코드이지만 내용은 확인하지 않았다.
- §3.3에 "1차 판, 최신은 §8" 표시를 달았다.
- **rebase**: main `d22f760`(M2-01ai·M2-01k-i·M2-01k-d) 위로 WIP 커밋 → rebase → `reset --mixed`를 했다. 충돌은
  없었다. `configured.ts`는 이 노드가 바꾸지 않는다.
