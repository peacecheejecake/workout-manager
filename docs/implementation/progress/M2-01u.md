# M2-01u · 실제 OIDC 수용

상태: **부분 수용 — (A) 로컬 인증 OP로 수행 + (B) 운영 IdP는 외부 gate.** 기준 HEAD `eae0ee1`.
`task-graph.json`·`AGENTS.md`·`CLAUDE.md`·`.geo-build`·M2-01k 매트릭스는 건드리지 않았다.
**`K-oidc`는 운영 IdP 증거가 없으므로 계속 `not_executed`다.** 이 노드가 바꾼 것은 "fixture만"에서
"표준 인증 OP(로컬)까지"이며, 그것을 운영 IdP 증거로 쓰지 않는다.

## 결론 먼저

1. **"실제 OIDC"의 운영 대상은 아직 정해져 있지 않다.** [oidc-setup.md](../oidc-setup.md)의 사용자
   결정은 "특정 로그인 공급자에 종속되지 않는 표준 OIDC"이고, 저장소 어디에도 운영 issuer·client
   등록·공개 HTTPS 도메인이 없다. 그러므로 운영 IdP 수용은 만들어 낼 수 없다 → **(B) 외부 gate**.
2. 그 대신 **(A)**: OpenID Certified OP 구현(panva `oidc-provider` 9.12.2)을 운영 등록과 같은 설정
   (confidential client, `client_secret_basic`, code + PKCE S256, `openid`, 정확한 redirect URI,
   dev 로그인 끔)으로 로컬에 띄우고 제품의 실제 RP 코드(`createOidcProvider` +
   `createIdentityService` + Fastify 라우트 + Next 화면)를 그대로 붙였다.
3. **fixture가 가리던 결함 1건을 찾아 재현하고 고쳤다.** 앱 로그아웃 뒤 "OIDC로 로그인"을 누르면
   실제 OP는 자기 SSO 세션으로 **자격 증명을 묻지 않고 직전 사용자로 다시 로그인시킨다.** 공유
   브라우저에서는 다음 사람이 앞사람 계정으로 들어간다. 로그인 중 계정 전환도 불가능했다.
   fixture는 `/authorize`마다 계정 선택 화면을 새로 보여 주는 구현이라 이것을 원리적으로 볼 수 없었고,
   기존 `oidc.spec.ts`의 "로그아웃 → Bob으로 로그인"과 "두 번째 탭 계정 전환"은 **fixture에서만 성립하는
   시나리오**였다.

## 조사: fixture provider는 무엇이었나

`scripts/fixtures/oidc-provider.ts`는 **손으로 쓴 최소 OP**다(인증된 구현을 fixture 설정으로 띄운 것이
아니다). discovery·JWKS(고정 RSA 키 1개)·`/authorize`(매번 Alice/Bob 링크 화면)·`/token`(Basic 인증,
PKCE 검사, 60초 id_token)만 있다. **세션이 없고**, grant·prompt·로그아웃·키 회전·`iss` 광고
(`authorization_response_iss_parameter_supported`)가 없다. RP 쪽은 인증된 RP 라이브러리
`openid-client` 6.8.8(내부 `oauth4webapi` 3.8.8)이다.

## 찾은 결함과 수정

**재현**(수정 전, `scripts/oidc-certified-check.mts`):

```
FAIL  account switch after app logout: the OP must ask for credentials again — OP signed the previous user in silently (SSO session reused)
FAIL  switch while signed in (no logout): the OP must ask for credentials again — OP re-used the SSO session silently
10/12 passed
```

**수정**(작음, migration 없음):

- `OidcProvider.authorizationUrl`에 `reauthenticate`를 추가하고, 참이면 `prompt=login`을 보낸다
  (`packages/server/identity/src/oidc.ts`).
- `createIdentityService.beginLogin(cookieHeader)`는 브라우저에 **세션 쿠키(=전환 의도)** 또는
  **로그아웃 표식 쿠키**가 있으면 `reauthenticate: true`. 표식은 존재만 본다(값이 틀려도 "다시 묻기"
  쪽으로 실패).
- `logout`은 표식 `__Host-workout_signed_out`(로컬 loopback은 `workout_signed_out`; HttpOnly,
  SameSite=Lax, Secure, 30일, 무작위 값)을 남기고, 다음 **완료된** 로그인이 지운다.
- `GET /bff/v1/auth/login`이 요청 쿠키를 `beginLogin`에 넘긴다(`apps/api/src/app.ts`).
- 표식이 없는 첫 로그인은 그대로 SSO다 — 매번 비밀번호를 묻게 만들지 않았다.
- **(검토 R1) 세션이 이미 없는 로그아웃도 표식을 남긴다.** 세션이 만료·철회된 뒤 누른 로그아웃은
  `preValidation`에서 401이 되고 화면은 그것을 로그아웃 성공으로 처리한다
  (`identity-workspace.tsx`). 수정 전에는 그 401에 `Set-Cookie`가 없어 표식이 남지 않았고, 다음
  로그인은 다시 조용한 SSO였다 — 공용 브라우저에서 자리를 비운 뒤 로그아웃하는, 이 결함이 가장 해로운
  경우다. 이제 `/bff/v1/auth/logout`의 401 응답은 **허용된 Origin에서 온 경우에만** 표식 하나
  (`identity.signedOutMarker()`, DB 접근 없음)를 붙인다. 세션·attempt 쿠키는 건드리지 않는다. 다른
  401 경로는 쿠키를 붙이지 않는다(시험). 남아 있는 무효 세션 쿠키는 그 자체로 다음 로그인을
  `prompt=login`으로 만든다.
  **CSRF 판단 — 처음 근거는 틀렸다(2라운드 검토 B1, 차단).** 1차 수정은 이 401에 앱 쿠키 삭제 +
  표식을 Origin 검사 없이 붙였고, 근거로 "교차 사이트 요청이 할 수 있는 것은 이미 무효인 쿠키의 삭제뿐,
  유효 세션이 있는 요청은 이 경로에 오지 않는다"고 적었다. **실측하지 않은 추론이었고 거짓이었다.** 세션
  쿠키는 `SameSite=Lax`라 **교차 사이트 POST에 실리지 않는다.** 그래서 로그인 중인 피해자의 요청도 서버에는
  "세션 없음"으로 보여 이 401 분기로 오고, 브라우저는 top-level navigation 응답의 Lax 쿠키 설정·삭제를
  적용한다. Fastify는 `enctype="text/plain"` 폼을 기본 parser로 받으므로(urlencoded·multipart는 415)
  공격자 페이지의 자동 제출 폼 하나로 **어떤 사이트든 로그인 사용자를 강제 로그아웃**시킬 수 있었다
  (서버 세션은 살아 있어 기밀성·무결성 영향은 없고 가용성·성가심). `oidc-setup.md`의 "logout POST는
  세션 일치·Origin·CSRF"와 "브라우저 cookie 삭제만으로 로그아웃을 처리하지 않는다" 계약도 깼다.
  검토자가 실제 Chromium에서 재현했고, 이 노드도 `scripts/logout-csrf-browser-check.mts`(두 site:
  `localhost:47831` 앱 / `127.0.0.1:47832` 공격자, `text/plain` 폼 top-level·popup 자동 제출)로 독립
  재현했다: 수정 전 두 변형 모두 `cookies after [workout_signed_out], session after 401`.
  **지금 막는 것(심층 방어 둘)**: (a) 401 분기는 표식만 설정 — 세션 쿠키 삭제 줄이 없으므로 교차 사이트
  요청이 세션을 지울 수 없다. (b) 그 표식도 `Origin ∈ allowedOrigins`일 때만 — 교차 사이트 폼(외부
  Origin 또는 `null`)·Origin 없는 요청은 쿠키 없는 401. 앱의 로그아웃은 same-origin `fetch` POST라
  Origin을 보내므로 R1 경로는 유지된다(브라우저 확인). 수정 후 같은 브라우저 시험: 두 변형 모두
  `cookies after [workout_session], session after 200`, 만료 세션의 same-origin 로그아웃은 표식 받음.
- **(검토 P-C) 8192바이트를 넘는 쿠키 헤더는 "표식 있음"으로 본다.** 수정 전에는 잘라서 검사해 pad
  8200에서 `false`, 즉 주석과 반대로 "묻지 않는" 쪽으로 실패했다. 판단할 수 없으면 더 묻는다. 같은
  크기에서 `readCookie`도 null이라 앱 인증이 안 되므로 실제 영향은 작았다.

보안 경계: 새 경로는 파라미터를 **더할** 뿐 어떤 검증도 완화하지 않는다. 표식은 인증 근거로 쓰이지
않으며, 위조되어도 효과는 "OP가 한 번 더 묻는다"뿐이다. `__Host-` 접두사라 다른 origin이 심을 수 없다.
운영 경로(`configured.ts`)에 인증 OP 모드로 가는 분기는 없다 — 그것은 `scripts/`의 시험 harness 안에만 있다.

**수정하지 않은 한계 — `auth_time` 미검증(정정됨)**: RP는 OP가 `prompt=login`을 실제로 지켰는지
검증하지 않는다. 처음 이 문서는 "시도 시작 시각이 필요해 migration(`045` 후보)"이라고 썼는데 **틀렸다.**
독립 검토자가 인증 OP + openid-client 6.8.8로 실측했다: 인가 요청에 `max_age=0`, callback에서
`authorizationCodeGrant(..., { maxAge: 0 })`이면 oauth4webapi가 `auth_time`을 필수로 요구하고 기본
허용 오차 30 s로 검사한다. OP가 조용히 SSO로 답하거나(`auth_time` 없음) 재인증 없이 `auth_time`만
보내면 거절되고, `prompt=login` + 비밀번호 입력이면 수락된다. "재인증 요청이었는가"는 callback의 같은
쿠키(표식은 로그인 완료 때만 지워진다)나 nonce 표시로 판단할 수 있다. **코드만으로 가능하고 migration은
필요 없다.** 이번 노드에서 구현하지 않은 이유는 **IdP 선택에 달려 있기 때문이다**: 운영 IdP가
`prompt=login`/`max_age`를 지원하지 않으면 강제 검사는 로그아웃 뒤 로그인을 **아예 실패**시킨다
(검토자의 미검증 기억: Google은 `prompt=login`을 지원 값으로 두지 않는다). 후속 노드로 추적된다.
운영 IdP가 `prompt=login`을 무시하면 지금의 수정은 효과가 없으므로 외부 gate의 확인 항목에 넣었다.

**설계상 선택과 경계**:

- **표식 30일**: 표식이 만료되면 표식 없는 첫 로그인과 같아지고, OP 세션이 30일보다 길면 그 뒤의
  로그인은 조용한 SSO가 된다. 표식이 영원히 남지 않게 한 의도적 상한이다.
- **다른 프로필·시크릿 창·전체 쿠키 삭제는 우회가 아니다**: OP 쿠키도 함께 없으므로 OP가 묻는다.
- **앱 쿠키만 골라 지우면** 조용한 SSO가 돌아온다. 사용자의 의도적 행동이며 막을 수 없다(표식은 브라우저
  상태다).

## 증명한 것 / 증명하지 못한 것

**증명(로컬 인증 OP, loopback HTTP)**: discovery 수용, code+PKCE+state+nonce+RS256 서명 id_token 경로,
RFC 9207 `iss` 강제, `client_secret_basic` 인코딩, 재사용·code 주입·잘못된 secret·취소 거절, 로그인·
세션·서버측 로그아웃, SSO 존재 하의 **재인증 계정 전환**(수정 후), 같은 subject의 안정 매핑, 첫 로그인의
SSO 유지, 기동 시 OP 부재의 fail-closed, 비사전게시 키 회전의 60 s 창과 무재시작 회복.

**증명하지 못함**: 운영 IdP 자체(클레임 형식·`sub` 안정성·pairwise 여부, 속도 한도, 동의 화면,
MFA, `prompt=login` 준수, 키 사전 게시 주기, 오류 응답 형식, 비밀값 인코딩 호환), HTTPS·`__Host-`
쿠키·TLS ingress 경로(로컬은 `allowInsecureLocalhost` loopback), 시계 오차, 다중 인스턴스 배포,
위조 토큰에 대한 거절(정직한 OP는 만들지 않는다 — 단위 시험의 위조 OP가 근거).

## 외부 gate (B) — 운영 IdP 수용에 필요한 것

누가: **사용자**(공급자 선택은 사용자 결정 사항이다).

1. 공급자 선택: 예) 자체 호스팅 Keycloak/Authentik, 또는 Google/Auth0/Entra ID 등. 조건: OIDC
   discovery, confidential client + `client_secret_basic`, PKCE S256, `prompt=login` 준수, JWKS 키
   사전 게시.
2. 공개 HTTPS origin(도메인 + TLS)과 client 등록: redirect URI 정확히
   `https://<public-host>/bff/v1/auth/callback`, scope `openid`.
3. 값 전달: `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`을 secret manager로(저장소·채팅 금지).
4. 시험 계정 2개(서로 다른 사람), 가능하면 MFA 켠 계정 1개.
5. 수행할 확인(사람이 브라우저로): 로그인·동의 저장·로그아웃·**로그아웃 뒤 다른 계정으로 로그인 시
   공급자가 다시 묻는지**·로그인 중 전환·취소·8 h 만료·같은 계정 재로그인 시 같은 athlete·공급자 키
   회전 공지 주기 확인. 결과는 이 문서와 M2-01k 매트릭스 `K-oidc`에 운영 증거로 기록한다.

## 미해결(보고 — 이 노드에서 고치지 않음)

1. **OP 장애 = API 전체 불가.** discovery를 기동 시 await하므로 OP가 내려가 있으면 API가 뜨지 않는다
   (로그인과 무관한 기능까지). 지연 discovery·재시도는 설계 결정.
2. **OP 쪽 로그아웃·계정 정지가 앱 세션에 닿지 않는다(최대 8 h).** back-channel logout 또는 짧은 세션 +
   재검증이 필요하면 설계 결정. RP-initiated logout(`end_session_endpoint`)도 없다 — "앱 로그아웃 ≠
   공급자 로그아웃"은 문서화된 설계이며 이번 수정은 그 위에서 계정 전환만 가능하게 했다.
3. **취소·OP 오류 시 브라우저에 401 JSON이 그대로 보인다.** `/account`로 돌려보내 메시지를 보이는 것이
   맞아 보이나 화면 결정이므로 보고만 한다.
4. **`auth_time` 미검증**(위). 코드만으로 가능(migration 불필요), IdP 선택에 달려 후속 노드.
5. **키 회전 60 s 창**: 라이브러리 동작. 운영 IdP가 키를 미리 게시하면 발생하지 않는다 — gate 확인 항목.
6. 기존 `tests/identity/oidc.spec.ts` 제목의 "actual OIDC"는 fixture를 뜻한다. M2-01v가 그 파일을
   다룰 수 있어 이름은 바꾸지 않았다.
