# M2-01m · 썸네일 객체 reconciliation 스윕

상태: **완료(implemented).** 기준 HEAD `065d0b5`. 계획 문서
[map-implementation-plan.md](../map-implementation-plan.md) 7절("기존 durable cleanup 패턴" —
저장 수명주기·삭제 연쇄·과잉 삭제 금지)을 수용 기준으로 삼았다. `task-graph.json`은 root 소유이므로
**건드리지 않았다.**

M2-01l은 썸네일 객체마다 `resource_object_cleanup` 영수증을 발행하게 만들었다. 그것은 **영수증
기반 보장**이고, 영수증 기반 보장은 **어떤 영수증이든 열려 있는 동안에만** 성립한다. 이 노드는
영수증이 전부 닫힌 뒤에도 성립하는 경로 하나를 추가한다.

## 1. 구멍을 먼저 재현했다

독립 검토가 보고한 절차를 그대로 실제 PostgreSQL 14.15에서 재현했고, 그 재현을 저장소에
시험으로 남겼다 —
`course-thumbnails.integration.test.ts > reclaims an object a stalled render published after every receipt for it closed`.

```
prepare 완료(fence 열림)
  → lease·fence·expires_at을 3시간 과거로
  → reap_course_thumbnail_renders  (render 포기, 두 ref queue)
  → cleanup drain                   (두 영수증 completed)
  → "잠에서 깬" writer가 writeTemporary + publishTemporary 완료
```

시험이 고정하는 실측값:

| 관측                                             | 스윕 이전 | 스윕 이후 |
| ------------------------------------------------ | --------- | --------- |
| `storage.stat(finalKey)`                         | 객체 있음 | `null`    |
| reaper·prune·drain 재실행 후 열린 영수증 행 수   | **0**     | 1 → 0     |
| `resource_object_cleanup` 재실행이 회수한 바이트 | **0**     | 전부      |

즉 **모든 영수증이 닫힌 뒤 도착한 객체는 어떤 receipt 경로로도 다시 보이지 않는다.** 삭제된
코스·supersede된 revision의 그림도 같은 방식으로 영구히 남는다.

두 번째 재현도 시험으로 남겼다 —
`still finds the orphan after housekeeping deleted the ledger row that named it`. 여기서는
`prune_course_thumbnail_history`가 7일 지난 닫힌 render 행을 지워 **ref를 담고 있던 원장 행 자체가
사라진** 뒤에도 스윕이 고아를 찾는다. 이것이 "`course_thumbnail`을 스캔하면 되지 않나"에 대한 답이다.

### 차단이 아니라 별도 노드인 이유(이 노드에서 없애지 않은 것)

프롬프트가 준 검토자 실측을 그대로 유지한다. 최종 key가 `(revisionId, sha256)` 내용주소이므로 늦은
writer는 **같은 바이트만** 쓸 수 있고 살아 있는 그림을 다른 내용으로 덮지 못한다. `finalize`는
`lease_lost`, fence는 닫힘, `resolveThumbnailObject`는 null이므로 **회수된 key가 다시 보이지 않는다.**
계정 말소는 `finish_resource_object_cleanup`의 30일 `account_erased` fence 재장전 덕에 **결국
회수된다.** 남는 바이트는 0–100 정규화 경로뿐이라 **절대 위치가 복원되지 않는다.** 그래서 이것은
저장 누수이지 접근·프라이버시 실패가 아니다. 과잉 대응하지 않았다.

## 2. 따른 패턴 — M2-01c(033, 1050~1130행)

새로 만든 것은 없다. 구성 요소 다섯 개를 그대로 옮겼다.

| M2-01c(033)                                   | M2-01m(039)                                           |
| --------------------------------------------- | ----------------------------------------------------- |
| `activity_track_object_ref` 영속 색인 표      | `course_thumbnail_object_ref`                         |
| 기존 행 backfill                              | `course_thumbnail`의 `temporary_ref`·`storage_ref`    |
| `activity_track_reconcile_state` cursor       | `course_thumbnail_reconcile_state` (**별도** cursor)  |
| `..._reconcile_candidates(text,integer)`      | `course_thumbnail_reconcile_candidates(text,integer)` |
| `settle_activity_track_object_ref(text)`      | `settle_course_thumbnail_object_ref(text)`            |

worker 쪽도 M2-01c의 자리에 붙였다: `runResourceCleanupWorker`가 reaper → drain →

## 3. 다르게 한 것 세 가지와 근거

### 3-1. 색인 유지를 **저장소가 아니라 트리거**로 한다

M2-01c는 `activity-tracks.ts`의 `recordObjectRefs()`가 `database.tenant` 안에서 색인에 INSERT하고,
그러기 위해 runtime role에 표 INSERT 권한을 준다(`migrate.ts`의 `grantActivityTracks`).

썸네일에서는 **둘 다 불가능하고 불필요하다.** `course_thumbnail`은
`course_thumbnail_writer_is_owner()` 트리거가 소유자 외의 writer를 전부 거부하고, 실제 writer는
enqueue 트리거와 M2-01l의 SECURITY DEFINER 함수들뿐이며, `prepare_course_thumbnail`을 부르는 render
worker는 **표 권한도 tenant 세션 변수도 없다.** 그래서 ref를 기록하는 곳을 ref가 만들어지는 바로
그 statement의 트랜잭션에 두었다: `record_course_thumbnail_object_refs` AFTER INSERT OR UPDATE 트리거.

결과적으로 **어떤 쓰기 경로도 잊을 수 없고**, 미래의 writer가 자동으로 상속하며, **이 표는 누구에게도
grant가 필요 없다**(표 권한 0 유지 — 요구사항과 일치).

`ON CONFLICT DO NOTHING`으로 충분한 근거: settle된 ref를 다시 이름 붙일 수 있는 경로가 없다. 임시
key는 매번 새 job UUID를 담고, 최종 key는 `(revision_id, sha256)`을 담는데 그 revision의
`course_thumbnail` 행은 revision INSERT 시점의 enqueue 트리거만이 만들고 그 시점은 이미 지났다.

### 3-2. "publish할 수 있는 writer가 없다"를 **fence + lease**로 표현한다

track은 만료를 가진 upload 상태기계지만, render는 **publication fence + render lease**다. 두 기한 모두
`queue_course_thumbnail_refs`가 이미 queue된 영수증의 `available_at`에 넣는 **같은 1시간 유예**를 받는다.
근거도 같다 — 어느 gate도 **이미 출발한 storage 호출에는 닿지 못한다.** `greatest`는 NULL을 무시하므로
lease도 prepare도 없던 행은 자기 `expires_at`만 기여한다.

`settle`이 감시를 멈추는 조건(전부 닫혀야 함):

1. 객체가 부재로 관측됨(호출자의 `stat` — 그래서 SQL 안에서 검사하지 않는다)
2. 열린 cleanup 영수증 없음
3. 살아 있는 그림이 이름하지 않음(`state IN ('prepared','ready')`)
4. `now >= greatest(expires_at, publication_lease_until+1h, lease_until+1h)`
5. **최소 7일 감시됨**

### 3-3. 말소가 색인 행을 **마지막에** 지운다(M2-01c는 먼저 지운다)

M2-01c는 `erase_account`의 첫 줄에서 색인을 지운다. 그래도 안전한 이유는 그 색인의 유일한 writer가
`database.tenant`를 거쳐 **이미 account lock(77206)을 공유로 쥐고 있기** 때문이다.

썸네일 색인은 그렇지 않다. render worker는 `prepare_course_thumbnail`·`fail_course_thumbnail` 등을
**advisory lock 없이 직접** 부르고, 그 트랜잭션은 `course_thumbnail` 행을 쥔 채 트리거를 통해 색인
행을 기다릴 수 있다. 즉 통상 방향은 **원장 → 색인**이다. 말소가 색인을 먼저 지우면 **역방향 간선**이
생겨 순환이 닫힌다.

**이것을 주장으로 두지 않고 되돌려 측정했다.** 039의 두 줄 순서만 뒤집고
`adds no new lock-order inversion to the writers of one tenant`를 돌리면 실패 메시지가
`['deadlock detected', 'deadlock detected']` — **`40P01`이 실제로 재현된다**(§8의 G13).

말소 후 늦게 도착하는 쓰기는 M2-01c와 같은 거래로 덮인다: 색인 행은 사라지지만 30일
`account_erased` 영수증 fence가 대신 받는다. 시험:
`removes the tenant reference index on erasure and keeps the erasure fence`.

## 4. 독립 검토 차단 B1 — `stat`/`delete` TOCTOU를 저장소 층에서 고쳤다

**1차 판의 검증이 운이 좋았다.** 통합 524 통과를 보고했지만, 잠금순서 시험만 격리해 8회 돌리면
실패한다. 동시성 시험은 한 번 초록이라고 안정된 것이 아니다 — 이번이 그 사례다.

### 재현 (DB 없이 저장소 층에서 직접)

`packages/server/media/src/local-filesystem.ts`의 `assertSafeExistingFile`은 경로를 한 칸씩 걸으며
`missing(current)`로 존재를 확인한 **뒤** 다시 `lstat(current)`를 불렀고, 마지막에 또 한 번
`lstat(path)`를 불렀다. 두 `lstat` 어느 쪽도 ENOENT를 흡수하지 않는다. `delete`는 객체를 unlink한 뒤
**빈 상위 디렉터리까지 prune**하므로, 읽는 쪽이 걷는 중에 지우는 쪽이 그 밑을 비우면 throw한다.

| 측정                                                        | 결과                                        |
| ----------------------------------------------------------- | ------------------------------------------- |
| 같은 key에 대한 순차 `stat`/`delete` 쌍 5,000회             | `{"stat-ok":4998,"THREW ENOENT":2}`         |
| 삭제를 걷는 중간에 떨어지도록 tick을 맞춘 경우(ticks 12~18) | 40회 중 최대 17회 throw                     |
| 잠금순서 시험만 격리 8회 (**수정 전**)                      | **6 통과 / 2 실패**, 전부 `ENOENT: … lstat` |

**`40P01`이 아니다.** 실패 메시지는 전부 `ENOENT: no such file or directory, lstat '…/thumbnails/temporary/…'`다.

### 귀속

이 노드의 스윕이 **cleanup drain이 동시에 지우고 있는 namespace를 `stat`으로 훑기** 때문에 상시
발화한다. 스트레스 루프에서 `reconcileCourseThumbnailObjects(...)`만 빼면 발화가 사라진다.

### 왜 운영에서 문제인가

`runResourceCleanupWorker`에 `catch`가 없으므로 ENOENT가 밖으로 전파되면 prune 다섯 개가 전부
건너뛰어지고, `advanceThumbnailReconcileCursor`가 스윕 루프 뒤에 있어 **커서가 전진하지 않는다.**
cleanup worker는 lease + `SKIP LOCKED` 설계라 **여러 프로세스 동시 실행이 전제**다. A의 drain과 B의
stat이 겹치는 것은 예외가 아니라 정상 운영 상태다.

### 수정 — 저장소 층에서, ENOENT만

`lstatIfPresent()`를 두고 두 `lstat`을 모두 그것으로 바꿨다. 동시에 `missing(current)` + `lstat(current)`
**쌍 자체를 하나의 호출로 합쳤다** — 그 두 호출 사이의 틈이 바로 창이었으므로, 가드를 덧대는 것보다
창을 없애는 쪽이 맞다.

**저장소 층에서 고친 이유**: 같은 잠복 결함이 **기존 track 스윕에도** 있다(`reconcileActivityTrackObjects`도
같은 `stat`을 부른다). 스윕 쪽에서 `stat`만 감싸면 track 쪽이 남는다.

**ENOENT만 흡수한다.** `assertSafeExistingFile`은 symlink·권한 가드 그 자체이므로 `EACCES`·`ELOOP`·`EIO`를
"부재"로 바꾸면 가드가 조용히 무력해진다 — 이 저장소가 반복해 온 "오류를 알려진 결과로 취급"이다.
`lstatIfPresent`는 ENOENT 외 전부 다시 던진다.

### 비공허성 — 두 곳이 각각 필요하다

새 시험
`local-filesystem.test.ts > answers absent, not an error, when a delete lands inside a concurrent stat`이
삭제를 걷는 중간에 떨어뜨린다(ticks 10~20 × 10회 = 110 시도). 이 시험은 기계가 다르면 **덜
잡을 수는 있어도 거짓 실패는 할 수 없다** — 가드가 있으면 `stat`이 ENOENT로 throw할 입력이 없다.

| 되돌림                       | 5회 실행 결과 |
| ---------------------------- | ------------- |
| 루프 안 가드만 되돌림        | **5/5 실패**  |
| 마지막 `lstat` 가드만 되돌림 | **4/5 실패**  |
| 둘 다 되돌림                 | **5/5 실패**  |
| 수정본                       | **5/5 통과**  |

즉 **한 곳만 고치면 안 된다**는 검토자의 측정이 이 트리에서도 재현된다.

### 8회 반복 — 1회 초록은 증거가 아니다

| 대상                                             | 결과                            |
| ------------------------------------------------ | ------------------------------- |
| 잠금순서 시험 격리 8회 (**수정 전**)             | 6 통과 / 2 실패                 |
| 잠금순서 시험 격리 8회 (**수정 후**)             | **8 / 8 통과**                  |
| `course-thumbnails.integration.test.ts` 전체 8회 | **8 / 8 통과** (매회 46 passed) |

§8의 G13(말소 순서 역전)도 저장소 수정 후 **4회 다시 재현**했다 — 4/4 모두 실패 메시지가
`deadlock detected`이고 ENOENT가 아니다. 즉 그 되돌리기가 잡는 것은 진짜 `40P01`이다.

## 5. worker에 `catch`를 두지 않기로 한 판단

**두지 않았다.** 근거를 주장이 아니라 시험으로 고정했다 —
`resource-cleanup-worker.test.ts > lets a sweep failure end the run rather than reporting a sweep that did not happen`.

- **삼키면 안 되는 오류들이다.** 스윕이 실제 객체 저장소를 읽으므로 올라올 수 있는 것은
  `UnsafeStoragePathError`(symlink 가드 발화), `EACCES`, `EIO`다. 이것을 "스윕했는데 아무것도 없었다"로
  바꾸는 것이 바로 "오류를 알려진 결과로 취급"이다. B1을 저장소 층에서 고친 것도 같은 이유다 —
  **거짓말 대신 진실(부재)을 답하게** 만들었지, 예외를 숨기지 않았다.
- **잃는 것이 유계다.** 시험이 실측으로 고정한다: 스윕이 throw해도 **사용자가 요청한 삭제는 이미
  끝나 있다**(`processOneResourceObjectCleanup`이 스윕보다 앞에 있다). 건너뛰는 것은 prune 다섯 개와
  커서 전진뿐이고, prune은 멱등·유계라 다음 tick에 다시 돌며, **커서가 전진하지 않는 것은 같은 창을
  다시 보는 것**이라 재개 규약상 올바르다.
- **이 구조는 이 노드가 들여온 것이 아니다.** `reapExpired`·`reapCourseThumbnailRenders`·기존 track
  스윕이 모두 prune 앞에서 `catch` 없이 돈다. 여기에만 `catch`를 다는 것은 일관성을 깨면서 정작
  중요한 오류만 가린다.

## 6. 7일 유예의 의미 — 1차 판에서 적은 근거를 실측으로 정정한다

**1차 판에서 나는 "`prune_course_thumbnail_history`가 닫힌 render 행을 7일 보관하므로, 색인이 그보다
먼저 settle하면 자기 원장 행이 아직 살아 있는 key의 감시를 멈추게 된다 — 그러므로 7일이 하한"이라고
적었다. 그것은 틀렸다.** 두 가지 이유로 틀렸다.

- **의미상**: prune 대상은 `superseded`/`failed` 행, 즉 **더 이상 publish할 수 없는** 행뿐이다. 그런
  행이 이름하는 key의 감시를 멈춰도 위험이 없다 — 게다가 settle은 애초에 객체가 **부재로 관측된**
  경우에만 부른다.
- **실측상**: 038의 prune 보존기간을 `7 days` → `0 days`로 바꿔 돌리면 **prune 자신의 시험 2건만**
  깨진다(`prunes a closed render only after its objects are accounted for, and never a live one`,
  `prunes an aged superseded render, but not while its receipt is still open`). **settle 시험은
  하나도 깨지지 않는다.** 두 값은 시험으로 결합돼 있지 않다.

**실질 근거는 하나뿐이고, 그쪽은 고정돼 있다.** 이 수명주기의 모든 기한은 7일보다 훨씬 짧다 — render
유효시간 1시간, lease 최대 5분, publication fence 2분, 회수 유예 1시간. 그래서 7일이 사는 것은 전부
**늦게 깨어난 writer를 위한 margin**이고, **7일보다 늦게 재개하는 writer는 이 회수의 범위 밖이라고
명시하는 바닥**이다. 이것이 M2-01c가 7일에 준 의미 그대로이고, 썸네일에 같은 값을 쓰는 이유는
"이 표의 사정이 달라서"가 아니라 **같은 성질의 margin이기 때문**이다.

되돌리면 깨진다: 039의 `recorded_at < now-7 days`를 지우면
`stops watching an absent reference only after seven days with every path closed`가 실패한다(§8 G1).

예산 쪽 여유도 덧붙인다(계산이지 측정이 아니다): 스윕 1회가 200행이므로 색인 N행의 한 바퀴는
`ceil(N/200)`회, worker 1회/분이면 7일 = 10,080회 = 200만 ref까지 한 바퀴를 돈다.

## 7. export — 넣지 않는다

M2-01l은 v21에서 "재계산 가능한 것은 내보내지 않는다"로, M2-01j는 v20에서 "소유자가 입력해 재계산
불가한 것은 내보낸다"로 답했다. `course_thumbnail_object_ref`는 **어느 쪽도 아니다** — 소유자 입력도
사용자 데이터도 아니고, **worker가 객체 key 위에 들고 있는 커서 상태**다. 그리고 담고 있는 값인 객체
key 자체는 export가 처음부터 거부해 온 바로 그것이다(M2-01l `expect(JSON.stringify(state)).not.toContain('private/v1')`).

그래서 export 표면은 **전혀 늘지 않고 schemaVersion은 21에 머문다.** 시험으로 고정했다:
`adds no export surface: the index is internal operating state` — 스윕이 감시 중인 ref가 있는 계정의
export가 여전히 v21이고, 그 storage ref도 `settled_at`도 담고 있지 않음을 확인한다.

## 8. 가드 되돌리기 측정 — 16/16 비공허, 그중 1건은 `40P01` 재현

**되돌리기 측정 자체가 틀릴 수 있다**는 경고를 받았으므로, 되돌리기 스크립트가 **치환이 실제로
일어났는지 먼저 확인**하고, 일어나지 않으면 `ANCHOR DID NOT MATCH — measurement invalid`로 중단하게
했다. 각 되돌리기는 **깨끗한 새 데이터베이스**에서 돌린다(migration checksum 때문에 필수).

**이 장치가 실제로 한 번 나를 구했다.** worker 호출부를 되돌릴 때 첫 시도의 anchor가 prettier가 한 줄로
합쳐 놓은 실제 코드와 달라 "18 passed(=실패 0)"가 나왔다. anchor를 고쳐 다시 재면 2건이 실패했다.
0건이 나오면 anchor부터 의심하라는 지시가 정확히 이 경우였다.

| #   | 가드                                                      | 되돌린 방식                   | 실패 시험 수                         |
| --- | --------------------------------------------------------- | ----------------------------- | ------------------------------------ |
| G1  | `settle`: `recorded_at < now-7 days`                      | 조건 삭제                     | 1                                    |
| G2  | `settle`: 열린 영수증 없음                                | 조건 삭제                     | 1                                    |
| G3  | `settle`: 살아 있는 그림(`prepared`/`ready`)              | → `false`                     | 1                                    |
| G4  | `settle`: `greatest(expires_at, fence+1h, lease+1h)` 유예 | → `false`                     | 2                                    |
| G5  | `reclaim`: 살아 있는 참조                                 | → `WHERE false`               | 1                                    |
| G6  | `reclaim`: fence·lease 1시간 유예                         | → `WHERE false`               | 1                                    |
| G7  | `reclaim`: 이미 열린 영수증이면 short-circuit             | 조건 삭제                     | 2                                    |
| G8  | `candidates`: `settled_at IS NULL`                        | 조건 삭제                     | 1                                    |

| G10 | ref 기록 트리거                                           | `CREATE TRIGGER` 삭제         | **12**                               |

| G13 | **말소가 색인을 마지막에 지움**                           | 두 줄 순서 뒤집기             | 1 — **`40P01 deadlock detected` ×2** |
| S1  | `assertSafeExistingFile` 루프 안 ENOENT 가드              | `missing`+`lstat` 쌍으로 복귀 | **5/5회 실패**                       |

**과장하지 않기 위해 구분해 적는다.** 위 16건은 모두 **되돌려서 실패를 실제로 관측한 것**이다.
중복 방어여서 실패할 시험이 없는 항목은 이 표에 없다 — 다만 G3·G4·G7은 **처음 재면 공허했고**,
공허하지 않게 만들기 위해 **가드를 지운 게 아니라 시험을 세 개 더 썼다**:

- G3 →`keeps watching a live picture whose object went missing, however old the reference`
  (30일 된 `ready` 그림의 객체가 저장소에서 사라진 경우. 살아 있는 참조라는 사실 하나만이 감시를
  유지한다.)
- G4 →`keeps watching an absent reference inside the grace after a closed render fence`
  (아무것도 publish되지 않았고 영수증도 전부 닫혔지만 fence가 2분 전이라 아직 호출이 날아오고 있을
  수 있는 경우.)
- G7 →`reports nothing queued for a key whose receipt is already open, and leaves it alone`
  (이미 열린 영수증의 `available_at`을 앞으로 당기지 않음 — 당기면 publish 중인 writer 밑에서 객체가
  지워진다.)

G3 첫 측정이 공허했던 이유도 기록해 둔다: `ready` 행의 `expires_at`이 아직 미래였기 때문에 G4가
대신 막고 있었다. 행을 30일 늙힌 뒤에야 G3만 남았다.

## 9. 과잉 삭제 금지(7절)를 고정한 시험

이 노드에서 가장 위험한 실패는 **스윕이 살아 있는 그림을 지우는 것**이다. 네 방향에서 막았고 전부
시험이다.

| 막는 것                                   | 시험                                                                             |
| ----------------------------------------- | -------------------------------------------------------------------------------- |
| 살아 있는 코스가 보여 주는 그림           | `never reclaims the picture a live course is still showing`                      |
| fence가 열린 render가 방금 publish한 객체 | `leaves a published key alone while its render can still be publishing`          |
| 닫힌 render지만 fence 유예 안             | `holds a closed render key back for the grace after its fence, then reclaims it` |
| 이미 열린 영수증의 유예를 앞당기지 않음   | `reports nothing queued for a key whose receipt is already open, ...`            |

그리고 **삭제 직전 재검증은 그대로다**: 회수는 `resource_object_cleanup`에 넣을 뿐이고,
`authorize_resource_object_cleanup`이 바이트를 지우기 전에 살아 있는 참조를 전부 다시 확인한다.
스윕이 틀려도 그 지점에서 `REFERENCE_PRESENT`로 닫힌다.

## 10. bounded

- **창 상한**: `least(greatest($2,1),1000)` — 데이터베이스가 clamp한다. 호출자를 믿지 않는다(G9).
- **스윕 1회 작업량**: 색인에서 최대 `limit`행(worker 기본 200) + 행당 `stat` 1회 + 유계 statement 1회.
  디렉터리를 걷지 않고 원장 표를 스캔하지 않는다.
- **N행 창이 정확히 N행을 읽는다**: `reads exactly one index row per candidate and touches no ledger table`이
  `pg_stat_get_xact_tuples_*`로 **트랜잭션 안에서 실제로 읽은 튜플 수**를 잰다 — `course_thumbnail` 0행,
  색인 ≤1행.
- **두 namespace는 서로를 굶기지 않는다**: cursor도 예산도 분리(`sweeps the thumbnail namespace in its
own bounded window, with its own cursor`).
- 창이 가득 차면 커서가 전진하고, 짧으면 `''`로 되감긴다(reaper·dead-letter와 같은 재개 규약).

## 11. 잠금 순서

새 writer 둘(`settle`, `reclaim`)은 advisory lock을 잡지 않는다. 방향:

- 통상 쓰기: `course_thumbnail`(행) → 트리거 → `course_thumbnail_object_ref`(행)
- `settle`: 색인 행 UPDATE → (`course_thumbnail`·`resource_object_cleanup`은 잠금 없는 SELECT)
- `reclaim`: (잠금 없는 SELECT) → `resource_object_cleanup` 행 INSERT/UPDATE

`queue_course_thumbnail_refs`와 같은 방향이고, `authorize_resource_object_cleanup`(영수증 행 FOR UPDATE
→ 원장 SELECT)과는 **원장 읽기가 잠금을 잡지 않으므로** 순환이 생기지 않는다. `delete_course`·
`erase_account`·`release_course_thumbnail_render`·reaper와의 실제 경합은
`adds no new lock-order inversion to the writers of one tenant`에 **스윕을 새 writer로 합류시켜** 잰다
(코스 생성·편집·삭제 30줄, render+drain+**sweep** 10줄, 그리고 그 밑에서 도는 말소). 역방향을
만들었을 때 실제로 `40P01`이 나온다는 것이 §6의 G13이다.

## 12. 권한

- 새 표 둘: RLS `ENABLE`+`FORCE`, tenant policy(색인 표), **표 권한 0**. 시험:
  `gives the sweep role no table access and keeps the new tables behind row-level security`,
  `gives the runtime role no reach into the reference index at all`(runtime role은
  `permission denied for table course_thumbnail_object_ref`).
- 새 SECURITY DEFINER 함수 5개 + 교체된 `erase_account`: `search_path=pg_catalog` 고정, `PUBLIC` 회수.
  시험이 `pg_proc.proconfig`를 6개 함수 전부에 대해 확인한다.
- worker role EXECUTE는 정확히 5개만 늘었다. 시험이 038 대비 **차집합**으로 확인한다.

## 13. 이전 migration 무간섭 — 격리 DB 업그레이드로 증명

`course-thumbnail-reconciliation-upgrade.integration.test.ts`는 **자기 전용 데이터베이스**를 만들어
038까지 적용 → 038 시점 권한 부여(`erase_account(text)` 포함) → 현재로 업그레이드 → 확인한다.

- **checksum 불변**: 1~38의 기록된 checksum이 업그레이드 전후로 전부 같다(`migration N changed`로
  어느 것이 바뀌었는지 지목).
- **이전 함수 권한 회수**: 039가 rename한 `erase_account_before_thumbnail_object_refs(text)`에
  소유자 외 grantee가 0이고, role은 **어느 이름으로도** erase를 실행할 수 없다. 즉 rename이 특권을
  조용히 물려주지 않는다.
- **backfill**: 038 데이터베이스에 M2-01l의 enqueue 트리거로 실제 queued render를 만든 뒤 업그레이드하면
  그 `temporary_ref`가 감시 창에 들어온다.

038 이하 파일은 한 글자도 건드리지 않았다. 함수 교체는 039 안의 rename + `CREATE FUNCTION`뿐이다.

## 15. 상속된 한계 — 색인에 들어간 적 없는 객체

`prepare_course_thumbnail`을 거치지 않고 publish된 객체는 색인에 기록된 적이 없으므로 **스윕이 볼 수
없다.** 현재 그런 객체를 만들려면 고장난 worker가 필요하다 — 정상 worker는 항상 prepare를 먼저 하고,
`prepare`는 key를 `(athlete, course, revision_id, sha256)`로 **정확히 검증**하므로 임의의 key를 기록할
수도 없다. M2-01c의 색인도 같은 성질이다(`reserve`/`prepare`가 기록하지 않은 key는 창 밖이다).

바꾸지 않았고, 기록만 남긴다: **이 스윕의 보장 범위는 "이 서버가 기록한 참조"이지 "저장소에 있는
모든 바이트"가 아니다.** 디렉터리를 걷지 않기로 한 M2-01c의 결정이 그대로 상속된 결과다.

## 16. 범위 밖 발견 — `writeTemporary` 와 `delete` 의 디렉터리 경합

B1을 재현하다가 **다른 경합**을 측정했다. 같은 코스의 형제 임시 객체를 하나는 쓰고 하나는 지우면,
`delete`의 `pruneEmptyParents`가 공유 디렉터리를 비우는 동안 `prepareParents`의 `mkdir`·`lstat`·`chmod`가
터진다. 500회 쌍 × 3회 실측:

```
{"ok":684, "THREW ENOENT@mkdir":182, "THREW ENOENT@lstat":56,
 "THREW EINVAL@mkdir":35, "THREW ENOENT@chmod":43}
```

**이 노드의 결함이 아니다.** 이 노드가 더하는 경로는 `stat`뿐이고 객체를 쓰지 않는다. 쓰는 쪽은
M2-01l의 render worker이고 지우는 쪽은 M2-04b의 cleanup worker이므로, 이 경합은 **M2-01l 시점에 이미
도달 가능**했다. 다만 **이 노드가 삭제 트래픽을 늘리므로 발생 확률은 올라간다.**

고치지 않았다 — `prepareParents`를 고치려면 `mkdir`의 `EINVAL`을 무엇으로 볼지, 재시도를 몇 번 할지를
정해야 하고 그것은 **쓰기 경로의 설계 결정**이지 스윕의 문제가 아니다. 이 노드에서 손대면 과잉
대응이다. 재현 방법과 실측을 여기 남기니 **별도 노드로 배정해 주기 바란다.** 저장소의 stress 시험
8회에서는 발화하지 않았다(한 코스의 임시 객체 삭제가 그 코스의 render보다 뒤에 오는 것이 보통이라).
