## 0. 결론

**결함이었다. 실제 PostgreSQL 14에서 재현했고 닫았다.**

- `delete_course`는 코스 행을 물리 삭제한다. 활동 삭제는 묘비(`activity_canonical.deleted`)를, 말소는
  `tenant_erasure` 행을 남기지만 코스 삭제는 **아무 행도 남기지 않았다.** 그래서 복원 절차가 재생할 원장이 없었다.
- 복원된 cluster는 백업 시점의 코스 행(이름·좌표·revision·즐겨찾기·접근성 메모·그림 행)과 object archive의 그림
  객체를 그대로 되돌린다. 기존 재생(말소·활동 삭제·제약·근거 철회)을 전부 마친 뒤에도 runtime repository가 그
  코스를 `available`로 읽고 목록에 보여 준다.
- 수정(migration **049** `049_course_deletion_ledger.sql`): 코스 삭제가 같은 트랜잭션에서 **삭제 원장 행**
  (`course_deletion`: tenant, course id, 시각 — 이름·좌표 없음)을 쓰고, 코스 디렉터리 **object-scope purge를 무장**하며,
  그 id는 **다시 코스가 될 수 없다**(terminal trigger). 복원은 원장을 DB 밖으로 캡처해 두었다가 복원 **완료 후**,
  runtime 접근 **전에** `replay_course_deletion`으로 항목마다 재적용한다 — fail-closed, 멱등.

## 1. 재현(수정 전 트리, drill, PostgreSQL 14.15, 실제 파일시스템)

drill에 fixture를 먼저 추가하고 수정 없이 실행했다. 살아 있는 tenant(`retainedAthlete`)가

- 백업 **전** 보존 기록에서 코스 `ownerDeletedCourse`를 만들고 즐겨찾기·접근성 메모를 달고 그림을 그린다;
- dump 뒤·archive 복사 전(틈)에 그 코스를 revision 2로 rename(그림 1장 더), 틈 안에서 코스 `gapBornCourse`를 새로 만든다(그림 1장);
- archive 복사 뒤 두 코스를 실제 `courses.remove`로 삭제한다;
- 복원 → 기존 재생 전부 → runtime DB 연결.

그 시점의 probe 출력(`drill-repro.log`, 재생 트랜잭션 COMMIT 뒤, runtime repository):

```json
{
  "m2_01ao_repro": {
    "ownerDeletedCourseAfterReplay": "available",
    "name": "Owner-deleted drill course",
    "coordinates": [
      [127.02, 37.5],
      [127.0201, 37.5001]
    ],
    "inOwnerList": true,
    "preferenceRows": [{ "favourite": true }],
    "thumbnailObjectPresent": true
  }
}
```

즉 소유자가 지운 코스가 이름·좌표·즐겨찾기·그림 객체와 함께 소유자 목록에 되살아났다. probe는 재현 뒤 제거했고,
같은 사실을 영구 check `restore_brings_back_owner_deleted_course_with_its_owner_facts_and_pictures`(재생 **전**
복원 cluster에 course·revision·lineage·preference·note·thumbnail 행과 두 그림 객체가 있음을 단언)로 남겼다.
이 check가 있어야 재생 뒤 부재 단언이 의미를 가진다.

share epoch(M2-01k-o 요구 D7)는 공유 링크만 막으므로 이 공백과 무관하다는 요구 문서의 판단도 재현으로 확인됐다:
공유 없이도 코스 자체가 돌아온다.

## 2. 설계

M2-01y의 object-scope purge와 같은 방식이다: **삭제는 종단적이고, 무장은 넓게, 파괴는 좁게.**

### 2-1. 원장 — `course_deletion`

- 열: `athlete_id`, `course_id`, `deleted_at`. PK `(athlete_id,course_id)`. 코스 FK 없음(코스는 이미 없다).
- 이름·좌표·revision 내용은 넣지 않는다. `activity_suppression`처럼 suppression 사실이다.
- RLS ENABLE+FORCE, tenant 정책 + 소유자(migrating role) 정책(047 방식: 비-superuser 소유자도 terminal 검사가
  session 설정에 기대지 않게). PUBLIC 회수, 어느 role에도 표 권한 없음(runtime `SELECT` → 42501, 통합 시험).
- **backfill 없음**: 049 이전의 삭제는 남긴 행이 없다(§6 open item).

### 2-2. 삭제 본문 하나 — `apply_course_deletion(text,uuid,timestamptz)` (권한 없음)

live 삭제와 복원 재생이 **같은 본문**을 돈다. 순서:

1. `supersede_course_thumbnails(…,'course_deleted')` — 그림 행이 이름하는 객체를 queue(038과 같음);
2. `arm_object_scope_purge(tenant,'course',course)` — 코스 디렉터리 `…/courses/<c>/` purge 무장(046). 그림 행의 fence를 읽어야
   하므로 revision 삭제 **전**. 이것이 **틈에서 그려져 어떤 복원 행도 이름하지 않는 그림**까지 지운다;
3. 036의 순서로 search → proposal → revision → course 삭제(preference·accessibility note·thumbnail·lineage는 cascade);
4. 원장 행 `INSERT … ON CONFLICT DO NOTHING`(마지막).

`delete_course`는 038 본문(tenant 검사, 행 잠금, revision 검사)을 유지하고 제거부만 이 호출로 바꿨다.
live 삭제도 이제 코스 purge를 무장한다 — 이전에는 활동 삭제의 회수(reclaim)만 무장했다(M2-01y). purge lease는
"있고 available인 코스"만 거절하므로 terminal trigger가 그 조건을 run 동안 보장한다.

**공유(M2-01k-o)**: 아직 main에 없다. 요구 §4는 공유 행을 `course_revision`에 `ON DELETE CASCADE`로 둔다 → 3단계의
revision 삭제가 공유 행을 함께 지운다. 따라서 이 노드의 재생은 공유 표를 이름으로 참조하지 않고도 공유 행을 회수한다.
M2-01k-o가 cascade가 아닌 다른 방식을 택하면 `apply_course_deletion`에 한 줄을 더해야 한다(§6).

### 2-3. terminal — `course_deletion_terminal` (BEFORE INSERT ON course)

원장에 있는 (tenant, course id)는 다시 삽입할 수 없다(`COURSE_DELETION_TERMINAL`). course id는 서버가 생성하고 create는
tenant command lock(0)을 잡으므로 runtime 경로에서 같은 id가 올 일은 없다. 이 trigger는 purge의 안전 조건과
"복원 재생 뒤 같은 id로 되살리기"를 DB가 거절하게 한다.

### 2-4. 복원 재생 — `replay_course_deletion(text,uuid,timestamptz) → text` (권한 없음, 복원 관리자 전용)

반환: `deleted`(복원 cluster에 코스가 있었다 → live와 같은 본문으로 삭제), `absent`(없었다 — 틈에서 태어나 지워진
코스 → 원장 행 + purge 무장), `already_applied`(원장 행이 이미 있고 코스가 없다 → **아무것도 바꾸지 않는다**; purge 행이
아예 없을 때만 무장). 같은 원장을 두 번 재생해도 두 번째는 상태를 바꾸지 않는다(drill·통합이 상태 스냅숏으로 단언).

거절(트랜잭션 실패 = fail closed): session tenant 불일치, 비-canonical tenant/course id, 없는·미래 삭제 시각, 말소된
tenant(호출자가 말소 충족으로 **계수**), **identity 계정이 없는 tenant**, 다른 tenant가 가진 course id.

"복원이 끝나기 전에 적용"에 대한 함수의 방어는 **스키마만 복원된 단계(pre-data)에 한정된다.** 그 cluster는 함수는
있고 tenant는 없다. 거기서 재생하면 `absent`로 원장만 남기고 뒤이은 데이터 section이 코스를 되살리므로, identity 계정이
없는 tenant를 거절한다(`COURSE_REPLAY_TENANT_UNKNOWN`). drill이 실제 `pg_restore --section=pre-data`만 한 DB에서 이를
단언한다(`course_deletion_replay_refuses_a_cluster_whose_data_is_not_yet_restored`). **데이터 적재 중**(계정 행은 이미
있고 코스 행은 아직, trigger·제약은 post-data에서야 생김)에 재생하면 함수는 그 상태를 알아볼 수 없어 `absent`를 기록할
수 있고, 남은 적재가 코스를 되살릴 수 있다. 그래서 절차(runbook "코스 삭제 원장 재적용")가 **데이터와 post-data 복원이
모두 끝난 뒤** 재생하도록 요구한다. 이 순서는 함수가 아니라 절차가 보장한다.

### 2-5. 말소와의 상호작용

- `erase_account` 체인에 한 겹 더: `77206 → 0 → DELETE course_deletion → 이전 체인`(047의 wrapper 방식, 이전 본문은
  `erase_account_before_course_deletion`으로 byte 동일 보존 — upgrade 시험).
- 원장 캡처는 말소 전에 한 항목을 따로 캡처해 합친다(활동 삭제 원장과 같은 overlap). 재생은 말소된 tenant 항목을
  `erasure_satisfied`로 **계수**하고 코스 부재를 단언한다. 함수 자체도 말소 tenant를 거절하므로 호출자가 계수를 빠뜨려도 조용히 통과하지 않는다.

### 2-6. lock 순서

- live 삭제: `database.tenant`(77206 shared → 0) → course 행 `FOR UPDATE` → thumbnail 행 → cleanup queue → purge 행 → search/proposal/revision/course
  → 원장 행. 활동 묘비의 회수(course 행 → thumbnail → course purge 행 → revision)와 같은 방향이다.
- 재생: `0` → course 행 → 위와 같음. 복원 트랜잭션 안, runtime 접근 전.
- 말소: `77206 → 0 → rows`(upgrade 시험이 본문 순서를 단언).
- 새 cycle 없음: purge worker는 purge 행만 잠그고 나머지는 잠그지 않고 읽는다(046).

### 2-7. migration 번호와 M2-01k-o

처음에는 main의 마지막이 047이어서 048로 만들었다. main이 `8429efa`로 이동하며 `048_garmin_unofficial.sql`(역시 `erase_account`를 감쌈)이 들어와, rebase하고 **049**로 옮겼다(§8). M2-01k-o가 병행해서 migration을 추가하면 나중에 병합하는 쪽이 번호를
올린다. 두 migration은 서로의 객체를 참조하지 않는다. 둘 다 `erase_account`를 rename-wrap하므로 **각자 병합 시점의 현재
`erase_account`를 감싼다**(047 방식이라 순서와 무관하게 성립). upgrade 시험은 파일 이름(`/^\d+_course_deletion_ledger\.sql$/`)으로
시작점을 찾아 재번호에 흔들리지 않는다.
