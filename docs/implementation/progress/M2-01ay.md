## 2. 설계와 근거

### 2.1 군사 구역: profile이 아니라 import 데이터에서 막는다

**의미.** 군사 구역(`landuse=military` 또는 `military=*` 면)을 합친 영역의 **경계를 지나는 보행 경로는 없다**. 경로는
들어가지도 나오지도 않는다. 구역 안 도로는 graph에 남는다. 그래서 구역 안의 점(판문점)은 그 안 도로에 snap되고, 밖에서
가는 요청은 `no_route`가 된다(사전 등록의 기대 결과가 `no_route`인 이유와 같다). 전부 금지(구역 안 edge 전체 priority 0)로
하면 GraphHopper가 그 점을 가장 가까운 **바깥** 도로에 snap해, 120 m 안이면 담장 밖 어딘가로 가는 경로를 조용히 내놓는다.
"경계 통과 금지"는 그 대체를 하지 않는다.

**구현(`scripts/geo/MilitaryPerimeterBarriers.java`, `build-routing-graph.mts`의 `deriveMilitaryPerimeterBarriers`).**
osmium으로 군사 면과 보행 가능 way(`selectFootGraphWays`: `highway=*`에서 profile이 무시하는 motorway·trunk 제외,
`route=ferry`·`shuttle_train`, `man_made=pier`, `railway=platform`, node 위치 포함 OPL)를 뽑는다. 도구가 면을 GeometryFixer로 고치고 합친 뒤(JTS
1.19, pin된 jar의 classpath; 인접·중첩 구역 사이는 경계가 아니다), 경계와 만나는 **각 선분에 새 node를 끼운다**
(`barrier=gate`, `access=no`, `foot=no`, `m2_01ay:military_perimeter=yes`, id 200억부터). 만나는 점이 기존 node면 그
node는 그대로 두고 닿는 선분마다 약 0.1 m 옆에 둔다. foot parser가 이미 막는 way(`foot`/`access` 제한 값)는 건드리지
않는다. 결과는 osmChange → `osmium apply-changes`(원본의 replication 헤더 유지)로 만든 파생 PBF이고, 엔진은 그것을
import한다. GraphHopper는 barrier node에서 way를 나누고 `foot` 값이 제한이면 그 barrier edge에 보행 접근을 주지 않는다
(`AbstractAccessParser.isBarrier`, 바이트코드 확인).

**provenance.** pin된 extract 파일은 바뀌지 않고 manifest의 `extractSha256`도 그 파일이다. 파생의 도구 SHA-256, 변경
SHA-256, 파생 PBF SHA-256, 개수, osmium 버전, 원본 최대 node id(200억과 겹치지 않음을 build가 검사)는 graph 디렉터리의
`edge-facts/derivation.json`에 있고, graph content hash(→ graph id)가 그것을 덮는다. 세 번의 독립 build(scratch
`33caecb71fe414c4`, `c1fa89fbaf155076`, 최종 `92e0fa5f319a41df`)가 같은 변경(`cda8e30e…`)과 같은 파생 PBF(`623b6705…`)를
냈다.

**먼저 시도하고 버린 것 — custom model area(측정).** GraphHopper 10.0의 custom model `in_<area>`(전역
`custom_areas.directory`)로 먼저 만들었다. 기능은 같았지만(82쌍 결과가 최종과 outcome·거리까지 같음) **요청마다 비싸다**:
GraphHopper는 요청마다 weighting을 만들며 custom model 전체를 문자열로 만든다(`CustomModel.toString` →
`JsonFeature.toString`이 area geometry를 WKT로 씀, 바이트코드 확인). 측정(`verification-logs/m2-01ay/design-measurements/`):

### 2.2 ferry: 유지하고 알린다(결정)

사전 등록은 FRY-01/FRY-02에 "mapped foot-allowed ferry를 쓰고 ferry 미터를 보고"를, BRG-MW-02(영종도)에는 도선 경로를
대안으로 받는다. ferry를 빼면 FRY-01/02·BRG-MW-02가 `no_route`(partial)가 되어 ferry 층(2/2.5)과 **핵심 층**
bridge-motorway-only(2.5/3)가 떨어진다. 제품 쪽 위험은 도선 거리가 걸은 거리로 읽히는 것이다. 그래서 경로에
`route_includes_ferry` 경고를 붙인다(계약 문서: 거리·시간에 걷지 않는 도선이 포함되고, 운항·요금은 모름). serving
profile 머리말에도 이 결정을 적었다. 독도 도선 때문에 NEG-ISL-01이 여전히 경로를 낸다(검토자 분류: sample-design).

### 2.3 시간 조건 접근: 경로가 조용하지 않게

GraphHopper 10.0은 `yes @ 6:00-24:00`이나 `opening_hours`를 encode하지 못한다(`OSMTemporalAccessParser`는
`DateRangeParser`만, 바이트코드 확인). 그래서:

- profile이 `osm_way_id`(31 bit; pin extract의 최대 way id 1,554,316,713)와 `road_environment`를 encode한다.
- build가 같은 extract에서 foot graph가 담을 수 있는 way(`selectFootGraphWays`, 군사 차단과 같은 선택: `highway=*`에서
  motorway·trunk 제외, `route=ferry`·`shuttle_train`, `man_made=pier`, `railway=platform`) 중 `access:conditional`·
  `foot:conditional`·`opening_hours`가 있는 way **77개**를 `edge-facts/time-conditional-ways.json`에 쓴다(graph content hash에
  포함; r1 전에는 `highway`/`route=ferry`만 골라 76개였다, §12).
- `loadRoutingDeployment`가 검증한 graph 디렉터리에서 그것을 읽어 `RoutingDeployment.edgeFacts`로 둔다(목록은 closure 안,
  바꿀 수 없음). `osm_way_id`와 목록 중 하나만 있거나, edge facts가 있는데 `road_environment`가 없으면(r1) `EDGE_FACTS_INVALID`로
  거절한다. M2-01ay 이전 graph는 둘 다 없어
  전과 같다(`null`, 경고 없음).
- adapter는 edge facts가 있을 때만 `road_environment`·`osm_way_id` detail을 더 요청하고(옛 graph에 `osm_way_id`를 요청하면
  모든 요청이 실패한다), 둘 중 하나라도 없거나 geometry를 덮지 않으면 `engine_contract_violation`이다. 경로가 목록의 way를
  쓰면 `route_includes_time_conditional_access`, ferry edge가 있으면 `route_includes_ferry`.
- 계약: `routeWarningCodeSchema`에 두 값 추가(additive, schema version 1 그대로). 저장 revision에도 남는다. UI는 경고 코드를
  기존대로 그대로 나열한다(문구화는 후속).

### 2.4 STR-04

실제 엔진 답(부산 40계단, 9 정점, 93.44 m)의 정점 7이 끝점에서 0.7 m였다. 옛 코드는 마지막 waypoint를 "커서부터 1 m 안의
첫 정점"(7)으로 찾고 커서가 마지막 정점(8)이 아니라서 거절했다. 이제 마지막을 뺀 waypoint만 순서대로 찾고, 마지막
waypoint는 이미 따로 검사하는 마지막 정점이다. 끝나기 전에 멈춘 geometry, 뒤집힌 geometry, 끝 뒤에야 중간 waypoint에
닿는 geometry는 여전히 거절한다(시험).

### 2.5 probe: 정확한 way, 보행자 기준 node

- `osm_way_id`가 있는 graph에서는 보조 요청이 그것을 받고, 경로 아래 way와 미터를 **엔진의 구간**에서 합친다
  (`wayMatchMethod: engine-way-ids`). 태그는 같은 extract에서 `osmium getid`로 읽는다(없는 id는 오류). `waysAlongRoute`에
  다리·터널도 넣는다(BRG-01 증거). 없는 graph는 기존 기하 대조 그대로.
- node: `restrictedNodesPassed`는 M0-06b와 같은 뜻으로 두고, `footRestrictedNodesPassed`(보행자가 막히는 node)와
  `accessRestrictedNodesWithFootOverridePassed`, `nodesOnRoute[].pedestrianAccess`를 더했다.
- 순수 대조 코드는 `scripts/routing-tag-check.ts`로 옮겨 단위 시험한다(옮긴 뒤 run 3이 run 1과 82쌍 모두 같음).
- graph 복사가 하위 디렉터리를 포함한다.

### 2.6 성능 probe의 부하 경로

부하 경로의 균등 경유점 6번(long-track 표본 10000)이 **용산기지 안**이다. 새 graph에서 37개 부하 요청이 모두 `no_route`가
되어 check가 실패했다(기록 전용 3회, 03:31Z). 전에는 그 경로가 기지를 가로질렀다. 경유점 6을 같은 구간 약 1.1 km 북쪽
표본 9700으로 옮겼다(`HEAVY_WAYPOINT_SAMPLE_OVERRIDES`, 경로 약 26 → 23 km). 시간 기준선은 다시 잡지 않았다.

## 10. 남은 일과 한계

1. **coverage 판정은 여전히 부족.** 남은 원인은 검토자 분류로 sample-design 셋(RUR-02 거리 하한, BRG-01 잠수교 지정,
   NEG-ISL-01 독도 도선)과 osm-data 하나(RUR-01 snap)다. 기준을 바꾸는 것은 검토자·사람의 결정이고 이 노드는 하지 않았다.
   BRG-01을 경로로 고치려면 OSM의 잠수교 보행로 데이터가 필요하다.
2. **군사 구역 안끼리의 경로는 막지 않는다.** 두 끝점이 같은 (합친) 군사 구역 안이면 그 안 도로로 경로가 난다(의도한 의미:
   경계 통과 금지). runbook도 이 조건을 그대로 적는다(r1). 작은 기지의 안쪽 도로가 subnetwork로 빠지면 점이 바깥 도로로 snap될 수 있다(담장 밖까지만).
3. **ferry는 경로에 남는다**(경고만). 운항 시각·요금·보행 승선 가능 여부는 모른다.
4. 시간 조건은 **경고**이지 회피가 아니다. 출발 시각이 없어 열려 있는지 판단하지 않는다. 경고 코드는 UI에 코드 그대로
   보인다(문구화 후속).
5. 경계 판정은 OSM 면의 정확도에 달려 있다. 태그 없는 군사 시설은 모른다. 교차 판정은 JTS 평면 기하(경위도)다.
6. build 호스트에 osmium이 필요하다(runbook에 적음). swap·운영 probe의 clip import도 파생을 거친다(실행하지 않음).
7. 시간 기준선(`engine.routeUnderLoadMs`)은 경로가 약 26 → 23 km로 바뀌었지만 다시 잡지 않았다(판정 p95 99/200).
8. 커밋 전 peer review(CLAUDE.md: 구현하지 않은 별도 Claude subagent)와 phase의 Codex 검토는 root 몫이다. 이 노드는 검토자를
   띄우지 않았다.
