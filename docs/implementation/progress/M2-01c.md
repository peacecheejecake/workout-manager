# M2-01c · private track 저장

상태: **서버 저장 경로(계약·migration·persistence·API·객체 수명주기·export/복원) 구현·검증 완료.
UI는 이 작업에 없고, 계획 7절의 메모리 상한은 "확인된 상한 아래에서만 파싱한다"까지만
달성했다**(프로세스·컨테이너 상한은 여전히 배포 몫). 기준 HEAD `7b189cc`.
계획 문서는 [map-implementation-plan.md](../map-implementation-plan.md) 3·4·7·8절이며 7절을
수용 기준으로 삼았다. `task-graph.json` 상태는 root가 소유하므로 바꾸지 않았다.

이 노드가 물려받은 두 부채를 먼저 적는다.

1. **실제 메모리 상한(M2-01a → b → c 이월).** 파싱은 `resourceLimits.maxOldGenerationSizeMb`가
   걸린 worker에서만 일어나고, **상한이 실제로 적용됐는지 매번 측정해 확인한 뒤에만** bytes를
   넘긴다. 적용되지 않았으면 파싱하지 않고 `TRACK_PARSE_CEILING_NOT_APPLIED`로 닫는다.
   **처음에는 "닫았다"고 적었는데 그것은 틀렸다**: 독립 검토가 부모 프로세스의
   `--max-old-space-size=1024`가 worker ceiling을 무력화하는 것을 재현했다(같은 60,000점 GPX가
   32 MiB ceiling에서도 약 1 GiB로 파싱되어 `TRACK_OUTPUT_TOO_LARGE`로 끝났다). 지금은 그
   경로가 fail closed이며, **부채의 나머지(프로세스·컨테이너 수준 상한)는 여전히 이 코드가
   걸지도 증명하지도 못한다.** 두 번째 검토에서 `ceiling + 384 MiB` 허용폭이 너무 넓어
   `--max-old-space-size=128` + ceiling 32 MiB가 통과하는 것이 드러나, 검사 대상을 **명시한
   총 heap 예산**(기본 `ceiling + 192 MiB`, 측정값)으로 바꾸고 그 값을 정확히 대조한다.
   상세와 남은 한계는 아래 "메모리 상한"에 있다.
2. **"재파싱은 새 revision"(M2-01a 계약 주석만 있던 규칙).** 강제하는 코드를 만들었다.
   sample 대응을 SHA-256 digest로 고정하고, revision row는 append-only trigger로 잠그고,
   head는 +1 전이만 허용한다. 대응이 달라진 재파싱은 revision 2로 **덧붙고** revision 1은
   byte 단위로 그대로 남는다(테스트로 고정, 가드 제거 시 실패 확인).

## 고정한 경계

- **저장 소유자는 세션에서만 나온다.** 모든 route가 `principal(request).athleteId`를 쓰고
  경로·query·body에 athlete id를 담을 자리가 없다. `activityTrackReserveMetadataSchema`는
  `strictObject`라 `athleteId`·`storageRef`·`samples`·`sampleCount`·`correspondenceDigest`·
  `trackRevision` 중 하나만 있어도 400이다. RLS(FORCE)·CSRF·인증 download를 적용한다.
- **서버는 클라이언트 parse 결과를 신뢰하지 않는다 — 신뢰할 통로 자체가 없다.** 업로드
  요청은 파일 bytes 하나뿐이고, 서버가 **자기가 저장한 temporary object를 다시 읽어**
  bounded worker에서 같은 규칙으로 재파싱한다. DB에 들어가는 parser id, format,
  sample/segment 수, 거리, 대응 digest, 정규화·지도 파생물은 **전부 그 재파싱의 산출물**이다.
  M2-01b의 브라우저 parse는 계획대로 preview로 남는다.
- **객체 key는 서버가 만든다.** `packages/server/media/src/keys.ts`에
  `private/v1/tenants/{t}/activities/{a}/tracks/{trackId}/{raw|normalized|map_path}/uploads/{uploadId}/sha256/{hash}.{fit|gpx|json}`
  (temporary는 `.../temporary/{uploadId}/{artifact}`)를 추가했다. raw는 `fit|gpx`, 파생물은
  `json`만 허용하고, 경로 순회·절대경로·대문자 digest·미지의 artifact를 거절한다. persistence는
  받은 ref를 **같은 규칙으로 다시 조립해 대조**하고 (tenant·activity·track·upload·digest·확장자)
  하나라도 다르면 `IDEMPOTENCY_CONFLICT`다. local filesystem adapter는 기존 O_NOFOLLOW·
  symlink·root 검사에 track pair 검사(같은 upload·같은 track·같은 artifact kind)를 추가했다.
- **DB를 먼저 쓴다.** reserve에서 **세 temporary ref를 모두** 기록하고, prepare에서 **세 final
  ref와 재파싱 결과를 모두** 기록한 뒤에야 객체를 publish한다. 중단된 업로드는 항상 정확한 key로
  회수 가능하다. 실패 경로는 "아직 durable하지 않은 것만" 요청이 직접 지우고, 그 뒤는 durable
  manifest에 맡긴다.
- **cleanup manifest·worker·lease·dead-letter는 M2-04b/c/d의 것을 그대로 쓴다.** 새 queue도
  새 worker도 만들지 않았다. `resource_object_cleanup`의 reason에 `activity_deleted`·
  `track_superseded`를 더하고, `reap_expired_resource_uploads`·`prune_resource_upload_history`·
  `authorize_resource_object_cleanup`을 확장했다. lease 시간·만료·expiry 판정은 전부 DB 시각
  (`statement_timestamp()`/`clock_timestamp()`)이고 호출자가 준 시각을 신뢰하지 않는다.
- **삭제 직전 live reference와 진행 중 업로드를 다시 확인한다.** `authorize_…`에 "live
  activity의 revision이 참조하는가"와 "만료되지 않은 track upload가 참조하는가"를 추가했다.
  참조가 있으면 삭제하지 않고 `REFERENCE_PRESENT`로 닫는다.
- **publish는 fence 안에서만 일어난다.** 이것이 없던 동안에는, prepare 뒤에 Activity 삭제와
  cleanup이 **끝까지** 진행되고(아직 존재하지 않는 key를 지우므로 성공으로 기록된다) 그 뒤에
  늦은 요청이 세 객체를 publish해 디스크에 남는 순서가 실제로 재현됐다. 지금 prepare는
  `publication_lease_until`(2분, DB 시각)을 함께 기록하고, `authorize_…`는 그 fence가 열려 있는
  동안 해당 ref의 삭제를 **완료로 기록하지 않고 fence 만료까지 미룬다**(attempt를 되돌려 주므로
  dead-letter 예산을 쓰지 않는다). fence는 prepare가 한 번 주고 연장할 수 없으며, 취소된 writer가
  publish를 끝낸 뒤 스스로 내려놓는 것만 허용한다(trigger가 그 delta만 통과시킨다). writer가
  publish 후 취소를 발견하면 `requeue_activity_track_upload_refs`로 완료된 queue row까지 다시
  열어 회수를 맡기고, 그 보상을 못 한 채 죽어도 fence 만료 뒤 같은 worker가 지운다.
  `finalized` upload의 fence는 더 기다리지 않는다 — 더 publish할 것이 없고 그 객체는 live
  revision이 지키기 때문이다.
- **API는 임의 삭제를 제공하지 않는다.** track을 지우는 endpoint가 없다. 회수는 Activity
  삭제로만 일어나고, 그것도 application 호출이 아니라 `activity_canonical` tombstone에 붙은
  **trigger**가 한다. 어떤 삭제 경로도 이 회수를 건너뛸 수 없다.
- **Activity 삭제는 기존 의미를 그대로 둔다.** `activity_suppression`·source head·source
  revision·overlay는 손대지 않고(테스트가 개수로 고정), raw track·정규화·지도 파생물만 회수하며
  진행 중 업로드를 닫는다. 삭제된 Activity의 track은 read·download·export에서 사라진다.
- **ingestion이 suppression을 우회하지 못한다.** reserve/finalize의 응용 검사 **위에** DB
  trigger(`activity_track_ingestion_allowed`)가 있어, 삭제된 Activity나 suppress된 source에
  대한 `activity_track`/`activity_track_revision`/`activity_track_upload_intent` INSERT를
  직접 SQL로도 거절한다.
- **중복과 동시성.** 같은 idempotency key는 같은 reservation을 돌려준다. 다른 key로 **같은
  대응 digest + 같은 원본 hash**를 다시 올리면 revision을 늘리지 않고 그 업로드가 만든 객체만
  `track_superseded`로 회수한다(live revision이 참조하는 key는 queue에 넣지 않는다). track
  revision은 reserve에서 고정하고 finalize에서 `head+1`을 다시 확인하므로, 같은 Activity에
  대한 두 동시 업로드 중 하나만 성공하고 다른 하나는 `REVISION_CONFLICT`다. Activity revision
  CAS도 finalize 안에서 다시 본다.
- **quota·만료·reaper·dead-letter.** tenant당 활성 업로드 10건, 활성+실패 100건,
  prepared/staged 128 MiB, 저장된 track 합계 512 MiB, Activity당 revision 20개, 업로드 만료
  30분. 만료·정리·dead-letter는 기존 worker 경로를 그대로 쓴다.
- **보관하는 이력과 과금하는 객체는 다르다.** live byte quota는 **live Activity의 revision만**
  센다. 삭제된 Activity의 revision metadata는 이력으로 남고, 그 객체는 tombstone과 같은
  transaction에서 **회수가 예약**된다(회수 자체가 그때 일어나는 것은 아니다). 그래서 예약만 되고
  아직 남아 있는 bytes는 **별도 예산**으로 묶는다: `activity_track_pending_cleanup_bytes()`가
  "cleanup row가 아직 열려 있는 이 tenant의 track object" 합계를 돌려주고, 512 MiB를 넘으면
  예약과 finalize를 `TRACK_CLEANUP_BACKLOG_EXCEEDED`로 거절한다. 이것이 없으면 worker가 밀리거나
  실패하는 동안 store→delete를 반복해 실제 객체를 무한히 쌓을 수 있었다(검토 지적).
- **로그·응답에 좌표·key·본문이 없다.** parser는 로깅을 하지 않고, worker에서 부모로 넘어오는
  실패는 `^[A-Z][A-Z0-9_]{2,63}$` 코드뿐이다(메시지·스택·파일 내용 없음). 공개 DTO와 계정
  export에는 storage ref가 없고, download 응답은 `private, no-store`다.
- **transaction 안에서 provider/LLM/파서를 부르지 않는다.** repository에는 파서 핸들도 storage
  핸들도 없다(타입상 불가능). 재파싱과 객체 I/O는 API가 DB transaction **밖에서** 수행하고,
  finalize는 `activity.track_stored`를 transactional outbox에 같이 쓴다.
- **privacy trim·공개 공유는 이 노드 밖이다**(계획 7절, M2-01j). 저장된 원본은 덮어쓰이지 않고
  파생물은 별도 object이므로 나중에 trim 파생 revision을 붙일 자리는 열려 있다.

## 메모리 상한 (계획 7절 이월 항목)

**설정한 상한은 적용된 상한이 아니다.** 이 절의 첫 판은 `resourceLimits`를 걸었다는 사실만으로
부채를 닫았다고 적었고, 독립 검토가 그것을 반증했다. V8의 heap 옵션은 프로세스 전역이라
`--max-old-space-size=1024`로 뜬 부모는 그 제약을 worker에 물려주고 per-worker ceiling은 더 이상
발동하지 않는다. Node 24.12.0에서 측정한 값이 그 차이를 그대로 보여 준다.

| 부모 실행 옵션              | ceiling 32 MiB에서 worker가 받은 heap 한도 | 같은 60,000점 GPX의 결과         |
| --------------------------- | ------------------------------------------ | -------------------------------- |
| (없음)                      | 224 MiB (= 32 + 192 고정 overhead)         | `TRACK_PARSE_MEMORY_EXCEEDED`    |
| `--max-old-space-size=1024` | 1,216 MiB (= 부모 자신의 한도)             | 수정 전 `TRACK_OUTPUT_TOO_LARGE` |

overhead 192 MiB는 ceiling 16·32·64·128·256·512·1024 MiB에서 모두 같았다.

**한 것**

- 파싱은 `new Worker(..., { resourceLimits: { maxOldGenerationSizeMb } })`에서만 일어난다.
  기본 256 MiB이고 16–4096 MiB 범위만 허용한다.
- **상한을 측정해 확인한다.** worker가 보내는 첫 메시지는 V8이 실제로 준 총 heap 한도이고,
  부모는 그것이 **명시한 예산**(`maxHeapLimitMb`, 기본 `ceiling + 192 MiB`) 이하일 때만 bytes를
  보낸다. 검사 대상은 "요청한 old-generation 값 근처"가 아니라 **우리가 받아들이겠다고 적은 총
  heap 한도 그 자체**이며, 부모 옵션이 한도를 조금이라도 올리면(`--max-old-space-size=128`
  포함) 예산을 넘어 거절된다. 벗어나면 **아무것도 파싱하지 않고**
  `TRACK_PARSE_CEILING_NOT_APPLIED`로 닫는다. 문자열 검사를
  신뢰의 근거로 쓰지 않는다 — 옵션은 command line·`NODE_OPTIONS`·wrapper·`v8.setFlagsFromString`
  어디로도 들어올 수 있다. worker에 직접 넘길 `execArgv`에 heap 옵션이 있으면 생성 시점에
  `TrackParseRuntimeConflictError`로 거절하지만, 그것은 우리가 통제하는 표면뿐이며 가드가 아니다.
- **초과 시험이 두 가지다.** (1) 같은 bytes·같은 코드에서 heap 1024 MiB는
  `TRACK_OUTPUT_TOO_LARGE`, heap 32 MiB는 `TRACK_PARSE_MEMORY_EXCEEDED`가 되고 **부모는 살아남아
  다음 parse에 성공한다.** (2) 부모를 `--max-old-space-size=1024` **와 `=128`** 로 띄운 자식
  프로세스에서 같은 ceiling 32 MiB 설정이 모두 `TRACK_PARSE_CEILING_NOT_APPLIED`로 끝난다
  (두 검토가 각각 재현한 시나리오).
- 요청당 worker 1개이므로 성공·파서 실패·메모리 초과·마감시간·취소 모든 경로에서
  `terminate()`된다. 파서 예산(작업량 계수기)은 그대로 두고, 그것을 메모리 상한이라고
  주장하지 않는다.

**하지 못한 것(명시)**

- **부채는 절반만 닫혔다.** 이 코드가 보장하는 것은 "확인된 상한 아래에서만 파싱한다"이지
  "프로세스가 N MB를 넘지 않는다"가 아니다. cgroup/컨테이너 memory limit은 배포 설정이며 이
  작업에서 설정·측정하지 않았다.
- **heap 옵션으로 뜬 배포에서는 track 저장이 실패한다.** 거절은 요청 시점이고(부팅 시점이 아니다)
  코드는 `TRACK_PARSE_CEILING_NOT_APPLIED`다. 운영 제약으로 기록한다.
- **기본 예산의 192 MiB는 이 기기·이 Node 버전(arm64)의 측정값이다.** overhead가 다른
  플랫폼에서는 정상 실행이 **거절**되며(조용한 통과가 아니라 fail closed), 그런 배포는
  `maxHeapLimitMb`로 자기 예산을 명시해야 한다. 이 검사가 보장하는 것은 "worker의 총 heap
  한도가 명시한 예산 이하"이지 "요청한 `maxOldGenerationSizeMb`가 그대로 적용됐다"가 아니다 —
  예산보다 **작은** 한도(예: 부모가 더 낮은 옵션을 건 경우)는 통과하며, 그때는 요청보다 일찍
  실패한다.
- **대표 장기 track의 실측 CPU/메모리 수치를 재지 않았다**(계획대로 d의 harness 몫).
- 파서로 넘기는 bytes는 한 번 복사해 **transfer**하므로 부모가 사본을 들고 있지 않지만,
  worker가 돌려주는 파싱 결과는 structured clone이므로 부모 힙에 들어온다(계약 상한 8 MiB).

- **UI가 없다.** 저장된 track을 보여 주는 화면·업로드 화면을 만들지 않았고, 따라서 Aside/Chrome/
  Playwright 브라우저 증거도 만들지 않았다(계획 4절: 저장된 활동 지도·차트는 M2-01e).
  `pnpm test:e2e`와 identity E2E는 실행하지 않았다. `scripts/identity-e2e.mts`에는 배포 일관성을
  위해 `grantActivityTracks` 한 줄만 더했고 그 스택을 다시 띄우지는 않았다.
- **프로세스 수준 메모리 상한(cgroup/컨테이너)은 설정·측정하지 않았다.** worker ceiling은
  파싱만 덮고, 그것조차 "적용됐음을 확인한 뒤에만 파싱한다"는 형태다(위 "메모리 상한").
- **publication fence는 2분이고, 늦은 publish 자체를 막지 못한다.** fence는 객체를 드러내기
  직전마다 다시 확인하지만 그것은 **진입 검사**이고, 확인 이후의 storage 호출이나 stall 뒤의
  재개에는 닿지 못한다. 객체 저장소가 fence token 조건부 쓰기를 지원해야 닫히는데 현재 port에는
  그런 원시 연산이 없다 — 그래서 **막았다고 주장하지 않는다.** 보장하는 것은 회수이며 그 경계는
  위 "늦은 publish"에 적었다. (이전 판들의 두 문장 — "요청이 죽으면 30분 만료 reaper가 같은 일을
  한다", "만료 뒤에는 publish가 불가능하다" — 은 **모두 거짓이었다.** 전자는 reaper가
  `reserved/prepared/staged`만 처리하기 때문이고, 후자는 진입 검사가 진행 중인 쓰기를 막지 못하기
  때문이다. 각각 재현한 뒤 고쳤다.)
- **회수의 남은 경계.** (1) 1시간 grace는 writer 마감시간에서 끌어온 수치일 뿐 절대적 상한이
  아니다. 그보다 더 오래 멈춰 있던 요청의 객체는 receipt가 아니라 **대조 sweep**이 가져간다.
  (2) sweep 한 번이 하는 일은 **색인 200행 읽기 + 그만큼의 `stat` + ref당 bounded statement 하나**
  이므로 leak은 **즉시가 아니라 몇 번의 실행 안에** 회수된다. 감시 중인 ref가 많으면 그만큼
  늦어진다. (3) **감시는 영원하지 않다.** ref는 객체가 없음을 확인했고, 열린 receipt도 없고,
  live revision도 publish 가능한 upload도 그것을 가리키지 않으며, **기록된 지 7일이 지났을 때**만
  감시에서 빠진다. 7일보다 더 늦게 깨어난 writer가 만든 객체는 이 회수의 범위 밖이다 — 상한이
  아니라 **명시한 바닥값**이다. (4) sweep의 후보는 이 색인이므로 **서버가 한 번도 기록하지 않은
  key는 범위 밖이다**(예: 누군가 bucket에 직접 써 넣은 파일). 이 milestone의 어떤 경로도 그런
  key를 만들지 않는다. (5) 계정 말소는 그 tenant의 색인 행도 지운다. 말소 이후의 늦은 write는
  M2-04c의 30일 `account_erased` receipt fence가 덮는다.
- **늦은 publish는 막지 못한다. 회수만 보장한다.** fence 검사는 publish의 **진입**만 통제하고
  이미 진행 중인 storage 호출에는 닿지 못한다(객체 port에 조건부 쓰기가 없다). 그래서 stall한
  요청은 fence가 지난 뒤에도, **upload가 만료된 뒤에도** 객체 하나를 드러낼 수 있다(재현했다).
  회수는 두 겹이다.
  1. **receipt를 열어 둔다.** cleanup이 "아직 없는 객체"를 지워 성공했더라도 그 ref가
     `prepared`/`staged`/`failed` upload의 것이고 **그 upload의 fence가 지난 지 1시간 이내**면
     receipt를 닫지 않고 1분 뒤로 재무장한다(`PUBLICATION_WINDOW_OPEN`, attempts 0이라
     dead-letter 예산을 쓰지 않는다). 창의 기준은 upload의 `expires_at`이 **아니라** writer 자신의
     마감시간이다: parse 마감 30초가 2분 fence 안에 있으므로 1시간은 이 서버가 시도하는 가장 긴
     publish의 약 30배다. `finalized` upload는 해당하지 않아 정상 회수가 지연되지 않는다.
     (이전 판은 창을 `expires_at`에서 끝냈고, "만료 후에는 publish가 불가능하다"고 적었다.
     **둘 다 틀렸다** — 재현으로 확인하고 고쳤다.)
  2. **전용 reference 색인과 객체 저장소를 대조한다.** 어떤 receipt도 열려 있지 않아도 leak이
     남지 않도록, worker가 **`activity_track_object_ref`**(ref 하나당 한 행, storage_ref가 PK,
     감시 중인 행에 partial index)에서 keyset window를 읽어(실행당 200 ref, DB 커서로 재개)
     ref마다 `stat` 한 번을 하고, 객체가 실제로 있으면 live revision도 publish 가능한 upload도
     참조하지 않는지 DB가 판정해 queue에 넣는다. 삭제 직전 `authorize`가 live reference를 다시
     확인하므로 과잉 삭제가 되지 않는다.
     - **디렉터리 순회는 하지 않는다.** 처음 판은 객체 저장소를 훑었고 예산이 "돌려준 key 수"만
       묶어서, 빈 디렉터리 1,000개가 있는 namespace에서 limit 1로 호출해도 1,001개 디렉터리를
       읽고 `truncated:false`(= 순회 완료)를 보고했다(재현함).
     - **ledger 테이블을 훑지도 않는다.** 두 번째 판은 두 ledger 테이블의 union에 LIMIT을
       마지막에 걸어서, 후보 1개를 얻는 데 실제 PostgreSQL에서 **498행을 읽고 381행으로 중복
       제거**했다(재현함). 지금은 색인 범위 스캔이며, 같은 호출에서 두 ledger 테이블이
       내놓은 행 수는 **0**이다(트랜잭션 통계로 측정·시험).
     - **upload 행이 사라져도 ref는 남는다.** 실패한 intent는 receipt가 닫힌 뒤 7일에 compaction
       되고 finalize하지 않은 upload는 객체 원장에도 등록되지 않아서, 이전 판에서는 그 시점부터
       해당 ref가 **영구히 발견 불가능**해졌다(재현함). 색인 행은 그것과 무관하게 남는다.
     - 부수적으로 객체 삭제 시 비워진 디렉터리를 정리하지만, 경계는 그것에 의존하지 않는다.
- **cleanup backlog 예산(512 MiB)은 예약된 bytes의 상한이지 실제 디스크 사용량 측정이 아니다.**
  객체 ledger(`activity_track_object`)와 upload intent가 기록한 크기를 **storage ref 기준으로
  합집합·중복 제거**해 더한다. 같은 artifact의 temporary/final은 같은 bytes이므로 한 항목이다.
  객체가 이미 사라졌는데 queue row가 남아 있는 구간에서는 실제보다 크게 잡는다(보수적).
  **크기를 아직 기록하지 못한 것은 세지 못한다**: prepare 전에 실패한 upload의 raw temporary
  객체가 그렇고, 그 경우는 활성 upload 수 상한(10)과 파일 상한(32 MiB)으로만 묶인다.
- **복원 시 Activity suppression 재적용은 drill의 ledger 경로로만 검증했다.** 운영 runbook에
  이 단계를 반영하는 일은 이 작업에 없다(drill이 그 순서를 강제할 뿐이다).
- **대용량·성능 실측이 없다.** 최대 32 MiB 파일을 재파싱할 때 API 프로세스가 bytes 한 벌을
  버퍼링한다(저장된 temporary object를 되읽는다). 측정은 하지 않았고, 대표 track 크기별 수치는
  계획대로 M2-01d/e의 몫이다.
- **같은 upload를 중간 실패 후 그대로 재시도하면 temporary key가 이미 있을 수 있다.** 그 경우
  `UPLOAD_RESUME_REQUIRED`/`UPLOAD_RETRY_REQUIRED`로 끝나고 새 idempotency key로 다시 예약해야
  한다. M2-04b의 파일 업로드와 같은 성질이며 자동 resume은 만들지 않았다.
- **Course revision 회수는 이 노드에 없다.** 계획 7절의 "해당 Activity 좌표에서 파생된 Course
  revision도 회수"는 Course 원장이 아직 없으므로(M2-01f) 적용할 대상이 없다. 삭제 확인 UI의
  "영향받는 코스 표시"와 `unavailable` 처리도 f/e 몫이다.
- **privacy trim 파생 revision을 만들지 않았다**(M2-01j). 보호 구역 재진입 검사도 없다.
- **공개 공유는 비활성 그대로다.** 이 노드는 소유자 인증 download만 만들었고 ACL·재식별 검토는
  건드리지 않았다.
- **FIT fixture는 합성이다.** 실제 Garmin 기기 파일로 시험하지 않았다(M2-01a/b와 같은 한계).
  통합 테스트의 parse 결과는 합성 GPX이고, persistence 통합 테스트는 parse 사실을 **주입**한다
  (실제 재파싱은 API 테스트가 실제 worker로 검증한다).
- **정규화·MapPath 파생물의 내용 검증은 M2-01a/b 테스트에 기댄다.** 이 노드는 그것이 어떤 bytes로
  어떤 key에 저장되고 어떻게 회수되는지까지만 검증한다. 저장된 파생물을 다시 읽어 지도에 그리는
  것은 e의 범위다.
- **tenant quota 숫자(10/100/128 MiB/512 MiB/20)는 운영 실측이 아니라 이 노드에서 정한 상한이다.**
  경계 시험은 활성 업로드 수에 대해서만 있다.
- **outbox 소비자가 없다.** `activity.track_stored` event를 소비하는 쪽은 만들지 않았다.
- `task-graph.json`은 바꾸지 않았다. 루트 공유 파일 중 `vitest.config.ts`(신규 패키지 테스트 경로
  한 줄), `pnpm-lock.yaml`(신규 패키지), `packages/contracts/package.json`(새 export subpath)를
  건드렸으므로 root가 직렬 통합해야 한다.
