## 설계 근거

1. **연결은 새 표가 아니라 갤러리 항목의 `activity_id`다.** M2-03의 migration 031이 이미
   `gallery_media_item.activity_id`와 복합 외래 키 `(athlete_id, activity_id) → activity_canonical(athlete_id, id)`,
   부분 index `gallery_media_item_activity`, revision이 오르는 수정(`PATCH /gallery/media/:id`)과 `activityId` 목록 필터를
   갖고 있었다. 노드 문구는 "권한·삭제·export는 **미디어 원본의 정책을 따른다**"이다. 별도 link 표를 만들면 같은 사실의
   두 번째 기록이 생기고, 그 표의 RLS·삭제 전파·erasure·export·purge를 따로 맞춰야 한다. 연결을 항목의 열로 두면
   - 권한: `gallery_media_item`의 FORCE RLS와 tenant 정책, 그리고 복합 외래 키가 남의 활동으로의 연결을 DB에서 막는다.
   - 삭제: soft delete 한 번으로 항목·연결·content 주소가 함께 닫힌다(`resolveObject`의 `m.deleted_at IS NULL`).
   - erasure: 031의 `erase_account` wrapper가 갤러리 행을 지우고 모든 object를 `resource_object_cleanup`에 넣는다.
   - export: v16 이후 `galleryMediaItems`가 `activity_id`를 이미 내보낸다(삭제된 항목 제외, storage ref 없음).
     따라서 **migration을 추가하지 않았다.** tenant object 경로도 새로 생기지 않으므로 purge 규칙(044–046) 추가가 필요 없고,
     advisory lock 순서(77206 → 0 → rows)도 바뀌지 않는다. 연결은 1 항목 : 0..1 활동이다. 다른 활동에 연결된 항목을
     연결하면 이 활동으로 **옮겨진다**(화면이 그렇게 말한다).
2. **서버 코드는 바꾸지 않았다.** 연결 저장은 기존 `PATCH`(album·caption은 읽은 값 그대로, `expectedAccessRevision` CAS,
   idempotency key)이고, 탭 목록은 기존 `GET /gallery/media?activityId=`다. 남의 활동 id로 목록을 물으면 RLS 때문에 빈 목록이며,
   남의 media id는 읽기·content·수정 모두 404다(존재 여부를 흘리지 않는다).
3. **패널은 갤러리 모듈이 소유하고 shell이 합성한다.** `apps → modules → kits` 방향을 지키려고 activities 모듈이 gallery
   모듈을 import하지 않는다. `@workout/modules-gallery/activity-media-panel`(새 공개 subpath)의 `ActivityMediaPanel`을
   두 shell이 `ActivityBrowser`의 새 slot `renderMediaTab(activityId)`에 넣는다(스트레칭 패널의 `renderActivityDetails`와 같은
   방식). `ActivityDetailTabs`는 고정 비활성 목록 대신 host가 넘기는 `unavailable` 사유 표를 받는다. slot이 없으면 미디어
   탭은 이전처럼 사유와 함께 비활성이다.
4. **사생활·수명:** 패널은 자기 `QueryClient`를 athlete·session·activity로 key 지정하고 unmount 때 비운다. 목록은
   **성공한 읽기만** 그린다(실패한 refetch가 남긴 캐시로 삭제된 thumbnail을 계속 보이지 않게, M2-03 규칙과 같음). thumbnail은
   기존 `MediaPreview`(viewport 진입 시 로드, unmount 때 blob URL revoke)를 공유한다. 원본 내려받기는 세션 transfer
   (`openGalleryMedia`, `x-workout-session-id` 필요)로 받은 blob을 클릭 한 번에 저장하고 즉시 revoke한다. 공유 가능한 URL은
   만들지 않는다. shell은 transfer 객체를 session마다 `useMemo`로 고정해 render마다 thumbnail을 다시 받지 않게 했다.
5. **갤러리 모듈 내부 정리:** `MediaPreview`·오류 문구·offset paging 계산을 `media-preview.tsx`·`gallery-errors.ts`·
   `gallery-paging.ts`·`media-transfer.ts`로 옮겨 갤러리 화면과 패널이 같은 구현을 쓴다. 갤러리 화면의 동작과 공개 export
   (`GalleryMediaTransfer` 등 타입 re-export 포함)는 그대로다.

## 시험이 단언하는 것

### 두 shell E2E (`tests/identity/activity-media.spec.ts:174`, Next 3100·Vite 4200 각각)

실제 OIDC, same-origin BFF, 격리 PostgreSQL, 갤러리 object storage다. 미디어는 갤러리 업로드 경로(예약 → content PUT의
signature 검사 → finalize)로 올린 실제 갤러리 항목이고, preview(thumbnail)도 같은 경로로 붙인다. 원본과 preview 바이트는 서로 다르다.

1. `/activities/<id>?tab=media`(M2-01k-k 별칭)가 `detailTab=media`로 가고, 미디어 탭이 **활성**이며 선택되고, "제공하지 않습니다"
   문구가 없다. 연결 목록은 빈 상태다.
2. **연결:** 선택 목록의 항목에서 "이 활동에 연결"을 누르면 연결 목록에 나타나고 선택 목록에서 빠진다. API로 읽은 항목의
   `activityId`가 이 활동이다. 화면의 thumbnail은 `blob:` 이미지이고, 화면이 받은 `content?variant=preview` 응답 본문이 preview
   바이트와 같다. 소유자가 같은 주소를 직접 읽으면 200·`private, no-store`·preview 바이트다. 320px에서 가로 넘침이 없다.
   새로고침 뒤에도 연결이 남는다.
3. **인증 다운로드:** "원본 내려받기"가 `finish.png`를 내려받고 파일 바이트가 원본과 같다. 세션 없는 context의 원본 주소는
   200이 아니고 원본 바이트를 주지 않는다.
4. **Bob:** 원본·thumbnail·항목 주소 모두 404, 연결 해제 PATCH 404, `?activityId=<Alice 활동>` 목록은 빈 목록, Alice 활동의 미디어

5. **해제:** "연결 해제" → 빈 상태, 선택 목록에 복귀, API `activityId`가 `null`.

비차단 지적과 반영:

1. **연결·해제 뒤 focus 유실.** 누른 버튼이 카드와 함께 다른 목록으로 옮겨지며 unmount되어 focus가 `<body>`로 떨어졌다. 이제 변경이
   성공하면 `onSettled`에서 목록 refetch를 **기다린 뒤** focus 요청을 올리고, effect가 옮겨 간 목록의 카드 제목(`h5`,
   `tabIndex={-1}`)으로 focus를 옮긴다. 카드가 새 목록에 없으면 그 목록의 제목(`h4`)으로 간다. 단위 시험 2개(옮겨 간 카드 제목,
   목록 제목 fallback)와 E2E 단언(실제 Chromium에서 연결 뒤·해제 뒤 카드 제목 `toBeFocused`)을 더했다. 변이 **MF**
   (`target?.focus()` → `void target`)가 단위 **2 failed / 10**.
2. **카드마다 같은 동작 이름.** "이 활동에 연결"·"원본 내려받기"·"연결 해제"에 카드 제목 id를 `aria-describedby`로 붙였다(카드
   `article`도 `aria-labelledby`로 같은 제목을 이름으로 쓴다). 단위 시험이 세 버튼의 accessible description을, E2E가 연결 카드 두
   버튼의 description을 단언한다. 변이 **MD**(해제 버튼의 `aria-describedby` 제거)가 단위 **1 failed / 10**.
3. **제목 수준.** 패널 제목이 활동 제목 `h3`의 형제였다. 패널 절 제목을 `h4`, 카드 제목을 `h5`로 내리고 CSS selector
   (`.panel h4`, `.card h5`)를 맞췄다. 단위 시험이 `h4`·`h5`와 패널 안 `h3` 0개를 단언한다. 변이 **MH**(패널 제목을 `h3`로)가 단위
   **2 failed / 10**.
4. **detail refetch마다 패널 remount(선택).** 미디어 slot만 `detail.isSuccess`로 gating한다(`!detail.isFetching` 제거). 패널은
   activity id로 key가 잡혀 있고 detail 내용을 읽지 않으므로 같은 활동의 background refetch에 remount할 이유가 없다. 다른 활동을
   고르면 query key가 바뀌어 `isSuccess`가 거짓이 되고, refetch가 404가 되면 역시 거짓이 되어 패널이 내려간다. 다른 탭의 gating은
   바꾸지 않았다. 이 항목은 전용 시험·변이가 없다(동작 보존 변경).
5. **문서:** 위 검토자 변이와, 삭제된 활동을 가리키는 연결을 제품 결정 대기로 "남은 일"에 적었다.

## 남은 일

- **제품 결정 대기 — 삭제된 활동을 가리키는 연결:** 활동을 삭제해도 연결된 미디어의 `activity_id`는 삭제된 활동을 가리킨 채
  남는다(미디어는 활동 삭제로 지워지지 않는다). 삭제된 활동의 탭은 열 수 없고 새 연결은 거절된다. 검토자 확인으로 이는 어떤 규칙도
  어기지 않는다. 활동은 soft delete만 있고 어디서도 hard delete하지 않으며, export는 삭제된 활동 행도 담고, `erase_account`는 둘 다
  지운다. 활동 삭제 때 연결을 끊을지는 제품이 정한다.
- 연결은 1 항목 : 0..1 활동이다. 한 사진을 여러 활동에 동시에 걸려면 별도 표가 필요하다(사양 근거가 없어 만들지 않았다).
- 갤러리 화면(S17)은 아직 항목의 연결 활동을 보여 주지 않는다. S17의 "활동 연결" 표시·filter는 이 노드 범위가 아니다.
- 선택 목록은 M2-03과 같은 offset paging이라 같은 한계(한 페이지 이상 겹치면 회수 못 함)를 가진다.
- 독립 검토와 commit은 root 몫이다(node-rules에 따라 이 노드는 검토자를 띄우지 않았다).
