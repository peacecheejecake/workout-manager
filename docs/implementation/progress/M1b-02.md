# M1b-02 · 보강 수동 core

상태: **completed** (S28~S30 수동 core). G1의 단일 Activity 정본 위에 사용자
동작 정의·불변 버전, CAS로 교체하는 루틴 템플릿, 수행 세트 revision/tombstone,
명시적인 수행 종료·중단, 서버 기준 시각의 휴식 timer를 연결했다. 동작 계열과
장비·저항, 좌우/total count, 0과 미상, confirmed actual을 분리한다. 계획된
set 또는 미확인 초안은 완료한 actual이 아니다. 세트는 기존 또는 새 수동
strength Activity 한 건의 상세이며 별도의 Activity를 만들지 않는다.

PostgreSQL `021`은 tenant RLS와 버전/identity 변경 방지, Activity 삭제 시 보강
상세 정리, 계정 삭제 시 세트·루틴·동작 정리를 포함한다. API는 세션 범위와
헤더 명령 키/경로 ID를 검증한다. V11 내보내기는 새 컬렉션을 포함하고 이전 V10
형식을 그대로 읽는다. Web·mobile-web은 같은 보강 모듈을 사용하며 러너 초안은
세션별 Zustand store, 서버 응답은 세션별 TanStack Query에 둔다.

검증: 계약 13건, API 경계 4건, 보강 UI 19건의 focused 테스트; 격리 PostgreSQL
전체 240/240; 전체 Vitest 1857/1857; 실제 로컬 OIDC·격리 PostgreSQL·Chromium
수용 1건. 수용 시험은
동작/루틴 각 두 버전, 예전 참조 고정, 단일 기존 Activity, 미확인 세트→확인·정정,
별도 초안 삭제 tombstone, timer 일시정지 후 Next 새로고침과 mobile-web 재진입,
명시 종료와 V11 내보내기를 확인한다. 두 웹 셸 production build, 타입·ESLint·
Prettier도 통과했다.

계획 세션에 frozen 보강 내용을 넣는 helper는 준비했으나 실제 연결은 계획 버전
승인 트랜잭션과 같은 원자적 경계가 필요하므로 M1b-03에서 사용한다. 혼합
Planner·joint approval, parent/bout·영양 이벤트 집계 회귀도 M1b-03 소유다.
이 작업은 네트워크 불확실성에서 같은 키 재시도를 지원하지만, 페이지 종료 후
오프라인 actual을 보존하는 동기화 대기함은 구현하지 않았다. 건강 초안을 기기에
지속 저장하려면 명시 동의·계정 범위·만료/삭제 정책이 필요하므로 V022-A27의
완료 조건을 M1b-03에 남긴다. 320px/고배율·OS IME와 iPhone 실기기 gate도
별도 수용 범위로 남는다.

실 브라우저는 AGENTS.md 순서의 Aside 업데이트 실패(`fetch failed`)와 Chrome
제어 런타임 실패(`runtime_open_timeout`) 뒤 Playwright Chromium을 사용했다.
Herdr split-pane 독립 리뷰는 base
`50284bf94120d5b339f6af16aeeb9dab15d30f4c`에서 시작했다. 1차 staged tree
`6f0155bba18788e9b07546a94a0da59a5f06bafc`에서 삭제 후 receipt 재노출,
요청 중 초안 변경으로 인한 재시도 키 유실, 재조회 실패 시 runner 초안 소실,
정정 발생 시각 변경, 409 뒤 timer/종료 복구 불가의 P2 다섯 건을 발견했다.
Activity 삭제 시 receipt 본문을 비식별화하고 삭제된 수행·세트 replay를 막았다.
입력 잠금·안정 명령 재전송·초안 유지와 재조회·정정 시각 보존·409 재확인을
추가했다. 재리뷰 tree `fe012c526d74ebcc92fad1559965d122bca81250`에서
이 다섯 수정은 확인됐고, 정정 중 최신 revision을 자동 채택하면 다른 탭의 변경을
덮어쓸 수 있다는 새 P2를 발견했다. 편집 시작 revision을 유지하고 차이가 나면
최신 기록을 다시 선택하기 전까지 저장을 막았다. 응답 유실·동시 수정·삭제 후
재시도 회귀 테스트로 해당 경계를 검증했다. 다음 재리뷰에서는 서버가 정정을
저장했으나 응답이 유실된 뒤 최신 revision을 조회하면 기존 명령 재시도까지
막히는 P2를 발견했다. 불확실한 동결 명령은 revision 변화와 무관하게 같은
키·본문으로 재전송하고, 확정 409 뒤에만 최신 기록의 명시적 재선택을 허용한다.
