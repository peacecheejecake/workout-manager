## 0. 결론

**결함이었고, 재현했고, 닫았다.** 1차에서 남겼던 틈 안에서 태어난 활동의 _source suppression_ 공백(검토 B1)은
2차에서 닫았다(§10).

- 살아 있는 tenant가 백업 **뒤** 활동을 삭제하면 복원은 그 삭제를 재생한다. 재생이 객체를 지우는 경로는 전부
  **행 기반**이다: 묘비 trigger(033)는 트랙 행이 이름하는 key를, 코스 회수(038)는 그림 행이 이름하는 key를
  queue하고, 두 스윕은 색인을 읽는다. drill 순서(DB dump → 객체 archive 복사) 사이에 저장된 객체는 **어떤
  복원 행도 이름하지 않고**, tenant는 살아 있으므로 M2-01x의 tenant purge도 무장되지 않는다. 그 객체(GPS
  트랙 원본 포함)는 **영원히 남는다.**
- 이름하는 것은 key다. 활동의 객체는 전부 `private/v1/tenants/<t>/activities/<a>/` 아래(트랙 세 산출물의
  temporary·final, 그 디렉터리에 쓰는 유일한 family), 코스의 객체는 전부 `…/courses/<c>/` 아래(그림)다.
- 수정(migration 045): 활동 묘비가 **그 활동 디렉터리의 purge를 durable하게 무장**하고, 그 삭제가 회수한
  **코스마다 코스 디렉터리의 purge도 무장**한다. 복원 재생의 묘비 UPDATE가 같은 trigger를 타므로 재생이 곧
  재무장이다. 복원 cluster에 행조차 없는 활동은 재생이 원장으로 **suppression에 필요한 행을 재구성하고** 무장한다(§10). cleanup worker가 DB와 무관하게 그
  디렉터리를 walk해 저장소의 기존 guarded `delete`로 지운다(M2-01x의 walk·삭제 경로 재사용, 가드 무변경).

## 2. 설계 판단

### 2-1. 무엇을 purge하는가 — "scope" = 활동 디렉터리 또는 코스 디렉터리

- key 배치 확인(`keys.ts`): 활동 아래는 `tracks/<T>/temporary/<U>/<kind>`와
  `tracks/<T>/<kind>/uploads/<U>/sha256/<h>.<ext>`뿐이다. 활동의 다른 객체 family는 없다. 활동에서 파생된
  **코스 그림은 활동 prefix 밖**(`courses/<c>/thumbnails/…`)이라 활동 purge만으로는 (c)를 못 닫는다 → 코스를
  두 번째 scope로 둔다.
- 삭제는 둘 다 **종단적**이다. 코스의 `unavailable`은 034의 전이 trigger가 되돌림을 막는다. 활동 묘비는 지금껏
  되돌리는 코드가 없었을 뿐 DB가 막지 않았다 → 045가 `activity_tombstone_terminal`(BEFORE UPDATE, `OLD.deleted
AND NOT NEW.deleted`면 예외)을 더한다. 그래서 "삭제됨/부재"로 lease된 scope는 run 동안 살아날 수 없다.

### 2-2. 언제 — writer fence 뒤 **한 번**

- 첫(유일한) pass는 그 scope의 writer fence 뒤: 트랙 업로드는 `coalesce(publication_lease_until+1h,
expires_at)`(044·finish와 같은 식, state `prepared/staged/failed`), 그림은 `greatest(publication_lease_until+1h,
lease_until+1h)`(038·044와 같은 식). `available_at = greatest(now, fence)`.
- 044처럼 30일 매시간 재무장하지 **않는다.** 044의 재무장은 fence 없는 writer(자원·갤러리·URL 업로드)
  때문이다. 활동·코스 디렉터리에 fence 없는 writer는 없다: 삭제된 활동에는 트랙 업로드를 예약조차 못 하고(033
  ingestion trigger), 회수된 코스의 render는 superseded되며 lease 열은 남겨져(038) fence로 읽힌다.
- 완결 pass(목록이 빈 run)는 purge를 닫는다. 예산을 다 쓴 run은 즉시 다시 due, 실패 run은 queue와 같은
  backoff(`least(attempts,10)*30s`), 100회에 dead-letter — 044와 같다.

### 2-3. 어디에 기록하는가 — 새 표 `object_scope_purge`

- 열: `athlete_id`(canonical UUID CHECK), `scope_kind`(`activity|course`), `scope_id`(canonical UUID CHECK),
  PK `(athlete_id,scope_kind,scope_id)`, 나머지는 044의 `tenant_object_purge`와 같다. RLS ENABLE+FORCE, 정책
  없음, PUBLIC 회수, 표 권한 0.
- FK를 두지 **않았다**: (b)의 활동은 복원 cluster에 행이 없다. 대신 **lease가** 살아 있는 소유자를 거절한다
  (§3 A10·A11) — "무장은 넓게, lease는 좁게".
- 무장 경로 셋:
  1. `object_scope_purge_on_activity_delete`(AFTER UPDATE ON `activity_canonical`, `NEW.deleted AND NOT
OLD.deleted`): 실제 삭제와 복원 재생의 묘비 UPDATE 모두. 이름 순서상 033·034 trigger 뒤에 발화한다(업그레이드
     시험이 순서를 단언).
  2. `object_scope_purge_on_course_reclaim`(AFTER UPDATE ON `course`, `available→unavailable`): 그 전이는 활동
     삭제의 회수만 한다. 발화 시점에 그림 행은 아직 있다(회수가 revision을 지우기 전) → fence가 읽힌다.
  3. `arm_deleted_activity_object_purge(text,uuid)`(권한 0, 복원 관리자 전용): 복원 cluster에 없는 활동의 ledger
     항목. 세션 tenant와 일치해야 하고, **있고 살아 있는** 활동이면 `ACTIVITY_NOT_DELETED`로 거절.
- upsert 규칙은 044와 같다: `armed_at=now`, 닫힌 행은 새 due로 다시 열고, 열린 행의 `available_at`은
  `greatest(기존, 새)` — **절대 앞당기지 않는다.**
- 비-canonical tenant·소유자 id는 어떤 key prefix도 이름하지 않으므로 무장하지 않는다(함수의 `IF`와 표 CHECK).
- **backfill**: 045 적용 시점의 삭제된 활동·회수된 코스(canonical) 전부를 `now`로 무장. 이전 복원이 이미 행 없는
  객체를 되살렸을 수 있다.

### 2-4. store port — `ObjectScopeEnumeration.listScopeObjects(scope, limit)`

- `keys.ts`: `ObjectScope`, `objectScopePrefix(scope)`(tenant·활동·코스 id 모두 **정확히** canonical, 정규화
  없음), `isObjectKeyOfScope(key, scope)`(key로 parse되고, 그 scope의 family이며, 같은 tenant·같은 소유자).
- `local-filesystem.ts`: M2-01x의 tenant walk 본문을 `listObjectsBelow(prefix, limit, maxDepth, belongs)`로
  옮겨 두 listing이 공유한다. **가드 줄은 한 글자도 바뀌지 않았다**; 바뀐 줄(`git diff | grep '^-'`)은 반환
  타입, RangeError 문구(`Tenant listing…`→`Listing…`), 변수 이름(`tenantDirectory`→`prefixDirectory`), 그리고
  상수·술어가 매개변수가 된 두 줄뿐이다. 깊이 상한: 활동 6(`tracks/T/<kind>/uploads/U/sha256/`), 코스
  4(`thumbnails/revisions/R/sha256/`).
- worker `processOneObjectScopePurge`: `processOneTenantObjectPurge`와 같은 가드·같은 순서 — 목록의 모든 key가
  **`…/activities/<a>/` 또는 `…/courses/<c>/`(뒤 구분자 포함)** 로 시작해야 하고 아니면 아무것도 지우기 전에
  `FOREIGN_KEY_LISTED`로 중단, 첫 오류에서 중단, ENOENT는 `stat`이 null일 때만 흡수, run당 ≤200 삭제·목록 ≤100,
  lease 2분(SQL 상한 5분). `runResourceCleanupWorker`에서 tenant purge 바로 뒤, derived 앞.

### 10-1. B1 — 복원 cluster에 없는 삭제 활동의 suppression (privacy regression)

**지적**: 1차 재생은 복원 cluster에 활동이 없는 원장 항목을 id로 무장하고 계수만 한 뒤 commit했다. suppression
행이 없으니 복원 뒤 기기 재동기화(`POST …/activities` → `importActivity`)가 source head를 못 찾고 그 활동을 **새
활동으로 다시 import**한다. 사용자가 지운 활동이 GPS까지 되살아난다(계획 7절 위반). 1차 이전에는 FK 오류로 복원이
fail closed였다. 알 수 없는 id나 다른 tenant의 id도 조용히 받아들였다.

**재현(수정 전 동작, 실제 스택)**: drill에 새 check
`restored_gap_born_deleted_activity_reimport_is_suppressed_without_a_new_activity`를 넣었다. 복원 뒤 (b) 활동의
source를 같은 identity·revision으로 다시 import하면 `suppressed`와 **같은 activity id**가 나와야 하고, 활동 행 수가
그대로이며, 되살린 행은 `{deleted: true, original: {}}`이어야 한다. drill의 재생 호출만 1차 동작(id로 무장, suppression
없음)으로 되돌리는 anchor **D4**에서 drill이 이 check에서 실패한다:
`backup-restore-drill.mts:3675 assert.equal(gapReimported.outcome, 'suppressed')` — **`actual: 'imported'`**.

**수정**: `arm_deleted_activity_object_purge`를 없애고 `replay_absent_activity_deletion(text,uuid,text,text,integer,integer,text)`
(권한 0, 복원 관리자 전용, 045 안)로 바꿨다. 원장 항목에 source head의 **source revision과 content hash**를 더했다
(drill의 원장 capture 두 곳). 두 값은 원장 필드이며 자리표시자가 아니다. 이 함수는 suppression에 필요한 것만
재구성한다.

- `activity_canonical`: 이미 삭제됨, 원장의 revision, **`original = {}`**. 제목·시각·거리 등 활동 값은 되살리지도
  지어내지도 않는다. 활동 값을 읽는 곳(`selectActivity`, 목록, 요약, dashboard, evidence, planner)은 모두
  `NOT deleted`로 거른다.
- `activity_source_head`: 원장의 kind, source id, source revision, content hash. import가 찾는 행이다. head의
  활동이 삭제됐거나 source가 suppression이면 `suppressed`로 답한다.
- `activity_suppression`: 실제 삭제가 쓰는 것과 같은 명시적 suppression이다. course lineage trigger도 이 행을 본다.
- 활동 디렉터리 purge 무장. 무장에 실패하면 예외다.

**fail closed**: 아래 경우는 모두 예외이며, **재생 transaction 전체가 rollback된다**. 조용한 commit은 없다.

| 거절 사유                                                                       | 오류 코드                          |
| ------------------------------------------------------------------------------- | ---------------------------------- |
| 세션 tenant 불일치                                                              | `ACTIVITY_REPLAY_TENANT_MISMATCH`  |
| 비-canonical tenant·활동 id(대문자, nil UUID)                                   | `ACTIVITY_REPLAY_INVALID_ID`       |
| 형식 오류: kind ∉ {fit, fixture}, source id 길이, revision ≤ 0, hash 형식, NULL | `ACTIVITY_REPLAY_INVALID_ENTRY`    |
| 말소된 tenant                                                                   | `ACTIVITY_REPLAY_TENANT_ERASED`    |
| identity 계정이 없는 tenant(복원 cluster가 모르는 tenant)                       | `ACTIVITY_REPLAY_TENANT_UNKNOWN`   |
| 이 tenant에 이미 있는 활동 id(부재가 아님, 묘비 경로를 써야 함)                 | `ACTIVITY_REPLAY_ACTIVITY_PRESENT` |
| 다른 tenant가 가진 활동 id                                                      | `ACTIVITY_REPLAY_FOREIGN_ACTIVITY` |
| 다른 활동으로 이미 알려진 source                                                | `ACTIVITY_REPLAY_SOURCE_CONFLICT`  |

- 함수는 repository처럼 tenant의 command lock(`0`)을 먼저 잡는다.
- drill은 행이 없는 항목에서 이 함수를 부르고 `{replayed: true}`를 단언한다. 원장에 source revision·content hash가
  없거나 형식이 틀리면 drill의 원장 파싱이 먼저 실패한다.
- `restoreBeforeRuntimeAccess`에 `replay_latest_activity_deletion_ledger_rebuilding_suppression_for_absent_activities`를
  더했고, `limitations` 문구를 이 동작에 맞게 바꿨다.

**시험(통합, 실제 PG14)**:

- `… rebuilt and suppressed for an activity the restore does not hold`: 재생 → 객체 purge → 재-import `suppressed`,
  같은 id, 활동 행 수 불변, `getActivity` null. 재구성된 행은 `{revision:2, original:{}, deleted:true,
source_revision:1, content_hash:'a'×64, suppressed:true}`다.
- `refuses a ledger entry it cannot verify, and writes nothing` 7개: 위 표의 경우 전부와, 항목 두 개를 한 transaction에서
  재생하다 두 번째가 거절되면 첫 번째까지 rollback되는 경우. 각 경우 그 항목의 source head·purge 행이 0인지 확인한다.
- 스트레스 시험에 재생 rebuild를 더했다(tenant는 identity 계정을 가진 tenant로 바꿈).

### 11-2. N4 — scope purge 배치

- `OBJECT_SCOPE_PURGE_RUNS_PER_INVOCATION = 20`과 `processObjectScopePurges`를 더했다. 규칙은 M2-01z의
  `processTenantObjectPurges`와 같다.
  - run마다 자기 lease(한 purge 행), 자기 delete budget(200), 첫 오류에서 중단.
  - `passed`/`continuing` 뒤에만 다음 run으로 가고, `empty`·`retry_scheduled`·`lease_lost`에서 멈춘다.
  - run은 겹치지 않는다. worker가 동시에 쥐는 scope lease는 최대 하나다.
- worker는 tenant purge 배치 바로 뒤에 이 배치를 부르고 결과를 `scopePurges` 배열로 낸다.
- 처리량: scope마다 완결 pass 한 번이면 닫힌다(30일 재무장 없음). 스케줄러가 1분마다 부르면 시간당 1,200 scope,

- **backfill 주의**: 046은 적용 시점에 **지금까지 삭제된 모든 활동과 unavailable 코스**를 무장한다. 예를 들어 삭제된

### 11-3. N5 — lost-lease 가시성 (M2-01z 규칙을 `object_scope_purge`에)

`lease_object_scope_purge`에 M2-01z의 045와 같은 세 단계를 넣었다. 셋 다 purge 행만 `FOR UPDATE SKIP LOCKED`로 잡고,
활동·코스는 잠그지 않고 읽는다.

1. attempts ≥ 100이고 lease가 만료된 행 → `DEAD_LETTER:LEASE_EXPIRED`로 표시하고 stale lease를 지운다(LIMIT 100).
2. 소유자가 살아 있어 거절되는 due 행 → 한 번만 표시한다. lease도, attempt 차감도, 삭제도 없다.
3. 만료된 lease를 넘겨받을 때 → `LEASE_EXPIRED`.

추가로:

- **표시 backfill → CHECK 순서**: `object_scope_purge_dead_letter_labelled`
  (`attempts<100 OR completed_at IS NOT NULL OR lease_owner IS NOT NULL OR coalesce(starts_with(last_error_code,'DEAD_LETTER:'),false)`)
  를 넣기 전에 045와 같은 표시 UPDATE를 돌린다. 이 표는 046에서 새로 생기고 backfill 행은 모두 attempts 0이라
  **이 UPDATE는 여기서 아무 행도 바꾸지 않는다.** 순서를 045와 맞추려고 둔 것이며, anchor N5d가 중복임을 보인다.
- 최종 lease용 부분 index `object_scope_purge_final_lease`.
- **INCONSISTENT_LEDGER 라벨을 둘지: 두기로 했다.** 라벨은 `INCONSISTENT_LEDGER:ACTIVITY_LIVE`와
  `INCONSISTENT_LEDGER:COURSE_AVAILABLE`이다.
  - 이 시스템의 어떤 경로도 살아 있는 소유자에게 purge를 무장하지 않는다.
    - 묘비·회수 trigger는 전이에서만 발화한다.
    - 복원 rebuild는 이미 있는 활동을 거절한다.
    - backfill은 삭제됐거나 unavailable인 소유자만 고른다.
    - 묘비는 되돌릴 수 없다(종단적).
  - 그러니 이런 행은 손으로 고쳤거나 깨진 원장에서만 생긴다. 재시도로는 고쳐지지 않고 사람이 봐야 한다. 라벨이 없으면
    attempts 0, 코드 NULL인 채 영원히 due로 남는다(045가 고친 것과 같은 조용한 정지).
  - 소유자가 나중에 실제로 삭제되면 trigger가 재무장하면서 코드를 지우고, 그때 purge된다(시험으로 확인).
- 시험(통합):
  - 살아 있는 활동·available 코스 거절 시험이 라벨을 단언하도록 고쳤다(삭제 뒤 코드가 지워지는 것도).
  - `a run that outlives its lease (N5)` 4개: 넘겨받을 때 `LEASE_EXPIRED` 표시와 완결 뒤 해제, 100번째 lease 유실 시
    `DEAD_LETTER:LEASE_EXPIRED`(rotation 밖, CHECK가 NULL·`LEASE_EXPIRED`를 `23514`로 거절, 재무장하면 복귀), 실행 중인
    100번째는 dead-letter하지 않음, 실패한 100번째는 자기 코드로 dead-letter.
