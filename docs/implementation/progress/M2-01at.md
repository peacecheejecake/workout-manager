# M2-01at · superuser가 아닌 소유 역할에서 object purge가 돌지 않던 결함

상태: **완료(2026-09-26).** 독립 검토(`m2-01at-review-r1`, tree `6ab8b786`) APPROVE 뒤 main `62ac0e3` 위로 병합했다. 병합 때 root가
검토 지적(policy의 역할 묶임, lease 비용, 남은 말소 실패, 잠금 순서, 복원 replay의 외래 id 확인)을 §8에 더했다. 기준 `b9c41da`(`merge-ko`, 승인된 병합 둘 — migration은 050까지). 새
migration은 **051**. 범위는 `task-graph.json`의 `M2-01at` scope(root가 merge-ko에서 `erase_account`를 포함하도록 넓혔다),
출처는 [M2-01k-o](M2-01k-o.md) §6·§8 항목 2. `AGENTS.md`·`CLAUDE.md`·`task-graph.json`·`.geo-build`·요구 매트릭스는
바꾸지 않았다. 개인 FIT/GPS·토큰·자격 증명은 없다(시험 id·객체는 모두 합성).

## 0. 결론

**결함이었고, 보고보다 넓었다. 실제 PostgreSQL 14에서 재현했고 두 purge에 대해 닫았다.**

schema 전체를 superuser도 BYPASSRLS도 아닌 역할(`NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE`, DB 소유자)이
`migrate()`로 만들면(그 역할로 된다 — 확장·특권 문 없음):

- **`erase_account` 자체가 실패한다.** 체인 끝의 arming `INSERT … ON CONFLICT`가 `tenant_object_purge`(FORCE, policy 0개)에서
  `42501 new row violates row-level security policy`로 거절되고 말소 전체가 rollback된다. 활동 삭제(묘비 trigger)와 코스
  삭제(`delete_course`)도 `object_scope_purge`에서 같은 이유로 실패한다.
- 두 lease는 queue 행을 **하나도 보지 못한다**(policy 없음 = 기본 거부). 보고된 대로 `lease_tenant_object_purge`는
  `tenant_erasure`를 tenant 없이 읽어 역시 0행이다.
- `lease_object_scope_purge`의 "살아 있는 소유자 거절"은 `NOT EXISTS(살아 있는 활동/코스)`인데, `activity_canonical`·`course`를
  tenant 없이 읽으므로 **살아 있는 행이 안 보이면 거절이 참으로 풀린다.** queue만 보이게 고치면 살아 있는 활동의 디렉터리를
  lease한다(변이 M5·M9로 실측: 살아 있는 활동의 객체가 지워진다). 그래서 두 절반을 함께 고쳤다.
- 044·046의 backfill은 그 소유자로 실행되어 말소 tenant·삭제 활동·unavailable 코스를 하나도 보지 못했다(upgrade 시험이 050
  시점에 0행을 단언).

시험 cluster의 migration 역할(`workout_admin`)이 superuser라 모든 기존 시험·drill이 이것을 보지 못했다.

## 1. 설계 (migration 051 `051_object_purge_plain_owner.sql`)

1. **purge 표 둘에 소유 역할 전용 policy 하나씩**(`TO current_user USING (true) WITH CHECK (true)`) — 047·049·050의
   선례. 두 표에는 runtime·worker 어떤 역할도 권한이 없다(grant helper 뒤까지 upgrade 시험이 단언). 따라서 이 policy가
   넓히는 것은 두 표를 만지는 소유자 함수들(무장·lease·완료·복원 재생)의 시야뿐이고, 그것이 목적이다.
2. **이전 tenant 표(`tenant_erasure`, `activity_canonical`, `course`)에는 policy를 더하지 않는다.** 소유자 전체 policy는 그
   소유자의 다른 모든 definer 함수 시야를 넓힌다. 대신 lease가 **행마다** 그 행의 tenant를 한 문장 동안 `app.athlete_id`로
   두고 기존 005/004/034의 tenant policy로 묻고, 호출자의 설정을 곧바로 되돌린다 — 050 `read_course_share`와 같은 방식.
   helper 둘: `object_purge_tenant_erased(text)`, `object_purge_scope_live(text,text,uuid)`. definer가 아니고(소유자로 도는
   lease 안에서만 불린다) 누구에게도 grant하지 않는다. 알 수 없는 scope 종류는 답이 아니라 예외다(표 CHECK가 이미 막는다).
3. **lease 둘은 제자리 교체**(`CREATE OR REPLACE`) — worker의 EXECUTE grant가 살아남아 grant helper 재실행이 필요 없다.
   본문은 045·046 그대로이고 tenant 없는 읽기 세 곳만 helper 호출로 바뀐다(upgrade 시험이 **이전 본문에 정확히 그 치환만
   한 문자열**과 같음을 단언). search path는 049·050처럼 `pg_catalog, pg_temp`로 고정.
4. **backfill 재실행**: purge 행이 전혀 없는 말소 canonical tenant·삭제 활동·unavailable 코스를 지금 무장한다. tenant를
   가로질러 읽으려고 세 표의 FORCE를 소유자로서 이 두 문장 동안만 풀고, 마이그레이션이 끝나기 전에 되돌린다(migrate는 한
   트랜잭션). superuser 소유 DB에서는 그런 행이 모두 이미 purge 행을 가지므로 아무것도 무장하지 않는다(멱등).

바뀌지 않은 것: finish 함수 둘, `erase_account`와 그 체인, `arm_object_scope_purge`, trigger 둘, `delete_course` — policy가
생기면 그대로 쓰기가 통과한다. 거절 조건과 label(`INCONSISTENT_LEDGER:*`, `DEAD_LETTER:*`)은 의미 그대로다.

잠금 순서: helper는 잠금을 잡지 않는다. lease는 여전히 purge 행만 `FOR UPDATE SKIP LOCKED`로 잡고 나머지는 잠금 없이
읽으므로 말소의 77206 → 0 → 행 → purge 행 순서에 되돌아오는 간선이 생기지 않는다.

비용: helper는 volatile plpgsql이라 planner가 semi-join으로 묶지 못하고 후보 행마다 한 번 불린다(PK 조회 하나 +
`set_config` 둘). tenant lease의 후보 검사는 FK 덕에 거의 첫 행에서 끝난다. scope lease의 `INCONSISTENT` 표시 문은 due 행을
최대 100개 찾을 때까지 due 행마다 부르므로 backlog N에 선형이다(이전에도 N에 선형인 EXISTS였다). 성능은 측정하지 않았다.

## 3. 시험

### 3.1 통합(`object-purge-plain-owner`): schema 전체를 plain 소유자가 만들고 grant helper도 그 역할이 실행

1. 그 역할이 정말 superuser·BYPASSRLS가 아니고 purge 표·함수·`tenant_erasure`를 소유한다.
2. `operations.eraseAccount`(runtime) 성공 → `tenant_erasure` 행과 purge 행 → worker가 lease·삭제·finish, 행 없는 객체 2개
   삭제, 살아 있는 tenant의 객체는 그대로, `passes 1`.
3. lease·finish만 따로: superuser가 넣은 말소 행과 purge 행을 worker가 처리한다(arming과 무관한 lease 실패를 따로 보인다).
4. 말소 항목이 없는 tenant의 purge 행(FK 끄고 심음)은 lease되지 않는다 — erasure 검사.
5. 말소됐는데 identity 계정이 있는 tenant: lease되지 않고 `INCONSISTENT_LEDGER:IDENTITY_ACCOUNT_PRESENT`, 계정을 지우면 purge.
6. 활동 삭제가 무장하고 purge된다. 같은 tenant의 살아 있는 활동에 심은 행은 lease되지 않고 `INCONSISTENT_LEDGER:ACTIVITY_LIVE`,
   객체 그대로.
7. available 코스의 행은 lease되지 않고 `INCONSISTENT_LEDGER:COURSE_AVAILABLE`, 없는 코스의 행은 purge.
8. `delete_course`(runtime)가 무장하고 purge된다.
9. worker 연결에서 호출자가 둔 tenant(어느 행의 tenant도 아닌 값)가 두 lease 뒤에도 그대로다.

### 3.2 upgrade(`object-purge-plain-owner-upgrade`): plain 소유자가 043까지 → 이전 행 → 050 → 051

- 050 시점: 무장된 행 0(044·046 backfill이 못 봄), 소유자는 tenant 없이 세 표에서 0행.
- 051 뒤: checksum 1–50 그대로. 함수: 새 것은 helper 둘뿐(definer 아님, 소유자, `pg_catalog, pg_temp`). 나머지 모든 함수의
  본문·definer·소유자·config가 그대로이고, lease 둘은 이전 본문에 정해진 치환(tenant lease 1곳, scope lease 2곳 — 각 원문이
  정확히 한 번 나타남을 먼저 확인)만 한 것과 같다. policy: 새 것은 정확히 두 개(두 purge 표, 소유자만, ALL/true/true),
  사라진 것 없음. 모든 표의 RLS/FORCE 플래그가 051 전과 같다. 소유자는 여전히 tenant 없이 `tenant_erasure`·`activity_canonical`·
  `course`에서 0행, tenant를 두면 1행. 050이 놓친 세 행이 due로 무장됨. 재실행 멱등(행 수 그대로).
- grant helper(`grantOperations`·`grantActivityTracks`·`grantCourses`·`grantResourceObjectCleanupWorker`)를 전체 migrate 뒤에
  돌린 다음: 두 purge 표에 소유자 외 권한 0(열 권한 포함). 두 표를 본문에서 참조하는 함수는 정확히 7개이고 모두 소유자 것.
  helper에는 소유자 외 EXECUTE 없음. worker는 lease 둘의 EXECUTE를 유지.
- backfill된 세 행을 worker가 lease·finish(`passes 1`씩).

## 5. 다른 definer 함수 — 같은 문제의 목록 (후속)

방법: 050·051 DB(plain 소유자)의 카탈로그에서 SECURITY DEFINER 함수마다 본문이 참조하는 FORCE 표를 찾아 분류했다
(`verification-logs/m2-01at/definer-audit-050.txt`·`-051.txt`, 정규식 기반 정적 분류 — 함수별 실행은 이 노드에서 두
purge 계열만 했다). 051로 purge 함수 4개가 목록에서 빠졌다. `erase_account` 체인은 따로 본다.

**B. policy가 전혀 없는 FORCE 표를 쓰거나 읽는 함수 — 36개(051 뒤).** 표는 `resource_object_cleanup`,
`resource_derived_cleanup`, `activity_track_reconcile_state`, `course_thumbnail_reconcile_state`. plain 소유자에서 읽으면 0행,
쓰면 `42501`. 따라서:

- 사용자 경로가 실패한다(정적 판독, 실행은 안 함): 추적이 있는 활동 삭제(`activity_track_cleanup_on_delete`), 업로드
  protect/supersede(`protect_*_upload_object(s)`, `supersede_activity_track_upload_objects`), 자료·갤러리 삭제의 정리 enqueue
  (`enqueue_resource_object_cleanup`, `enqueue_gallery_media_cleanup`), 썸네일 준비(`prepare_course_thumbnail`), 그리고 **객체를
  가진 tenant의 계정 말소**(033·038·042 단계가 `resource_object_cleanup`에 쓴다 — 이 노드 시험의 말소 tenant는 행이 이름 붙인
  객체가 없어서 통과한다).
- worker가 아무것도 lease하지 못한다: `lease_resource_object_cleanup`, `lease_resource_derived_cleanup`, sweep cursor·settle·
  reclaim, prune.
- **주의(fail-open 위험):** `authorize_resource_object_cleanup`은 queue 행을 받은 뒤 13개 tenant 표를 tenant 없이 읽어 "아직
  살아 있는 참조"를 확인한다. 이 queue에 소유자 policy만 더하면 M5와 같은 방식으로 살아 있는 객체를 지울 수 있다. 051이 두
  purge에 한 것처럼 행마다 tenant를 두는 읽기로 함께 바꿔야 한다.

**C. tenant policy 표를 tenant 없이 읽는 worker 함수 — 30개.** plain 소유자에서 0행을 봐 조용히 아무 일도 하지 않는다(닫힌
실패): 썸네일 render lease/finalize/fail/release/reap, URL 수집 lease/prepare/mark/finalize/fail/reap/hop, sweep window·fault,
`reap_expired_resource_uploads`, `prune_resource_retrieval_cache`. `assert_*_quota`·`supersede_course_thumbnails`·
`course_thumbnail_publication_fence_open`처럼 tenant 트랜잭션 안에서 불리는 것도 정규식에는 걸린다 — 호출 문맥별 확인은
후속의 몫이다.

**영향 없음(확인):** 050 `read_course_share`(tenant를 둠), `auth_create_session`(tenant를 둠), 047·049·050의 자기 표
소유자 policy를 쓰는 함수, 호출자 tenant를 검사하는 함수들(`current_setting('app.athlete_id')` 비교 뒤 그 tenant 행만 다룸),
tenant 트랜잭션 안에서만 발화하는 trigger 함수(B 표에 쓰지 않는 한).

제안: 후속 노드 하나로 B·C를 닫는다 — queue·state 표에 소유자 policy, 그 queue의 생존·소유 검사는 행별 tenant 읽기,
worker 함수는 lease한 행의 tenant를 두고 읽기. 그 전까지 runbook·HANDOFF가 "소유 역할은 superuser나 BYPASSRLS"를 조건으로
적는다(이 노드에서 갱신).

## 8. 남은 것

- §5의 B·C: 후속 노드 제안(root가 task-graph에 등록). 그 전에는 소유 역할을 superuser나 BYPASSRLS로 둔다.
- backfill 중 세 표의 FORCE를 푸는 동안 `ALTER TABLE`이 migration 트랜잭션 끝까지 AccessExclusive 잠금을 잡는다. migration
  시간 동안 runtime의 그 표 접근이 기다린다(이미 migrate 전체가 한 트랜잭션이다). 대량 backfill 시간은 측정하지 않았다.
- helper 호출 비용: 구현자는 재지 않았다. 독립 검토자가 잰 값(모두 죽은 queue의 `lease_object_scope_purge`): 1만 행 70–82 ms(046 본문
  3–4 ms), 10만 행 723–790 ms(046 본문 34–36 ms). superuser 소유에서도 비슷하다. INCONSISTENT 단계가 행마다 plpgsql helper를 부르기
  때문이다. 한 호출에 scope 하나를 lease하므로 N행을 비우는 비용은 O(N²)이고 상수가 약 20배다. 현실적인 queue 크기에서는 괜찮다고 root가 판단했다(측정한 결론은 아니다).
- 실제 운영 배포의 소유 역할 구성은 확인하지 않았다(`not_executed`).
- peer review: root가 받았다(APPROVE). 검토가 남긴 것(root 기록):
  - policy는 051을 적용한 역할에 묶인다. 소유 이전(`REASSIGN OWNED`)·`--no-owner` 복원 뒤에는 다시 실패한다(runbook에 적었다).
  - 051 뒤에도 plain 소유자에서 실제 계정 말소는 042 단계(`resource_object_cleanup`)에서 `42501`로 실패한다(추적 객체 참조가 하나라도
    있으면). 이 노드 범위(purge 표 무장·lease)는 충족했지만 "plain 소유자에서 계정 말소가 된다"는 아직 아니다.
  - 복원 replay(`replay_absent_activity_deletion`·`replay_course_deletion`)의 외래 id 거절은 tenant를 `$1`로 둔 채 다른 tenant 행을 찾으므로
    plain 소유자에서는 보지 못한다. 051 전에는 무장 INSERT에서 실패로 닫혔고 051 뒤에는 커밋된다. PK와 purge prefix가 tenant별이라
    다른 tenant 것은 지우지 않지만 "외래 id 거절" 불변식이 조용히 사라진다.
  - 051 적용 중 잠금 순서가 동시 말소와 반대라 교착 시 migration이 되돌려진다(runbook).
  - 모두 후속 M2-01au 범위다.
