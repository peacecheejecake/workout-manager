## 1. 설계 근거

두 행은 "통합 시험 524개"라는 묶음으로만 판정되어 있었다. 그래서 조건 하나하나가 실제로 단언되는지
알 수 없었다(`reason`: "Individual concurrency cases not re-read here"). 이 노드는 두 행의 조건을 하나씩
나눴다. 각 조건에 대해 다음을 했다.

1. 조건마다 **시험 하나**(또는 drill check 하나)를 고른다. 인용은 `file:line`과 시험 이름이다.
2. 그 시험이 지키는 **제품 가드**를 한 곳에서 되돌린다. 가드는 제품 코드나 migration에 있다. 되돌리는
   anchor는 파일 안에서 정확히 한 번 나와야 한다(한 번이 아니면 스크립트가 적용을 거부한다).
3. 그 시험만 실행해 **실패**를 확인한다. 파일을 되돌린 뒤 원본 사본과 `cmp`로 비교하고, `git diff`가
   깨끗한지도 본다.
4. 대응하는 시험이 없는 조건에만 새 시험을 쓴다. 새 시험도 같은 방법으로 실패를 보인다.

조건의 출처:

- `P8-postgres-object`(계획 8절 표): tenant/RLS · idempotency · CAS · 동시 upload/삭제 · publish 실패 · lease
  race · cleanup 재실행 · export/erasure · 백업 복원.
- `P7-durable-lifecycle`(계획 7절): temp/prepared/final 상태를 DB에 먼저 기록 · publish 실패 · DB rollback ·
  중복/동시 upload.
- 과제가 명시한 M2-01n 항목: sweep dead-letter와 공유 디렉터리 경합. 과제 문장은 공유 디렉터리 경합을
  "M2-01o"로 적었지만, task-graph와 [M2-01n.md](M2-01n.md) §1에 따르면 경합을 고친 노드는 **M2-01n**이다.
  M2-01o는 저장소 **루트 경로 가드**를 고쳤다([M2-01o.md](M2-01o.md) §1). 그래서 둘 다 대응표에 넣었다.

대표 객체는 **activity track**(원본·정규화·지도 경로 세 객체)이다. 계획 7절이 말하는 upload → publish →
finalize 흐름을 가진 유일한 지도 객체이기 때문이다. dead-letter와 lease race는 track에 해당 경로가 없다.
그래서 dead-letter는 썸네일 참조로, lease race는 활동·코스 scope purge로 대응했다. 이 두 경로도 지도
객체(썸네일·track)를 지운다.

변이 도구(scratchpad, 커밋하지 않음): `h-mut.py`(anchor 1회 확인 → 원본 보존 → 적용 / 복원 → `cmp` →
`git diff --quiet`), `h-mrun.sh`(변이 하나 적용 → 시험 하나 실행 → 복원). migration을 바꾼 변이는 **새
데이터베이스**에서 실행했다(`migrate()`는 이미 적용된 migration의 checksum이 바뀌면 거부한다).
통합 시험의 변이는 private PostgreSQL 14 cluster에서 실행했다(unix socket 전용, TCP 없음).

**publish 실패 시험.** 실제 API(`createApi`), 실제 PostgreSQL, 실제 로컬 파일시스템 저장소를 쓴다. 시험이
끼우는 것은 하나뿐이다. **두 번째** `publishTemporary` 호출에 틀린 sha256을 넘긴다. 그러면 실제 저장소가
해시 검증에서 `ObjectStorageConflictError`로 게시를 거절한다. 이때 첫 객체(raw)는 이미 게시되어 있다.
활동은 살아 있고 fence도 열려 있다. 그래서 객체를 돌려줄 수 있는 것은 writer 자신의 실패 처리뿐이다.
단언:

- 응답이 `409 OBJECT_STORAGE_CONFLICT`다. 이어서 보낸 finalize는 `409 UPLOAD_FAILED`다.
- intent가 `failed`/`OBJECT_STORAGE_CONFLICT`다.
- raw 최종 객체가 **실제로 보인다**. 즉 중간에 실패한 경우다.
- drain 뒤 최종 참조 3개와 임시 참조 3개 모두 receipt가 **열린 채** `PUBLICATION_IN_PROGRESS`로 보류된다.
  6개 모두 기록된 것이다.
- fence가 지난 뒤 같은 worker가 여섯 객체를 모두 지운다. 활동에는 track이 없다.

**DB rollback 시험.** 48 MiB짜리 track 10개로 tenant 한도를 채운 뒤 11번째 upload를 `staged`까지 올린다.
finalize의 quota 검사는 head·revision·객체 원장을 **쓴 뒤에** 돈다(`activity-tracks.ts:994`). 그래서 이
검사의 거절은 실제로 쓴 것을 되돌리는 rollback이다. 단언: `TRACK_QUOTA_EXCEEDED`, 그 활동의 head 0·revision
0·세 참조의 원장 행 0·완료 receipt 0, intent는 `staged` 그대로, track 읽기는 `unavailable`.

그다음 이 upload를 **durable cleanup 패턴**에 맡긴다(B1 반영). :780 시험(#12)과 같은 방법으로 intent를 DB
시계 기준으로 만료시킨다(transition trigger는 `finally`에서 다시 켠다). 그리고 worker의 `reapExpired`를
부른다. 단언: intent가 `failed`/`UPLOAD_EXPIRED`다. 임시 참조 3개와 최종 참조 3개(서로 다른 6개, 최종 3개는
prepare 때 기록된 키와 같음) **모두**에 대해 `upload_abandoned` receipt가 열려 있다. 최종 객체는 rollback 전에
이미 게시되었을 수 있으므로 최종 참조 3개가 핵심이다.

### 3.1 변이별 주의

- **#5 CAS.** TS 쪽 비교를 지워도 두 번째 revision은 생기지 않는다. 방어가 두 겹 더 있기 때문이다. 하나는
  DB의 head 전이 trigger(`activity_track_head_transition_valid`)다. 다른 하나는 `activity_track_revision`의
  PK `(athlete_id, activity_id, track_revision)`(`033_activity_track_storage.sql:90`)다. 변이가 깨는 것은
  **충돌 계약**이다. API가 `409 REVISION_CONFLICT`(`PersistenceConflict`) 대신 분류되지 않은 DB 오류(→ 5xx)를
  낸다. revision 수 단언(1)은 변이 상태에서도 참이다. 또 이 시험은 두 finalize를 **순차로** 호출한다.
  그래서 `FOR UPDATE`의 직렬화는 경쟁 상태로 시험되지 않는다. 비공허성이 보인 것은 **409 충돌 분류**뿐이다.
- **#3 RLS.** repository 조회는 `WHERE athlete_id=$1`로도 거르므로 repository 단언은 변이 상태에서도
  통과한다. 실패를 만드는 것은 같은 시험의 raw `SELECT count(*)`(WHERE 없음, 다른 tenant 문맥)다. 이 시험은
  두 경로를 모두 단언한다.
- **#2 경합.** 주 근거는 결정적 구조 시험(:707)이다. 마지막 객체를 지운 뒤 공유 바닥이 남는지, 단위
  디렉터리가 사라지는지를 본다. 변이 상태에서 10종 모두 실패했다. 보조 근거인 다중 프로세스 시험(:731)은
  타이밍에 의존한다. 이 기계에서는 변이 상태 3/3회 실패했다(M2-01n은 8/8을 측정). 다른 기계에서는 경합을
  덜 잡을 수 있지만, 수정 상태에서 거짓으로 실패할 수는 없다(M2-01n §1.4). 두 시험 모두 `pnpm test`(vitest,
  실제 FS)로 돈다. `test:integration`에는 속하지 않는다.
- **#13 rollback.** 변이는 전역 transaction wrapper 한 곳이다(모든 repository가 쓴다). 새 시험이 지키는
  성질은 "finalize가 쓴 뒤에 거절되면 흔적이 없다"다. 이 성질을 만드는 것이 바로 그 wrapper다.
- **#10a export.** 지운 것은 tenant command lock(`…,0`) 하나다. 두 번째 lock(`…,77209`, 동의 철회 직렬화)은
  남아 있다. 이 lock만으로는 삭제와 직렬화되지 않음을 보인 것이다.
- **#11 복원.** **이 변이는 복원에 특화되지 않았다.** 변이한 곳은 복원 뒤 삭제 ledger 재생이 기대는 삭제
  trigger다. 이 trigger는 평소의 활동 삭제에도 쓰인다. 실제로 같은 변이는 복원과 무관한 통합 시험
  `activity-tracks.integration.test.ts:825` `reclaims the raw track, normalized data and map derivative when the activity is deleted`도
  죽였다(새 DB, `expected [] to have a length of 3 but got +0`). 따라서 이 결과가 보이는 것은 "복원 절차가 삭제 재생을 통해 이 trigger에 의존하고, drill이 그
  결과를 단언한다"는 것까지다. 복원 전용 가드(예: `replay_absent_activity_deletion`)의 비공허성은 보이지
  않았다. drill이
  실행하는 복원 절차(재생 → worker drain)는 바꾸지 않았다. 원본 cluster와 복원 cluster가 같은 migration으로
  만들어지므로 변이는 양쪽에 걸린다. 첫 실패 지점은 복원 뒤 단언(:3729)이다. 백업 전 단계는 통과했다.
