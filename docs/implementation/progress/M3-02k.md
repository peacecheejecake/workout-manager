# M3-02k · HealthKit 전역 UUID 귀속 원장·수신 차단

상태: **로컬 PostgreSQL 수용 완료 / 루트 최종 확인 후 그래프 완료 반영 대상**. [계정별 운동 등록 ADR](../research/healthkit-account-registration-adr.md)와 [M3-02j 계약 기록](M3-02j.md)에 따른 서버 영속화 범위를 구현하고 합성 자료로 집중 검증했다. 계정 내보내기·합성 DB dump/restore·DB protocol fence를 유지하는 rollback 수용까지 로컬 검증했다. 후속 API/native 연결과 운영 이미지 rollback·실기기 수용은 각각 M3-02l–o/h에 남는다. 이 문서만으로 그래프 상태를 앞당기지 않는다. 이 기록은 과거 M3-02a–i 검증 결과를 소급 변경하지 않는다.

## 현재 구현 범위

- `packages/server/persistence/migrations/094_healthkit_workout_registration.sql`: 전역 `sample_id` 기본 키로 활성 UUID의 단일 귀속을 보장하는 claim, 계정별 registry head와 등록 idempotency receipt를 추가했다. 세 테이블에 tenant RLS와 `FORCE ROW LEVEL SECURITY`를 적용했다. `tenant_erasure` 삽입 후 실행되는 definer trigger가 계정 말소 시 세 테이블을 지운다. 사용자 결정에 따라 `consent`의 AFTER trigger도 HealthKit 동의 철회 시 claim→등록 receipt→registry head를 같은 거래에서 지운다. 기존 059 raw purge와 거래를 공유하며 동의 row lock을 사용하는 등록/수신과 직렬화한다. 기존 raw를 소유권 증거로 자동 backfill하지 않는다.
- `packages/server/persistence/src/healthkit-registration.ts`: 명시적 귀속 선언·동의 revision·registry revision을 검사하는 등록/목록 저장소다. 등록은 계정 명령 잠금과 현재 동의 확인 뒤 한 거래에서 처리한다. 전역 UUID 충돌은 계정 식별자를 노출하지 않는 `CLAIM_CONFLICT`로 반환한다. 동일 idempotency key의 동일 요청은 원래 claim epoch·revision을 반환하고, 다른 key로 활성 UUID를 다시 등록하면 충돌한다. 목록 cursor는 계정 digest와 registry revision에 묶어 다른 계정 재사용과 stale cursor를 거절한다.
- `packages/server/persistence/src/healthkit-ingestion.ts`: 구형 `schemaVersion: 1`과 무등록·타 계정·오래된 claim epoch 또는 동의 revision의 v2 이벤트를 receipt/raw 쓰기 전에 거절한다. 등록된 v2 이벤트의 ACK·raw 저장·삭제 tombstone은 기존 거래 경계 안에서 처리한다. 개별 운동 등록 해제는 구현하지 않았다.
- 루트 통합 변경인 `packages/server/persistence/src/migrate.ts`가 094를 등록하고 runtime role에 registry head `SELECT,INSERT,UPDATE`, claim과 registration receipt `SELECT,INSERT`를 부여한다. `packages/server/persistence/package.json`은 public `./healthkit-registration` subpath를 노출한다. 이 공유 파일들은 이 저장소 slice의 소유 범위 밖에서 통합됐다.
- `packages/server/persistence/migrations/095_healthkit_receipt_protocol_fence.sql`: 기존 v1 receipt는 역사 표식으로 보존하고, 신규 runtime receipt에는 v2만 허용하는 DB 제약·trigger를 추가했다. runtime의 역사 표식 위조와 protocol 변경을 거절하며 실제 DB 백업 복원은 migration owner 경계에서 처리한다. 기존 raw나 역사 receipt를 명시 등록의 증거로 자동 이행하지 않는다.
- 계정 export v29는 인증된 owner의 귀속 사실·registry head·등록 건수 projection만 내보낸다. 재사용 가능한 claim epoch·등록 command receipt 본문·DB 역사 표식은 제외한다. export는 UUID 귀속 복원 명령이 아니다.
- 집중 검증 파일은 `packages/server/persistence/tests/healthkit-registration.integration.test.ts`다.

## 2026-10-05 실행한 검증

- `/private/tmp`의 일회용 실제 PostgreSQL 14에 `migrate()`와 runtime grants를 적용한 뒤 집중 Vitest **1개 파일·5개 테스트 통과**. 합성 UUID만 사용해 동시 A/B 단일 소유자·RLS, v1/미등록 수집 차단, 등록 멱등과 동일 owner의 다른 key 충돌, 계정 간/stale 목록 cursor, 계정 말소 후 B의 명시 재등록, 등록된 삭제 UUID의 tombstone을 확인했다. 임시 DB는 실행 종료 시 정지·삭제했다.
- `@workout/server-persistence` typecheck와 build, `@workout/api` typecheck, 변경 TypeScript 파일 ESLint·Prettier, `git diff --check` 통과. API typecheck는 새 v2 경로의 동작 검증이 아니다.
- 첫 실DB 시도에서는 테스트 기대값과 claim 조회의 `FOR SHARE` 권한 요구 때문에 5건 중 4건이 실패했다. 테스트의 registry revision·계정별 집계와 Promise 오류 기대값을 바로잡고, 계정 말소가 tenant gate로 직렬화되는 현재 정책에 맞춰 claim을 `SELECT`로 검사한 뒤 위 **5/5**를 재실행했다. 초기 실패를 통과로 세지 않는다.

## 2026-10-05 기존 HealthKit 회귀와 동의 철회 보강

- 기존 persistence 7개 파일(`healthkit-ingestion`, `healthkit-activity`, `healthkit-binding`, `healthkit-review`, `healthkit-consent-suppression-event`, `activity-tracks`, `dashboard`)의 성공 fixture를 명시 등록 ACK→claim epoch→v2 배치로 전환했다. 구형 v1 배치는 무기록 거절을 별도로 검증한다.
- 최초 7개 회귀 suite는 **72개 통과·1개 실패**였다. `healthkit-consent-suppression-event.integration.test.ts:178`에서 동의 철회 후 claim/registration receipt/registry head의 기대 건수 **0/0/0**과 실제 **1/1/1**이 달라 실패했다. 철회 후 세 원장의 purge 누락을 직접 확인한 결과다. 이 실패는 당시 미구현 purge의 증거로 보존한다.
- 094 AFTER consent trigger의 원자적 claim/등록 receipt/head purge를 추가한 뒤, 위 7개와 `healthkit-registration`을 합친 일회용 실제 PostgreSQL 검증은 **8개 파일·79개 테스트 통과**했다. 등록 집중 suite를 다시 실행해 **6개 테스트 통과**를 확인했다. 동의 철회 후 과거 등록 제거와 새로운 명시 재등록을 검증했다. 합성 자료만 사용했다.
- persistence typecheck/build, 변경 TypeScript ESLint·Prettier, `git diff --check` 통과. 이 결과는 API/native 동작, 운영 DB migration, 백업 복원 또는 제품 실기기 증거가 아니다.
- 개별 운동 등록 해제 정책은 관련 기록 정리 후 귀속 해제이며, 정리 완료 뒤 타 계정 명시 재등록을 허용한다. 해당 runtime DTO/API와 삭제 orchestration은 아직 구현하지 않았다.

## 2026-10-05 export v29·DB 복원·rollback fence 수용

- owner만 귀속 사실을 내보내는 export v29 projection과 계약을 검증했다. 동의 철회 후 귀속 사실이 제거되고 command receipt·claim epoch·protocol 역사 표식이 export에 노출되지 않는다.
- migration 095를 유지한 채 legacy runtime의 v1 receipt 쓰기와 역사 표식 위조를 DB에서 거절했다. 합성 자료를 넣은 실제 `pg_dump`/`pg_restore`로 기존 v1 receipt의 역사 사실과 신규 v2 fence가 복원 후 보존됨을 검증했다. 철회 suppression replay와 삭제된 귀속이 재생되지 않는 경계를 확인했다.
- A의 철회 거래가 진행 중일 때 B의 같은 UUID 등록이 기다리고, A commit 후 새 등록이 가능하며 A rollback 후에는 기존 claim 충돌로 거절됨을 실제 동시 거래로 검증했다. 실패한 철회 거래는 raw·receipt·claim/head 변경을 원자적으로 되돌린다.
- 계약 집중 검증 **22/22 통과**, contracts/persistence/API/platform/mobile-web typecheck, 변경 TypeScript **29개 파일** ESLint·Prettier 통과. 전체 실제 PostgreSQL 재실행은 초기 migration smoke **1/1**, 본 suite **130개 파일 통과·1개 파일 건너뜀 / 1,057개 테스트 통과·3개 건너뜀·0개 실패**다. 실행 로그는 `/private/tmp/wm-m3-registration-fence-full-integration-r2.log`이며 임시 로컬 실행 자료로 관리한다. 건너뛴 항목을 통과로 세지 않는다.
- 초기 집중 실행 **11개 통과** 이후 중간 12-suite 실행은 **85개 통과·export assertion 5개 실패**였다. 첫 전체 실행은 **1,043개 통과·assertion 2개 실패·15개 건너뜀**과 별도 **hook 실패 8개**가 있었다. 구형 schema의 grant 대상에 새 원장 세 테이블이 없는 문제, foundation migration 기대값 93→95, 현재 export 기대 버전 v28→v29를 바로잡고 위 전체 재실행을 통과했다. 초기 실패는 실패 이력으로 보존한다.
- 여기서 DB safe rollback은 **095 fence를 유지하고 legacy 쓰기를 거절하는 상태**, 실패한 거래의 rollback, 합성 DB의 실제 dump/restore를 뜻한다. 운영 서버의 이미지 rollback이나 운영 백업 복원을 실행한 증거는 아니다.

## 후속 통합·외부 게이트

- 현행 `apps/api/src/healthkit-ingestion-routes.ts`와 API 테스트의 v1 batch/ACK는 M3-02l에서 등록·목록·v2 수신 경로 및 오류 매핑으로 전환해야 한다. 개별 등록 해제 runtime DTO/API와 관련 기록 정리 후 귀속 해제 orchestration도 M3-02l 범위다.
- native의 선택·등록 UUID predicate·outbox/anchor 수명주기와 화면/bridge는 M3-02m/n 범위다. 위 typecheck·실DB 검증은 이 연결의 수용 증거가 아니다.
- 운영 이미지 배포·rollback, 운영 백업 복원·legacy raw 감사와 공개 HTTPS 검증은 M3-02o의 운영 수용에 남는다. 이 slice에서 AWS·제품 iPhone·서명된 HealthKit collector를 실행하지 않았다. M3-02h 실기기 수용은 **not_executed**다.
