# M2-01k-c2 · 로그 redaction 단언

상태: **완료.** 독립 검토 6라운드 끝에 승인(tree `9a2bcaf1`, 차단 0). 구현 기준 HEAD `9aa110b`, 병합 때 `2e2dc21` 위로 rebase했다.
구현 agent는 검토자를 띄우거나 커밋하지 않았다. root가 띄운 **독립 검토(tree `76b35621`)**는
코드를 승인했지만 **실제 누출 하나(B1: routing 엔진 access log의 정확한 waypoint)**를 찾았다. 수정과
비차단 지적의 반영은 §8에 있고, §1의 "새는 값은 없었다"는 **API와 worker에 대한** 1차 결론이다. `task-graph.json`·`AGENTS.md`·`CLAUDE.md`·
`.geo-build`는 바꾸지 않았다. 매트릭스는 편집하지 않았다(판정 제안은 §6).

범위(task-graph `M2-01k-c2`, [M2-01k.md §13.6](M2-01k.md)): 코스·routing·track 라우트와 worker의 로그
stream을 버리지 않고 모아, 좌표·waypoint·객체 key·토큰·본문이 **없고** trace id·version은 **있음**을
단언한다. 각 필드를 로그에 넣는 변이로 실패를 보인다. 닫을 행: `P7-no-coordinates-in-logs`, `V2-F36`.

## 1. 발견 — 새는 값은 없었고, trace id·version이 없었다

실제 stream을 모아 보니 **금지 값(좌표·waypoint·객체 key·토큰·본문)이 새는 경로는 찾지 못했다.** API
로거는 이미 `req`/`res`/`err` serializer를 비우고(`err`는 `redacted`), Fastify의 요청 로그를 끄고
(`disableRequestLogging`), 직접 쓰는 줄은 `request_completed{method,statusCode}`·`request_failed{code}`
뿐이다. 어댑터가 좌표·key·bearer·본문을 담은 오류를 던져도(§3.2) 로그에는 고정 code만 남았다.

대신 요구의 다른 절반이 **실제로 빠져 있었다.**

| stream                                       | 전                                              | 후                                             |
| -------------------------------------------- | ----------------------------------------------- | ---------------------------------------------- |
| API(모든 라우트) — trace id                  | `reqId`                                         | `reqId`(변경 없음)                             |
| API — version                                | **없음**                                        | `version`(모든 줄, `WORKOUT_RELEASE`)          |
| thumbnail worker 이벤트 — trace id / version | **없음 / 없음**                                 | `runId`(실행마다 UUID) / `version`             |
| thumbnail worker CLI stdout                  | `{kind,result}` — **둘 다 없음**, logger 미연결 | 이벤트 줄 그대로(`event,result,runId,version`) |

**왜 빠졌나.** 경로 시험들이 `logStream`에 받은 줄을 모두 버리는 `Writable`을 넘겼다(M2-01k 매트릭스
사유 그대로). 무엇이 기록되는지를 단언하는 시험이 없었으니, 줄에 버전이 없다는 사실도 드러나지 않았다.
worker는 logger를 주입받을 수 있었지만 CLI가 주입하지 않았고, CLI가 따로 찍는 결과 줄에는 추적할 것이
결과 하나뿐이었다.

**재발 방지.** (1) 여섯 경로 시험 파일과 두 lifecycle 통합 시험이 이제 stream을 **보관**하고 매 시험 뒤
감사한다. 새 로그 필드나 새 로그 호출이 금지 값을 싣거나 `reqId`/`version`을 잃으면 그 파일의 시험이
실패한다(§4 변이). (2) 감사는 **허용 목록**을 쓴다: 운영 필드(`level,time,pid,hostname,msg,event,version,
method,statusCode,code,result` + trace 필드) 밖의 최상위 필드는 `unexpected_field`로 실패한다. 무심코 더한
필드는 통과하지 못하고, 더하려면 시험에서 명시적으로 허용해야 한다. (3) `version`은 pino `base`에 묶여
요청 child 로거를 포함한 모든 줄에 붙는다 — 개별 로그 호출이 챙길 필요가 없다. (4) worker의 `runId`는
lease에서 파생하지 않은 새 UUID다. 그래서 tenant·코스·객체를 가리킬 수 없다.

## 2. 설계

### 2.1 재사용 helper — `@workout/server-courses/log-audit`

`packages/server/courses/src/log-audit.ts`(새 public export `./log-audit`). api와 worker가 **모두** 이미
의존하는 패키지라 lockfile을 바꾸지 않고 두 app의 시험이 같은 코드를 쓴다(앱끼리의 상대 경로 import는
boundary lint가 막는다). M2-01k-o(코스 공유)가 같은 helper로 공유 링크·정확한 위치를 단언하도록 만들었다.

- `createLogCapture()` — stream을 **버리지 않고** 보관한다. 세 입구: pino/Fastify용 `stream`(Writable),
  worker 이벤트 콜백용 `sink(event)`, 자식 프로세스 stdout용 `append(text)`. 줄바꿈 없는 마지막 조각도
  줄로 돌려준다(잘린 쓰기를 `unparseable`로 잡기 위해).
- `auditLogLines(lines, expectation)` — findings 배열(비면 통과). 한 줄마다:
  1. JSON 객체여야 한다(`unparseable`).
  2. `traceField`(API `reqId`, worker `runId`)가 UUID여야 한다(`missing_trace_id`). 예외는
     `untracedMessagePrefixes`로 이름 붙인 프로세스 수준 줄(예: `Server listening at `)뿐이고 그 줄도
     version·누출 검사는 받는다.
  3. `version`이 기대값과 정확히 같아야 한다(`missing_version`).
  4. 누출 4겹 — **필드 이름**(어느 깊이든 `waypoints`·`geometry`·`lat`·`objectKey`·`storageRef`·
     `authorization`·`cookie`·`*token`·`body`·`req`·`url`·`name`…), **값 모양**(소수 숫자, 소수점 아래
     세 자리 이상 문자열 — ISO 시각의 밀리초는 제외, `private/v<n>/`·`/tenants/<uuid>/`·`sha256/<hex>`
     경로, `Bearer …`, UUID를 뺀 뒤 32자 이상 토큰형 연속 — 대문자/소문자 snake 어휘는 제외),
     **probe**(시험이 심은 정확한 값: 보낸 좌표, 저장소가 돌려준 key, 헤더의 토큰, 본문의 코스 이름이
     줄 어디든 나오면 실패), **허용 목록**(`unexpected_field`).
  5. `minRecords`보다 적은 줄은 `too_few_records` — 버려진 stream이나 꺼진 로거는 통과할 수 없다.
- finding은 줄 번호·JSON 경로·규칙 이름만 담고 **값은 절대 담지 않는다**. 실패 메시지가 잡은 비밀을
  다시 출력하지 않는다(시험으로 단언).
- `coordinateProbes(positions, kind)`, `valueProbes(kind, values)`, `formatLogFindings(findings)`.

M2-01k-o가 쓸 방법: 공유 토큰·링크는 `valueProbes('token', [shareToken, shareUrl])`, 정확한 위치는
`coordinateProbes(exactPositions)`, 새 운영 필드는 `allowedFields`로 명시 허용한다. 공유 URL 경로 모양은
값 모양 규칙이 모르므로 probe로 심어야 한다.

### 2.2 API 시험 연결 — `apps/api/tests/log-audit-support.ts`

`auditRouteLogs(probes)`는 파일 최상단에서 한 번 부르면 `afterEach`를 등록하고, `createApi`에 펼칠
`options()`(보관 stream + `version: testRelease`)를 준다. 매 시험 뒤 그 시험에서 만든 모든 app의 줄을
감사한다. hook은 역순으로 돌아 app이 닫힌 뒤 감사한다. 앱을 만들고 요청을 안 보내는 시험이 있어 여기서는
최소 줄 수를 요구하지 않고, 최소 수는 전용 시험(§3.2)과 lifecycle 시험이 단언한다. probe가 `beforeAll`
뒤에야 정해지면(저장소 root) 함수로 넘긴다.

### 2.3 제품 변경

- `apps/api/src/app.ts`: `ApiOptions.version?`(기본 `unreleasedVersion = 'unreleased'`)을 pino `base`
  (`pid`,`hostname`,`version`)에 묶었다.
- `apps/api/src/configured.ts`: 선택 env `WORKOUT_RELEASE`(`^[A-Za-z0-9][A-Za-z0-9._+-]{0,63}$`)를
  읽어 `version`으로 넘긴다. 모든 줄에 쓰이므로 이름 외의 것을 담을 수 없게 모양을 제한했다.
- `apps/worker/src/config.ts`: thumbnail worker 설정에 `release`(같은 env·같은 모양, 잘못되면
  `INVALID_WORKOUT_RELEASE`).
- `apps/worker/src/course-thumbnail-worker.ts`: 이벤트 `{event,result,runId,version}`
  (`CourseThumbnailWorkerEvent`), 실행마다 `randomUUID()`.
- `apps/worker/src/course-thumbnail.ts`: CLI가 logger를 연결해 이벤트 줄을 stdout에 쓴다. 예전의
  `{kind:'course_thumbnail_worker_result',result}` 줄은 없앴다(저장소 안 소비자 없음, 문서
  M2-01l.md:182는 이벤트 모양만 적었다).

### 3.2 전용 시험 — `apps/api/tests/course-log-redaction.test.ts`

한 API에 courses·routing·track·extras를 모두 붙이고 **모든 어댑터를 "새는" Proxy로** 둔다. 어떤 메서드든
좌표·waypoint·`private/v1/…` key·`Bearer …`·본문 조각을 담은 오류로 거부한다. 요청 11개:

- 어댑터 실패 500 × 7: routing 계산, 코스 생성(본문에 코스 이름), 코스 읽기, GPX export, track 읽기,
  장소 검색(본문에 검색어와 `near` 위치), bearer 헤더를 곁들인 코스 읽기
- 경계 거부: query에 좌표(400), 좌표를 담은 깨진 JSON(400), 본문 한도 초과(413), 좌표가 경로에 든
  없는 route(404)

단언: 상태 배열이 정확히 위와 같다(조용한 성공이 아님). 감사 findings `[]`(`minRecords` = 11). 완료 줄
11개의 `statusCode`가 응답과 같고 `reqId`가 모두 다르다. 실패 줄 10개가 모두 자기 요청의 `reqId`를 단다.
모든 줄의 `version`이 설정값이다. 추가로 성공한 routing 계산(엔진 graph id를 probe로)과 release 미설정
(`unreleased`)을 단언한다.

### 3.3 실제 스택 — 통합 시험

- `course-lifecycle.integration.test.ts`: 실제 PostgreSQL·bounded parse worker·파일 저장소 위에서
  업로드→코스 생성→GPX export→rename→삭제 흐름의 API stream을 감사하고 완료 줄이 13개 이상인지 단언한다.
  **코스 저장이 넣은 thumbnail render를 배포 형태 그대로의 CLI**(`apps/worker/src/course-thumbnail.ts`,
  별도 프로세스, 전용 DB role `workout_course_thumbnail_worker`, `WORKOUT_RELEASE` 설정)로 이 코스의
  그림이 `ready`가 될 때까지 돌리고(다른 파일이 남긴 오래된 render가 먼저 lease된다. 상한 = 대기 수 + 1),
  각 프로세스의 exit 0·stderr 빈 문자열·stdout 한 줄을 확인한 뒤 `runId`/`version`으로 감사한다.
- `activity-track-lifecycle.integration.test.ts`: 취소된 writer·정리 경로를 포함한 4 시험의 API stream을
  보관·감사한다(probe에 저장소 root 경로).

### 3.4 worker 단위 — `apps/worker/tests/course-thumbnail-worker.test.ts`

실행이 끝날 수 있는 7가지(`empty`,`ready`,`superseded`,`unavailable`,`lease_lost`,`failed`(오류 메시지에

root·lease token probe). 줄마다 `runId`가 다르다.

### 3.5 helper 단위 — `packages/server/courses/tests/log-audit.test.ts`

각 규칙이 제 종류를 잡고, 깨끗한 줄·UUID·긴 오류 code·snake 이벤트 이름·ISO 밀리초는 통과하며,
finding에 값이 들어가지 않음을 단언한다(13 시험).

## 7. 남은 것

1. **배포가 `WORKOUT_RELEASE`를 설정하지 않는다.** 저장소에 배포 manifest가 없어 지금은 설정하지 않으면
   `version: "unreleased"`가 찍힌다. 배포(예: git SHA)에서 설정해야 버전이 의미를 갖는다. identity harness도
   설정하지 않는다.
2. **이 노드가 감사하지 않은 stream.** coaching·resource·garmin 등 다른 라우트 파일은 여전히 버리는
   stream을 쓴다(버전은 공통 `base`라 이미 붙는다). resource cleanup·URL ingestion·coaching fixture
   worker는 trace id·version이 없다. helper는 그대로 쓸 수 있다.
3. **CLI 설정 실패 줄**(`COURSE_THUMBNAIL_RENDER_FAILED`, stderr)은 JSON이 아니고 run id·version이 없다.
   run이 시작되기 전(설정 거부)이라 run id가 없고, 설정 거부 메시지에 connection string이 섞이지 않게
   고정 문구로 둔 기존 설계를 유지했다.
4. **감사가 닿지 않는 Fastify 내부 경로.** `Reply was already sent … "<raw url>"` 경고(핸들러가 두 번
   응답하는 프로그래밍 오류에서만)와 종료 중 요청 거부 줄(`res` 키, serializer로 비어 있음)은 시험이
   재현하지 않았다. 둘째는 `res` 필드 이름으로 감사에 잡힌다. 첫째의 `msg` 속 URL 경로는 **잡히지
   않는다** — URL에 좌표·key 모양이나 probe 값이 든 경우만 잡힌다. 모든 query는 빈 schema로 거부되고
   위치는 본문으로만 받지만, 이 경고가 raw URL을 싣는다는 점은 남는다. 또 **앞으로
   `request.log.warn({ err })`처럼 오류 객체를 로그에 넘기면**, serializer가 `err`를 `redacted`로 바꿔도
   pino가 `err.message`를 `msg`로 복사한다(검토자가 Fastify 5.12.4에서 재현). 지금 코드는 `err`를 넘기지
   않는다. 넘기는 코드가 생기면 그 경로의 감사가 `msg` 속 값으로 잡을 때만 막힌다. 그래서 `err`를 넘기지
   말고 고정 code만 기록해야 한다.
5. **값 모양 규칙의 한계.** 정수 좌표, 소수점 아래 두 자리 이하 문자열 좌표, 32자 미만 토큰, 모양이
   알려지지 않은 공유 URL은 모양으로는 잡지 못하고 probe에 의존한다. 허용 목록이 새 필드를 막는다.
6. **CLI stdout 모양 변경.** `{kind,result}` → 이벤트 줄. 저장소 안 소비자는 없다.
7. drill은 돌리지 않았다: 저장소·말소·영속 계층을 바꾸지 않았다(규칙의 조건부 항목).
8. **엔진 로그 보호는 두 겹에 의존한다**(§8.1): 저장소 안 기동 경로의 override
   `-Ddw.server.request_log.type=external`, **그리고** profile의 콘솔 `threshold: WARN`. 후속 노드(root가
   만든다)가 할 일은 셋이다: profile 파일에 `server.request_log.appenders: []`(다음 graph 재빌드),
   `RouteResource` logger를 WARN/OFF로 고정, `POST /route` 검토. 저장소 밖에서 helper를 거치지 않고 엔진을
   띄우는 운영 절차는 runbook 명령을 따라야 한다. guard는 저장소 안만 본다.

### 8.1 B1 — routing 엔진이 정확한 waypoint를 기록했다(차단, 수정함)

**새던 이유.** adapter는 waypoint를 요청 줄에 담아 보낸다(`GET /route?...&point=lat,lon`,
