## 1. 설계 근거

### 1.1 기존 것을 먼저 확인했다

- 고도 데이터는 M2-01j의 자체 dataset(`geoDatasets.elevation`, `.geo-build/geo-data/elevation.json`, OSM `ele` 태그
  821점, 반경 150 m)과 `createElevationIndex`가 이미 있다. 계약 `courseElevationResultSchema`는 결손을 `null`로,
  누적 상승 없음으로 정해 두었다.
- 하지만 유일한 route `GET /courses/:courseId/elevation`은 **저장된 head**만 읽는다. 그래서 "고도 확인 → 저장" 순서가
  불가능했다(매트릭스 S14-flow 사유). 새 코스 미리보기는 서버에 행이 없고(preview는 저장하지 않는다는 M2-01r 계약),
  제안(proposal)은 저장되지만 새 코스 쪽과 같은 길이 필요했다.

### 1.2 API: 저장되지 않은 선의 고도 (추가만)

- `POST /bff/v1/courses/elevation-profiles`, 본문 `lineElevationRequestSchema = { geometry: LineString(2..20 000) }`.
  응답은 **기존** `courseElevationResultSchema` 그대로(profile / no_dataset / outside_region). 같은 index, 같은 표본화
  (최대 200점), 같은 규칙(모르면 `null`, 0·보간·누적 상승 없음)이다.
- POST인 이유: 선은 정확한 사적 위치다. request line은 로그에 남고 본문은 남지 않는다(place search와 같은 규칙).
  CSRF·인증은 기존 plugin 그대로 적용된다(시험으로 401·403 확인). body 한도는 `courseLimits.geometryBytes + 4 KiB`.
- 본문은 선 하나뿐이다. course id·dataset·반경을 받지 않으므로 요청자가 답을 조종할 수 없다(계약 시험으로 거절 확인).
  아무것도 저장하지 않는다. 선은 소유자 자신의 미리보기이고 dataset은 공개 OSM 파생이라 소유권 검사 대상이 없다.
- **버전·호환:** 새 schema와 새 route만 더했다. 기존 필드·route·schemaVersion은 바뀌지 않았다(additive). 생성 검사
  (`pnpm check:generated`)는 responsive 생성물이며 영향이 없음을 실행으로 확인했다.

### 1.3 화면: 고도/거리 확인 단계

- 새 파일 `course-route-elevation.tsx`: `useRouteElevationCheck(source, route)` hook과 `RouteElevationProfile` 컴포넌트.
  - 요청 key는 `proposalId:draftRevision:attempt`다. "확인 중"은 상태에 쓰지 않고 **현재 key의 답이 없음**에서 파생한다.
    그래서 옛 선의 늦은 답이나 재시도 전의 답이 현재 선을 대신할 수 없다(단위 시험 "never shows a late answer").
  - `profile`의 `vertexCount`가 검토 중인 선의 정점 수와 다르면 쓰지 않고 거절한다(다른 선의 고도).
  - 표시: 값 있는 표본 수, 모름 표본 수, **모름 구간 수**, SVG 그래프(값 있는 표본만 점, 이웃한 값끼리만 선, 모름 구간은
    빗금 띠이며 그 위로 선을 긋지 않음), 표본별 목록("정점 n: 106.83m" / "정점 n: 모름 (150m 안에 값 없음)"),
    dataset 출처·버전·갱신 주기. 결손을 0으로 두는 코드 경로가 없다(`elevationRuns`가 known 값만 run에 넣는다).
  - `no_dataset`·`outside_region`은 문장으로 말하고 **아무것도 그리지 않는다**(빈 그래프는 "평지"로 읽힌다).
  - 요청 실패는 "모름, 평지나 0m가 아님" + "고도 다시 확인" 버튼.
- **저장 관문:** 두 편집기(새 코스 `NewCourseEditor`, 저장된 코스 `CourseEditor`의 계산된 경로 검토)에서 고도 확인이
  답(어떤 결과든)을 내기 전에는 "위 내용을 검토했습니다" checkbox가 disabled이고 저장 버튼과 `save()`가 막힌다.
  `no_dataset`도 답이므로 저장은 가능하다. 배포되지 않은 데이터가 코스 저장을 영원히 막으면 안 되기 때문이며, 대신
  화면이 그 사실을 말한다. 순서가 코드로 강제된다: 계산 → 고도/거리 확인 → 저장.
- **관문 정책(검토 r1 #2에서 명시):** 관문의 조건은 "소유자가 이 선의 고도 **상태**를 보았다"이지 "데이터가 좋다"가
  아니다. 그래서 요청 **실패**(`failed/request`)와 **다른 선의 답 거절**(`failed/mismatch`)도 답으로 치고 저장을 연다.
  화면은 두 경우 모두 "모름이며 평지나 0m가 아님"이라고 말한다. 고장 난 endpoint가 코스 저장을 영원히 막지 않게 하려는
  선택이다. "고도 다시 확인"을 누르면 새 key로 다시 pending이 되고, 그 답이 올 때까지 checkbox·저장이 다시 막힌다.
  단위 시험 "lets a failed check through to save, and shuts the save again while a retry is out"이 이 정책을 고정한다
  (정책을 뒤집는 변이 F1과 관문을 없애는 M3가 모두 이 시험을 실패시킨다, §4).
- **관문 범위(검토 r1 #3):** 관문은 **경유점 routing 흐름**, 즉 새 코스 미리보기(`NewCourseEditor`)와 저장된 코스의 계산된
  제안(`CourseEditor`의 "계산된 경로 검토")에만 있다. 목표 거리 **후보** 저장 경로(`course-editor.tsx`의 "고른 후보 저장")는
  고도 확인을 거치지 않는다(M2-01k-j와의 충돌 회피, §8).
- 거리: 검토 요약(`RouteReviewSummary`, 기존)의 `route-engine-distance`가 엔진의 `engineDistanceMeters`다. 새 코드는
  없고, E2E로 단언하고 변이로 비공허성을 보였다(§4 M2).
- **fixture 변경:** identity harness의 결정적 routing fixture가 엔진 거리 = 그린 선의 길이로 답했기 때문에, "선을 재서
  엔진 거리라고 표시"하는 변이가 fixture 모드 E2E에서 살아남는다. 실제 엔진처럼(보고 거리는 자기 네트워크 경로 길이,
  돌려주는 선은 단순화된 그림) **보고 거리 = 선 길이 × 1.04**로 바꿨다(`ENGINE_DISTANCE_OVER_LINE`). 이 fixture를 쓰는
  다른 spec(후보 25% 허용 오차 등)은 identity 전체 실행 ×2에서 통과했다(§5).
- 실제 엔진에서는 선이 조밀해 두 값이 표시 정밀도(1 m)에서 같다(실측: 엔진 684.186 m, 그린 선 684.1 m). 그래서
  real-engine 모드의 E2E는 "엔진 값이 표시됨"을 단언하고 두 값을 annotation으로 기록한다. 변이 판별은 fixture 모드와
  단위 시험이 맡는다(§6 한계).

## 3. E2E 설계 (`course-elevation-review.spec.ts`)

실제 OIDC(fixture provider)·API·격리 PostgreSQL·자체 place/elevation dataset·routing 포트(fixture 또는
`IDENTITY_E2E_ROUTING=graphhopper`), Next(3100)와 Vite(4200) 각각:

1. **검색:** 자체 place 데이터에서 "진달래길" → 결과 필수(`no_dataset`이면 실패).
2. **지점:** 검색한 위치를 시작점으로, `[127.01, 37.66]`을 끝점으로.
3. **계산:** 고도 요청을 `page.route`로 **붙잡아 둔 채** 미리보기 계산.
4. **고도/거리 확인:** 표시 거리 = `metres(preview.engineDistanceMeters)`(fixture 모드에서는 그린 선 길이와 다름을 먼저
   확인), graph id 표시, 고도 요청 본문 = 미리보기 geometry 그대로. 붙잡힌 동안 checkbox·저장 disabled, 강제 클릭해도
   저장 요청 없음. 풀어 준 뒤 응답이 **`profile`이어야 함**(dataset 미배포는 실패), 화면의 점 = 응답의 known 값 목록,
   표본별 `data-known` 패턴 = 응답의 null 패턴, 모름 표본은 "모름"이고 숫자가 아님, 빗금 띠 ≥ 1, known ≥ 1·모름 ≥ 1.
   fixture 모드에서는 정확히 `[106.83, null, null]`.
5. **저장:** 그 뒤에만 저장. 요청 순서가 정확히 `place-search → route-previews → elevation-profiles → POST /courses`.
   저장된 revision의 geometry = 미리보기 geometry, `generation.engineDistanceMeters` = 미리보기 값, graph id 같음.
6. **저장된 코스의 제안:** 편집 화면에서 경유점 추가 → 제안 계산 → 고도 요청 본문 = 제안 geometry, 화면 = 응답, 엔진 거리
   표시 → 저장(revision 2), 저장 geometry = 제안 geometry.

**배치·키보드(검토 r1 #1, 6건):** 320·768·1280 px × Next·Vite. 첫 고도 답을 500으로 주어 "고도 다시 확인" 버튼을 만든 뒤,
Tab으로 재시도 버튼에 도달(초점 표시 확인)해 Enter로 다시 묻고(실제 서버, 200) profile이 되는지 본다. 그다음 페이지
가로 overflow 0, 검토 group·고도 확인·그래프가 viewport 안에 있고 각자 가로 overflow 0, 그래프 폭 > 200 px·높이 > 60 px,
Tab으로 `<details>` summary에 도달(초점 표시)해 Enter로 표본 목록을 열고 목록이 viewport 안·글자 ≥ 12 px, Tab으로 검토
checkbox에 도달(초점 표시)해 Space로 체크. 각 폭 화면을 캡처했다.

별도 시험(각 shell): 고도 응답을 `no_dataset`으로 **명시해** 준 경우 "이 서버에는 고도 데이터가 배포되어 있지
않습니다"·"확인되지 않음" 문장, 그래프·점 0개. 이 시험은 문구만 단언하며, dataset 배포 요구는 위 흐름 시험이 진다.

### 6.1 알려진 한계(검토 r1 #4)

- `POST /courses/elevation-profiles`에는 **요청률 제한이 없다.** 비용은 한 요청당 본문 ≤ 1 MiB(`geometryBytes` + 4 KiB),
  표본 ≤ 200점, 표본당 dataset 격자 조회(반경 150 m, 채워진 셀로 제한)로 묶여 있고 DB·엔진·외부 호출이 없다. 인증·CSRF를
  요구한다. tenant 한도가 필요하면 routing의 admission limiter와 같은 층에서 따로 결정한다.

## 8. 남은 것

- 독립 검토 1차 REQUEST CHANGES(#1–#6)를 반영했고 2차에서 APPROVE를 받았다.
- 자체 고도 데이터가 희소해 실제 코스 대부분이 "모름"으로 나온다. 고도 데이터 확충(DEM 등)은 별도 데이터 결정이다.
- 후보(목표 거리) 검토에는 고도 확인을 붙이지 않았다(M2-01k-j와의 충돌 회피, S14 흐름 문장은 경유점 routing 흐름).
  필요하면 같은 hook을 한 줄로 붙일 수 있다.
- 모바일·태블릿 폭은 Aside가 아니라 Playwright로 확인했다(§6). Chrome 도구는 이 세션에 없다.
- 새 endpoint에 요청률 제한이 없다(§6.1).
- 병렬 노드와의 예상 충돌: M2-01k-j는 `course-editor.tsx`의 import 블록과 `<RouteReviewSummary/>` 바로 뒤, M2-01k-a는
  `course-extras-routes.ts`·`course-extras-api.ts`의 끝(양쪽 추가)에서 겹친다.
