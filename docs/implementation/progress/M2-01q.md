## 2. 상태 모델 — 무엇을 근거로 무엇을 말하는가

`MapView`(`packages/experience/geo-kit/src/map-view.tsx`)를 마운트하는 컴포넌트는 셋(`course-workbench`,
`activity-track-panel`, `track-preview`)이고 두 shell에서 쓰여 6가지 화면이 된다(검토 정정: 처음엔 "다섯
화면"이라 적었다). 공통 leaf이므로 여기서 고쳤다. 상태는 `MapViewStatus`:

| 상태          | 근거                                                                                  | 화면·스크린리더 문구(`role="status"`)                                       |
| ------------- | ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `preparing`   | 렌더러 없음                                                                           | 지도 준비 중                                                                |
| `drawing`     | style `load`(배경 또는 무배경 canvas)만                                               | 배경 지도를 불러왔습니다. 경로를 그리는 중입니다. / 경로를 그리는 중입니다. |
| `drawn`       | 관측에서 뷰포트 안의 **모든 종류**(선·점)가 그려짐                                    | 지도에 경로를 표시했습니다. / 배경 지도 없이 경로를 표시했습니다.           |
| `not-drawn`   | 한 번도 그린 적 없는 렌더러가 뷰포트 안 경로를 0개 그림, 또는 **10초 안에 관측 없음** | 지도가 경로를 그리지 못했습니다. 아래 좌표 목록을 사용하세요.               |
| `out-of-view` | 뷰포트에 경로 정점이 없음                                                             | 경로가 지금 보이는 지도 영역 밖에 있습니다.                                 |
| `unconfirmed` | **이미 그린** 렌더러가 지금 경로를 그렸다고 보일 수 없음(§9 B1)                       | 경로가 지도에 그려졌는지 지금은 확인하지 못했습니다.                        |
| `unavailable` | adapter 실패, 분류별                                                                  | WebGL 없음 / WebGL 중단 / 배경 지도 실패를 각각 다른 문구로                 |
| `invalid`     | 표시 계약 위반                                                                        | 좌표를 표시할 수 없습니다 (문제 코드).                                      |
| `empty`       | **데이터만으로** 판정(경로 0개 또는 좌표 0개)                                         | 표시할 좌표가 없습니다.                                                     |

**빈 경로 vs 그릴 수 없음.** `empty`는 렌더러를 묻기 전에 props로 결정한다. 그래서 GPS 없는 기록·
경유점 없는 코스는 feature를 기다리지 않고 deadline도 걸리지 않는다(단위 시험, 변이 M5). 반대로
"그릴 수 없음"은 **뷰포트 안에 우리 정점이 있는데** 그린 것이 없을 때만 말한다. 정점이 하나도 뷰포트에
없으면 판단하지 않는다(`out-of-view`) — 선이 정점 없이 뷰포트를 가로지르는 경우도 추측하지 않는다.

**관측(`render-evidence.ts`, 순수 함수).** adapter는 선 layer와 점 layer를 **따로** `queryRenderedFeatures`
하고, 현재 source에 넘긴 collection과 뷰포트로 "무엇이 그려져 있어야 하는지"(`expectedVisibleGeometry`)를
함께 보고한다. `judgeRender`는 선이 기대되는데 선이 0이면 점이 있어도 `not-drawn`이다.

**관측 시점.** 부정(not-drawn)은 `idle`(렌더러가 가진 것을 다 그림)에서만. 긍정은 `idle` 또는 **우리
source가 새 경로를 로드한 뒤 그 경로를 그린 첫 frame**. 후자가 필요한 이유는 §4 F-q2.

**deadline 10초.** worker가 없으면 `idle`이 영원히 오지 않는다. 그래서 넘긴 경로를 10초 안에 아무 관측도
확인하지 않으면 `not-drawn`. 이후 관측이 오면 `drawn`으로 회복한다.

**렌더러 도장.** 새 basemap은 새 렌더러를 만든다(Vite shell은 basemap을 비동기로 받는다). 보고에는
만든 렌더러(factory, basemap)가 찍혀 있어 옛 렌더러의 `drawn`이 새 렌더러로 넘어가지 않는다(변이 M8).

**남는 한계(정직하게).** (1) 이미 그린 렌더러의 worker가 나중에 죽으면 `unconfirmed`로 말한다 — "그릴 수
없음"도 "그림"도 아니다. (2) 데이터 변경 뒤 확인 전까지는 직전 판정을 유지한다(편집마다 live region이
울리지 않도록). 확인이 10초 안에 오지 않으면 한 번도 그린 적 없는 렌더러는 `not-drawn`, 그린 적 있는
렌더러는 `unconfirmed`. 1차 판에서는 이 (2)가 그린 렌더러에도 `not-drawn`을 내는 **거짓 음성**이었다
(검토 B1, §9).

## 4. 실제 브라우저에서 찾은 것

- **F-q1 (결함, 수정) 420px pane에서 지도 폭 20px.** desktop 합성(`1fr` + `24rem`)이 viewport로만
  정해져, 좁은 module pane 안에서는 목록 track이 먼저 384px를 가져갔다. 첫 실행 두 shell 모두
  `map width in a 420px pane — Expected >= 240, Received 20`. `courses.module.css`에 container query를
  넣었다(pane 최소 폭에서 유도: desktop 24+1+15rem=40rem, tablet 16+1+15rem=32rem 미만이면 쌓음,
  07 §3 "특수 kit는 근거와 최소 폭을 명시해 별도 container 조건"). 이후 지도 폭 388px, 선 렌더.
- **F-q2 (신호 결함, 수정) 느린 배경 tile이 `idle`을 10초 넘게 붙잡음.** Aside에서 4200 첫 로드 때
  `preparing → drawing → not-drawn → drawn` 전이를 봤다. `idle`은 모든 배경 tile을 기다린다. 경로는
  이미 그려졌는데 deadline이 먼저 왔다. adapter가 우리 source 로드 후 frame마다(확인 전까지만) 긍정
  관측을 보고하게 했다. 이후 drawing→drawn 120–190 ms(이전 1.3–4.2 s), 반복 측정에서 거짓 음성 없음.
- **F-q3 (신호 결함, 수정) 재렌더마다 deadline 재시작.** 코스 편집기는 렌더마다 새 paths 배열을
  만든다. 매번 `setData`와 deadline이 다시 시작되므로, 화면이 계속 재렌더되면 worker 없는 지도가
  `drawing`에 머물 수 있다. 코드 읽기로 찾았다 — 첫 E2E 실패(`Received "drawing"`)는 확인해 보니 30 s
  시험 timeout 때문이었으므로 **실제 브라우저에서 이 결함이 발현한 증거는 없다.** MapView가 내용이
  같으면 같은 collection을 유지한다(단위 시험·변이 M12). 부수 효과로 렌더마다 `setData`하던 것도
  없어졌다.
- 확인: 4200 세션. Playwright identity 스위트는 이미 4200을 돌고 있었다(cookie는 host 기준,
  `127.0.0.1`의 3100 로그인 = 4200 세션, 4200 preview가 `/bff`를 4300으로 proxy). **이번 Aside에서도
  4200 `/bff/v1/session`이 200**이었다(M2-01k 때 401의 원인은 재현되지 않았다).

## 5. 증거와 비공허성

### 5.1 E2E — `tests/identity/map-render.spec.ts`(신규, 2 shell × 5 = 10건)

각 shell(3100 Next, 4200 Vite)에서:

1. 320/767/768/1279/1280 각 폭에서 **새 문서**로 코스를 열어 `data-map-status=drawn`, 상태줄 문구,
   **선 layer** feature > 0, 지도 canvas ≥ 240×200, 보이는 pane(map/list/sheet) ≥ 240px, 가로 overflow 0.
   이어서 **420px module pane**(코스를 열기 전에 좁힘 → 그 안에서 만든 렌더러)에서 같은 단언. 전 과정의
   상태 이력(MutationObserver)에 `not-drawn`·`unavailable` 없음.
2. 서울 ↔ 부산 코스 전환마다 선 렌더(전환 시 fit이 없으면 새 코스는 화면 밖).
3. MapLibre worker 요청을 abort하면 **코스·저장 경로·미리보기 세 화면 모두** 상태줄이
   "지도가 경로를 그리지 못했습니다…", 선 0, 상태 이력에 `drawn` 없음, 페이지 어디에도 "표시했습니다"·
   "지도 표시 중" 없음.
4. 저장 경로·미리보기의 선 렌더.
5. WebGL context를 주지 않는 브라우저에서 코스 지도가 WebGL 전용 문구.

기존 spec의 대리 단언을 바꿨다: `activity-track-map.spec.ts`(4곳), `track-preview.spec.ts`(1곳)의
"렌더된 경로 feature" 텍스트, `course-acceptance.spec.ts`의 `data-rendered-path-features` poll → 공통
`expectLineDrawn`(`tests/identity/map-evidence.ts`).

**identity 157 → 167(+10)의 증가분은 전부 `map-render.spec.ts`의 10건**이다(Next·Vite 각 5건: 반응형
경계+420 pane, 코스 전환, worker 없음 3화면, 저장 경로+미리보기 렌더, WebGL 없음).

## 9. 독립 검토 1차 반영

### B1 (차단) — 이미 그린 렌더러가 "그리지 못했습니다"라고 말했다

**재현.** 검토자 RV2(두 shell): 코스 `drawn` → 배경 tile 30초 지연 → 지도를 끌어 옮김 → 경유점 추가 →
약 10초 뒤 `["preparing","drawing","drawn","not-drawn"]`, 상태줄 "그리지 못했습니다", 코스 안내 "지도를
표시할 수 없습니다". 원인은 deadline 경로가 `drew`를 무시한 것이다. frame 긍정은 `drawn`만 보고하므로
화면 밖 경로를 확인할 수 없고, `idle`은 모든 tile을 기다린다.

**수정.** 새 상태 `unconfirmed`("경로가 지도에 그려졌는지 지금은 확인하지 못했습니다."). 이 렌더러가
그린 적 있으면(`drew` — 렌더러마다 초기화되는 ref):

- deadline 만료 → `not-drawn`이 아니라 `unconfirmed`.
- settled frame에서 뷰포트 안 정점이 있는데 0개(축소로 한 픽셀 미만 등) → 1차 판의 `out-of-view`가 아니라
  `unconfirmed`. `out-of-view`는 이제 "뷰포트에 정점이 없음"만 뜻한다.

**반대쪽(거짓 양성)을 다시 열지 않는 근거.**

- `unconfirmed`는 "그렸다"를 말하지 않는다. 상태줄은 "표시했습니다"가 아니며 `data-map-status`도
  `drawn`이 아니다. 검토자 권고(현재 판정 유지)는 따르지 않았다 — 직전 `drawn`을 유지하면 첫 성공 뒤
  worker가 죽은 경우 새 경로를 영원히 "표시했습니다"라고 말하게 된다. 그것이 바로 되살아나는 거짓 양성이다.
- 검토자의 다른 권고(`out-of-view`)도 택하지 않았다. `out-of-view`는 원인("화면 밖")을 주장하는데, worker
  사망이나 경로가 화면 안인데 확인이 늦는 경우에는 그 원인이 거짓이다. `unconfirmed`는 관측한 것만 말한다.
- 한 번도 그린 적 없는 렌더러는 여전히 `not-drawn`(단위 "still says a renderer that never drew cannot
  draw a changed path", E2E worker 거부 6화면).
- 이후 확인 관측이 오면 `drawn`으로 돌아간다(단위).

**비공허성.** 단위 M13(deadline을 `not-drawn`으로 되돌림) → "says a changed path is unconfirmed…" 1 failed.
E2E B1REV(같은 anchor) → §9.6.

### N1 — 전환 단언이 이전 판정을 보고 통과했다

`MapView`가 `data-paths-generation`(내용이 바뀔 때마다 증가, mount마다 고유한 `useId` 접두)과
`data-evidence-generation`(판정이 어느 경로에 대한 것인지)을 낸다. `expectLineDrawn`은 두 값이 같고 상태가
`drawn`일 때까지 기다린다. `changedFrom`을 주면 동작 전 generation과 달라야 한다. 코스 전환 시험은 캐시된
서울 코스로 돌아가는 세 번째 전환까지 `changedFrom`으로 단언한다. 단위 M16(판정에 generation 미기록) →

### N3 — 화면 밖 경유점 점

### N4 — 재렌더마다 `JSON.stringify`

측정(이 기계, load 20–24, 20,000 정점 코스, 100회 평균): `JSON.stringify` 2.84 ms, 새
`collectionKey` 0.43 ms(참고: `toFeatureCollection` 0.03 ms). 문자열을 만들지 않고 좌표를 1e-7°(약 1 cm)
단위로 두 개의 독립 32-bit hash에 접고, feature 수·정점 수·feature id를 함께 둔다. 충돌하면 다음 변경까지
이전 선이 남는다 — 두 hash와 id·개수가 모두 같아야 하므로 받아들였다. 단위 "keys a collection by its
content…"(약 1 m 이동, 같은 수를 다르게 나눈 경우를 구분), M15(좌표를 key에서 뺌) → 2 failed.

### N5 — container query 폴백

### 10.3 NB1 — 변경 뒤 이전 "drawn"이 최대 10초 서 있음(수정)

판정이 **다른 generation에 대한 `drawn`**이면 상태를 `drawing`("…경로를 그리는 중입니다.")으로 내린다.
10초 deadline은 그대로다(그린 적 있으면 `unconfirmed`, 없으면 `not-drawn`).
